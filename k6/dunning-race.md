## 1. ★ k6 는 이 시나리오에서 부하 발생기가 아니다

시나리오 ①②는 k6 가 HTTP 를 쏘면 그게 곧 부하였다. **③은 다르다.**

```
①② 웹훅 폭주      부하원 = k6.  앱은 받는 쪽
③  재시도 레이스   부하원 = 스케줄러 자신.  k6 가 쏠 곳이 없다
```

Dunning 은 **폴링으로 스스로 깨어난다**(`@Scheduled`). 밖에서 요청을 넣어 트리거하는 경로가
없고, 만들 수도 있지만 그러면 **프로덕션에 없는 모양**을 재게 된다 — 실제로는 톰캣 스레드풀이
폴러를 병렬로 부르는 일이 일어나지 않는다.

그래서 **동시성의 출처를 인스턴스 다중화로 잡았다.** 리스(`claimBillingDate` ·
`claimForRetry`)가 겨누는 것이 정확히 그것이기 때문이다 — `SubscriptionChargeService`
javadoc 이 *"인스턴스 둘이 같은 주기를 집으면 둘 다 PG 를 부른다"* 로 세워둔 자리다.

| | 이 시나리오에서 하는 일 |
|---|---|
| **앱 인스턴스 N개** | **부하원.** 같은 DB 를 보고 각자 폴링한다 |
| **k6** | 시딩 규모 조절 · 표집(`/actuator/prometheus`) · 판정. **부하는 안 만든다** |

**계획서 문장을 좁힌다**(8주 연속). *"k6로 부하테스트"* 는 남지만 **k6 의 역할이 계기 쪽으로
바뀐다**. 이걸 안 적고 k6 스크립트만 있으면, 나중에 이 폴더를 보는 사람은 부하를 k6 가
만들었다고 읽는다.

## 2. ★ 정정 — P1 의 충돌 창은 좁지 않다

설계 초안에서 다중 인스턴스 방식을 *"창이 좁고 우연에 맡긴다 — 폴링 주기 60초에 두 인스턴스가
같은 순간에 겹쳐야 한다"* 로 적었다. **P1 에 대해서는 틀렸다.**

```
P2 재시도    next_retry_at 이 주기마다 흩어져 있다     → 한 시각에 도래하는 행이 적다.  창이 좁다
P1 정기청구  next_billing_date 는 날짜다               → 그날 도래분이 통째로 한 배치다. 창이 넓다
```

`findBillingDue` 는 `ORDER BY next_billing_date, id LIMIT 100` 이다. 인스턴스 둘이 같은 초에
폴링하면 **정렬이 같아 같은 목록을 받고 같은 순서로 훑는다.** 우연히 한 행에서 겹치기를
기다리는 게 아니라 **배치 전체가 경합 대상**이다. 승자가 PG 왕복(느림)에 묶여 있는 동안 패자는
CAS 에서 즉시 지고(빠름) 앞으로 달려나가므로, 둘의 진행 속도가 달라 **뒤엉키는 지점이 계속
새로 생긴다.**

→ **헤드라인 시나리오는 P1 이다.** P2 는 곁가지로 같이 재되, 0 이 나와도 *"막았다"* 로 읽지
않는다(안 부딪혔을 수 있다 — §8).

## 3. 무엇을 세나 — 계기 둘과 그 사이의 항등식

W5D3 이 계기를 우리 DB 에서 PG 호출 수로 바꿨고, W5D4 가 *"줄어드는 건 호출이 아니라 키"*
라고 갈랐다. **둘 다 필요하다.**

| | 계기 | 어디서 읽나 | 무엇을 뜻하나 |
|---|---|---|---|
| **헤드라인** | 주기당 **서로 다른 `merchant_payment_id` 개수** | DB | **PG 가 별개 청구로 볼 것**의 수 |
| **교차검증** | `resilience4j_circuitbreaker_calls_seconds_count{name="pg-approve"}` 증가분 | `/actuator/prometheus` | **실제로 PG 에 간 횟수** |

교차검증 계기가 이미 있다는 건 오늘 확인했다 — `ResilientPgClient.approve` 가
`@CircuitBreaker(name = "pg-approve")` 로 감싸여 있어 **성공·실패·거절이 전부 이 카운터를
지난다**. PG 클라이언트 자체에는 메트릭이 없다.

### 두 계기가 어긋나는 게 정상이고, 그 차이에 이름이 있다

```
PG 호출 증가분  −  서로 다른 키 개수  =  재전송 횟수
```

재전송은 **호출을 늘리면서 키를 안 늘린다**(W5D4 §7). 그래서 둘이 같아야 한다고 보면
재전송을 이중 청구로 오독한다. 위 항등식이 성립하려면 두 전제가 필요하다:

- **회로가 닫힌 채로 끝나야 한다.** 열리면 호출이 카운터에 잡히면서 PG 엔 안 간다 → 좌변 과다
- **그 실행에 주문 결제가 섞이지 않아야 한다.** 이 카운터는 **전역**이다(승인 전체) — 구독만
  도는 실행이어야 증가분을 구독 것으로 돌릴 수 있다

**둘 다 실행 조건이지 사후 보정이 아니다.** ②에서 `status != 'PAID'` 를 고아로 세다 틀렸던
것과 같은 계열이라, 판정식보다 실행 조건을 먼저 못 박는다.

### 이 항등식은 이미 한 번 성립했다 (W5D5 대조군 A)

부하가 아니라 단위 테스트에서지만, **CAS 를 뺀 상태의 실데이터에서 그대로 맞았다**:

```
[실측] P1 동시 폴링 10개 · CAS 제거 → 키 10 · PG approve 호출 19
       19 − 10 = 9  = 뒤 스레드들이 앞 스레드의 PENDING 주기를 회수하며 낸 재전송
```

**계기를 설계만 하고 안 재본 게 아니라는 점에서 값이 있다.** 다만 그때 계기는 Mockito 였고
부하 환경의 계기는 Prometheus 카운터라, **같은 관계가 다른 계기로도 성립하는지는 실행일에
확인한다.**

## 4. 중복 청구 0건의 정의

```
중복 청구  =  같은 billing_cycle 에 서로 다른 키가 2개 이상 나간 것
```

`payment` **행 수가 아니다.** W5D2 요약이 *"동시 폴링 10개 → 청구 1회"* 라고 쓴 것을 W5D3 이
정정한 자리가 여기다 — 행을 세면 *"한 시도 = 한 PG 호출"* 이라는 **검증 대상 코드 자신의
성질**을 근거로 삼게 된다.

주의: **재시도가 정상으로 만든 키는 중복이 아니다.** 사다리를 태우면 한 주기에 키가 최대
4개까지 정당하게 생긴다. 그래서 판정은 *"키 ≤ 1"* 이 아니라 **동시 도래분에 대해
*"한 라운드에서 한 주기가 받은 키 ≤ 1"*** 이다.

```sql
-- 위반 행. 0 행이면 통과다.
SELECT billing_cycle_id, count(DISTINCT merchant_payment_id) AS keys
  FROM payment
 WHERE billing_cycle_id IS NOT NULL
   AND created_at >= :round_started_at
 GROUP BY billing_cycle_id
HAVING count(DISTINCT merchant_payment_id) > 1;
```

| 앱 인스턴스 | **3** | 2 는 승/패만 보이고, 3 이면 *"진 둘"* 이 생겨 CAS 가 다수에게도 배타적인지 본다 |

| PG 결과 | 승인 70 / 타임아웃 30 비율 고정 | ②와 같은 이유 — 전부 타임아웃이면 **회로가 열려 시나리오가 죽는다**(W4D3 실측) |
| 리스 | 5분 (그대로) | 프로덕션 값이다. 건드리면 재는 대상이 바뀐다 |

### ★ 회로는 인스턴스마다 따로다

resilience4j 의 상태는 **프로세스 안**에 있다. 인스턴스 3개면 회로도 3개고, 각자 자기
`minimum-number-of-calls: 10` 창을 따로 채운다. 그래서 **W4D4 의 규약이 3배로 늘어난다**:

> 실행 전에 **세 인스턴스 전부** `circuitbreaker_state` 를 확인한다. 하나만 열려도 그 인스턴스는
> PG 에 안 가면서 카운터는 올리므로 §3 의 항등식이 깨진다.

## 7. ★ 설계 중에 드러난 것 — k6 가 진짜로 쓰이는 레이스가 따로 있다

*"동시에 여러 재시도 트리거"* 를 폴러끼리로만 읽었는데, **트리거의 종류가 둘이다.**

```
폴러  billing_cycle 을 집어 시도를 만든다
웹훅  이미 나간 시도의 결말을 반영하면서 next_retry_at 을 정한다   ← HTTP 다
```

둘이 같은 주기를 **동시에** 만지는 창이 있다. 폴러가 `claimForRetry` 로 리스를 잡고 PG 를
부르는 사이에, **직전 시도의 웹훅이 도착**하면 `applySubscriptionFailure` 가 같은 주기의
사다리를 다시 계산한다. 이건 **k6 가 실제로 부하를 줄 수 있는 자리**다.

W5D3 이 이 경로를 뚫어놨고(웹훅 → 구독 청구 라우팅), W5D4 가 off-by-one 하나를 여기서 고쳤다
(`countConcludedAttemptsExcluding`). **그 수리는 단건으로만 검증됐다.**

> **이건 오늘 안 정했다.** ③-b 로 따로 세울지, ③에 합칠지는 실행일에 정한다.
> 다만 *"k6 를 왜 쓰나"* 에 대한 답이 ③보다 ③-b 쪽에 있다는 건 적어둔다.

## 8. 이 시나리오가 뜻하지 않는 것

- **위반 0건은 *"레이스가 없다"* 가 아니라 *"이 규모에서 안 샜다"*** 이다. 충돌이 실제로
  일어났는지는 **패자 수**로 따로 봐야 한다 — CAS 에서 진 횟수가 0 이면 아무것도 안 겨눈 실행이다.
  → **패자 수를 세는 계기가 지금 없다.** `claimBillingDate` 가 0 을 돌려준 횟수는 로그에도 안 남는다
- 인스턴스 셋이 **한 노트북**에 뜬다. DB·Redis·Kafka 와 CPU 를 나눠 쓰므로 처리량은 서버 용량이
  아니다(W4 README 와 같은 한계)
- P2 결과는 §2 대로 약한 통과다
- **부하를 넣기 전에 대조군**: 인스턴스 1개로 같은 시딩을 돌려 위반 0 · 키 500 을 먼저 확인한다.
  안 하면 나온 숫자가 다중화 때문인지 시딩 때문인지 못 가른다(W4D3 이 배선 확인 대조군으로
  44건을 걸러낸 것과 같은 자리)

## 9. 실행 절차 — 착수 전 필요한 것

~~**아직 없다: 구독을 만드는 경로.**~~ → **해소됨(2026-08-18)**: `POST /subscriptions` 가 생겼다
([W5 마무리](../docs/week5/W5_마무리.md) §1). **시딩을 SQL 이 아니라 이 엔드포인트로 한다** —
부하가 프로덕션 경로를 타고, k6 가 시딩을 맡는 게 §1 에서 정한 *"k6 의 역할"* 과도 맞는다.

두 가지가 이 시나리오에 그대로 유리하다:

- **생성이 청구하지 않는다** — `next_billing_date` 가 **오늘**로 박히고 청구는 폴러가 한다.
  §2 가 요구한 *"전부 같은 날짜로 도래"* 가 **시딩의 부수효과로 저절로 성립**한다
- **셀러당 활성 구독 하나**(V13) — 구독 500개를 만들려면 **셀러도 500개** 필요하다.
  ⚠️ `seed.sql` 이 지금 몇 명을 만드는지 확인하고 모자라면 늘려야 한다

```
[x] 셀러 500명 시딩            k6/seed-subscription-race.sql (리셋도 겸한다)
[x] 구독 500개 시딩            k6/dunning-race.js — 폴러를 끈 인스턴스에 POST × 500
[x] 인스턴스 다중화            compose 가 아니라 java -jar × N (아래 참고)
[x] 폴링 간격 1000ms 주입
[x] 대조군: 인스턴스 1개
[x] 본 실행: 인스턴스 3개
[x] 판정                       bash k6/verify-dunning.sh verdict
```

**compose 오버라이드는 안 썼다.** 앱은 호스트에서 `java -jar` 로 띄운다 — 프로메테우스가
이미 `host.docker.internal` 로 호스트의 앱을 긁도록 돼 있고(compose.yaml), 이미지를 새로
만들면 **재는 대상(앱)의 실행 방식**이 W4 와 달라진다. 인스턴스를 늘리는 데 필요한 건
포트와 프로퍼티뿐이다.

```bash
# 0) 인프라 + 스키마. 앱을 한 번 띄워야 Flyway 가 돈다
docker compose -p settleflow up -d
docker compose -p settleflow port postgres 5432    # 랜덤 포트를 확인해 아래에 넣는다
docker compose -p settleflow port redis 6379

./gradlew bootJar
JAR=build/libs/settleflow-0.0.1-SNAPSHOT.jar
DB="--spring.datasource.url=jdbc:postgresql://localhost:<PG>/mydatabase \
    --spring.datasource.username=myuser --spring.datasource.password=secret \
    --spring.data.redis.host=localhost --spring.data.redis.port=<REDIS>"

# 1) 시딩 인스턴스 — ★ 폴러를 끈다. 만드는 도중에 집히면 "동시 도래"가 안 만들어진다
java -jar $JAR --server.port=8080 $DB --settleflow.dunning.scheduler.enabled=false

# 2) 마스터 데이터(셀러 500) + 지난 회차 리셋. 출력의 seller_from 을 k6 에 넘긴다
docker exec -i settleflow-postgres-1 psql -U myuser -d mydatabase < k6/seed-subscription-race.sql

# 3) 구독 500개 — 프로덕션 경로로
SELLER_FROM=<위 출력> TIMEOUT_PER_10=1 k6 run k6/dunning-race.js
#    ↑ 10% 다. 30% 로 두면 인스턴스 하나의 회로가 열린다(§10)

# 4) 시딩 인스턴스 종료 후 N개 기동
for p in 8091 8092 8093; do
  java -jar $JAR --server.port=$p $DB \
    --settleflow.dunning.billing-poll-ms=1000 --settleflow.dunning.retry-poll-ms=1000 &
done

# 5) ★ 부하 전에 인스턴스 수를 눈으로 센다 (§10 절차 결함)
```

## 10. 실행 결과 (2026-08-18)

환경: 로컬 단일 머신. Postgres/Redis/Kafka 는 compose, 앱은 `java -jar` 로 여러 개.
구독 시딩은 `POST /subscriptions`(k6), 마스터 데이터는 `k6/seed-subscription-race.sql`,
판정은 `bash k6/verify-dunning.sh verdict`.

### ★ 헤드라인

```
[실측] 인스턴스 3개 · 폴링 1초 · 구독 500개가 같은 날짜에 동시 도래
       ★ 중복 청구(한 주기가 서로 다른 키를 2개 이상 받은 것) = 0건
       ★ 서로 다른 merchant_payment_id = 500  (구독 500 · 주기 500 · 시도 500 과 정확히 일치)
       구독당 주기 2개 이상 = 0 · cycle_no 최대 = 1     ← P1 CAS 가 시계를 한 번만 밀었다
       주기 PAID 450 / PENDING 50 (타임아웃 10% 설계와 일치)
       journal 450 · 구독수익 13,500,000 = 450 × 30,000
       회로 3개 전부 CLOSED
       PG 실호출 :8091 160 · :8092 169 · :8093 171  →  합 500
```

**세 인스턴스가 500건을 160/169/171 로 나눠 가진 것이 경합의 직접 증거다.** 셋 다 같은
`findBillingDue` 목록을 같은 순서로 훑었고, 어느 행이 누구 것이 되는지는 CAS 가 갈랐다.
§8 이 *"위반 0건은 레이스가 없다는 뜻이 아니다"* 라고 경계한 자리를 이 분배가 메운다 —
**패자 수를 직접 세지는 못해도, 승자가 셋으로 갈렸다는 건 셋이 같은 것을 노렸다는 뜻이다.**

항등식(§3)도 성립했다: `PG 호출 500 − 키 500 = 0`. 이 라운드에는 재전송이 없다 —
`PENDING` 주기의 회수는 P1 이 **다음 청구일(30일 뒤)** 에 하기 때문이다(W5D4 이월 2).

### 대조군 — 인스턴스 1개 (§8 의 요구)

```
[실측] 인스턴스 1개 · 타임아웃 30%
       위반 0 · 키 500 · 주기 500 · 시도 500
       PAID 350 / PENDING 150   (설계한 30% 와 정확히 일치)
       회로 CLOSED · PG 호출 500(성공 350 / 실패 150) · journal 350 · 구독수익 10,500,000
```

**0 이 나와야 할 자리에서 0 이 나왔다.** 이제 3 인스턴스 실행의 수치는 다중화 때문이라고
말할 수 있다(W4D3 이 배선 확인 대조군으로 고아 44건을 걸러낸 것과 같은 자리).

### ★ 그런데 첫 3 인스턴스 실행은 회로가 열렸다 — 그리고 그게 정확히 설명된다

```
[실측] 인스턴스 3개 · 타임아웃 30%
       위반 0 · 키 500 (헤드라인은 성립)
       그러나 주기 PAID 274 / FAILED 107 / PENDING 119
       :8082 회로 OPEN · PG 실호출 393(179 / 52 / 162)
       ★ 393 + 107 = 500  — 미발송 107 이 FAILED 107 과 정확히 같다
```

**107 은 유실이 아니라 W4D1 의 결정이 프로덕션에서 실제로 작동한 것이다** — 회로가 열려
PG 에 닿지 않았고, *"안 보냈으니 확실한 앎"* 이라 `FAILED` 로 확정됐다. 그 판단을
**단위 테스트 밖에서 처음 관측했다.**

#### 왜 열렸나 — 인덱스로 고정한 비율이 인스턴스별로 깨진다

W4D3 은 *"난수면 창마다 비율이 흔들리니 전역 이터레이션 번호로 고정한다"* 로 30% 를 보장했다.
**그 보장은 소비자가 하나일 때만 성립한다.** 인스턴스가 셋이면 각자 **부분집합**을 받고,
그 부분집합의 앞 10건(`minimum-number-of-calls`)에 타임아웃이 몰릴 수 있다.

```
전체 비율      30%  (설계대로 고정)
:8082 의 실제  18/52 = 34.6%  — 전체로는 임계 미만인데
                              앞 10건 창에서 5건을 넘겨 열렸다
```

→ **수리: 타임아웃 비율을 10% 로 낮췄다.** 회로는 끄지 않는다(W4D3 과 같은 태도 —
프로덕션 동작이므로 부하 쪽을 맞춘다). 10% 에서 세 인스턴스 모두 CLOSED 로 끝났고,
실패 수도 13+23+14 = 50 으로 `PENDING` 50 과 맞았다.

> **설계 문서가 틀린 자리 하나**: §3 은 회로가 열리면 *"호출이 카운터에 잡히면서 PG 엔 안 간다
> → 좌변 과다"* 라고 적었다. **반대였다** — 개방된 호출은 `kind="failed"/"successful"` 어디에도
> 안 잡혀 **좌변이 과소**가 된다(393 < 500). 방향을 거꾸로 적었고, 실행이 고쳤다.

### ★ 절차 결함 하나 — 안 뜬 인스턴스가 수치를 정상처럼 보이게 했다

중간 라운드에서 **`:8083` 이 포트 점유로 기동에 실패**했는데, 판정 수치는 멀쩡했다:

```
[실측] (실제로는 인스턴스 2개) 위반 0 · 키 500 · PAID 450 / PENDING 50
       PG 실호출 252 + 248 = 500        ← 둘이 정확히 반씩
```

**그대로 *"인스턴스 3개"* 라고 적었으면 거짓 기록이 됐다.** 드러난 계기는 판정 쿼리가 아니라
`:8083` 의 프로메테우스 응답이 **비어 있던 것**이었다.

> **규약: 부하 전에 인스턴스 수를 `/actuator/health` 로 세어 기록한다.**
> W4D4 의 *"분자는 부하 발생기의 자기 보고가 아니라 서버가 받은 수"* 와 같은 계열이다 —
> 이번에 자기 보고를 한 건 **실행 스크립트가 아니라 나 자신**이었고(*"3개 띄웠다"*),
> 그 보고가 틀렸다. 최종 실행은 `★ 3개 전부 up (5s)` 를 찍고 나서 시작했다.

### 이 수치가 뜻하지 않는 것

- **인스턴스 3개는 로컬 한 대**다. DB·Redis·Kafka·k6 와 CPU 를 나눠 쓴다
- **P2(재시도) 레이스는 여전히 약한 통과다**(§2) — 이 실행은 P1 만 겨눴다.
  `next_retry_at` 이 흩어져 있어 같은 시각 도래분이 적고, 실패 주기를 만들려면
  라운드를 하루 이상 굴려야 한다
- **재전송 경로는 안 밟혔다** — `PENDING` 50건의 회수는 30일 뒤라 이 실행에 안 들어온다.
  §3 의 항등식은 `= 0` 으로만 확인됐고, **0 이 아닌 값으로는 아직 못 봤다**
- CAS **패자 수는 여전히 못 센다**(§8 이월). 분배(160/169/171)가 그 대리 지표다
