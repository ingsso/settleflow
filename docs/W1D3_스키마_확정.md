## 1. 오늘 확정한 것

### `merchant_payment_id` — 우리 측 결제 식별자

PG 호출 **전**에 Payment 행을 만드는데(§2), 그 시점엔 `pg_transaction_id`가 NULL이라 웹훅이 와도 행을 못 찾는다. 그래서 **우리가 만든 키를 PG에 넘기고 웹훅이 되돌려주게** 한다.

**PK를 쓰지 않는 이유** (오늘 유도해서 얻은 답):
- `1, 2, 3...` 연번은 **추측 가능** → 남의 결제 조회(IDOR)·웹훅 위조가 쉬워짐
- 장사 규모가 노출됨 (오늘 1000번, 내일 1200번 → 하루 200건)
- PK는 **내부 DB 사정**. 외부 회사와의 계약(contract)에 묶으면 안 됨

→ UUID, `NOT NULL UNIQUE`.

### `Idempotency-Key`와는 **다른 것** — 세는 단위가 다르다

| | 무엇을 묻나 | 세는 단위 |
|---|---|---|
| `merchant_payment_id` | *"이 웹훅은 **어느 결제**에 대한 것인가"* | **결제 1건당 1개** (여러 웹훅이 공유) |
| `Idempotency-Key` | *"이 웹훅을 **이미 처리했나**"* | **배달 1건당 1개** (PG가 주는 이벤트 ID) |

재전송된 웹훅은 `merchant_payment_id`가 **같다**(같은 결제니까 당연). 그래서 그걸로는 중복을 못 잡는다. 후자는 컬럼이 아니라 **Redis에 산다**(W1D4 `SETNX`).

상태 가드(`PAID`에서 승인 웹훅 → 무시)가 이미 있는데도 멱등키가 필요한 이유: 재전송 2건이 **동시에** 도착하면 둘 다 `PENDING`을 읽고 둘 다 전이를 시도한다(W1D2에서 실측한 lost update와 같은 모양). **입구(멱등키) + DB(상태 가드)** 두 겹.

### `OrderStatus` — 3개로 축소

`CREATED` / `PAID` / `CANCELED`. 배송 상태는 5주 계획에 없어서 제외(상태 하나 = 전이표 칸 + 가드 + 테스트).
`취소중`/`취소완료`도 제외 — 환불 상태는 **`refund` 합계에서 파생**하기로 §1에서 확정했는데, Order에 또 두면 같은 사실이 두 군데 살고 반드시 어긋난다.

**저장 방식**: 네이티브 ENUM 타입이 아니라 `VARCHAR(20)` + `CHECK (status IN (...))`.
값 변경 시 제약만 교체하면 되고 JPA는 `@Enumerated(STRING)`으로 그대로 붙는다. 핵심은 **아무 문자열이나 못 들어가게 하는 것** — `'PAIDD'` 같은 오타는 Week 3 대사가 조용히 놓치는 종류의 버그다.

### `updated_at`은 "이 행은 변한다"는 선언

| 테이블 | `updated_at` |
|---|---|
| `seller` / `product` / `orders` / `payment` | 있음 (실제로 변함) |
| `order_item` / `refund` | **일부러 없음** |

`order_item`에 `updated_at`을 달면 *"수정해도 된다"*는 잘못된 신호를 준다. **`total_amount` 비정규화가 안전한 유일한 근거가 "`order_item`은 생성 후 불변"**인데, 누군가 수량을 UPDATE하는 순간 드리프트가 나고 Week 3 대사가 깨진다. `refund`도 append-only(§5: *지우개가 아니라 빨간 펜*).

> **스키마는 문서다. 없는 컬럼도 말을 한다.**

**갱신 주체 함정**: 네이티브 조건부 UPDATE(재고 차감·환불)는 JPA를 우회하므로 `@UpdateTimestamp`가 **안 먹는다**. → SQL에 `updated_at = now()`를 직접 쓴다.

### 기타

- **`TIMESTAMPTZ`** (not `TIMESTAMP`) — 타임존이 없으면 "며칠자 매출"의 경계가 흔들리고, PG사 리포트(저쪽 타임존 기준)와의 대사가 어긋난다. **금액과 시각은 정산 시스템의 두 축.**
- **`seller` 테이블 신설** — Week 3 "셀러별 일 매출 집계"의 집계 단위.
- **FK ≠ 인덱스** — Postgres는 FK에 인덱스를 자동 생성하지 않는다(PK·UNIQUE만). 명시적으로 3개 추가.
- **`PaymentAnomaly`는 Week 3으로 연기** — 대사 배치가 없는 지금은 필요한 컬럼을 상상으로 정해야 해서 시기상조. Flyway라 나중에 마이그레이션 한 장이면 된다.

## 2. 계획 반박 — 재고에 Redis 락을 쓰지 않는다

계획서 W1D2 항목 *"StagePass `SET NX PX` 패턴을 좌석→재고로 이식 → `InventoryLockService`"* 를 **폐기**했다.

**두 문제는 시간의 모양이 다르다.**

| | 좌석 선점 (StagePass) | 재고 차감 (SettleFlow) |
|---|---|---|
| 점유 시간 | **지속** — 결제창 입력 중 수 분 | **순간** — 깎고 끝 |
| DB 트랜잭션으로? | ❌ 수 분간 커넥션·행 락 점유 → 풀 고갈 | ✅ `UPDATE ... WHERE stock >= :qty` |
| 고객 이탈 시 | 아무도 안 풀어줌 → **자동 만료 필요**(`PX`) | 잡은 게 없음 |

Redis `SET NX PX`가 풀던 건 **동시성이 아니라 "시간"**이었다. Redis의 그건 락이 아니라 **시한부 예약(lease)**이다.

정합성은 원자적 조건부 UPDATE로 **DB가 이미 보장**한다 — W1D2 `RefundRaceTest`에서 같은 모양의 SQL로 실측 완료(가드 O → 성공 1건/8000, 가드 X → 성공 2건/11000).

재고에 Redis를 얹으면 아무것도 더 지키지 못하면서 **재고의 진실이 Redis와 DB 둘로 갈라진다** — 이 프로젝트의 주제(정합성·대사)와 정면 충돌.

### 채택: 주문 생성 시 원자적 차감 + 미결제 주문 쓸이 배치로 복원

쓸이 배치는 "느린 TTL"이 아니라 **"조회할 줄 아는 TTL"**이다.

```sql
WHERE status = 'CREATED' AND created_at < now() - interval '30 minutes'
```

복원 **전에** PG에 조회해서 *"정말 결제 안 된 게 맞나"*를 확인해야 한다. 타이머만 믿고 복원하면:
재고 복원 → 다른 고객이 사감 → 그런데 원래 결제는 승인돼 있었음 → **돈은 받고 물건은 없음(이중판매)**.
§3 그대로다 — `PENDING`/`UNKNOWN`은 실패가 아니라 **정보의 부재**. 재고 복원은 시간의 문제가 아니라 **사실 확인의 문제**.

> Redis TTL은 시간을 안다. 하지만 **결제가 어떻게 됐는지는 모른다.**

**"Redis 락이 정말 필요한가"는 Week 4 k6로 측정해서 답한다.** 인기 상품 1건에 동시 부하를 걸어 DB 행 락 경합이 실제 병목인지 재보고, 병목일 때만 재고려. 추측이 아니라 수치로.

| 부분 유니크 인덱스 — 비-PAID 다중 허용 | 같은 주문에 `FAILED`×2 + `PENDING` + `PAID` INSERT | **전부 성공** |

### 엔티티 ↔ 스키마 매핑 (`SchemaMappingTest`)

Hibernate `ddl-auto=validate`로 부팅해 Flyway가 만든 **실제 테이블**과 엔티티 매핑을 컬럼 단위로 대조. 오타 하나만 있어도 컨텍스트 로딩이 실패한다.

| 검증 | 결과 |
|---|---|
| 엔티티 6개 매핑 | 통과 (Flyway `Migrating schema` → `Successfully applied` 확인) |
| **음성 대조군** — `Payment.status`의 컬럼명을 `payment_status`로 틀리게 | **FAILED** → 매핑 오류를 실제로 잡아냄 |

### 재고 차감 동시성 (`InventoryConcurrencyTest`) — **W1D3 결정의 근거**

```
[실측] 동시 10명 / 재고 3 → 성공 3, 재고부족 7, 최종재고 0
```

| 검증 | 결과 |
|---|---|
| 재고 3개에 동시 10명이 1개씩 주문 | **성공 정확히 3건 / 재고부족 7건 / 최종재고 0** — 초과 판매 0 |
| 재고보다 많은 수량 요청(재고 3, 요청 4) | 거부, 재고는 3 그대로 |
| **음성 대조군** — `AND stock >= :quantity` 가드 제거 | **2건 다 FAILED**, `DataIntegrityViolationException ... chk_product_stock` |

**락도 Redis도 없이** `WHERE stock >= :qty` 한 줄이 초과 판매를 막았다. → §2의 "Redis를 쓰지 않는다"가 **의견이 아니라 측정값**이 됨.

음성 대조군이 보여주는 두 겹 방어:
- **가드(`WHERE`)** = 깔끔한 **거부** (영향 행 0 → `OutOfStockException` → 트랜잭션 롤백)
- **CHECK 제약** = 가드가 뚫렸을 때의 **마지막 선** (음수 재고 자체를 차단)

가드가 없으면 정상 거부가 아니라 **예외 사고**가 된다. 둘은 대체재가 아니라 층위가 다르다.

### 예외 검증을 못 박아야 하는 이유

`DataIntegrityViolationException`은 Spring이 **모든 제약 위반**(CHECK/FK/UNIQUE/NOT NULL)을 싸잡아 던지는 우산이다. 그것만 검사하면 *"뭔가 제약이 터졌다"*까지만 확인된다.

```java
.isInstanceOf(DataIntegrityViolationException.class)
.hasMessageContaining("chk_product_stock")   // ← 이게 있어야 "stock 제약이" 막았음이 확정
```

**제약에 이름을 붙여둔 게 여기서 회수된다.** 익명 제약이었으면 이 검증 자체가 불가능했다.
W1D2 `SchemaBehaviorTest`의 `.hasMessageContaining("subquery")`와 정확히 같은 처방 — 같은 함정을 두 번째로 만난 것.

## 4. 정직한 한계

- **음성 대조군을 스스로 돌리지 않았다.** 초록불을 보고 그대로 제출했고, Claude가 대신 제약을 빼서 빨간불을 확인했다. W1D2에 *"화재감지기에 연기를 갖다 대 봐야 한다"*고 정리해놓고 **다음 날 그 절차를 건너뛴 것**. → **초록불을 본 순간 "이게 빨간불이 될 수 있나"를 스스로 한 번 돌린다**를 습관으로.

## 5. 엔티티 — 규칙을 구조로 강제하기

패키지는 **도메인형**(`seller`/`product`/`order`/`payment`), 각 도메인 안을 `domain`/`repository`/`service`/`api`로 나눈다. 계층형(`entity/`·`service/`···)은 기능 하나를 고치려고 4개 폴더를 열어야 한다.

### `Payment` — §4 전이표가 코드가 되다

`setStatus()`를 만들지 않았다. 상태는 **사건 보고 메서드 셋**을 통해서만 바뀐다.

```java
public TransitionResult onApproved()   // 승인 확정
public TransitionResult onDeclined()   // 거절 확정
public TransitionResult onTimedOut()   // 타임아웃
```

**메서드 이름이 명령이 아니라 사건이어야 하는 이유**: `markPaid()`는 *"PAID로 만들어라"*인데, `FAILED` 상태에선 실제로 안 만든다(무시+알람). 이름이 거짓말을 한다. `onApproved()`는 *"승인 확정 사건이 왔다"*이고, 그래서 뭘 할지는 **엔티티가 자기 상태를 보고 정한다**.

**반환값이 `void`도 `boolean`도 아닌 이유**: 전이표 12칸의 결과가 셋이다.

| 결과 | 칸 수 | 서비스가 할 일 |
|---|---|---|
| `TRANSITIONED` | 5 | 부수효과 실행(분개 생성 등) |
| `IGNORED` | 5 | 아무것도 안 함. `200 OK` |
| `CONFLICT` | 2 | 이상 테이블 기록 + 알람. 상태는 그대로. `200 OK` |

`boolean`으로는 **"무시"와 "모순"이 구분되지 않는다** — 둘 다 "상태 안 바뀜"이지만 하나는 정상이고 하나는 사람을 불러야 한다.

**예외를 안 던지는 이유**: (1) 웹훅엔 `200 OK`를 줘야 PG 재전송이 멈춘다. (2) 예외는 트랜잭션을 롤백시키는데, 모순 칸에서 **반드시 해야 하는 일**이 이상 테이블에 행을 쓰는 것이다. 모순은 예외적 상황이 아니라 **예상하고 기록하기로 한 사건**이다.

> **엔티티는 판단만 하고, 행동은 서비스가 한다.** 엔티티가 전이표를 소유하고, 서비스가 부수효과를 소유한다.

### 세 번째로 반복된 오류 — 종착지가 움직였다

`onTimedOut()` 초안이 `UNKNOWN`만 걸러내고 **나머지를 전부 `UNKNOWN`으로 덮어썼다.** 즉 `PAID` 결제에 타임아웃이 오면 `PAID`를 떠난다 → 부분 유니크 인덱스가 풀리고 **이중청구 구멍**이 열린다(§4).

체크리스트 W1D1에 적어둔 그 패턴이다 — *"종착지 상태를 사건이 움직이게 함. 근본 원인은 '모든 사건이 상태를 바꿔야 한다'는 전제."* 이번엔 설계가 아니라 **코드**라, 안 잡혔으면 실제 사고가 났다.

**처방**: `onApproved`/`onDeclined`는 "무시할 칸"을 먼저 나열하는 방식으로 맞혔지만, `onTimedOut`은 무시가 3칸이라 그 방식이 안 통했다. → **"전이하는 칸을 먼저 찾는다"**로 뒤집으면 항상 맞는다(12칸 중 전이는 5개뿐).

```java
public TransitionResult onTimedOut() {
    if (this.status != PaymentStatus.PENDING) return TransitionResult.IGNORED;
    this.status = PaymentStatus.UNKNOWN;
    return TransitionResult.TRANSITIONED;
}
```

이 열엔 `CONFLICT`가 **없다** — 타임아웃은 확정 정보가 아니라 정보의 부재라서 확정 상태와 모순을 일으킬 수 없다(§4 규칙 1).

### `Order` — 총액 드리프트를 구조로 봉쇄

`addItem(product, quantity)`가 **스냅샷을 뜨고 총액을 동시에 누적**한다. 호출부는 이름·가격을 따로 넘길 수 없고(Product에서 직접 읽는다), `setTotalAmount()`도 없다. `OrderItem` 생성자는 패키지 전용이라 `Order.addItem()`을 통하지 않으면 만들 수 없다.

→ **총액과 항목이 갈라질 틈 자체를 없앴다.** §7의 "`order_item`은 불변"이 관례가 아니라 구조가 된다.

### JPA 함정 (실제로 밟은 것들)

- **`@Enumerated` 없이 enum을 쓰면 `ORDINAL`(숫자)로 저장된다.** `VARCHAR + CHECK` 컬럼과 충돌하고, 나중에 enum 순서를 바꾸면 **이미 저장된 값의 뜻이 통째로 바뀐다**(`PAID`였던 결제가 `FAILED`가 된다). → `@Enumerated(EnumType.STRING)` 필수.
- **`updatable = false`는 UPDATE에서만 뺀다.** INSERT엔 여전히 포함되므로 `refundedAmount`를 생성자에서 `0L`로 초기화하지 않으면 NOT NULL 위반.
- **인자 있는 생성자를 만들면 기본 생성자가 사라진다.** JPA는 리플렉션으로 빈 객체를 만들므로 `protected Xxx() {}`가 반드시 있어야 한다.
- **`@ManyToOne`의 기본값은 `EAGER`.** 항상 `LAZY`로 명시 — Week 3 정산 배치가 수만 건을 훑을 때 N+1로 터진다.
- **`OffsetDateTime`** (not `LocalDateTime`) — `TIMESTAMPTZ`의 자바 짝. `LocalDateTime`을 쓰면 타임존이 날아가서 §7의 결정이 자바 쪽에서 무너진다.
- **엔티티에 `@Setter`/`@Data`를 붙이지 말 것.** 모든 필드에 setter가 열려 불변식을 지킬 수 없다. `@Getter`만.

### 재고 차감 — `InventoryService`

```java
@Modifying(clearAutomatically = true, flushAutomatically = true)
UPDATE product SET stock = stock - :quantity, updated_at = now()
 WHERE id = :productId AND stock >= :quantity     // ← 영향 행 0 = 재고 부족
```

- **`clearAutomatically`**: 네이티브 UPDATE는 영속성 컨텍스트를 모른다. 안 비우면 1차 캐시가 **차감 전의 낡은 `stock`**을 계속 들고 있다.
- **`updated_at = now()`를 SQL에 직접**: 이 경로는 JPA를 우회하므로 `@PreUpdate`가 안 먹는다.
- **재고 부족 → `OutOfStockException`(런타임)**: `@Transactional`이 전부 롤백 — 이미 만든 `Order`도, 앞서 깎은 다른 상품 재고도 되돌아간다.

**데드락 방지 — productId 오름차순 정렬(`TreeMap`)**

주문 하나에 상품이 여럿 담긴다. 두 고객이 같은 상품 둘을 **반대 순서**로 건드리면 서로의 행 락을 기다려 순환 대기 → 데드락. Postgres가 감지해 한쪽을 죽이므로 멈추진 않지만, **그 주문은 이유 없이 실패**하고 1초를 날린다.

> 규칙: **여러 행에 락을 잡을 땐 항상 같은 순서로 잡는다.** 재고를 건드리는 모든 코드 경로가 지켜야 한다 — 한 곳만 어겨도 데드락이 돌아온다.
