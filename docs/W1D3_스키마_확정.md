## 1. 오늘 확정한 것

### `merchant_payment_id` — 우리 측 결제 식별자

PG 호출 **전**에 Payment 행을 만드는데(§2), 그 시점엔 `pg_transaction_id`가 NULL이라 웹훅이 와도 행을 못 찾는다. 그래서 **우리가 만든 키를 PG에 넘기고 웹훅이 되돌려주게** 한다.

**PK를 쓰지 않는 이유** (오늘 유도해서 얻은 답):
- `1, 2, 3...` 연번은 **추측 가능** → 남의 결제 조회(IDOR)·웹훅 위조가 쉬워짐
- 장사 규모가 노출됨 (오늘 1000번, 내일 1200번 → 하루 200건)
- PK는 **내부 DB 사정**. 외부 회사와의 계약(contract)에 묶으면 안 됨

→ UUID, `NOT NULL UNIQUE`.

### `Idempotency-Key`와는 **다른 것** — 세는 단위가 다르다

| | 무엇을 묻나 | 세는 단위 |
|---|---|---|
| `merchant_payment_id` | *"이 웹훅은 **어느 결제**에 대한 것인가"* | **결제 1건당 1개** (여러 웹훅이 공유) |
| `Idempotency-Key` | *"이 웹훅을 **이미 처리했나**"* | **배달 1건당 1개** (PG가 주는 이벤트 ID) |

재전송된 웹훅은 `merchant_payment_id`가 **같다**(같은 결제니까 당연). 그래서 그걸로는 중복을 못 잡는다. 후자는 컬럼이 아니라 **Redis에 산다**(W1D4 `SETNX`).

상태 가드(`PAID`에서 승인 웹훅 → 무시)가 이미 있는데도 멱등키가 필요한 이유: 재전송 2건이 **동시에** 도착하면 둘 다 `PENDING`을 읽고 둘 다 전이를 시도한다(W1D2에서 실측한 lost update와 같은 모양). **입구(멱등키) + DB(상태 가드)** 두 겹.

### `OrderStatus` — 3개로 축소

`CREATED` / `PAID` / `CANCELED`. 배송 상태는 5주 계획에 없어서 제외(상태 하나 = 전이표 칸 + 가드 + 테스트).
`취소중`/`취소완료`도 제외 — 환불 상태는 **`refund` 합계에서 파생**하기로 §1에서 확정했는데, Order에 또 두면 같은 사실이 두 군데 살고 반드시 어긋난다.

**저장 방식**: 네이티브 ENUM 타입이 아니라 `VARCHAR(20)` + `CHECK (status IN (...))`.
값 변경 시 제약만 교체하면 되고 JPA는 `@Enumerated(STRING)`으로 그대로 붙는다. 핵심은 **아무 문자열이나 못 들어가게 하는 것** — `'PAIDD'` 같은 오타는 Week 3 대사가 조용히 놓치는 종류의 버그다.

### `updated_at`은 "이 행은 변한다"는 선언

| 테이블 | `updated_at` |
|---|---|
| `seller` / `product` / `orders` / `payment` | 있음 (실제로 변함) |
| `order_item` / `refund` | **일부러 없음** |

`order_item`에 `updated_at`을 달면 *"수정해도 된다"*는 잘못된 신호를 준다. **`total_amount` 비정규화가 안전한 유일한 근거가 "`order_item`은 생성 후 불변"**인데, 누군가 수량을 UPDATE하는 순간 드리프트가 나고 Week 3 대사가 깨진다. `refund`도 append-only(§5: *지우개가 아니라 빨간 펜*).

> **스키마는 문서다. 없는 컬럼도 말을 한다.**

**갱신 주체 함정**: 네이티브 조건부 UPDATE(재고 차감·환불)는 JPA를 우회하므로 `@UpdateTimestamp`가 **안 먹는다**. → SQL에 `updated_at = now()`를 직접 쓴다.

### 기타

- **`TIMESTAMPTZ`** (not `TIMESTAMP`) — 타임존이 없으면 "며칠자 매출"의 경계가 흔들리고, PG사 리포트(저쪽 타임존 기준)와의 대사가 어긋난다. **금액과 시각은 정산 시스템의 두 축.**
- **`seller` 테이블 신설** — Week 3 "셀러별 일 매출 집계"의 집계 단위.
- **FK ≠ 인덱스** — Postgres는 FK에 인덱스를 자동 생성하지 않는다(PK·UNIQUE만). 명시적으로 3개 추가.
- **`PaymentAnomaly`는 Week 3으로 연기** — 대사 배치가 없는 지금은 필요한 컬럼을 상상으로 정해야 해서 시기상조. Flyway라 나중에 마이그레이션 한 장이면 된다.

## 2. 계획 반박 — 재고에 Redis 락을 쓰지 않는다

계획서 W1D2 항목 *"StagePass `SET NX PX` 패턴을 좌석→재고로 이식 → `InventoryLockService`"* 를 **폐기**했다.

**두 문제는 시간의 모양이 다르다.**

| | 좌석 선점 (StagePass) | 재고 차감 (SettleFlow) |
|---|---|---|
| 점유 시간 | **지속** — 결제창 입력 중 수 분 | **순간** — 깎고 끝 |
| DB 트랜잭션으로? | ❌ 수 분간 커넥션·행 락 점유 → 풀 고갈 | ✅ `UPDATE ... WHERE stock >= :qty` |
| 고객 이탈 시 | 아무도 안 풀어줌 → **자동 만료 필요**(`PX`) | 잡은 게 없음 |

Redis `SET NX PX`가 풀던 건 **동시성이 아니라 "시간"**이었다. Redis의 그건 락이 아니라 **시한부 예약(lease)**이다.

정합성은 원자적 조건부 UPDATE로 **DB가 이미 보장**한다 — W1D2 `RefundRaceTest`에서 같은 모양의 SQL로 실측 완료(가드 O → 성공 1건/8000, 가드 X → 성공 2건/11000).

재고에 Redis를 얹으면 아무것도 더 지키지 못하면서 **재고의 진실이 Redis와 DB 둘로 갈라진다** — 이 프로젝트의 주제(정합성·대사)와 정면 충돌.

### 채택: 주문 생성 시 원자적 차감 + 미결제 주문 쓸이 배치로 복원

쓸이 배치는 "느린 TTL"이 아니라 **"조회할 줄 아는 TTL"**이다.

```sql
WHERE status = 'CREATED' AND created_at < now() - interval '30 minutes'
```

복원 **전에** PG에 조회해서 *"정말 결제 안 된 게 맞나"*를 확인해야 한다. 타이머만 믿고 복원하면:
재고 복원 → 다른 고객이 사감 → 그런데 원래 결제는 승인돼 있었음 → **돈은 받고 물건은 없음(이중판매)**.
§3 그대로다 — `PENDING`/`UNKNOWN`은 실패가 아니라 **정보의 부재**. 재고 복원은 시간의 문제가 아니라 **사실 확인의 문제**.

> Redis TTL은 시간을 안다. 하지만 **결제가 어떻게 됐는지는 모른다.**

**"Redis 락이 정말 필요한가"는 Week 4 k6로 측정해서 답한다.** 인기 상품 1건에 동시 부하를 걸어 DB 행 락 경합이 실제 병목인지 재보고, 병목일 때만 재고려. 추측이 아니라 수치로.

## 3. 실측 검증 (전부 실제 실행 결과)

| 검증 | 방법 | 결과 |
|---|---|---|
| 스키마 적용 | 실물 Postgres 컨테이너에 `psql -f` | 테이블 6개 + 인덱스 4개 생성, 에러 0 |
| 부분 유니크 인덱스 — 비-PAID 다중 허용 | 같은 주문에 `FAILED`×2 + `PENDING` + `PAID` INSERT | **전부 성공** |
| 부분 유니크 인덱스 — PAID 중복 차단 | 2번째 `PAID` INSERT | `duplicate key ... uq_payment_order_paid` **거부** |
| 과다환불 CHECK | `refunded_amount = 12000` (amount 10000) | `violates ... chk_payment_refunded_amount` **거부**. 8000은 통과 |
| `CHECK (stock >= 0)` | `ProductStockConstraintTest` (INSERT·UPDATE 두 경로) | 2건 통과 |
| **음성 대조군** | 스키마에서 `CHECK (stock >= 0)` **제거** 후 재실행 | **2건 다 FAILED** → 테스트가 빨간불 낼 능력 있음 |
| **판별력 검증** | stock은 정상, `seller_id`만 FK 위반으로 바꿔 실행 | **FAILED** → 느슨한 검증이었다면 **가짜 통과**했을 케이스 |

전체 스위트: **7건 통과** (`failures=0, errors=0`), postgres:17 통일.

### 예외 검증을 못 박아야 하는 이유

`DataIntegrityViolationException`은 Spring이 **모든 제약 위반**(CHECK/FK/UNIQUE/NOT NULL)을 싸잡아 던지는 우산이다. 그것만 검사하면 *"뭔가 제약이 터졌다"*까지만 확인된다.

```java
.isInstanceOf(DataIntegrityViolationException.class)
.hasMessageContaining("chk_product_stock")   // ← 이게 있어야 "stock 제약이" 막았음이 확정
```

**제약에 이름을 붙여둔 게 여기서 회수된다.** 익명 제약이었으면 이 검증 자체가 불가능했다.
W1D2 `SchemaBehaviorTest`의 `.hasMessageContaining("subquery")`와 정확히 같은 처방 — 같은 함정을 두 번째로 만난 것.

## 4. 정직한 한계

- **음성 대조군을 스스로 돌리지 않았다.** 초록불을 보고 그대로 제출했고, Claude가 대신 제약을 빼서 빨간불을 확인했다. W1D2에 *"화재감지기에 연기를 갖다 대 봐야 한다"*고 정리해놓고 **다음 날 그 절차를 건너뛴 것**. → **초록불을 본 순간 "이게 빨간불이 될 수 있나"를 스스로 한 번 돌린다**를 습관으로.
- `RefundRaceTest`/`SchemaBehaviorTest`는 아직 **자기 테이블을 인라인으로** 만들어 쓴다(Day 2엔 스키마가 없었으니까). 이제 운영 스키마가 있으니 **W2D3에서 운영 스키마 대상으로 재작성**.
- 엔티티·리포지토리·서비스 미착수 → 방법1(서비스 메서드 경로) 검증은 여전히 미실시.

## 5. Day 4 진입점

### 1. 엔티티 클래스 6개 (`seller`/`product`/`orders`/`order_item`/`payment`/`refund`)

스키마가 확정됐으니 대부분 기계적 매핑이지만, **두 군데는 생각할 것**:

- **`Payment.status`에 setter를 열어두면 안 된다.** 종착지 불변(§4: *한 번 `PAID`면 영원히 `PAID`*)을 지키려면 전이 가드를 통과하는 메서드만 노출해야 한다. `setStatus()`가 public이면 §2 함정3(웹훅이 동기 응답보다 먼저 도착)에서 확정 상태가 뒤집힌다.
- **`refunded_amount`는 JPA가 관리하지 않는다.** 네이티브 조건부 UPDATE로만 갱신되므로, 엔티티 필드를 통해 쓰면 가드를 우회한다. 읽기 전용으로 두거나 `@Column(updatable = false)` 고려.

### 2. 재고 차감 로직

```sql
UPDATE product SET stock = stock - :qty, updated_at = now()
WHERE id = :id AND stock >= :qty
```
영향 행 0 → 재고 부족으로 거부. **Redis 없음**(§2).
