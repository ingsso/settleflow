## 1. Mock PG — 인프로세스 스텁 + 매직 금액

별도 프로세스 서버 대신 인프로세스 스텁(`StubPgClient`). 승인/거절/타임아웃 세 결과를 **매직 금액**으로 유발한다 — 실제 PG 샌드박스(토스 테스트 카드, Stripe 테스트 금액)의 관행.

- `amount % 1000 == 111` → 거절, `== 222` → 타임아웃, 그 외 → 승인
- **규칙은 스텁 안에만 산다.** `PaymentService`·도메인은 이 금액 코드를 모른다 — 알게 하면 매직 금액이 온 코드에 샌다.

### 동기 응답과 웹훅을 분리한다

인프로세스 스텁은 **동기 응답**(승인/거절/타임아웃)까지만 한다. 웹훅은 **실제 HTTP 엔드포인트**(`WebhookController`)로 배달한다 — 그래야 컨트롤러 + Redis SETNX 경로를 진짜로 태운다. 스텁이 자바 메서드 리턴으로 끝나면 멱등성을 아예 검증하지 못한다.

### "타임아웃"은 종착 결과가 아니다 — 2단계

승인/거절은 한 번에 끝나지만 타임아웃은 두 단계다:
- 동기 호출 → 타임아웃(`PgTimeoutException`) → `PENDING → UNKNOWN`
- **나중에 웹훅**이 승인/거절을 물고 옴 → `UNKNOWN → PAID/FAILED`

타임아웃을 값이 아니라 예외로 표현한 이유: "승인됐는데 응답만 못 받은 것"과 "거절"을 같은 칸에 두면 이중청구(W1D1 §3). `PgResult` enum엔 APPROVED/DECLINED만 있고 타임아웃은 없다.

## 2. 웹훅 바디 — 컨트롤러가 하려는 일에서 필드가 나온다

`PgWebhookRequest`. 각 필드에 "이거 없으면 그 일을 못 하나?"를 물어 정했다.

| 필드 | 컨트롤러가 이걸로 하는 일 |
|---|---|
| `merchantPaymentId` | **어느 결제인지 찾는다** (W1D3, pg_transaction_id는 PENDING 시점 NULL이라 매칭 불가) |
| `eventType` | `onApproved`/`onDeclined` 중 뭘 부를지 |
| `eventId` | **이 배달 이미 처리했나** — 멱등키(Redis SETNX) |
| `pgTransactionId` | Payment에 채운다. 이미 다른 값이면 모순(§7) |
| `amount` | PG가 본 금액. 우리 DB와 다르면 대사 불일치 신호(Week 3 이상 테이블 후보) |

**웹훅은 늘 확정(승인/거절)을 나른다** — 타임아웃은 "응답이 안 온 것"이라 애초에 웹훅으로 배달될 수 없다. 그래서 `PgEventType`은 APPROVED/DECLINED 둘뿐.

## 3. 컨트롤러 순서 — SETNX를 전이보다 먼저

```
SETNX(eventId)  ── 실패(중복) ─→ 200 OK  (아무 일도 안 함)
     │ 성공(처음)
     ▼
전이 dispatch (PaymentTransitionService)
     ▼
200 OK
```

**왜 SETNX가 먼저인가**: 재전송 2건이 동시에 들이닥칠 때, 두 번째 놈이 PENDING을 읽어보기도 **전에** 문전박대해야 lost update가 안 생긴다. 전이를 먼저 하면 이미 둘 다 PENDING을 읽은 뒤라 늦다(W1D2에서 실측한 것과 같은 모양).

**왜 항상 200 OK**: 중복도, 없는 결제도 정상이다. non-2xx를 주면 PG가 몇 시간 재전송한다(W1D1 §4). "이미 처리했음"은 에러가 아니라 성공.

**실패 시 키 삭제**: 일시적 실패(DB 등)면 SETNX 키를 지워 재전송이 다시 처리하게 한다 — 멱등키가 '끝나지 않은 일'을 영영 막지 않도록.

## 4. 오늘의 핵심 — SETNX는 fast-path, backbone은 상태 가드 + 낙관적 락

SETNX 위치를 정하다 딜레마에 부딪혔다:

| | 막는 것 | 못 막는 것 |
|---|---|---|
| 키를 **일 전에**(관문) | 동시성 | **크래시** — 키만 박히고 일이 안 끝나면 재전송이 영영 막힘 |
| 키를 **일 후에**(완료표시) | 크래시 | **동시성** — 관문이 없어 둘 다 PENDING 읽고 둘 다 전이 |

**하나의 SETNX 위치로는 둘 다 못 잡는다.** 그래서 정합성의 주인은 SETNX가 아니다.

> **Backbone = 상태 가드(`PAID + 승인 → IGNORED`) + 낙관적 락(`@Version`).**
> 크래시가 나든 두 놈이 동시에 오든, PAID된 결제엔 부수효과가 두 번 안 생긴다.
> **SETNX는 흔한 중복을 싸게 쳐내는 fast-path**일 뿐, 없어도 정합성은 backbone이 지킨다("두 겹").

### 상태 가드만으론 동시성에서 안 버틴다 → 낙관적 락

두 웹훅(또는 동기응답+웹훅)이 동시에 오면 둘 다 읽을 때 `PENDING`이라 인메모리 `if (status==PAID)` 가드가 둘 다 안 걸린다. `PENDING → PAID` 전이를 **원자적으로** 만들어야 지는 쪽이 진짜 PAID를 보고 튕긴다 → 재고·환불에서 쓴 것과 같은 문제, 여기선 **`@Version`(B안)**으로 푼다.

### 왜 B안(낙관적 락)인가 — 조건부 UPDATE가 아니라

결제 전이는 결과가 **셋**(`TRANSITIONED`/`IGNORED`/`CONFLICT`)이다. 블라인드 조건부 UPDATE의 영향 행 0은 IGNORED와 CONFLICT를 뭉갠다. `@Version`을 쓰면 `onApproved()`가 세 갈래를 그대로 소유하고(엔티티가 전이표 소유, W1D3 §5), 동시에 진 쪽만 `OptimisticLockException` → 재조회 → 종착지 → IGNORED.

구현: `PaymentTransitionService`가 재시도 루프(load→on*→save)를 소유하고, 엔티티가 전이표를 판단한다. `pay()`(동기)와 `WebhookController`(비동기)가 이 서비스를 **공유**한다.

## 5. PaymentService — PG 호출 전 PENDING 선커밋

```
tx1: PENDING INSERT + 커밋   ← PG 부르기 전에 끊고 커밋
----- 트랜잭션 경계 -----
PG 동기 호출 (느리고 터질 수 있음)
----- 트랜잭션 경계 -----
tx2: 결과 반영 (PaymentTransitionService, 낙관적 락)
```

PG 호출을 tx 안에서 하면 호출이 터졌을 때 롤백되어 PENDING 행이 사라지고, 나중 웹훅이 매칭할 행이 없다(W1D1 §2 함정1). 자기호출 함정을 피하려고 `TransactionTemplate`으로 명시적으로 tx1을 커밋한다.

## 6. 실측 (전부 실제 실행 결과)

동시 20 VU, `CyclicBarrier`로 동시 발사, 실제 HTTP 엔드포인트에 POST(JDK `HttpClient`).

| 시나리오 | 관측 | 결과 |
|---|---|---|
| 정상 승인 | pay() → status | `PAID`, 주문 `PAID` |
| 뒤늦은 승인 웹훅 | 전이 결과 / pgTx | 전이 IGNORED(PAID 유지)지만 **pgTx는 이 웹훅이 처음 링크** |
| 타임아웃 2단계 | pay()→웹훅 | `UNKNOWN` → 웹훅 승인 → `PAID` |
| **같은 eventId 20개 동시** | `applyApproved` 호출 / version | **호출 1회 / version 1** (SETNX 관문) |
| **다른 eventId 20개 동시** | 호출 / version | **호출 20회 / version 1** (관문 무력화해도 backbone이 1회로 수렴) |
| **음성대조군 B — 가드 제거** | TRANSITIONED 카운트 | 가드 O → **1**, 가드 X → **20** |

- 전체 스위트 **14건 통과**(failures=0). `SchemaMappingTest`로 `@Version`(V2 마이그레이션) 매핑도 실측.
- 스캐폴드(`IntegrationTestSupport`): Postgres + Redis 컨테이너, `RANDOM_PORT`. Redis는 자동 연결 지원이 없어 `@DynamicPropertySource`로 host/port 배선.

### version 관측의 사각 — 오늘 가장 중요한 발견

가드를 제거해도 **version은 1**이었다. `PENDING → PAID`라는 실제 상태 변경은 한 번뿐이고, 중복 전이는 **같은 값을 재기록**(멱등)이라 dirty가 아니라서 version이 안 오른다. 즉:

> **version은 correctness 증거로는 훌륭하지만(항상 1), backbone 제거에는 눈이 멀었다.**
> 가드를 지운 채 스위트를 돌려도 **네 시나리오 다 초록불** — version도 호출 수도 가드 제거를 못 잡는다.

피해가 눈에 보이는 건 **TRANSITIONED 횟수**다(가드 O → 1, 가드 X → 20). 그래서 `1ad8243`에서 스파이(`doAnswer`)로 TRANSITIONED를 세어 `== 1`을 단언하는 **backbone 회귀 테스트**를 넣었다 — 이제 누가 상태 가드를 지우면 CI가 빨강. version만 보던 사각이 메워졌다.

지금 코드엔 셀 수 있는 **비멱등 부수효과가 아직 없어서**(markPaid는 멱등) version으로 B 피해가 안 보이는 것이다. Week 2의 ledger 행 수에서 이 이중 실행이 "분개 20행 = 이중장부 붕괴"로 진짜 보인다.

## 7. linkPgTransaction 모순 감지 (D3 미결 #4 해소)

`linkPgTransaction`이 조용히 덮어쓰던 걸 **모순 감지**로 바꿨다. 처음이면 채우고, 같은 값이면 멱등, **다른 값이면 false**(같은 결제에 PG 거래번호가 둘일 리 없다) → 호출부(`PaymentTransitionService`)가 알람. 지금은 로그뿐이고, 이상 테이블은 Week 3.

## 8. 정직한 한계

- **음성대조군 B를 처음엔 카운터를 `blast` _뒤_에 설치**해서 0이 나왔다(스파이는 코드 실행 전에 깔아야 함). 순서를 고쳐 20을 확인. A는 자동, B는 손으로 가드를 주석 처리해 빨간불을 봄 — W1D2부터 3세션 이월된 "화재감지기에 연기"를 이번엔 직접 돌렸다.
- **`CONFLICT`와 링크 모순은 로그뿐** — 이상 테이블(`PaymentAnomaly`)은 Week 3.
- **`Order.markPaid()/cancel()`에 가드 없음**(W1D3 진입점 #5) — 오늘 안 함. `CANCELED`에서 `markPaid()` 통과. Week 2 환불 흐름에서 볼 자리.
- 회귀 테스트 메서드 이름이 아직 `음성대조군B_..._version은_1이다`인데 실제론 TRANSITIONED를 단언 → 이름이 실체와 어긋남(사소).
- **crash 창은 여전히 존재**: SETNX 성공 후 커밋 전에 죽으면 키만 남는다. TTL 만료 + 미결제 쓸이 배치가 회수하는 설계지, 코드로 막은 건 아님.
- `Idempotency-Key` TTL 24h는 임의값 — PG 재전송 창을 넘긴다는 가정. 실측한 수치 아님.

### Boot 4 이관 메모
- `TestRestTemplate`이 `org.springframework.boot.resttestclient`로 이동 + `spring-boot-restclient` 의존성 필요 → 새 의존성 대신 JDK `HttpClient`로 우회.

## 9. Day 5 진입점

**Day 5의 정의는 "배선"이다.** 통합테스트(`PaymentFlowTest`)는 오늘 사실상 끝났고, 결제 코어도 다 있다. 문제는 **조각들이 따로 논다는 것** — `InventoryService`(재고차감)와 `PaymentService.pay`(결제)가 한 진입점으로 안 묶였고, **로컬 실행용 주문 엔드포인트가 없다**(웹훅 엔드포인트뿐). 주말 체크포인트가 *"로컬에서 실제로 확인"*이라 이 배선이 핵심.

### 목(7/16) — 돌아가는 흐름까지만
1. **`OrderService`(가칭)** — 주문 생성 + `InventoryService.decrease`를 한 트랜잭션으로 묶고 → `PaymentService.pay` 호출. **유일한 설계 판단**: 재고차감 tx와 PENDING 선커밋 tx의 경계를 어떻게 나눌지(오늘 §5 선커밋 논리의 연장).
2. **주문 REST 엔드포인트**(`POST /orders` 류) — 사람이 눌러 흐름을 태울 입구.
3. **`Order.markPaid()/cancel()` 가드** — 상태 전이 방어(§8). **숙제: Claude가 스캐폴드하기 전에 전이표를 혼자 초안**(D3에서 `onApproved`를 혼자 맞힌 방식).
4. 통합테스트에 **재고차감 단계 포함**(지금 `PaymentFlowTest.createOrder`는 재고를 안 탐).

> ⚠️ **목요일엔 README·리팩터를 넣지 않는다.** 흐름 완성이 밀린다. 목요일의 정의는 "관통 성공" 하나로 좁힌다.
