## 0. 왜 엔티티보다 검증을 먼저 했나

Day 1 설계(특히 §1 A안: `refunded_amount` 비정규화 + 원자적 조건부 UPDATE)는 **검증 안 된 Postgres 동작 3건 위에** 얹혀 있었다. 이게 틀리면 엔티티 설계가 통째로 바뀌므로, **엔티티를 짜기 전에 지반부터 확인**(설계 문서 §10 순서). 지반이 물렀다면 벽(엔티티)을 세운 뒤 철거해야 하는데, 검증(SQL 몇 줄)이 엔티티보다 훨씬 싸다.

## 1. 검증 결과 — 미검증 3건 → 0건

| # | 주장 | 검증 테스트 | 실측 결과 |
|---|---|---|---|
| 2 | READ COMMITTED에서 조건부 UPDATE가 동시 환불 레이스 차단 | `RefundRaceTest` | 가드 O → 성공 1건 / 최종 8000, 음성 대조군(가드 X) → 성공 2건 / 최종 11000 |
| 1 | Postgres가 서브쿼리 담은 CHECK 거부 | `SchemaBehaviorTest` | `cannot use subquery in check constraint` 예외 발생 |
| 3 | unique 인덱스가 NULL 다중 삽입 허용 | `SchemaBehaviorTest` | NULL 2행 INSERT → count=2 |

**전부 통과** (tests=4, failures=0, errors=0). → §1 A안의 지반이 실측으로 단단함을 확인. 엔티티를 얹어도 헛수고 아님.

## 2. 테스트 파일 위치와 각각이 증명하는 것

### `src/test/java/com/settleflow/RefundRaceTest.java`
- **검증 방식**: 방법2(수동 JDBC) — Spring 컨텍스트 없이 순수 JUnit + Testcontainers. `DriverManager.getConnection()`으로 커넥션을 직접 열어 "커넥션 풀 1개" 함정 회피, `setAutoCommit(false)`로 트랜잭션 경계를 직접 통제.
- **동시성 재현**: `CyclicBarrier(2)`로 두 스레드를 문 앞에서 대기시켰다가 동시 발사 → 실제 충돌 강제.
- **핵심 SQL**: `UPDATE payment SET refunded_amount = refunded_amount + ? WHERE id = ? AND refunded_amount + ? <= amount` — 한도 초과면 영향 행 0(거부).
- **음성 대조군**: 위에서 `AND ...` 가드만 뺀 버전. 실제로 11000(이중환불)이 나오는 걸 관측 → 가드 있을 때의 8000이 "가드 덕분"임을 증명(테스트가 빨간불 낼 능력이 있음을 확인).

### `src/test/java/com/settleflow/SchemaBehaviorTest.java`
- 동시성 없음. SQL 날리고 결과(예외/건수)만 본다.
- **서브쿼리 CHECK 거부**: `CHECK (x <= (SELECT 100))` 담은 CREATE TABLE 시도 → `assertThatThrownBy(...).hasMessageContaining("subquery")`로 "서브쿼리라서 거부됨"을 못 박음(문법 오타로 인한 가짜 통과 방지).
- **NULL 다중 unique**: `pg_transaction_id VARCHAR(64) UNIQUE` 컬럼에 NULL 행 2개 INSERT → count=2. → §2 함정4(웹훅 매칭용 nullable+unique 식별자)의 근거.

## 3. 오늘 처음 배운 개념 (다음에 헷갈릴 때 참고)

- **Testcontainers vs docker-compose**: compose는 "내가 관리하는 장기 인프라"(손으로 up, 계속 삶, 앱 구동용), Testcontainers는 "테스트가 소유하는 일회용 인프라"(테스트가 자동 기동/폐기, 랜덤 포트, 매번 새 DB). 검증은 격리·재현이 생명이라 떠있는 Postgres를 안 건드리고 Testcontainers가 자기 컨테이너를 띄우게 함. 검증 대상이 Postgres **고유** 동작이라 H2 대체 불가.
- **`PreparedStatement`의 `?`/`setLong`은 2단계**: SQL 문자열엔 빈칸(`?`)만. `setLong(n, 값)`은 `prepareStatement` **다음** 별도 줄에서 n번째 빈칸을 채움. (문자열 안에 `setLong`을 넣는 게 흔한 첫 오해.)
- **CyclicBarrier**: N명이 다 모이면 같이 출발. 두 스레드를 억지로 동시에 부딪히게 하는 장치. 없으면 겹칠지 안 겹칠지 OS 마음.
- **음성 대조군(negative control)**: "이 테스트가 빨간불을 낼 능력이 있는가"를 확인하는 절차. 통과한 테스트는 실패할 수도 있었을 때만 의미가 있다. (화재감지기: 조용한 게 불이 없어서인지 감지기가 고장 나서인지 구분하려면 연기를 갖다 대 봐야 한다.)
- **`assertThatThrownBy`**: 값이 아니라 "예외가 나는 것"을 검증. `.isInstanceOf(...)` + `.hasMessageContaining(...)`로 올바른 이유로 터졌는지까지 확인.

## 4. 검증 범위의 한계 (정직하게)

- 오늘은 **방법2(수동 JDBC)로 A안(원자적 조건부 UPDATE)만** 검증. 기각한 B안(SELECT FOR UPDATE)은 안 건드림 — 채택안을 검증한 것이라 맞음.
- **방법1(서비스 메서드 경로, `@Transactional`)은 아직**. 엔티티·리포지토리·서비스가 생긴 뒤 운영 코드 경로로 재검증 → **W2D3 "불변식 DB 제약 검증 테스트" 산출물로 재사용** 예정.
- `PostgreSQLContainer("postgres:16")` 문자열 생성자 deprecation 경고 있음(무해). 신경 쓰이면 `DockerImageName.parse(...)`로 교체.
