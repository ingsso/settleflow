## 한 줄

**돈이 두 번 나가지 않는다는 것을, 수치로 증명하는 결제·정산 시스템.**

이커머스 결제부터 **셀러 정산**까지를 한 줄기로 다룬다. 주문·결제(웹훅 멱등성) → 복식부기 장부
→ 정산 배치와 **대사(reconciliation)** → 관측성·부하테스트 → **정기결제 재시도(Dunning)** 순으로
쌓았다.

**결제 도메인을 고른 이유**는 *"틀렸을 때 조용한"* 오류가 많아서다. 화면이 안 뜨면 누구나
알지만, **정산액이 조금 많으면 아무도 신고하지 않는다.** 이 프로젝트의 대부분은 그
*조용한 오류*를 **스스로 드러나게** 만드는 일이었다.

```
Java 21 · Spring Boot 4.1.0 · PostgreSQL · Redis · Kafka

```

## 핵심 문제 1 — 웹훅이 중복으로 와도 장부는 한 줄

**문제.** PG 는 같은 결제 통보를 **여러 번 보낸다**(응답이 늦거나 유실되면 재전송한다).
그대로 처리하면 **매출이 두 번 적힌다.**

**원인.** 흔한 해법인 Redis 키(SETNX)는 **효율 장치이지 정합성 장치가 아니다.** 키가 만료되거나
키를 만들기 전에 프로세스가 죽으면 그대로 뚫린다 — *"키가 있으니 안전하다"* 는 **키가 없을 때
무슨 일이 일어나는지**를 안 본 것이다.

**해결.** 방어를 **두 층**으로 갈랐다.

```
Redis SETNX   효율   — 대부분의 중복을 앞에서 되돌려보낸다 (그리고 뚫려도 된다)
전이표        정합성 — PAID 는 종착지다. 종착지를 떠나는 전이가 없으므로
                       뒤늦은 통보는 상태를 못 바꾸고, 부수효과(장부·이벤트)는 1회로 묶인다
```

**결과.**

- **서버가 받은 중복 웹훅 1,000건 → `journal` 증가 1** (payment version 2, outbox 1)
- 분자를 **부하 발생기가 아니라 서버 카운터**로 잡았다 — k6 자기 보고는 실제로 어긋났다
  (보냄 1,000 / 도달 965)
- 부하 중 **강제 종료**로 유실 구멍의 크기를 쟀다: 고아 키는 시스템 고유값이 아니라
  **종료 순간 in-flight 요청 수의 함수**였다(활성 3 → 0건 / 활성 99 → **23건**)

## 핵심 문제 2 — 아무도 신고하지 않는 정산 오류를 스스로 찾기

**문제.** 정산 로직의 오류에는 비대칭이 있다. **덜 주면 다음 날 전화가 오지만, 더 주면 아무도
말하지 않는다.** 과지급만 만드는 버그는 **신고 경로 자체가 없다.**

**원인.** 검증을 *같은 계산*으로 하면 아무 소용이 없다. 배치가 쓴 집계 쿼리를 대사가 다시
돌리면 **틀려도 영원히 일치한다**(통장을 안 보고 가계부를 두 번 읽는 것).

**해결.**

- **원천을 바꿔 재구성한다.** 배치는 장부를 합치고, 대사는 **결제·주문 항목을 다시 쪼개** 정산액을
  독립적으로 만든다
- **제약과 대사를 갈랐다.** `정산액 = 장부합` 은 DB 트리거로 강제할 수 **있었지만 안 걸었다** —
  이건 *어긋날 수 있는* 관계라 막으면 방어가 아니라 **고장**(정산이 아예 안 써진다)이다.
  **절대 어긋나면 안 되는 것엔 제약, 어긋날 수 있는 것엔 대사**
- **불일치는 고치지 않고 쌓는다.** 값어치가 *"지금 어긋남"* 이 아니라 **"며칠째 안 메워짐"** 에
  있어서다

**결과 — 결함 주입으로 증명.** 집계 SQL 의 **부호 하나**(`-금액` → `+금액`)를 제거했더니:

- 정산 배치 테스트는 **6건 중 4건이 통과**했다(그 데이터엔 환불 줄이 없어 분기를 안 탄다) —
  **초록불은 코드가 옳다는 뜻이 아니라 그 경로를 안 밟았다는 뜻**
- 오차는 **환불액의 2배**이고 **부호가 항상 과지급 방향** = 신고가 안 들어오는 오류
- **그리고 대사가 그걸 잡았다** — 2건, 차액 합 10,000, 둘 다 양수

**대사가 스스로 눈감지 않게 한 것**: 대사 대상 날짜를 *"정산이 방금 돈 날짜"* 로만 정하면,
정산이 통째로 죽었을 때 **볼 게 없어서 불일치 0건 = 초록불**이 된다. 그래서 날짜 출처를
셋으로 뒀다(정산이 돈 날 / 미해소 불일치가 있는 날 / **최근 7일 — 정산이 뭘 하든 무조건**).

## 핵심 문제 3 — 정기결제 재시도에서 이중 청구 0건

**문제.** 구독 결제는 **실패가 정상 경로의 일부**다(한도 초과는 며칠 뒤 풀린다). 그래서 재시도가
필요한데, **재시도는 웹훅 중복과 성질이 다르다** — 웹훅은 *같은 사실이 두 번 통보되는* 것이라
우리 DB 안에서 막지만, 재시도는 **우리가 PG 에 두 번 거는** 것이라 못 막으면 **돈이 실제로 나간다.**

**원인.** 낙관적 락이 여기서 안 듣는다. 인스턴스 둘이 같은 주기를 집으면 **둘 다 PG 를 부르고**,
커밋 시점에 하나가 롤백돼도 **나간 돈은 안 돌아온다 — 롤백은 우리 DB 만 되돌린다.**
웹훅은 [판정 → 부수효과]인데 폴링은 **[부수효과 → 판정]**이라 순서가 뒤집혀 있다.

**해결.**

- **배타성을 집는 단계로 옮겼다(리스/CAS).** 돈이 나가기 전에 **커밋되는 사실**을 만들고,
  진 인스턴스는 0행을 잡고 물러난다
- **결말이 안 난 시도는 새 청구가 아니라 재전송이다.** `PENDING`·`UNKNOWN` 은 *"돈이 움직였는지
  모른다"* 이고, **되돌릴 근거가 없으면 새로 낼 근거도 없다.** 같은 멱등키로 다시 보내면
  PG 에겐 같은 한 건이다
- **상한을 값으로 안 적었다.** `maxAttempts=3` 은 간격 목록 `[1,3,7]` 과 항상 같아야 하는 값의
  복제다 — **포기는 목록에 다음 칸이 없다는 사실**이지 따로 적는 수가 아니다

**결과 — 인스턴스 3개로 실제 경합을 만들어 쟀다.**

| 계기 | 값 |
|---|---|
| 구독 500개가 같은 날짜에 동시 도래, 인스턴스 3개가 1초마다 폴링 | |
| **한 주기가 서로 다른 키를 2개 이상 받은 것** | **0건** |
| 서로 다른 멱등키 | **500** (구독·주기·시도와 정확히 일치) |
| PG 실호출 분배 | **160 / 169 / 171** → 합 500 |
| 차단기 | 3개 전부 CLOSED |

- **세 인스턴스가 500건을 거의 3등분한 것**이 경합의 직접 증거다 — 셋 다 같은 목록을 같은
  순서로 훑었고, 어느 행이 누구 것이 되는지는 CAS 가 갈랐다
- **방어를 빼면 어떻게 되는지도 쟀다**: CAS 조건 한 줄 제거 → 같은 시나리오에서
  **서로 다른 키 10개 · PG 호출 19회**. *"0건"* 만으로는 **막은 것인지 안 부딪힌 것인지** 못 가른다
- 이중 청구는 **실재했다**: 크래시 후 재집기에서 **PG 승인 3회 · 키 3개** → 재전송 도입 후 **키 2개**

## 이 프로젝트에서 가장 많이 쓴 사고 — 계기를 의심한다

기능보다 **재는 방법**을 고치는 데 시간을 더 썼고, 그게 이 프로젝트의 실질이다.

**① 초록불은 코드가 옳다는 뜻이 아니다.** 그래서 방어 장치를 **직접 제거해보고** 무엇이
빨간불이 되는지를 매번 예측하고 실행했다(마지막 주에만 **12회 · 예측 12/12 적중**).
빨간불이 **안 나는** 것도 결과다 — *"있는데 아무도 안 재는 코드"* 세 자리를 그렇게 찾아냈다.

**② 재는 자와 재이는 것이 경로를 공유하면 그 수치는 스스로를 검증 못 한다.**

```
DB 가 죽으면 SQL 알림도 같이 죽는다        → 관측을 다른 저장 경로로
배치와 같은 SQL 로 대사하면 영원히 일치     → 원천을 바꿔 재구성
부하 발생기의 자기 보고는 어긋났다          → 분자를 서버 카운터로
```

**③ 같은 수치를 세 번 다르게 셌다.** *"중복 청구 0건"* 을 처음엔 우리 DB 의 행 수로 셌는데,
그 대리 지표의 근거가 **검증 대상 코드 자신의 성질**이었다. → **PG 호출 수**로 옮겼고,
재전송이 생기자 그것도 부족해 → **서로 다른 멱등키 개수**로 다시 옮겼다. 지금은 둘을 나란히
두고 그 차이에 이름을 붙여 쓴다(`PG 호출 − 키 = 재전송 횟수`).

**④ 전제는 만료된다.** 마지막 주에 *"어제까지 참이던 판단이 오늘 정의역을 잃는"* 일이
**사흘 연속** 났다 — 셋 다 버그를 넣은 게 아니라 **새 호출부·새 분기가 기존 판단의 적용 범위를
조용히 좁힌 것**이었다. 검증 안 한 추측보다 **검증했고 참이었던 문장**이 더 오래 살아남아
위험하다는 걸 여기서 배웠다.

## 정직한 한계

- **PG 는 스텁이다.** *"같은 키에 한 번만 과금한다"* 는 **검증 불가한 외부 계약**이라, 테스트
  파일을 절로 갈라 *우리가 보증하는 것*(키 개수)과 *PG 에 기대는 것*(스텁 위의 가정)을
  **파일 구조로** 분리했다
- **부하는 로컬 단일 머신**이다. 처리량 수치는 서버 용량이 아니라 이 노트북의 값이다
- **재시도 시각 축(P2)의 경합은 약한 통과**다 — 부하는 정기 청구 축(P1)만 겨눴다
- **CAS 에서 진 횟수를 세는 계기가 없다** — *"충돌이 실제로 일어났나"* 를 분배로 추정한다
- 차단기가 열린 동안 **재시도 간격이 그냥 소모되는 것**은 미구현
- 운영 환경 배포·인증·멀티 테넌시는 범위 밖
