## 1. 오늘의 범위

`POST /webhooks/pg` 는 바디 형식만 맞으면 누가 보냈든 처리했다. 서명·IP 제한·시크릿 헤더 중
아무것도 없었다. 오늘 붙인 것은 HMAC-SHA256 서명이고, 판단의 본체는 **어디에** 붙이느냐였다.

```
서명 검증 ── 실패 → 401  (멱등키 안 남김)
   │
파싱·검증 ── 실패 → 400
   │
SETNX(eventId) ── 이미 있음 → 200
   │
전이 dispatch → 200
```

진행 방식은 평소와 달랐다: 설계가 가이드 문서에 이미 있었고, **구현은 Claude 가 가이드를 읽고
했다.** 사용자의 몫은 예측(§5)과 머지 뒤 검토(§4 정정)였다. §9 에 따로 적는다.

## 3. 구현에서 가이드와 다르게 한 것

### 매퍼 — 가이드의 전제가 이 프로젝트에 없었다

가이드: *"Spring Boot 4 / Jackson 3 환경이므로 기존에 주입받는 매퍼 빈을 그대로 사용한다."*
실제: 주입받는 매퍼 빈이 없다. `OutboxWriter`·`RefundRequestedConsumer` 가 Jackson 2 `JsonMapper` 를
직접 만든다(Boot 4 는 webmvc 만으론 ObjectMapper 빈을 안 만든다 — W3D1). 같은 방식을 따랐다.

그 대가로 하나를 손으로 맞춰야 했다. 직접 만든 매퍼는 **모르는 필드에서 실패하는 게 기본값**이다.
`@RequestBody` 로 받던 시절엔 Spring 의 매퍼가 파싱해 PG 가 필드를 추가해도 통과했는데, 기본값을
그대로 두면 **PG 가 필드 하나 추가하는 순간 모든 웹훅이 400** 이 된다. `FAIL_ON_UNKNOWN_PROPERTIES` 를 껐다.

### 고정값 대조 테스트 1건 추가 — 동어반복 차단

`sign()` 과 `verify()` 가 같은 클래스라, 둘이 **똑같이** 틀리면(예: 구분자 `.` 누락) 나머지 테스트는
전부 초록불이고 실제 PG 와는 안 맞는다. 기대값을 이 코드가 아니라 Python `hmac` 으로 계산해 박았다.
W3D4 의 *"같은 SQL 을 두 번 읽으면 대사가 아니다"* 와 같은 축이다.

### 시크릿 기본값을 안 뒀다 + 빈 값이면 기동 실패

`${WEBHOOK_SECRET}` 에 기본값이 있으면 운영에서 환경변수를 빠뜨려도 앱이 뜨고, **아무나 아는
시크릿**으로 서명을 받는다. 비어 있으면 생성자에서 멈춘다 — 안 멈추면 요청 시점에 `SecretKeySpec` 이
터져 모든 웹훅이 500 이고, PG 는 원인 모르는 재전송만 반복한다.

### 곁가지 — 컨텍스트가 안 뜬 테스트 둘

첫 전체 실행에서 `SettleflowApplicationTests`·`InventoryConcurrencyTest` 가 깨졌다
(`Could not resolve placeholder 'WEBHOOK_SECRET'`). 둘은 `IntegrationTestSupport` 를 안 거쳐
테스트 시크릿을 못 받는다. `@SpringBootTest(properties = ...)` 로 직접 줬다. 테스트용 yaml 을 만드는
길은 W3D2 에 메인 yaml 을 통째로 가렸던 전례가 있어 안 갔다.

## 4. 정정 — 401 응답 규약 (머지 뒤 사용자 검토)

가이드 8장 초안: ~~서명 불일치 시 401, 재전송하지 말 것~~

| 상황 | 응답 | 제휴사 조치 |
|---|---|---|
| 서명 불일치 | 401 | 재전송 (가맹점 측 시크릿 확인 후 정상 처리됨) |
| 바디 형식 오류 | 400 | 재전송해도 결과 동일, 연동 담당자 확인 필요 |

401 의 실제 원인은 위조보다 **우리 쪽 시크릿 설정 실수**가 훨씬 흔하다. 그때 PG 가 재전송을 멈추면
진짜 결제 통보가 영영 사라진다. 계속 재전송하면 시크릿을 고친 뒤 들어오는 재전송이 정상 처리되고,
위조는 몇 번을 재전송해도 401 이라 손해가 없다.

**이 규약이 성립하는 근거는 구현에 이미 있었다** — 401·400 은 SETNX **전에** 반환되므로 멱등키가 안
남고, 재전송이 "중복"으로 막히지 않는다. 그리고 §5 가 그 반대(키가 남는 순서)에서 무슨 일이 나는지를
보여준다. 정정과 대조군이 같은 성질의 양면이다.

**여전히 참인 것**: 응답 코드와 판정 순서. 바뀐 건 제휴사에게 요구하는 조치뿐이다.

## 5. ★ 음성대조군 — 3 red / 4 green

**제거 대상**: `WebhookController.receive()` 의 `verifier.verify(...)` if 블록을 `setIfAbsent` 아래로.
파싱 블록은 SETNX 위에 그대로(SETNX 가 `req.eventId()` 를 쓴다). 방어층은 한 겹이다 —
`PaymentTransitionService` 의 상태 가드는 위조가 SETNX 를 통과한 *뒤*의 장치라 이 공격과 무관하다.

**실행**: 사용자가 "네가 돌려"라고 해서 Claude 가 실행. `--tests "*WebhookSignatureTest"` — 클래스
단위 필터라 실험을 무효화하지 않는다.

```
[실측 2026-10-21] 위조→진짜(같은 eventId): 위조 HTTP 401, 위조 뒤 멱등키 있음, 진짜 HTTP 200, 최종 status=PENDING
```

| 케이스 | 결과 | 실패 메시지 |
|---|---|---|
| 정상 서명 | 🟢 | |
| 서명 틀림 | 🔴 | 멱등키 `expected false but was true` |
| 헤더 누락 | 🔴 | 두 번째 요청 `expected 401 but was 200` |
| 바디 변조 | 🟢 | |
| 5분 지난 타임스탬프 | 🟢 | |
| 위조 → 같은 eventId 진짜 | 🔴 | `expected PAID but was PENDING` |
| 외부 계산 고정값 대조 | 🟢 | |

**원복**: `git checkout` 으로 되돌린 뒤 같은 클래스 재실행 → **7/7 green**,
`[실측]` 은 `멱등키 없음 · 진짜 200 · PAID` 로 돌아왔다.

### 예측 대조

| 누가 | 예측 | 결과 |
|---|---|---|
| 사용자 | 2건 red, 위조 뒤 멱등키 있음, 진짜 200인데 PENDING | `[실측]` 세 값 **전부 적중**, 개수 **2 → 3** |
| 검토 메모 | 위조→진짜만 red, 나머지 6건 green | 빗나감 |
| Claude (테스트 javadoc) | *"다른 케이스는 앞이든 뒤든 초록불"* | 빗나감 (§8) |

### 빨간불 셋은 원인이 하나다 — 401 이 멱등키를 남긴다

같은 현상을 세 자리에서 봤다:

- **서명 틀림** — 키를 직접 단언해서 잡혔다.
- **헤더 누락** — 첫 요청이 남긴 키 때문에 **서명 없는 두 번째 요청이 검증까지 가지도 않고 200** 을 받았다.
  위조자가 같은 eventId 로 두 번 쏘면 두 번째부터 "수신 확인"을 받는다. 가이드가 적은 피해(진짜 통보
  차단) 말고 **하나가 더 있었다** — 이건 대조군을 돌려서야 보였다.
- **위조 → 진짜** — 진짜 통보가 200 을 받고 버려진다. 성공 응답이라 **PG 도 재전송하지 않는다**.
  즉 이 피해는 스스로 회복되지 않고, 대사(W3D4 외부 축) 말고는 발견 경로가 없다.

초록불 넷은 요청을 한 번만 쏘고 키를 안 보므로 순서와 무관하다. **"red 4 개가 안 났다"가 아니라
"애초에 이 실험의 경로를 안 밟는 케이스"** 다(W3D3 음성대조군과 같은 모양).

## 8. Claude 오류

1. **테스트 javadoc 에 대조군 결과를 예측으로 단정했다.** *"이 테스트가 순서를 지키는 유일한 단언 —
   다른 케이스는 앞이든 뒤든 초록불"*. 같은 javadoc 의 바로 위 문단에 *"키가 안 남았다는 게 순서다"*
   라고 써놓고, 키를 단언하는 "서명 틀림" 케이스를 셈에서 뺐다 — **자기가 쓴 설계를 안 읽은 것**
   (W3D2 *"두 겹이라 써놓고 한 겹만 찍음"* 과 같은 모양). 대조군이 드러냈고 javadoc 을 실측으로 고쳤다.
2. **401 규약 오류를 구현 때 못 잡았다.** "401 은 멱등키를 안 남긴다"를 코드 주석에 직접 쓰면서, 그게
   *재전송이 안전하다*는 뜻이라는 데까지 안 갔다. 가이드의 "재전송하지 말 것"을 그대로 두었고, 사용자
   검토에서 잡혔다.
3. 머지 첫 시도에서 `git merge -F -` 가 표준 입력을 못 읽어 실패(브랜치 커밋은 정상). 파일로 재시도.
