## 2. 핵심 설계 판단 — "무엇을, 왜"

| 판단 | 근거 한 줄 | 출처 |
|---|---|---|
| 재고에 Redis 락 **폐기** | 좌석 선점(지속)≠재고 차감(순간). Redis가 풀던 건 정합성이 아니라 "시간"; 정합성은 원자적 조건부 UPDATE로 DB가 함 | W1D3 §2 |
| 웹훅 멱등: SETNX=**fast-path**, 정합성=backbone(상태가드+낙관적 락) | 다른 eventId 20개로 SETNX 우회당해도 `version`은 1로 수렴 | W1D4 §4 |
| 타임아웃 = **UNKNOWN**(FAILED 아님) | 정보의 부재는 확정 정보를 뒤집지 못한다 | W1D1 §3 |
| 환불을 `Order` enum → **`Refund` 엔티티**로 | 역분개가 건별 금액을 요구 (W2D5가 실제로 씀) | W1D1 §1 |
| 과다환불: 비정규화 `refunded_amount` + **원자적 조건부 UPDATE** | 조회-후-판단은 레이스 (8000이어야 할 값이 가드 없으면 11000) | W1D1 §1, W1D2 |
| `CANCELED + 결제확정 = CONFLICT` | 실재하는 **이중판매 구멍** — 종착지는 안 떠난다 | W1D5 §1 |
| `place()`에 `@Transactional` **안 붙임** | 재고차감 tx와 PG 호출 사이 경계 — 트랜잭션이 PG I/O를 물면 안 됨 | W1D5 §5 |

## 3. 검증한 것 vs 못한 것

**✅ 실측으로 검증**
- Day 1 미검증 3건 → 0건 (`RefundRaceTest`, `SchemaBehaviorTest`)
- 재고 차감 동시성: 성공 1건 / 최종 8000, 가드 제거 시 11000
- 웹훅 중복 20개 동시 → 실제 처리 1건, backbone TRANSITIONED 정확히 1회
- 음성대조군 A·B·C·D **직접 실행**("화재감지기에 연기")
- 주문 1건 bootRun 관통 (주문→재고차감→결제→웹훅)

**⬜ 못한 것 → 이월**
| 이월 | 성격 |
|---|---|
| `Order` 가드 동시성 미검증 | `Payment.@Version` 뒤라 단독 동시 전이 안 일어난다 **추정** |
| `CONFLICT`/이상 기록이 **로그뿐** | 이상 테이블(W3) 생기면 "행 1개"로 단언 가능 |
| `cancel()` 가드 미정 | 쓸이 배치 자리 (W2 이후) |
