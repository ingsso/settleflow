## 1. `Order` 전이표 — 본인이 초안

`Payment`의 12칸(W1D1 §4)과 달리 6칸이다.

| 현재 \ 사건 | 결제확정 | 취소 |
|---|---|---|
| `CREATED` | → `PAID` (TRANSITIONED) | → `CANCELED` (TRANSITIONED) |
| `PAID` | IGNORED | **미정** — 호출부 생길 때 |
| `CANCELED` | **CONFLICT** | IGNORED |

### 거절이 열에 없는 이유

`Payment`는 승인확정/거절확정을 다른 열로 뒀는데 `Order`는 결제확정 하나뿐이다. **거절은 `Order` 상태를 안 움직이므로 애초에 사건이 아니다.**

근거는 Day 1 초안의 **`Order ↔ Payment` 1:N**이다 — 거절이 주문을 움직이면 실패 기록을 보존할 이유가 없어지고 재결제도 막힌다. `PaymentTransitionService.applyDeclined`의 주석(*"주문은 CREATED 로 남는다"*)이 같은 말을 이미 하고 있었다.

### `CANCELED + 결제확정 = CONFLICT` — 실재하는 이중판매 구멍이었다

이 칸 하나 때문에 결과값 셋(`TRANSITIONED`/`IGNORED`/`CONFLICT`)이 검증됐다. `boolean`이었으면 `PAID+결제확정`(정상 멱등)과 같은 값으로 뭉개졌을 자리다 — W1D3 §5에서 `Payment`에 대해 한 그 판단이 `Order`에서 반복됐다.

도달 경로(실제로 열려 있었다):

```
주문 CREATED / 결제 PENDING
  → 쓸이 배치가 order.cancel()  → CANCELED, 재고 복원 → 다른 고객이 사감
  → 늦은 웹훅 승인 도착
  → applyApproved → payment PENDING→PAID = TRANSITIONED
  → 부수효과 order.markPaid()   ← 가드가 없어 CANCELED 가 조용히 PAID 로 덮였다
```

W1D3 §2에 글로만 적어둔 *"타이머만 믿고 복원하면 이중판매"*가 코드에 그대로 있었다.

### `PAID + 취소`는 미정으로 남겼다

`IGNORED`로 두면 **호출부가 취소된 줄 안다.** 다른 두 `IGNORED` 칸(`PAID+결제확정`, `CANCELED+취소`)은 *"이미 아는 사실이 또 왔다"*라 무시해도 아무도 손해를 안 보는데, 이 칸은 **새로 들어온 요청을 거절하는 것**이라 성격이 다르다.

상태를 안 바꾸는 것 자체는 맞다 — 환불해도 `Order`는 `PAID`로 남는다(W1D1 §1: 환불 상태는 `refund` 합계에서 파생). **문제는 상태가 아니라 결과값과 호출부**다.

검토한 선택지:
- **A. `CONFLICT`로 분류** — `CONFLICT`의 뜻이 흐려진다. Payment에서 `CONFLICT`는 *"확정 정보끼리 모순 → 사람을 부른다"*였는데, 이건 모순이 아니라 *"그건 취소가 아니라 환불입니다"*다. 사람 부를 일이 아닌데 Week 3 이상 테이블에 오탐이 쌓인다.
- **B. 네 번째 결과값**(`REJECTED` 류) — 뜻은 정확하나 결과값이 넷이 된다.
- **C. 예외** — 호출부가 안 볼 수 없다. 다만 W1D3 §5가 `Payment`에서 예외를 버린 두 이유가 여기 적용되는지 따로 봐야 한다.

**결론: 지금 정하면 상상으로 정하는 것.** `cancel()`은 **호출부가 0개**다. 결과값은 *"호출부가 이걸로 뭘 하나"*에서 나오는데(D4 §2에서 웹훅 바디 필드를 그렇게 정했다) 그 호출부가 없다. `PaymentAnomaly` 컬럼을 Week 3으로 미룬 것과 같은 이유. **도달 가능하고 실제로 사고를 내는 칸(`CANCELED+결제확정`)만 오늘 배선했다.**

## 2. 이름 — `markPaid()` → `onPaymentConfirmed()`

W1D3 §5에 본인이 적어둔 원칙이 그대로 걸렸다:

> `markPaid()`는 *"PAID로 만들어라"*인데, `FAILED` 상태에선 실제로 안 만든다. **이름이 거짓말을 한다.**

가드를 넣는 순간 `Order.markPaid()`가 정확히 그 상태가 됐다 — `CANCELED`에선 PAID로 안 만든다. 사건 이름을 "결제확정"으로 정했으니 메서드가 그 이름을 따라갔다.

## 3. `OrderTransitionResult` — 전용 타입(B안)

`payment.domain.TransitionResult`와 값이 같지만 분리했다.

- **순환**: 의존 방향이 `payment → order → product`인데(Payment 가 Order 를 참조), Order 가 payment 의 enum 을 반환하면 `order → payment`가 생긴다.
- **미정 칸의 자유도**: `PAID+취소`가 나중에 네 번째 값을 요구할 수 있다. 공용이면 그 값이 결제 어휘로 샌다.
- 기각한 A안(`TransitionResult`를 공용 패키지로 이동)은 개념적으로 정직하지만 `Payment`·서비스·테스트를 건드린다 — 오늘 규칙이 *"리팩터 안 넣는다"*였다.

## 4. 예외를 던지지 않는 이유 — 셋이 동시에 깨진다

`onPaymentConfirmed()`는 결제 전이 트랜잭션 안에서 불린다(`PaymentTransitionService#dispatch`). 예외를 던지면:

1. **롤백** — `PENDING → PAID` 전이까지 되돌아가 *"결제는 승인됐다"*는 사실이 사라진다
2. **재전송 폭주** — `WebhookController:72-77`이 `RuntimeException`을 잡아 **키를 지우고 500**을 던진다. PG 가 재전송하면 SETNX 가 또 뚫려 또 500. 끝나지 않는 루프
3. **기록 소실** — 모순 칸에서 반드시 해야 하는 일이 이상 기록인데 그게 롤백된다

W1D3 §5가 `Payment`에서 예외를 버린 이유 **둘 다** 여기 적용된다(당시 세션에서 Claude 가 *"둘 중 하나"*로 좁혔던 건 오류 — 컨트롤러를 읽고 정정).

## 5. `OrderService` — 트랜잭션 경계가 오늘 유일한 설계 판단

```
tx1: 주문 생성 + 재고 차감 + 커밋
----- 트랜잭션 경계 -----
결제 (PaymentService.pay — 그 안에서 다시 PENDING 선커밋 → PG 호출 → 결과 반영)
```

### `place()`에 `@Transactional`을 붙이면 안 된다

**전파(propagation)**: 트랜잭션이 이미 열려 있는데 또 요구하면 어떻게 할지의 규칙. 기본값 `REQUIRED` = *"있으면 껴서 쓰고, 없으면 새로 연다."*

`place()`를 `@Transactional`로 감싸면 `pay()` 안의 `txTemplate.execute()`가 **새 트랜잭션을 여는 대신 바깥 것에 껴든다.** `execute()`가 끝나도 커밋이 안 된다(바깥이 끝나야 커밋). 결과: `PENDING` 행이 **커밋되지 않은 채로** PG 를 부르게 되고, PG 호출이 터지면 통째로 롤백돼 `PENDING` 이 사라진다 → **나중 웹훅이 매칭할 행이 없다**(W1D1 §2 함정1).

### tx1 을 `@Transactional` 메서드로 빼서 자기가 부르는 것도 안 된다

**자기호출 함정**: Spring 은 프록시로 트랜잭션을 거는데, 자기 자신을 부르면 프록시를 안 거친다 → 트랜잭션이 아예 안 열린다. `PaymentService`가 같은 이유로 `TransactionTemplate`을 쓴다(D4 §5). **A안(TransactionTemplate) 채택** — 코드가 한 방식으로 통일된다.

### 주문 생성과 재고 차감은 반드시 같은 tx

`InventoryService.decrease`는 `@Transactional`(REQUIRED)이라 tx1 에 껴든다. 재고가 모자라 `OutOfStockException`이 나면 **이미 만든 주문도 함께 롤백**된다.

### 결제 거절 시 재고를 되돌리지 않는다

즉시 복원하면 **재결제**가 깨진다. `Order↔Payment`가 1:N 인 이유가 거절 후 재결제 허용인데, 재고를 바로 복원해두면 재결제 승인 시 재고를 안 깎은 채로 주문만 `PAID`가 된다 — 또 이중판매. 복원은 쓸이 배치가 **PG 에 조회해 확인한 뒤**에 한다(W1D3 §2: *재고 복원은 시간의 문제가 아니라 사실 확인의 문제*).

## 6. 실측 (전부 실제 실행 결과)

```
[실측] 주문 관통 → order=PAID payment=PAID 재고 5-2=3 총액=20000
[실측] 재고부족 거부 → 주문 0건, 결제 0건, 재고=1
[실측] 거절 → order=CREATED payment=FAILED 재고=4
[실측] 취소된 주문에 늦은 승인웹훅 → HTTP200, order=CANCELED payment=PAID
```

전체 스위트 **19건 통과**(failures=0, errors=0). D4 의 16건 + `OrderPlacementTest` 3건.

### 음성대조군 C — 직접 실행 (2세션 연속)

| | 조작 | 관측 |
|---|---|---|
| **C-1** | `CANCELED` 가드 주석 처리 | `order=PAID` — **이중판매 구멍이 열린다** |
| **C-2** | `CONFLICT` 반환 대신 예외 | `HTTP500, order=CANCELED payment=PENDING` |

**C-2 가 단언을 나눠둔 이유를 증명했다.** 예외 버전에서 `order=CANCELED`는 **초록불**이었다 — 가드가 지켜서가 아니라 롤백돼서. 주문 상태만 봤으면 **가짜 통과**했다. `payment=PAID` 단언만이 둘을 구분한다.

> D4 §6의 *"version 은 correctness 증거로는 훌륭하지만 backbone 제거에는 눈이 멀었다"*와 같은 모양.
> **관측축 하나로는 못 본다.**

### Claude 가 오늘 낸 오류 2건

- **매직 금액을 단가에 건다고 착각** — 실제로는 `payment.amount = order.totalAmount`라 **총액**에 걸린다. `10_111 × 2 = 20_222`가 되어 거절이 아니라 타임아웃이 났다(`expected: FAILED but was: UNKNOWN`). 부수 소득: 타임아웃 경로도 배선됨을 확인.
- **예외 시 어느 단언이 먼저 터지는지를 미검증으로 단정** — "payment=PENDING 을 볼 것"이라 했으나 실제로는 `status == 200`이 먼저 터진다(500). 컨트롤러를 읽고 정정.

## 9. 점검 결과 (2026-07-18) — 전부 실측

계획상 금(7/17)이었으나 토요일로 밀림. §8 진입점을 실제로 관통했다.

### 배선 자동화 — `application.yaml` 미검증 해소

`./gradlew bootRun` 한 번으로 뜬다. `spring-boot-docker-compose`(developmentOnly)가 `compose.yaml`을 자동 기동하고 랜덤 호스트 포트를 앱에 주입한다.

```
JDBC URL: jdbc:postgresql://127.0.0.1:28830/mydatabase   ← 랜덤 포트 자동 주입
컨테이너: settleflow-postgres-1(5432→28830), redis(6379→28829)  ← 손으로 안 올림
Started SettleflowApplication in 13.463 seconds
```

**빈 `application.yaml`은 정상이다.** `compose.yaml`이 포트를 `'5432'`(랜덤)로 열어 하드코딩이 불가능하고, 모듈이 실행 중 컨테이너에서 url/user/password를 읽어 주입한다. W1D4 §9의 *"연결 설정 필요"*는 **틀린 추측**이었다(실측 반증).

### 실제 주문 1건 관통 (§8-1)

seed 없으므로 seller+product 직접 심고 `POST /orders`:

```
POST /orders {"items":[{"productId":1,"quantity":2}]}
 → 201 {"orderStatus":"PAID","totalAmount":20000}
DB 대조: orders PAID/20000 · payment PAID/20000 · product stock 5→3 · order_item 10000×2
```

§6 첫 줄이 실제 앱에서 재현됐다. 첫 e2e가 뱉을까 걱정한 잔버그(LAZY 로딩·트랜잭션 경계)는 happy path 에선 없었다.

- **`pg_transaction_id = null` 은 설계대로.** 동기 승인 경로는 null 을 넘긴다(`PaymentTransitionService:46` *"pgTransactionId 는 웹훅이 실어온다"*). 스키마의 UNIQUE+nullable 도 의도 — 동기 승인 결제는 다 null(Postgres 는 null 을 유일성으로 안 침)이고, **웹훅이 값을 채운 뒤에만** 유일성을 건다.

### 음성대조군 D — 실행함 (§7 이월 해소)

`decrease`를 tx1 밖(주문 커밋 뒤, `pay` 앞)으로 빼고 시나리오 2 재실행:

| | 조작 | 관측 |
|---|---|---|
| **D** | `inventoryService.decrease` 를 `txTemplate.execute` 밖으로 | 시나리오 2 `expected: 0L but was: 1L` — 주문이 커밋된 채 남음(**빨간불**). 시나리오 1·3 은 통과 |

### 정리 (§8-2,3)
