## 2. 핵심 설계 판단 — "무엇을, 왜"

| 판단 | 근거 한 줄 | 출처 |
|---|---|---|
| **회로가 여는 거절은 타임아웃과 뜻이 다르다** | 타임아웃은 *"보냈는데 답을 못 들었다"*(정보의 부재)지만 개방은 *"아예 안 보냈다"*(확실한 앎) — W1D1 §3 의 근거가 여기선 **반대로** 작동한다 | W4D1 |
| **그 앎을 경로마다 다르게 읽는다** | 승인 → `FAILED`(안 보냈으니 빚이 안 생긴다) / 환불 → 예외를 내보내 **재배달**하고 `REQUESTED` 유지(**이미 진 빚**) | W4D1 |
| 회로를 **갈아끼워지는 자리 밖**에 둔다(데코레이터) | 구현체에 붙이면 테스트가 그 빈을 대체할 때 회로도 사라져 **테스트 회로를 검증**하게 된다. 덤으로 프록시 경계 문제 소멸 | W4D1 |
| 회로는 **둘**(`pg-approve`/`pg-refund`) | 승인 장애가 **갚아야 할 돈**을 막으면 안 된다 | W4D1 |
| **계기보다 축이 먼저** | 불일치 건수는 이미 `reconciliation_run` 에 있고 Grafana 가 Postgres 에 직접 붙으므로 SQL 한 줄로 그려진다 | W4D2 |
| ★ **DB 가 죽으면 알림도 같이 죽는다** | 감시 수단이 감시 대상과 **저장 경로를 공유**하면 안 된다 — W3D4(금액 계산의 독립) → W3D5(볼 목록의 독립)에 이은 **세 번째** | W4D2 |
| 불일치는 **Counter 로 못 센다** | *"재대사하면 6이 되는데 실제 불일치는 3건"* — 재대사는 새 불일치가 아니라 같은 것을 다시 본 것. 기준: **해소되면 내려가야 하는가** | W4D2 |
| 값의 출처는 **재구성**(밀어넣기 아님) | 밀어넣으면 재시작에 0 → 미해소 3건인데 초록불. *"유지"가 아니라 **재구성**이 성질* | W4D2 |
| 부재는 **마지막 성공 시각 + NaN** | 0 은 1970년이라 갓 띄운 앱이 거짓 경보. ⚠️ NaN 은 `time()-metric>26h` 에 안 걸려 `absent()` 짝이 필요 — 어느 안을 골라도 남는 대가 | W4D2 |
| 라벨을 안 단다 | **메트릭은 수위, DB 는 명세** — 카디널리티를 사는 대신 Grafana 에 Postgres 를 병치 | W4D2 |
| **k6 가 무엇을 새로 증명하나** | `PaymentFlowTest` 가 이미 같은 명제를 증명했으므로 1,000 VU 로 같은 걸 재는 건 동어반복 → 답은 **자원**, 값은 *"터진 상태에서도 명제가 유지되는가"* | W4D3 |
| 시나리오를 **둘로 나눈다** | 부하 형태가 배타적 — 같은 키 폭주는 Redis 키가 1개뿐이라 고아 크기가 안 보이고, 고유 키만 쓰면 계획서의 "중복 폭주"가 빠진다 | W4D3 |
| 헤드라인은 **`journal` 증가분** | 우리 웹훅은 중복에도 200 이라(non-2xx 면 PG 가 몇 시간 재전송) StagePass 의 *"409 997건"* 형태가 **원리적으로 불가능**하고 HTTP 로는 방어가 안 보인다 | W4D3 |
| **회로를 끄지 않는다** | 프로덕션 동작이므로 끄고 잰 수치는 우리 시스템의 수치가 아니다. 대신 타임아웃 **30% 혼합**으로 닫아둔다 | W4D3 |
| 비율은 난수가 아니라 **전역 이터레이션 번호** | 난수면 20건 창에서 임계 초과 확률 ~5% → **재현 안 되는 부하는 근거가 못 된다** | W4D3 |
| ★ **분자는 서버가 받은 수다** | `http_reqs` 는 부하 발생기의 **자기 보고**이고 8/8 에 실제로 어긋났다(보냄 1,000 / 도달 965) | W4D4 |
| 카운터는 **델타**로 잰다 | `journal` 과 결론만 같고 이유가 다르다 — journal 은 **식별 수단이 없는** 데이터 모델 문제 / Counter 는 **계기가 시점 값을 안 주는** 성질(못 바꾼다) | W4D4 |
| 분자의 출처가 **시나리오마다 다르다** | Counter 는 프로세스와 수명을 같이해 ②(kill)에선 못 쓴다 → ②의 분자는 **Redis 키** | W4D4 |
| ★ 고아 수는 **kill 순간 in-flight 와 나란히** 놓아야 값이 된다 | 고아 수는 rate 로 조절되므로 그 자체론 시스템 고유값이 아니다 | W4D4 |
| **재는 대상을 바꾸는 게 아니라 도구를 붙이는 것** | `server.shutdown` 은 실험 대상이라 켜고, `/actuator/shutdown` 노출은 관측 수단이라 **열었다 되돌린다** | W4D4 |
| **부하 시나리오는 앱 재기동으로 격리한다** | 회로 창은 시나리오가 아니라 **앱 생애**의 상태 — ①의 PG 실패 2건이 ②의 회로를 열었다 | W4D4 |
| ★ **빨간불이 계기 자체를 못 쓰게 만든다** | red 가 하나 있으면 새로 깨진 것과 원래 깨져 있던 것을 **구분할 수단이 없다** → 회귀일의 첫 작업 순서를 정함 | W4D5 |
| 전제를 **단언한다**(가정하지 않는다) | `Sort` 단언이 *인덱스 설계*와 *데이터가 마침 뭉쳐 있는가*를 한 칸에서 재고 있었다 — **한 칸이 둘을 겸하면 갈라진다**(W3D4·W3D5 에 이은 세 번째) | W4D5 |
| ★ **백오프만 만들고 DLT 는 안 만든다** | DLT 는 *"치워둔 것을 누가 보나"* 를 새 숙제로 남기고, 안 보면 건너뜀과 같다(W3D5 *"안 나타남"의 모호함*). 환불은 **이미 진 빚**이라 건너뜀이 성립 안 함 | W4D5 |
| 재시도 **상한을 설정 항목으로 열지 않는다** | *"포기하지 않는다"* 가 정책의 내용 그 자체 — 항목으로 있으면 조용히 되돌려진다 | W4D5 |

## 3. 검증한 것 vs 못한 것

### ✅ 실측으로 검증

- **resilience4j 가 Boot 4.1.0 에서 실제로 도는지**(자동설정·AOP·설정 바인딩) — W3 회고 §5-3 미검증 닫음
- 회로 4케이스(개방 판정·경로별 결과·`CallNotPermittedException` 기준·회로 분리)
- **관측 라이브 전 구간** — 앱 → 스크레이프 → TSDB → 질의. `A÷N=0.013s` vs `B평균=0.010s` 로 해석 완결
- **결함 주입 2회** — 1차 예측 실패에서 값이 나옴(`recentDates()` 가 오늘을 제외 → *"출처 ③은 오늘에 대해 상관 실패를 못 끊는다"*)
- **★ 헤드라인**: 서버가 받은 중복 웹훅 **1,000건 → `journal` 증가 1** (919 에서도 성립)
- 관문 거절 경로 **천장 ≈ 6,100 req/s**, 435,150건 전부 200(포화가 에러가 아니라 지연으로)
- **고아 = kill 순간 in-flight 의 함수** — A(active 3)→0 / B(active 99)→**23** / graceful(active 175)→0
- **인덱스 red 의 정체** — 같은 커밋에서 배치가 뒤집힌다(green: date corr 1.0 / red: 0.0283)
- **재시도 기본값이 무한이 아니다** — `FixedBackOff(0ms, 9)` + 건너뛰는 recoverer
- 음성대조군 **4회 본인 실행**(D1 VACUUM red 재현 / D2 결함주입 2회 / D5 인덱스 A·B)

## 4. 반복된 패턴 (회고에서 뽑을 결)

### ★ 4-1. 검증 없이 적힌 단정이 다음 세션의 설계 전제가 된다 — 이번 주의 결

이 주에 **두 번** 났고, 둘 다 D5 에서 대가를 치렀다.

| | 단정 | 어떻게 전제가 됐나 | 실제 |
|---|---|---|---|
| ① | D1 커밋 메시지의 *"고쳤다"* (실행 1회 green) | D2·D3·D4 이월 표가 *"상관도 가설"* 로 물려받아 **원인을 잘못 좁힌 채** 4회 이월 | 원인은 상관도가 맞았지만 **깜빡임**이었고, 진단은 30초짜리였다 |
| ② | 소비자 javadoc 의 *"지금은 장애 시 무한 재시도"* | **W4D1 이 그 위에 재배달 설계를 얹었다**(예외를 내보내 오프셋을 안 밀기) | 무한이 아니라 **10회 즉시 재시도 후 유실** — W4D1 이 막으려던 결과를 기본값이 대신 하고 있었다 |

**②가 더 나쁘다.** 문제를 **정반대로** 알고 있었기 때문이다 — *"뜨겁게 돈다"* 를 식히러 갔는데
실제 문제는 *"식기 전에 포기한다"* 였다. D1 이 스스로 적어둔 *"자동설정이 미끄러지면 에러가
아니라 무음이다"* 가 **프레임워크 기본값**에서 한 번 더 실현된 셈이다.

### 4-2. 재는 자와 재이는 것이 같은 경로를 공유하면 그 수치는 스스로를 검증 못 한다

- **D2**: DB 가 죽으면 SQL 알림도 같이 죽는다 → 저장 경로의 독립(W3D4·W3D5 의 세 번째 적용)
- **D4**: `http_reqs` 는 부하 발생기의 자기 보고 → 분자를 **서버 카운터**로
- **D4**: 포화 구간에서 폴러가 12표본 연속 실패 → **재려는 값이 가장 큰 곳에서 계기가 눈을 감았다**
- **D5**: 테스트가 자기 데이터가 아니라 **스위트가 남긴 배치**를 재고 있었다

### 4-3. 어긋난 것이 감시 대상이 아니라 측정 도구 쪽이었다 — 3일 연속

D3(대조군이 설계 오류 둘을 잡음) → D4(어긋난 칸 셋 전부 측정 도구) → D5(seed 삽입 순서 /
프레임워크 기본값 / 테스트 페이로드 / 프로퍼티 우선순위). **W4 는 시스템보다 계기를 더 많이
고친 주다.**

### 4-4. 한 칸이 둘을 겸하면 갈라진다 — 세 번째

W3D4 `refunded_amount`(가드↔라벨) → W3D5 `created_at`(귀속↔진행) → **W4D5 `Sort` 단언**
(인덱스 설계↔물리 배치).

### 4-5. Boot 4 에서는 "떴다"가 "일한다"를 뜻하지 않는다 — 세 번

D1(스모크를 선결로 돌린 이유) → D2(`@AutoConfigureAfter` 의 문자열이 없는 이름이라 순서 제약이
증발, **에러 0건에 메트릭 하나만 없음**) → D5(에러 핸들러 빈이 없어 기본값이 조용히 돌았다).
**그래서 D5 의 회귀 테스트는 빈 존재가 아니라 배달 횟수를 잰다.**

### 4-6. 계획서 전제를 근거를 갖고 폐기 — 4주 연속

재고 Redis 락(W1) → 보상 트랜잭션(W3D2) → 조인 키(W3D4) → **DLT(W4D5)**.
