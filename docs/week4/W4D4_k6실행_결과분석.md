## 2. ★ 헤드라인

```
[실측] 시나리오 ① 2회차 — 같은 eventId 1,000 VU
       서버가 받은 요청 1,000건 → journal(PAYMENT) 증가 = 1
```

**1,000건의 중복 웹훅이 장부에 1줄을 남겼다.**

StagePass 의 *"409 997건"* 과 **형태가 다른 건 원리적이다**. 우리 웹훅은 중복에도 200 을

이유이고, 오늘 그 선택이 값을 냈다.

## 3. ★ 먼저 물은 것 — 분자를 무엇으로 세는가

8/8 실행에 `서버 도달 965 / dial 실패 35` 가 남아 있었다. 그러면 *"1,000건 중복 웹훅"* 이라고
쓸 수 있는가. 못 쓴다면 분자는 어디서 오는가.

> **"서버가 받은 수가 분자야, k6 가 보냈다는 수 말고."** — 본인

`http_reqs` 는 **부하 발생기의 자기 보고**이고, 8/8 에 그 자기 보고가 실제로 어긋났다.
서버가 센 수를 쓰면 발생기가 몇 개를 흘렸든 명제의 분자가 안 흔들린다. W4D2 에서
*"DB 가 죽으면 알림도 같이 죽는다"* 로 잡았던 축 — **재는 쪽과 재이는 쪽이 같은 경로를
공유하면 그 수치는 스스로를 검증 못 한다** — 이 부하 쪽에서 한 번 더 걸린 자리다.

### 그런데 그 카운터를 그냥 읽으면 안 된다

> **"카운터는 누적이라 이전 실행이 섞여, 델타로 재야 해."** — 본인

맞고, **`journal` 과 결론만 같고 이유가 다르다**:

| | 왜 델타인가 | 성질 |
|---|---|---|
| `journal` | **소유 관계가 없다.** FK 가 `payment.journal_id → journal.id` 라 journal 에서 이 실행으로 돌아오는 길이 없어, "이번에 생긴 것"을 **식별할 수단 자체가 없다** | **데이터 모델** — 스키마를 바꾸면 없앨 수 있다 |
| `http_server_requests_seconds_count` | 식별 수단이 없는 게 아니라 **계기가 시점 값을 안 준다.** Counter 는 단조 증가가 정의다 | **계기** — 못 바꾼다. W4D2 의 *"재대사하면 6이 되는데 불일치는 3건"* 과 같은 성질 |

### 그리고 이게 시나리오마다 분자를 갈랐다

Counter 는 **앱 프로세스와 수명을 같이한다.** 재기동하면 0이다. 그래서 **②(kill)에서는 이
카운터를 분자로 못 쓴다** — 실행이 끝나는 순간 앱이 죽어 있어 읽을 대상이 없고, 되살리면
이미 0이다. ②의 분자는 **Redis 키 개수**다(앱이 죽어도 남는다). D3 §8 이 *"검증 시점엔 앱이
죽어 있으므로 Postgres·Redis 를 직접 본다"* 로 이미 덮어둔 자리였다.

| | 분자의 출처 | 앱 상태 |
|---|---|---|
| ① | 서버 Counter 델타 | 살아 있다 |
| ①-b | 서버 Counter 델타 | 살아 있다 |
| ② | Redis 키 개수 | **죽어 있다** |

셋 다 k6 자기 보고가 아니다.

## 4. 시나리오 ① — 중복 폭주 (2회)

| | **1회차** (기동 직후) | **2회차** (가열 후) |
|---|---|---|
| k6 성공 | 919 | **1,000** |
| **서버 카운터 델타** | **919** (0 → 919) | **1,000** (919 → 1,919) |
| 실패 | 81 `connection refused` | **0** |
| p95 | 569.78ms | 131.68ms |
| 처리량 | 883/s | 3,011/s |
| **★ journal 증가** | **1** | **1** |
| payment.status / version | PAID / 2 | PAID / 2 |
| outbox / ledger_entry / 멱등키 | 1 / 3 / 1 | 1 / 3 / 1 |

**두 독립 경로가 정확히 일치했다** — k6 가 성공으로 센 수와 서버가 센 수가 919=919,
1,000=1,000, 누적 1,919 로 산술이 닫힌다.

**헤드라인은 2회차로 하되 1회차도 싣는다**(본인 판단). 근거는 수치의 크기가 아니다 —
명제(`journal=1`)가 **919 에서도 1,000 에서도 성립**했으므로, 1회차는 버리는 데이터가 아니라
**명제가 도달 수에 안 흔들린다는 추가 증거**다. 버리면 오히려 증거가 줄어든다.

### 81건은 서버 용량이 아니다

에러가 `connection refused` 였다 — 8/8 의 `invalid pointer address`(소켓 계층)와 **다르다.**
그런데 2회차에 0건이고, 원인이 표 안에 있다: 1회차 p95 **570ms** → 2회차 **131ms**,
처리량 883 → 3,011/s. **미가열이라 요청이 4배 느리게 빠졌고 그동안 커넥션이 accept 큐에
쌓여 넘쳤다.** 즉 톰캣 backlog 가 맞지만 **정상 상태의 서버 용량이 아니라 가열 상태의 함수**다.

`gate-rate.js` 주석의 결론(*"서버 임계가 아니다"*)은 유지되고 **근거만 바뀐다.**

## 5. 시나리오 ①-b — 관문 처리율

`gate-rate.js` 는 이미 키가 있는 `eventId` 를 쏴 **100% 거절 경로**만 태운다. 1,000건 폭주에서
관문이 실제로 하는 일의 999/1000 이 이 경로다. 부수 효과로 **PG 를 한 번도 안 부른다.**

| 목표 rate | MAX_VUS | 달성 req/s | dropped | p95 | VU 최대 |
|---|---|---|---|---|---|
| 1,000 | 300 | 999 | 0 | 2.19ms | 11 |
| 3,000 | 300 | 2,994 | 0 | 12.54ms | 29 |
| 6,000 | 300 | 5,630 | 7,336 | 52.37ms | 288 |
| 6,000 | **800** | 5,852 | 2,885 | 108.37ms | 679 |
| 9,000 | **800** | **6,145** | 56,612 | 190.85ms | 800 |

**천장 약 6,100 req/s.** VU 상한을 2.7배 풀고 목표를 1.5배 더 올렸는데 달성치는 **+9%** 에서
멈췄고 지연만 52 → 191ms 로 갔다. 포화의 정의다.

### ★ 스크립트가 적어둔 판별 기준이 틀렸다

teardown 에 이렇게 적혀 있다:

> `dropped_iterations > 0` → k6 가 VU 를 못 대준 것. **클라이언트 한계, 서버 값 아님**

그런데 여기 dropped 는 **서버 포화의 파생 결과**였다. 클라이언트 한계였다면 상한을 풀었을 때
처리량이 따라 올랐어야 하는데, dropped 만 7,336 → 2,885 로 줄고 처리량은 안 늘었다.
**소켓 압력을 고정하려고 VU 상한을 묶은 장치 자체가, 서버 신호를 클라이언트 신호처럼
보이게 만들었다.** 8/8 에 소켓 문제를 피하려 넣은 설계가 오늘은 원인을 가리는 쪽으로 작동했다.

### 포화가 에러가 아니라 지연으로 나타났다

```
[실측] 435,150건 전부 HTTP 200. 5xx 0건, 앱 예외 0건.
[실측] 서버 카운터 누적 435,150 = 1,919 + 20,000 + 59,999 + 112,668 + 117,180 + 123,384
[실측] pg-approve / pg-refund 회로 CLOSED 유지 (PG 를 안 부르는 설계가 실제로 그렇게 작동)
```

D3 §4 가 Redis 에 대해 예측한 *"풀이 없으니 고갈이 아니라 지연으로 나타난다"* 가 **관문 전체
수준에서 실현됐다.**

## 6. ★★ 회로가 다시 열렸다 — 그리고 가르는 실험이 원인을 갈랐다

②로 넘어가기 전 운영점을 재려고 `RATE=200` 탐침을 돌렸더니:

```
[실측] payment  FAILED +2,993 / PAID +10 / UNKNOWN 0
[실측] "차단기 개방 — 요청을 보내지 않고 FAILED 확정" 로그 = 2,993건 (FAILED 수와 일치)
[실측] buffered_calls  실패 6 / 성공 4   →  failure_rate = 60.0
```

**D3 §10① 이 물렸던 자리가 다른 rate 에서 다시 열렸다.** 설계는 30% 인데 판정 순간의 창은
60% 였다.

### 왜 30% 혼합이 안 막았나

설정은 `sliding-window-size: 20` / `minimum-number-of-calls: 10` / `failure-rate-threshold: 50`.
D3 의 수리는 *"3/10 → 20창에서 6/20 = 30%"* 로 **정상상태를 계산했지만, 첫 판정은 표본이
가장 작은 10건째에 먼저 일어난다.** 거기에 둘이 겹쳤다:

1. **이월된 실패** — 회로 창은 시나리오가 아니라 **앱 생애**의 상태다. 오늘 ①을 2회 돌렸고
   각 `setup` 이 10,222원 주문이라 **PG 타임아웃 2건**이 이미 창에 있었다.
2. **완료 순서 뒤섞임** — `iterationInTest % 10 < 3` 은 *이터레이션 번호* 순으로 30% 지만,
   회로는 *완료* 순으로 기록한다. RATE=200 은 253 VU 동시라 순서가 섞인다.

### 둘을 가르는 실험

앱을 재기동해 **창을 비우고 같은 탐침을 다시** 돌렸다.

```
[실측] 회로 CLOSED 유지 (개방 0회), buffered 실패 4 / 성공 16 → failure_rate 20.0
[실측] payment  PAID +2,041 / FAILED +0
```

**안 열렸다.** 뒤섞임만으로는 부족했고 **이월된 실패가 필요조건**이었다.

> **오늘 나온 절차 규칙: 부하 시나리오는 앱 재기동으로 격리해야 한다.**
> ①과 ②를 같은 앱 생애에서 돌리면 앞 시나리오의 PG 실패가 뒤 시나리오의 회로를 연다.

### 같은 실험이 두 개를 더 뒤집었다

**탐침의 운영점 자체가 오염된 값이었다.** 회로가 닫힌 상태에서 RATE=200 의 지연은 404ms 가
아니라 **4.18s**(p95 5.51s), 달성 91 it/s, dropped 960 이다. 404ms 는 **회로가 열려 주문이
PG 를 안 거치고 싸게 실패하던 값**이었다 — 내가 "톰캣 200 스레드 포화점"으로 읽은 활성 199 는
실제 작업 부하의 포화점이 아니었다(§9 ②).

**그리고 그 포화에서 관측이 굶었다.** 폴러의 `/actuator/prometheus` 호출이 **12표본 연속
실패**했다(1초 타임아웃 초과). **재려는 값이 가장 큰 구간에서 계기가 눈을 감았다.** W4D2 의
*"DB 가 죽으면 알림도 같이 죽는다"* 와 같은 계열이 부하 쪽에서 나왔다.

→ 운영점을 이 경로의 실제 용량(약 90 it/s) 기준으로 **RATE=50 / 100** 으로 내리고,
폴러 타임아웃을 5초로 올린 뒤 ②를 돌렸다.

## 7. ★ 시나리오 ② — 강제 종료로 만든 고아, 그리고 in-flight

> **"kill 순간 in-flight 수랑 나란히 놓아야지."** — 본인

고아 수는 rate 로 조절되므로 그 자체로는 값이 아니다. **무엇과 나란히 놓아야 설명되는
수가 되는가**가 오늘 ②의 설계였다. 활성 요청 수는
`http_server_requests_active_seconds_count`(LongTaskTimer)를 200ms 간격으로 표집해 **kill
직전 표본**을 썼다.

| | **kill A** | **kill B** | **graceful 대조군** |
|---|---|---|---|
| RATE | 50 | 100 | 100 |
| 종료 방식 | `taskkill /F` | `taskkill /F` | `POST /actuator/shutdown` |
| **종료 순간 활성 POST** | **3** | **99** | **175** |
| 종료 시점 회로 | closed, 6/14 (30%) | closed, 6/14 (30%) | closed, 6/14 (30%) |
| webhook_sent | 1,739 | 2,896 | 3,081 |
| Redis 키 총계 | 1,739 | 2,886 | 3,022 |
| PAID | 1,739 | 2,863 | 3,022 |
| **★ 고아(UNKNOWN)** | **0** | **23** | **0** |
| FAILED / 기타 / 결제행 없음 | 0 / 0 / 0 | 0 / 0 / 0 | 0 / 0 / 0 |

**산술이 닫힌다**: 2,863 + 23 = 2,886 ✓ / 3,022 + 0 = 3,022 ✓.

### 세 회차 모두 FAILED 0 — 그래서 23은 kill 때문이다

회로가 종료 순간까지 CLOSED 였고 창이 정확히 30%(6/14)였다. D3 대조군(kill 없이 고아 0) +
kill A(in-flight 3 → 0) + kill B(in-flight 99 → 23) 세 점이 받친다.

### `webhook_sent` − `키` = SETNX 에 닿기도 전에 죽은 요청

kill B 는 10건, graceful 은 59건(= `webhook_failed` 59와 일치). **이건 고아가 아니다** — 키가
없으니 PG 재전송이 정상 처리된다. D3 §5 가 *"Redis 를 내리면 키가 애초에 안 생겨 안전한
쪽으로 닫힌다"* 고 한 자리가 kill 에서도 같은 모양으로 나타났다.

### 관계

고아 / 활성 POST = **23/99 ≈ 0.23**. 활성 카운터는 uri 태그가 안 붙어 `/orders` 와
`/webhooks/pg` 가 안 갈리므로, 웹훅만 치면 대략 절반인 ~50 이고 그중 23 ≈ **46%** 가 취약
구간(SETNX 통과 ~ 커밋 전)에 있었던 셈이다. **이 46% 는 추정이다**(절반 가정이 들어갔다).

두 점으로 비례를 단정하지 않는다. 다만 **고아 수가 시스템 고유값이 아니라 kill 순간
in-flight 의 함수**라는 건 지지되고, D3 §12 가 미리 적어둔 한계와 정확히 맞는다.

## 8. graceful 대조군 — D3 §5 의 예측이 실측으로 닫혔다

D3 §5 는 *"graceful 이면 in-flight 가 끝날 때까지 기다리므로 ③이 정상 실행돼 구멍이 안
열린다"* 고 적고 D4 판단으로 넘겼다. 오늘 kill B 가 23을 냈으므로 대조 가치가 생겼다.

**기계적 문제가 있었다.** `server.shutdown=graceful` 만으로는 부족하고 SIGTERM 등가의 종료
요청이 필요한데, 오늘 쓴 `taskkill /F` 는 `TerminateProcess` 라 훅이 안 돈다(그래서 SIGKILL
등가로 쓴 것이다). `/F` 를 빼면 `WM_CLOSE` 인데 `bootRun` 의 java 는 콘솔 창이 없는 자식이라
전달이 보장되지 않는다. 확실한 경로는 `/actuator/shutdown` 뿐이었다.

> **판단: 이건 재는 대상을 바꾸는 게 아니라 도구를 붙이는 것**(본인). `server.shutdown` 은
> 실험 대상 자체라 켜는 게 맞고, `/actuator/shutdown` 노출은 관측 수단이므로 **열었다가
> 되돌린다.** D3 가 *"회로를 끄지 않는다 — 끄고 잰 수치는 우리 시스템이 아니다"* 로 세운
> 기준을 적용한 결과다.

```
[실측] POST /actuator/shutdown → {"message":"Shutting down, bye..."}
[실측] 직후에도 8080 LISTENING (in-flight 를 기다리는 중)
[실측] 고아 0건 / 키 3,022 / PAID 3,022
```

**in-flight 가 kill B 보다 더 많은 순간(175 vs 99)에 0 이 나왔다** — 대조가 약해지는 게
아니라 강해지는 방향이다. 그리고 종료 후 들어온 59건은 커넥터가 먼저 닫혀 **SETNX 에 닿지
못했다**(= 안전한 쪽). 실험 뒤 `application.yaml` 두 곳을 되돌렸고 `git status` 로 확인했다.

## 9. Claude 오류

**① 빈 파일을 grep 하고 "회로 개방이 아니다"라고 보고했다.** `"차단기 개방" 0건` 을 근거로
*"회로 개방으로 FAILED 가 된 게 아니라는 뜻"* 이라고 했는데, 실제로는 리다이렉트 때문에 비어
있던 파일을 본 것이었다. 진짜 로그에는 2,993건이 있었다. **대화 중 자진 정정.** 파일이 비었을
가능성을 확인하지 않고 "0건"을 발견으로 취급한 게 오류다.

**② 오염된 운영점을 포화점으로 읽었다.** 탐침의 활성 199·지연 404ms 를 "톰캣 200 스레드
포화"로 해석했는데, 그건 **회로가 열려 주문이 PG 를 안 거치던 값**이었다(§6). 같은 화면에
`FAILED +2,993` 이 있었는데 두 수치를 연결하지 않았다.

**③ 폴러 타임아웃을 1초로 잡았다.** 정작 재려던 포화 구간에서 12표본 연속 실패해 **부하 중
활성 요청 수를 한 개도 못 건졌다.** 계기를 만들면서 그 계기가 부하를 견디는지 안 따졌다.

**④ 폴러 종료를 확인 안 했다.** kill A 로그 끝에 다음 실행의 표본이 섞였다(`active=10`).
kill 직전 표본 자체는 taskkill 165ms 전 값이라 영향이 없지만, 로그를 그대로 인용하면 오독될
자리다.

> ①②는 **같은 계열**이다 — 화면에 있는 수치를 다른 수치와 대조하지 않았다. W4D2 §11 ④
> (대시보드를 안 보고 커밋), D3 §11(실행해보기 전엔 안 걸리는 종류)에 이어 세 번째다.

## 10. 정직한 한계 / 이월

### 이 수치가 뜻하지 않는 것

- **6,100 req/s 는 관문의 거절 경로 처리율**이다. 결제 처리량이 아니다. 실제 전이를 밟는
  전체 경로(주문+웹훅)의 용량은 **약 90 it/s** 였다(§6).
- **고아 23건은 이 시스템의 고유값이 아니다.** kill 순간 in-flight 의 함수이고, 두 점으로
  비례를 증명하진 못했다.
- **웹훅 in-flight 46% 는 추정이다.** 활성 카운터에 uri 태그가 안 붙어 절반 가정이 들어갔다.
- **graceful 대조군은 동일 조건 재현이 아니다.** in-flight 가 175 로 kill B(99)와 달랐다.
  방향이 보수적이라 결론은 서지만, 같은 in-flight 에서의 대조는 아직 없다.
- **graceful 은 지금 꺼져 있다.** 오늘 잰 건 *"켜면 어떻게 되는가"* 이고, 프로덕션 설정은
  실험 전 상태로 되돌렸다. **켤 것인가는 아직 결정 안 됨**(아래 이월).
- 부하는 **로컬 단일 머신**이다. 클라이언트·서버·DB·Redis·Kafka 가 CPU 를 나눠 쓴다.
- **시나리오 ①은 완전 동시가 아니다**(k6 에 배리어가 없다). `PaymentFlowTest` 의
  `CyclicBarrier` 20개와는 성질이 다르다 — 테스트는 좁은 창의 경합을, k6 는 규모를 본다.

## 11. 체크리스트용 메모

**#1 설계** — 선택지 없이 먼저 나온 답: *"서버가 받은 수가 분자야"*(§3) /
*"카운터는 누적이라 델타로 재야 해"*(§3) / *"kill 순간 in-flight 수랑 나란히 놓아야지"*(§7) /
*"도구를 붙이는 거야"*(§8). **넷 다 오늘 실험의 축이 됐다** — 분자의 출처가 시나리오별로
갈린 것도(§3 표), ②의 설계 전체도(§7), graceful 대조군이 성립한 것도(§8) 여기서 나왔다.

**#3 AI 없이 푼 것** — §3 의 "델타로 재야 해"는 카운터의 성질을 스스로 짚은 것이고, §8 의
"재는 대상 vs 도구" 구분은 D3 가 회로에 적용한 기준을 **새 상황에 옮겨 적용**한 것이다.

**#4** — Claude 오류 4건 중 **①은 자진 정정, ②③④는 그 자리에서 반박 가능**했다. 특히 ②는
같은 화면에 `FAILED +2,993` 이 떠 있었다.

**#5 값은 어긋난 칸에서 나왔다(4번째)** — 오늘은 **어긋난 칸이 셋**이었다: 8/8 의
`invalid pointer address` → 오늘은 `connection refused`(§4) / 스크립트가 적어둔 판별 기준이
틀림(§5) / D3 의 회로 수리가 다른 rate 에서 뚫림(§6). **셋 다 측정 도구 쪽**이었고,
D3 §10 의 *"이번에 어긋난 건 감시 대상이 아니라 측정 도구"* 가 하루 만에 반복됐다.
