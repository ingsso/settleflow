## 3. 인덱스 red — 기준선부터

D1 이 두 번 데인 자리라 측정 절차를 고정했다: **`cleanTest` 필수**(`:test UP-TO-DATE` 로 거짓
초록 한 번), **클래스 단독 말고 전체 스위트**(단독은 green, 전체에서만 red).

```
[실측] 전체 스위트  103건 중 1 red   (SettlementIndexPlanTest:85 — doesNotContain("Sort"))
[실측] 클래스 단독  green
```

플랜 전문에 **증거가 이미 같은 화면에 있었다**:

```
① 날짜 단독   40행 → Bitmap Heap Scan   cost=108.08   Heap Blocks: exact=40
③ 셀러 단독  300행 → Index Scan          cost= 18.54
```

**40행을 읽는 게 300행을 읽는 것보다 6배 비싸다.** 같은 테이블, 같은 힙이고, 다른 건
두 컬럼의 물리적 배치뿐이다. `Heap Blocks: exact=40` 은 40행이 **40개의 서로 다른 블록**에
있다는 뜻이다(한 블록당 한 행).

> ⚠️ 이 대조는 **D1 때도 같은 printf 에 찍혀 있었다.** ①과 ③을 나란히 안 놨을 뿐이다 —
> W4D4 §9 ①②(화면에 있는 수치를 다른 수치와 대조하지 않음)의 **네 번째**다.

## 4. ★ 가설 6개 반증 — 그리고 반증이 방향을 줬다

일회용 PG17 컨테이너에 스키마·행수·인덱스를 그대로 재현해 재현을 시도했다. **전부 실패했다.**

| | 가설 | 결과 |
|---|---|---|
| 1 | `FROM seller s, generate_series(...)` 조인 순서가 셀러-major 를 만든다 | ❌ 날짜-major, corr **1.0000** |
| 2 | `DELETE` 뒤 재삽입이 배치를 흩뜨린다 | ❌ 둘 다 `Index Scan` |
| 3 | 바인드 파라미터가 플랜을 가른다 | ❌ 리터럴판·파라미터판 **플랜 문자 그대로 동일** |
| 4 | `seller` 통계 부재(1,130행 추정)가 순서를 뒤집는다 | ❌ `ANALYZE` 후 `rows=40` 이어도 `generate_series` 가 여전히 바깥 |
| 5 | `DELETE`+`VACUUM` 뒤 재삽입(빈 자리 재사용) | ❌ 재사용이 **블록 순서대로** 일어나 40행 → 1블록 |
| 6 | generic plan (반복 실행 뒤 갈아타는 것) | ❌ `rows=1000` 이어도 순서 안 바뀜 |

**그런데 프로브의 correlation 표를 실제 플랜과 나란히 놓자 방향이 나왔다** — 정반대였다:

| | 날짜 | 셀러 |
|---|---|---|
| 프로브(전부) | corr **1.0000** → `Index Scan` | corr **0.0283** → `Bitmap` |
| 실제 red | → **`Bitmap`** | → **`Index Scan`** |

같은 SQL 문자열인데 물리 순서가 뒤집혀 있었다. 그러면 남은 차이는 SQL 이 아니라 **플래너가
그것을 어떻게 실행했느냐**다.

> **여기서 방법을 바꿨다.** 추측을 더 쌓는 대신 **실제 스위트 안에 계기를 넣는다**
> (본인 지시: *"진단 실측 먼저 돌려봐"*). 프로브로 재현 조건을 6번 못 맞혔으므로,
> 재현을 포기하고 현장에서 재는 쪽이다.

## 5. ★★ 진단 실측 — 같은 커밋, 뒤집힌 배치

임시 진단(`pg_stats.correlation` + `ctid` 순 앞 12행 + 블록 분포)을 넣고 전체 스위트를 돌렸다.

| | 🟢 green 실행 | 🔴 red 실행 |
|---|---|---|
| `correlation(settlement_date)` | **1.0000** | **0.0283** |
| `correlation(seller_id)` | 0.0283 | **1.0000** |
| `ctid` 앞 12행 | 날짜 고정·셀러 증가 → **날짜-major** | **셀러 고정(136)·날짜 증가 → 셀러-major** |
| `'2026-03-01'` 40행 | **1블록**(134)에 40행 | **40블록**에 1행씩 |
| 힙 블록 / 행 수 | 225 / 12,000 | 225 / 12,000 |
| 시작 블록 | 112 | 112 |

**행 수·블록 수·시작 위치까지 같다.** 다른 건 중첩 루프의 안팎이 뒤집혔다는 것 하나다.

크로스 조인이라 **어느 쪽이 바깥이 되는지가 비용 추정에 달려 있고 두 플랜의 비용이 거의
붙어 있다.** 바깥이 뒤집히면 → 어느 컬럼이 뭉치는지가 뒤집히고 → 플래너의 `Index Scan`/
`Bitmap` 선택이 뒤집히고 → `Sort` 유무가 뒤집힌다.

**무엇이 뒤집는지는 못 찾았다.** 그게 오늘 이 자리의 정직한 상태다.

## 6. ★ 진짜 문제는 단언이 두 개를 한 칸에서 재고 있었다는 것

```java
assertThat(dateOnly).doesNotContain("Sort");
```

주장은 *"인덱스 컬럼 순서를 `(date, seller_id)` 로 고른 값어치"* 다. 그런데 `Sort` 가 붙느냐는
플래너가 순서를 보존하는 `Index Scan` 을 고르느냐에 달렸고, 그 선택은 인덱스 순서가 아니라
**힙의 물리적 배치**가 정한다. 배치는 이 테스트가 통제하지 않고 **스위트에서 앞에 뭐가
돌았느냐**가 정한다.

즉 이 한 칸이 *인덱스 설계가 옳은가* 와 *데이터가 마침 뭉쳐 있는가* 를 겸하고 있었다 —
**W3D4 `refunded_amount`(가드↔라벨), W3D5 `created_at`(귀속↔진행)과 같은 모양이다.**
한 칸이 둘을 겸하면 갈라진다. 그리고 그 갈라짐이 4회 이월의 정체였다: red 를 볼 때마다
*"인덱스 설계가 틀렸나?"* 를 물었는데 실제로는 *"전제가 안 섰다"* 였다.

### 세 갈래와 선택

| | 무엇 | 대가 |
|---|---|---|
| (가) `CLUSTER` 로 배치를 못박는다 | 물리 순서를 인덱스에 맞춘다 | 프로덕션엔 `CLUSTER` 가 없다 — **없는 조건을 만들어 초록을 얻는다** |
| (나) `Sort` 단언을 뺀다 | 인덱스를 타는가만 남긴다 | 컬럼 순서를 그렇게 고른 **직접 증거**를 잃는다 |
| **(다)** 전제를 단언한 뒤 그 위에서 `Sort` 를 단언 | red 의 **뜻**이 갈린다 | 전제가 안 서면 red 인 건 같다 |

**(다) 선택**(본인). 그리고 (다)만으로는 초록이 안 되므로 조각 하나를 더했다.

### 수리 둘

| | 무엇 | 왜 |
|---|---|---|
| ① | `seed()` 의 `INSERT ... SELECT` 에 `ORDER BY settlement_date, seller_id` | 전제를 **못박는다** |
| ② | `Sort` 단언 앞에 `correlationOf("settlement_date") > 0.9` | 전제를 **단언한다** |

**①이 "원하는 답이 나오게 데이터를 배치하는 것"이 아닌 근거**는 프로덕션 배치에 있다.
`upsertDailyNetBySeller(date, ...)` 는 `CAST(:date AS date)` **한 값** + `GROUP BY seller_id` 라
**하루치씩** 넣는다. 실제 힙은 날짜순으로 쌓인다. **셀러-major 는 프로덕션에 존재하지 않는
배치였고, seed 가 절반의 확률로 그것을 만들고 있었다.** 순서를 명시하는 건 없는 조건을
만드는 게 아니라 **있는 조건을 재현**하는 것이다.

**②가 필요한 근거는 §5 의 실패**다 — 원인을 못 찾았으므로 전제를 *가정*할 수 없다.
①만 넣으면 초록은 되지만 **왜 초록인지가 코드에 안 남고**, 반증한 가설 6개가 다시 쌓인다.

## 7. 인덱스 수리의 검증 — 그리고 음성대조군

```
[실측] 수리 후 전체 스위트 6연속 green (직후 4회 + 재시도 작업 중 1회 + 원복 후 1회)
       마지막 실행: 104건 0실패 / SettlementIndexPlanTest 2건 0실패
```

⚠️ **증명이 아니다.** `ORDER BY` 없는 상태의 실측을 다 합치면 **5 red / 9회 ≈ 56%**
(아침 red + 진단 green + 재실행 red + 대조군 3/6). 그 비율이 유지된다는 가정 아래
6연속 green 이 나올 확률은 **0.44⁶ ≈ 0.7%** 다. 낮지만 0 이 아니다.
D1 이 *"1회 green 을 고쳤다로 단정"* 한 자리라 이 수치를 그대로 남긴다 —
**"안 흔들린다"가 아니라 "0.7% 아래로 내려갔다"가 지금 말할 수 있는 것이다.**

### 음성대조군 (본인 실행·원복 완료)

**예측을 먼저 적고** 대조했다(W3D3 에서 빠졌던 습관).

| | 제거 대상 | 예측 | 실측 | |
|---|---|---|---|---|
| A | `seed()` 의 `ORDER BY` 한 줄 | 6회 중 일부 red | **3 red / 6** | ✅ |
| B | (A 상태에서) 첫 실패가 전제 단언인가 | 전제 단언 | **전제 단언** | ✅ |

**B 가 값을 냈다.** ②가 실제로 작동한다 — AssertJ 는 첫 실패에서 멈추므로 **단언 순서가 곧
검증 여부**이고, 그게 맞는 자리에 있었다(W3D4 에서 대사 단언이 실행조차 안 됐던 자리의 반대).

**필터 주의를 미리 적어두고 지켰다**(W3D5 에서 1차 대조군이 무효였던 원인):
클래스 단독은 수리 전에도 green 이라 **red 를 낼 능력이 없다** → 전체 스위트로 돌렸다.
그리고 56% 라서 **1회 green 은 판정이 아니다** → 6회 돌렸다.

원복은 커밋된 기준선(`bc177b6`)에 대해 검증했다 — `git status` 비어 있음 + `ORDER BY` 실재
확인. W3D3 에서 Claude 가 준 원복 *증명* 절차가 틀렸던 자리(untracked 라 기준선이 없었다)가
이번엔 성립한다.

## 8. ★★ 재시도 정책 — 이월 항목의 전제가 틀렸다

계획서·이월 표는 *"Consumer DLT + 지수 백오프"* 를 한 묶음으로 적어뒀다. 착수 전에 물었다:
**이 소비자에서 DLT 는 무엇을 위한 장치인가.**

`RefundRequestedConsumer` 는 *"재시도해도 안 바뀌는 것"* 을 이미 재시도 경로에서 빼놨다
(`[POISON]` 역직렬화 실패, `[ORPHAN]` refund 행 없음 — 기록하고 넘긴다). 그러면 예외가
밖으로 나가는 건 **기다리면 풀리는 것**(회로 개방, DB 다운)이고, 여기에 세 번째 부류가 있다:
**영구적이지만 이름이 안 붙은 예외**(제약 위반·W3D2 언더플로 백스톱·NPE).

그런데 그보다 먼저 확인해야 할 게 있었다 — **javadoc 이 "지금은 무한 재시도"라고 단정한다.**

```
[실측] 에러 핸들러 빈 0개 → spring-kafka 4.1.0 기본값이 그대로 돈다
[실측] SeekUtils.DEFAULT_MAX_FAILURES = 10
[실측] SeekUtils.DEFAULT_BACK_OFF     = FixedBackOff(0L, 9L)      ← 간격 0ms
[실측] DefaultErrorHandler() = 위 BackOff + recoverer 없음(= 로그 남기고 건너뜀)
```

**무한이 아니었다. 간격 0ms 로 10번 즉시 재시도한 뒤 오프셋을 밀어버린다.**

### 그게 W4D1 의 설계를 정면으로 깨뜨리고 있었다

| | |
|---|---|
| W4D1 설계 | 회로 개방 시 **예외를 내보내 재배달** — *"잡으면 오프셋이 밀려 환불이 조용히 사라진다"* |
| 회로 설정 | `wait-duration-in-open-state: 30s` |
| 실제 재시도 | 0ms × 10회 = **수 밀리초** |

**재시도가 회로가 열린 창을 못 넘는다.** 10번이 밀리초 안에 다 실패하고 기본 recoverer 가
오프셋을 민다. `refund` 는 `REQUESTED` + 예약금 그대로 남고 아무도 다시 안 집는다.
**W4D1 이 막으려 한 결과를 프레임워크 기본값이 대신 해주고 있었다.** javadoc 이 적어둔
위험(*"영구 실패 하나가 파티션을 막는다"*)은 일어나지 않고 **정반대가** 일어난다.

## 9. 백오프만 만들고 DLT 는 만들지 않았다

> **"백오프만 필요하고 DLT 는 필요 없어 보이는데."** — 본인
> **"(가)+(라)로 가고, 상한은 없애자."** — 본인

소진 시 동작으로 넷을 놓고 골랐다:

| | 소진 시 | 대가 |
|---|---|---|
| **(가)** 소진 없음 | — | 이름 안 붙은 영구 예외가 파티션을 **영구 점유**하고, **그게 조용하다** |
| (나) 건너뜀 | 현재 동작 + 백오프 | **이미 진 빚이 조용히 사라진다.** 지금 버그를 늦추기만 함 |
| (다) DLT | | **DLT 를 누가 보나** — 안 보면 (나)와 같다 |
| **(라)** (가) + 관측 | | 대시보드 한 벌 |

**(가)+(라).** 근거의 축은 W4D1 이 이미 세운 것이다 — *"승인은 실패해도 빚이 안 생기지만
환불은 이미 진 빚"*. 건너뜀은 승인에서는 성립하고 환불에서는 안 된다. 그리고 DLT 를 안 만든
근거는 W3D5 와 같은 계열이다: 치워둔 것을 안 보면 *"안 나타남"* 이 **깨끗했다/안 봤다** 둘을
뜻하게 되고, 그건 (나)와 구별되지 않는다. 이 소비자의 기존 정책은 **상한으로 자르는 게
아니라 분류해서 빼내는 것**이었고, 그 결에 맞춘 선택이다.

### 상한이 설정 항목에 없는 게 판단이다

```
[실측] ExponentialBackOff (spring-core 7.0.8)
       DEFAULT_INITIAL_INTERVAL = 2000ms / DEFAULT_MULTIPLIER = 1.5
       DEFAULT_MAX_INTERVAL     = 30000ms
       DEFAULT_MAX_ELAPSED_TIME = DEFAULT_MAX_ATTEMPTS = Long.MAX_VALUE
```

`new ExponentialBackOff()` 가 **그대로 무제한**이다. `maxAttempts`·`maxElapsedTime` 를
**설정 가능하게 만들지 않았다** — *"포기하지 않는다"* 가 이 정책의 내용 그 자체라 항목으로
열어두면 조용히 되돌려진다. 조절하는 건 간격뿐이다.

`max-interval` 30초의 근거는 회로가 아니라 **컨슈머** 쪽이다: 블로킹 재시도라 대기 중
컨슈머 스레드가 멈추고, **한 번의 대기**가 `max.poll.interval.ms`(기본 300초)를 넘으면
그룹에서 쫓겨나 리밸런스 루프에 빠진다. 30초는 그 한참 아래고, 하트비트는 별도 스레드가
보내므로 `session.timeout.ms` 와는 무관하다.

### (라) 관측 — 무제한의 대가를 갚는다

W4D2 의 기준(*해소되면 내려가야 하는가*)으로 계기를 갈랐다:

| 지표 | 종류 | 근거 |
|---|---|---|
| 재시도 누적 횟수 | **Counter** | 아니다 — 역사적 사실이라 해소돼도 안 내려간다 |
| 막혀 있는 시간 | **Gauge** | 그렇다 — 풀리면 0. **알림을 걸 자리는 여기다** |
| 막힌 파티션 수 | **Gauge** | 그렇다 — 한 건이 막았나 여러 파티션이 막혔나를 가른다 |

여기서 `0` 은 **부재가 아니라 실제 값**이다("안 막혀 있다"). W4D2 가 `last_success_timestamp`
에서 0 을 안 쓴 건 1970년으로 읽혔기 때문이고, 이 지표엔 그 문제가 없어 `NaN` 짝이 필요 없다.

훅을 둘 쓴다. `RetryListener` 에 **성공 통보가 없기 때문**이다 — `recovered` 는 상한이
소진될 때만 불리므로 **무제한 설정에선 영원히 안 불린다.** 그래서 게이지를 내리는 쪽은
`RecordInterceptor.success` 로 받는다. 둘 다 컨테이너 훅이라 **리스너 코드를 안 건드린다**
(W4D1 이 회로를 데코레이터로 뺀 것과 같은 이유).

### 회귀 테스트는 빈 존재가 아니라 행동을 잰다

W4D2 에서 Boot 4 자동설정이 조용히 미끄러진 자리가 정확히 그 모양이었다(에러 0건,
`/actuator/prometheus` 200, 메트릭 **하나만** 없음). 그래서 단언을 이렇게 잡았다 —
**배달 횟수가 옛 기본 상한 10 을 넘는가.** 우리 핸들러가 안 꽂히면 기본값이 돌아 **정확히
10회**에서 멈춘다. 넘으면 꽂혔고 상한이 없다는 뜻이다. **하나가 둘을 동시에 증명한다.**

```
[실측] 배달 시도 14회 (옛 기본 상한 10)
[실측] retry counter = 13            (14회 중 13회 실패 — 산술 닫힘)
[실측] 막혀 있던 동안 blocked.seconds = 6.577s
[실측] 해소 후 blocked.seconds = 0.000 / blocked.partitions = 0
[실측] 전체 회귀 103 → 104건 0실패, 소요 1분 55초(무제한 재시도가 스위트를 매달리게 하지 않음)
```

**간격만 50ms 로 줄이고 상한은 안 건드렸다** — 재는 대상(포기하지 않는다는 정책)은 그대로
두고 **도구의 눈금만** 바꾼다. W4D1 의 *"회로를 끄고 잰 수치는 우리 시스템이 아니다"* 와
D4 §8 의 *"재는 대상을 바꾸는 게 아니라 도구를 붙이는 것"* 을 같은 기준으로 적용한 것이다.

### 음성대조군 (본인 실행 대기)

| | 제거 대상 | 예측 | 실측 | |
|---|---|---|---|---|
| **A** | `RefundSagaErrorHandlingConfig` 의 `@Bean` | 배달 시도 = **정확히 10** → 첫 실패는 `isGreaterThan(10)` | **배달 시도 10회**, 첫 실패 `isGreaterThan(10)`(`actual: 10`) | ✅ |
| **B** | `handler.setRetryListeners(metrics);` | 배달 14회는 유지되고 counter 0 → 첫 실패는 `retryTotal` 단언 | **배달 14회 통과 / counter 0**, 첫 실패 `retryTotal`(`actual: 0.0`) | ✅ |
| **C** | `RefundSagaRetryMetrics.success(...)` | 앞 세 단언 통과 + 막힘이 안 내려감 → 마지막 단언 실패 | **14 / 13 / 6.570s 통과, `partitions=1`** 에서 실패 | ✅ |

**A 가 가장 중요했다** — 수리 검증이 아니라 **§8 이 주장한 버그 자체의 증명**이었다.
§8 의 근거는 바이트코드 정적 확인뿐이었는데, **A 가 정확히 10 을 냈다:**

```
[실측] 배달 시도 10회 (옛 기본 상한 10 = SeekUtils.DEFAULT_MAX_FAILURES)
[실측] 첫 실패 = isGreaterThan(10)   Expecting actual: 10 / to be greater than: 10
[실측] retry counter = 0
```

**바이트코드로 읽은 상수가 실제 배달 횟수로 재현됐다.** 그리고 10회 뒤 재배달이 더 없었다 =
**그 환불 이벤트가 버려졌다.** §2 헤드라인 ②가 추론에서 실측으로 올라간 자리다.

### ★ 덤으로 나온 것 — A 는 B 의 증상을 포함한다

`retry counter = 0` 이 같이 나왔다. **관측이 핸들러 빈에 매달려 있다**는 뜻이다(핸들러가 없으면
`RetryListener` 가 아예 안 불린다). 그래서 **A 와 B 를 같은 것으로 읽으면 안 된다** — B 의 값은
*"배달 14회는 그대로 나오면서 counter 만 0"* 이고, 그게 **재시도와 관측이 분리돼 있다**를
증명한다. A 만 보고 B 를 건너뛰면 그 분리는 미검증으로 남는다.

### ⚠️ A 의 1차 시도는 무효였다 — 원인이 하네스였다

1차 실행도 red 를 냈지만 **증거를 못 얻었다.** `awaitAttempts` 헬퍼가 `[실측]` 출력과 단언보다
**먼저** 있어서 거기서 `AssertionError` 를 던졌고, 실패 메시지는
*"시도 횟수가 14 에 도달하지 않았다"* 하나였다 — **10 인지 0 인지 리스너가 안 뜬 건지 구별이
안 된다.** W3D5 에서 클래스 단독 필터 탓에 대조군이 무효였던 것과 같은 계열인데, 거기선
*red 를 낼 능력*이 없었고 여기선 **증거를 남길 능력**이 없었다.

수리: 헬퍼가 던지지 않고 **타임아웃 뒤 조용히 반환**하게 바꿨다. **기다림은 대기이고 판정은
단언이 한다** — W3D4 의 *"클래스가 겨누는 축의 단언이 먼저"* 가 헬퍼 때문에 깨진 자리다.

### ★★ C 가 예측보다 한 겹 더 냈다 — Gauge 가 조용히 Counter 가 된다

```
[실측] C — 막혀 있던 동안 6.570s → 해소 후 7.090s (blocked.partitions = 1)
```

예측은 *"막힘이 안 내려간다"* 였는데, 실측은 **계속 올라간다**였다. 이 지표는 *"막힌 뒤로 흐른
시간"* 이라 내리는 훅이 없으면 **무한히 증가하는 값**이 된다 — **Gauge 로 고른 것이 Counter 처럼
행동한다.** W4D2 가 세운 계기 선택 기준(*해소되면 내려가야 하는가*)이 바로 그 자리에서 깨진다.

실제 피해는 알림 쪽이다: `blocked.seconds > 5분` 에 알림을 걸면 **한 번 재시도가 있었던 뒤로는
영원히 발화하고 값은 계속 커진다.** 상시 울리는 알림은 아무도 안 본다 — W4D2 가 `NaN`/0 에서
다룬 *"거짓 경보가 계기를 죽인다"* 와 같은 계열이고, **훅을 둘 쓴 판단의 근거가 여기서 실측으로
확정됐다**(`RetryListener` 만으로는 이 게이지를 못 내린다).

### 예측 적중률

**이번 주 음성대조군 5건(인덱스 A·B + 재시도 A·B·C) 전부 예측 적중이다.** 그리고 셋은 예측을
넘는 것을 냈다 — 인덱스 B(*단언 순서가 곧 검증 여부*), 재시도 A(`counter=0` 으로 관측이 핸들러에
매달려 있음이 드러남), 재시도 C(위). **예측이 맞은 것보다 예측을 넘은 자리가 값이 컸다.**

필터 주의는 인덱스 쪽과 **반대**다: 이 클래스는 순서 의존이 아니라 **단독으로도 red 를 낼
능력이 있다.**

## 10. ★ `graceful` 을 켰다 — 대가를 재고 나서

D4 가 실측 근거(고아 23 → 0)를 만들고 대가를 미룬 자리다. **5세션 미결정이었고 오늘 닫았다.**

### 반대편 항을 무엇으로 두나 — 이게 실험의 어려운 부분이었다

D4 는 `taskkill /F`(즉시)와 `/actuator/shutdown`(graceful)을 비교했는데, **대가를 재는 데는 그
비교를 못 쓴다** — `/F` 는 `TerminateProcess` 라 종료 시간이 정의상 0 이고 배포는 `/F` 를 안 쓴다.

> **"같은 종료 경로에 immediate 만 바꿔서 비교하고, ①②는 나눠 재자."** — 본인

두 대가를 나눈 게 핵심이었다. **①** in-flight HTTP 를 기다리는 시간(D4 가 상정한 것) /
**②** 재시도 중인 Kafka 레코드를 기다리는 시간 — **②는 오늘 생겼다**(무제한 재시도가 블로킹이라
리스너 컨테이너가 라이프사이클 빈으로 종료를 붙잡을 수 있다). 섞이면 어느 쪽이 지연을 만들었는지
안 갈린다.

### 격리 방법

- **①은 환불을 만들지 않는다** — `@KafkaListener` 가 환불 하나뿐이라 그러면 ②가 안 섞인다
- **②는 HTTP 부하를 0 으로 둔다.** 재시도 중임은 **오늘 만든 `blocked.seconds` 게이지**로 확인했다
  (도구가 만든 날 바로 쓰였다)
- 재시도는 **프로덕션 경로**로 만들었다 — 다만 여기서 가정이 하나 깨졌다(아래)

### ⚠️ PG 타임아웃은 재시도를 만들지 않는다

처음엔 환불 금액을 `…222`(`MAGIC_TIMEOUT`)로 두면 재시도가 걸린다고 봤다. **아니었다.**

```
[실측] 환불 1건 …222 → refund.pg_status = UNKNOWN
[실측] 로그: "환불 확정 처리 refundId=1 → UNKNOWN"  (정상 종료, 예외 없음)
[실측] settleflow_refund_saga_retry_total = 0 (2분간)
```

타임아웃은 **예외가 아니라 `UNKNOWN` 반환**이다 — 소비자 javadoc 이 *"정상적 사업 결과에 예외를
던지지 않는다"* 고 적어둔 그대로다. **재시도를 만드는 유일한 프로덕션 경로는 회로 개방**
(`CallNotPermittedException`)이고, 그게 정확히 W4D1 이 설계한 것이다. 타임아웃 10건을 쌓아
`pg-refund` 를 열자 재시도가 돌았다.

### 실측

```
[실측] ② 재시도 진행 중 · HTTP 부하 0   (활성POST=0 / blocked.partitions=1 로 격리 확인)
       immediate  blocked=18.447s → 2,190 ms
       graceful   blocked= 4.731s → 2,255 ms          차이 +65 ms

[실측] ① 포화 부하 RATE=300 · 재시도 0  (blocked=0 으로 격리 확인)
       immediate  8,963 ms / 8,757 ms
       graceful   9,674 ms / 8,001 ms
```

**graceful 2회차가 immediate 2회차보다 빨랐다.** 조건 **내부** 편차(9,674↔8,001 = 1,673ms)가
조건 **사이** 차이보다 크다 → *"graceful 이 X초 더 걸린다"* 를 이 측정으로는 **말할 수 없다.**
말할 수 있는 건 **대가가 노이즈보다 작다**는 것이다.

**그리고 진짜 발견은 다른 데 있었다 — 종료 시간은 설정이 아니라 부하가 지배한다.**
무부하 2.2초 → 포화 8~9초이고, 그 8~9초는 **`immediate` 에서도 똑같이** 걸린다.

### 내 예측 둘이 틀렸다

| 예측 | 실측 |
|---|---|
| ②가 최대 30초 (재시도가 종료를 붙잡는다) | **+65ms.** `DefaultBackOffHandler` 가 `ListenerUtils.stoppableSleep` 을 쓴다는 정적 확인이 실측으로 닫혔다 — **graceful 은 재시도를 안 기다린다** |
| ①-a `immediate` 는 1초 이내 | **8.9초.** in-flight 를 안 기다려도 컨텍스트 종료가 부하에 눌린다 |

### 곁가지 — 오늘 설계의 성질이 사고로 드러났다

②를 세팅하다 환불 이벤트가 **308건** 백로그로 쌓였고, 소진이 **165초 폴링에도 안 끝났다.**
전부 타임아웃 금액이라 회로가 계속 다시 열리고, **단일 파티션 + 블로킹 무제한 재시도**라
이벤트마다 최대 30초를 밟는다. **유실은 없지만(설계 의도) 지연이 시간 단위로 간다.**
`RefundSagaErrorHandlingConfig` javadoc 의 *"알고 남기는 구멍"* 의 실물이고,
**오늘 만든 게이지가 그걸 보이게 했다.** 실험을 위해 오프셋을 latest 로 리셋해 비웠다.

### 정직한 한계

- **n=2 다.** 노이즈가 1.7초인데 표본이 둘이라 *"차이 없음"* 이 아니라 **"차이를 못 봤다"** 다
- **in-flight 수를 못 건졌다** — RATE=300 에서 `/actuator/prometheus` 가 5초 타임아웃을 넘겼다.
  **D4 §6 의 "포화 구간에서 관측이 굶는다"가 그대로 재현됐고**, D4 가 원한
  *"같은 in-flight 에서의 대조"* 는 **오늘도 못 했다**
- **①은 D4 조건과 다르다** — D4 는 RATE=100 에서 활성 175 였는데 오늘은 **3** 이었다.
  같은 rate 가 같은 부하가 아니다
- `/actuator/shutdown` **자체가** 포화에서 4.6~6.2초 걸렸다 — 종료 신호조차 큐에 밀린다
- **`timeout-per-shutdown-phase`(기본 30초) 상한 구간은 안 쟀다.** in-flight 가 30초 넘게
  안 끝나면 거기서 잘린다

## 11. Claude 오류

**① 재현 조건을 모르는 상태에서 재현을 6번 시도했다.** 실제 red 실행에 계기를 대는 게
30초짜리 작업이었는데, 일회용 컨테이너 프로브를 **네 개 먼저 돌린 뒤에야** 그 방향으로
갔다(본인 지시가 있어서 갔다). 프로브 하나하나는 정당한 실험이지만, **현장 측정보다
재현 시도를 앞세운 순서 판단이 틀렸다.** D4 §9 ③(계기를 만들면서 그 계기가 부하를 견디는지
안 따짐)과 같은 계열 — 계기를 어디에 댈지를 늦게 물었다.

**② 손으로 쓴 JSON 이 스키마와 어긋났다.** `RefundRequestedEvent` 를 안 읽고 페이로드를
썼다(`merchantPaymentId` 없음, `occurredAt` 누락 → Jackson 이 거부). 증상이 `[POISON]` 이라
**"재시도가 안 됐다"로 보였다.** → 실제 레코드를 직렬화하게 고쳐 스키마 드리프트가
컴파일에서 걸리게 했다. W3D3 #2(테스트 케이스 코드 안 보고 설명)의 변종이다.

**③ 프로퍼티 우선순위를 확인 안 했다.** `spring.kafka.listener.auto-startup=true` 를
`@TestPropertySource` 로 되돌리려 했는데, 부모의 `@DynamicPropertySource` 가 **우선순위가
높아** 안 먹었다. 리스너가 아예 안 떴고, 이 실패의 증상도 **"재시도가 안 됐다"** 였다.

> **②③은 같은 계열이다** — 계기(테스트)를 만들면서 **계기 자체의 전제를 안 쟀다.**

> (*"무제한 재시도가 배선이 안 됐다"*)에 도달할 자리였다. W3D5 §의 *"red 를 낼 능력이
> 없는 필터"* 와 같은 함정이 이번엔 페이로드와 프로퍼티에서 나왔다.

**④ 추정치를 먼저 말했다.** 4연속 green 의 의미를 *"50/50 가정 아래 1/16 ≈ 6%"* 로 적었는데,
뒤집힘 비율을 실측(56%)한 뒤 **3.7%** 로 정정됐다. 방향은 맞았지만 실측 전 추정을 수치로
제시한 건 증거 원칙에 걸린다.

**⑦ 방금 종료시킨 앱을 상대로 5분을 폴링했다.** ②-b 측정이 앱을 종료시킨 직후에 백로그 소진을
폴링했다 — **측정이 곧 종료라는 걸 계산에 안 넣었다.** 5분 타임아웃을 태우고 나서야 알았다.

**⑧ `Invoke-WebRequest` 에 `-UseBasicParsing` 을 안 붙였다.** PowerShell 5.1 은 IE 엔진을 쓰려

`415` 로 실패해 `120,047ms` 라는 무의미한 값이 나왔고 버렸다).

**⑥ 대기 헬퍼가 판정보다 먼저 던져 음성대조군 A 를 무효로 만들었다.** `awaitAttempts` 가

재실행하니 예측대로 `actual: 10` 이 찍혔다.

> **②③⑥은 같은 계열이고, 이게 오늘의 가장 반복된 실수다** — **실패의 겉모습이 다 똑같이

> 전부 *"재시도가 안 됐다"* 로 보였다. 세 번 다 **계기 자체의 전제를 안 쟀다.**
> W4D4 §9 ③(계기가 부하를 견디는지 안 따짐)의 연장이다.

**⑤ javadoc 의 단정을 초기 질문의 전제로 썼다.** *"지금은 무한 재시도"* 를 받아 DLT 질문을

않았다면 *"뜨거운 루프를 식히는 백오프"* 라는 **틀린 문제를 풀었을** 자리다.

### 이 수치가 뜻하지 않는 것

- **인덱스 수리의 6연속 green 은 증명이 아니다**(§7). *"①이 원인의 하나"* 까지가 말할 수
  있는 것이고 *"이제 안 흔들린다"* 는 아니다. **뒤집는 트리거는 여전히 모른다.**

- **끝단(실제 PG·장부까지)은 이 테스트가 안 덮는다.** `RefundSagaTest` 가 덮는다.

## 12. 체크리스트용 메모

**#1 설계** — 선택지 없이 먼저 나온 답 셋이 **오늘의 순서와 결론을 다 정했다**:
*"빨간불인 게 더 불안정하지"*(§1 — 오늘의 작업 순서) / *"진단 실측 먼저 돌려봐"*(§4 → §5 —
**방법을 바꾼 지점**) / *"백오프만 필요하고 DLT 는 필요 없어 보이는데"*(§9 — 계획서 항목의 절반
폐기) / *"상한은 없애자"*(§9). 선택지를 받아 고른 것은 (다)와 (가)+(라)다.

**#2 재설명** — 안 물었다. 소재는 있었다(`pg_stats.correlation` 이 왜 플랜을 가르는가 /
`RetryListener` 에 성공 통보가 없다는 것의 뜻 / Counter↔Gauge 를 가른 기준). **Claude 가 안
물은 것**이고, W4D1·D2 교차검증이 지적한 패턴이 또 반복됐다.

**#3 AI 없이 혼자 푼 것** — **DLT 불필요 판단**이 가장 크다. Claude 가 넷을 내밀기 전에
*"백오프만 필요해 보인다"* 가 먼저 나왔고, 그게 계획서·이월 표의 *"DLT + 지수 백오프"* 라는
한 묶음을 **둘로 쪼갠 지점**이다. W3D2 가 보상 트랜잭션을 *"구현하지 않고 필요 없게 만든"*
것과 같은 모양이고, **계획서 전제를 근거를 갖고 폐기한 것이 4주 연속**이 된다
(재고 Redis 락 → 보상 트랜잭션 → 조인 키 → DLT).

**#4** — Claude 오류 5건(§10). ①은 **본인 지시로 교정된 것**이고(*"진단 실측 먼저"*),
②③은 그 자리에서 *"그 스키마 봤어?"* / *"그 프로퍼티 실제로 먹었어?"* 가 가능했다.
거부·수정은 여전히 0건인데, **오늘은 순서 판단 하나를 본인이 바꿨다**(§4 → §5) — 그건
거부는 아니지만 방법 개입이다.

**#5 값은 어긋난 칸에서 나왔다(5번째)** — 오늘은 **어긋난 칸이 크게 둘**이었다:
① **가설 6개가 전부 반증됐고**, 그 실패가 *"추측을 쌓지 말고 현장에 계기를 대라"* 로 방향을
바꿨다(반증이 없었으면 프로브를 계속 늘렸을 것이다).
② **javadoc 의 단정이 틀렸고**, 틀린 방향이 나쁜 쪽이었다 — *"뜨겁게 돈다"* 를 고치러 갔는데
실제 문제는 *"식기 전에 포기한다"* 였다. **문제를 정반대로 알고 있었다.**
그리고 W4D2·D3·D4 에 이어 **어긋난 게 또 측정·기술 도구 쪽**이었다(seed 의 삽입 순서 /
프레임워크 기본값 / 테스트 페이로드 / 프로퍼티 우선순위).
