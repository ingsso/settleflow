## 2. ★ 먼저 물은 것 — k6 가 무엇을 새로 증명하나

웹훅 중복 폭주는 **이미 테스트가 증명하고 있다**:

| `PaymentFlowTest` | 증명한 것 |
|---|---|
| 케이스 3 | 같은 `eventId` **20개 동시** → HTTP200 20개, **`version=1`** |
| 음성대조군 A | 다른 `eventId` 20개 → SETNX 를 못 막아도 version 은 1로 수렴 |
| 음성대조군 B | 같은 상황의 부수효과 `TRANSITIONED` **1회** |

두 겹 방어(SETNX + 상태 가드·낙관적 락)가 **각각** 일한다는 것까지 갈려 있다.
그러니 *"1,000 VU 로 같은 걸 다시 확인"* 은 W3D4 §4-2 가 경계한 **동어반복**에 가깝다.

> **20개가 되면 1,000개도 된다가 자동으로 성립하지 않는 이유가 무엇인가.**
> 그게 안 나오면 오늘 만드는 건 이미 초록인 명제를 더 크게 다시 확인하는 것이다.

답: **자원.** "Redis 커넥션 풀이나 톰캣 스레드가 먼저 터질 것 같은데"(본인)

## 3. 그런데 자원이 터지는 것 자체는 값이 아니다

*"1,000 VU 에서 p95 가 올라갔다"* 는 성능 정보지 이 프로젝트의 주제(정합성)에 대해서는
아무 말도 안 한다. 값이 나오는 자리는 **"터진 상태에서도 명제가 유지되는가"** 다.

그리고 코드에 실제로 걸릴 자리가 있다:

```java
Boolean firstTime = redis.opsForValue().setIfAbsent(key, "1", DEDUP_TTL);   // ① 관문
if (!Boolean.TRUE.equals(firstTime)) return ok();

try { dispatch(req); }                          // ② DB 전이
catch (RuntimeException e) {
    redis.delete(key);                          // ③ ★ 이것도 Redis 를 쓴다
    throw e;
}
```

③ 이 있는 이유는 javadoc 에 있다 — *"멱등키가 '끝나지 않은 일'을 영영 막아버리지 않도록"*.
그런데 ③이 안 돌면:

> ②가 실패하고 ③도 못 돌면 **키가 남는다.** PG 가 재전송하면 ①에 막혀 **200 을 받고
> 재전송을 멈춘다.** payment 은 `UNKNOWN` 인 채 남고, **그 뒤로는 어디에도 에러가 안 난다.**
> — 본인 추적

**조용한 유실**이다. 회수는 TTL(24h) 만료 + 미결제 쓸이 배치(W1D3)로 넘어간다.

## 4. ★ 실측 — 풀이 없다. 예측이 틀린 자리에서 값이 나왔다

시나리오를 짜기 전에 **그 실패 모드가 우리 설정에서 도달 가능한지**를 쟀다.
안 재고 짜면 안 일어나는 일을 겨누게 된다.

```
[실측] Redis CLIENT LIST
       id=13  name=Lettuce(spring-data-redis_v4.1.0)  tot-cmds=6    ← 앱
       id=14  name=                                   tot-cmds=0    ← 방금 띄운 redis-cli
       connected_clients: 2
```

앱이 잡고 있는 커넥션은 **정확히 1개**다. 클래스패스에 `commons-pool2` 가 없고
(`lettuce-core` 만), `application.yaml` 에 Redis 설정이 한 줄도 없고, 커스텀 팩토리도 없다.
Spring Boot 기본값은 **Lettuce 단일 커넥션 멀티플렉싱**이라 **고갈될 풀 자체가 존재하지 않는다.**

| 추측 | 실측 |
|---|---|
| Redis 커넥션 풀이 먼저 터진다 | ❌ **풀이 없다.** 고갈이 아니라 **지연**으로 나타난다 |
| Tomcat 스레드가 먼저 터진다 | ✅ 유효. 기본 200개이고 제일 먼저 닿을 한계다 |

### 그래서 시나리오가 갈렸다

**볼륨만으로는 §3 의 구멍에 도달하지 못한다.** Redis 는 느려질 뿐 안 죽는다.
도달하려면 결함을 **주입**해야 한다.

---

## 5. ★ 그런데 Redis 를 내리는 것으로도 도달 못 한다

**①이 맨 앞이다.** Redis 를 내리면 ①이 먼저 터지고, 그러면 **키가 애초에 안 생긴다** —
요청은 500 으로 실패하지만 아무것도 안 남고 재전송이 정상적으로 다시 처리한다.
**안전한 쪽으로 닫힌다.**

고아 키가 생기려면 **①은 성공하고 ③은 안 돌아야** 한다. javadoc 이 그 경로를 이미 적어뒀다:

> 반대로 커밋 **전** 크래시로 키만 남는 경우는 TTL 만료 + 미결제 쓸이 배치가 회수한다.

> **"부하 중에 앱을 죽이면 되지 않나"**(본인)

그러면 ③은 *실패하는 게 아니라 실행 자체가 안 된다.* 이게 오늘 시나리오 ②의 전부다.

**⚠️ 반드시 SIGKILL 이어야 한다.** graceful shutdown 이면 in-flight 가 끝날 때까지 기다려주므로
③이 정상적으로 돌고 구멍이 안 열린다. → 파생 질문: *`server.shutdown=graceful` 을 켜면 이
구멍이 얼마나 좁아지는가.* D4 대조군 후보로 남겼다(§12).

## 6. 시나리오를 둘로 나눴다 — 부하의 모양이 배타적이다

계획서 문장 하나로는 두 가지를 동시에 못 잰다:

| 부하 형태 | Redis 키 | 앱이 죽었을 때 고아 키 |
|---|---|---|
| **같은** eventId × N | **1개** | 최대 1개 — 구멍 크기가 안 나온다 |
| **고유** eventId × N | N개 | 죽는 순간 in-flight 였던 만큼 |

| | ① `webhook-duplicate-burst.js` | ② `webhook-crash-orphan.js` |
|---|---|---|
| 부하 | 같은 eventId × N VU | 고유 eventId + 강제 종료 |
| 겨누는 것 | 정합성 — N번 와도 **장부는 1줄** | 구멍 **크기** |
| 근거 | 계획서 Week 4 표 | `WebhookController` javadoc 이 인정한 구멍 |
| 기존 증명과의 관계 | `PaymentFlowTest`(20개)의 **확대** | **새 명제** |

## 7. 헤드라인을 `journal` 로 잡았다

계획서 주말 체크포인트는 StagePass 의 *"1,000 VU → 409 997건"* 에 **대응되는 수치**를 요구한다.
그런데 **우리 웹훅은 중복에도 200 을 준다** — javadoc 이 이유를 명시한다:

> **항상 200 OK** — 중복도, 없는 결제도 정상 응답이다. non-2xx 를 주면 PG 가 몇 시간 재전송한다.

즉 **HTTP 로는 방어가 일했는지 아예 안 보인다.** 명제는 DB 에 있다.

| 세는 것 | 증명하는 것 |
|---|---|
| `payment.version` | 전이가 1회 — `PaymentFlowTest` 가 이미 쓰는 축(**확대 확인**) |
| **`journal` 증가분** | **부수효과가 1회** — *"중복 청구가 장부에 안 남았다"* |
| `outbox` 증가분 | 이벤트 발행이 1회 |

셋 다 재지만 헤드라인은 `journal` 이다. 결제 시스템에서 제일 세게 읽히는 문장이고,
**경로에 안 흔들린다**(§9 의 `version=2` 문제).

**증가분으로 재는 건 강제된 선택이다.** `journal` 에는 payment 로 돌아오는 참조가 없다
(FK 방향이 `payment.journal_id → journal.id`). 소유 관계로 셀 수 없어 기준선을 먼저 뜬다.

## 8. `eventId` 에 `merchantPaymentId` 를 넣는다

고아를 세려면 **키에서 결제로 가는 길**이 있어야 한다. 성공한 웹훅의 키도 **24시간 남으므로**
(설계상 TTL) 키 개수만으로는 못 센다.

```
Redis  webhook:dedup:k6-orphan-<mpid>   →  mpid 를 잘라낸다
DB     그 mpid 의 payment.status 가 UNKNOWN 이면  →  고아
```

**이게 프로덕션 동작을 안 바꾼다.** `eventId` 는 앱에게 **불투명한 문자열**이다 — Redis 키로만
쓰이고 아무도 파싱하지 않는다. 실제 PG 는 자기 규칙대로 만들지만 무엇이 들어있든 코드 경로가
같다. **관측을 위해 재는 대상을 바꾸지 않는 자리**라, W4D1 이 회로를 데코레이터로 뺀 것과
같은 계열의 판단이다.

그리고 시나리오 ②는 **검증 시점에 앱이 죽어 있다.** 앱을 통한 검증(전용 엔드포인트 등)은
애초에 못 쓴다 — Postgres·Redis 를 직접 본다(`verify.sh`).

## 9. 셋업 경로 실측 — 매직 금액

웹훅이 **실제로 전이시킬 대상**이 있어야 부하에 뜻이 있다. `StubPgClient` 의 매직 금액
(`amount % 1000 == 222` → `PgTimeoutException`)으로 결제를 `UNKNOWN` 으로 만든다.

```
[실측] POST /orders {productId:5, quantity:1}
       → HTTP 201, orderStatus=CREATED, totalAmount=10222, payment.status=UNKNOWN, version=1
[실측] POST /webhooks/pg (eventId=k6-probe-<mpid>)
       → HTTP 200, payment PAID, version 1→2, journal 1건, Redis 키 생성
```

**`version` 이 2 다.** `PaymentFlowTest` 케이스 3 의 `version=1` 은 `PENDING → PAID` 라 출발점이
다르다 — 헤드라인이 `journal` 인 쪽이 나은 이유가 하나 더 생겼다.

```
[실측] 시나리오 ① 5요청 스모크
       journal 증가=1 / version=2 / outbox 증가=1 / ledger_entry 증가=3 / 멱등키=1
```

## 10. ★★ 대조군이 설계 오류 둘을 잡았다

시나리오 ②를 **앱을 안 죽이고** 돌렸다. 배선 확인이 목적이었고 고아 **0건**이 나와야 했다.
**44건이 나왔다.** HTTP 는 전부 200, 실패 0건.

```
[실측] pg-approve OPEN = 1
[실측] payment id  7~15 (9건)  → PAID     ← 회로가 닫혀 있던 동안
[실측] payment id 16~59 (44건) → FAILED   ← 회로가 열린 뒤
[실측] "PG 차단기 개방" 로그 = 44건        ← FAILED 수와 정확히 일치
```

### ① 어제 만든 차단기가 시나리오를 깨뜨렸다

모든 주문에 타임아웃 매직 금액을 써서 PG 호출이 **100% 실패**였다. `pg-approve` 가 10건 만에
열리고(`minimum-number-of-calls: 10`, `failure-rate-threshold: 50`), 그 뒤로는 호출이 PG 에 닿지도
않고 바로 `FAILED` 다 — **셋업 경로가 처음 10건에서만 성립했다.**

W4D1 이 만든 동작이 그대로 일한 것이고, **단건 검증(§9)을 부하로 확대하면서 그 사이에 회로가
있다는 걸 계산에 안 넣은 게 오류다.**

**수리: 타임아웃을 30% 로 섞어 회로를 닫아둔다.** 회로를 **끄지 않는 게 판단**이다 — 그건
프로덕션 동작의 일부이고, 끄고 잰 수치는 *"우리 시스템이 이렇다"* 가 아니게 된다(W4D1 이
회로를 테스트가 갈아끼우는 자리 밖에 둔 것과 같은 이유).

비율은 **난수가 아니라 전역 이터레이션 번호로 고정**한다. 난수로 30% 를 뽑으면 20건 창에서
우연히 10건을 넘길 확률이 약 5% 라 **실행마다 회로가 열렸다 말았다 한다** — 재현되지 않는
부하는 수치의 근거가 못 된다.

### ② 고아 정의가 틀렸다

`status != 'PAID'` 로 셌는데 **`FAILED` 는 정당한 종착지**다. 회로가 열려 안 보냈거나 PG 가
거절한 결제이고, 거기 웹훅이 와도 `onApproved` 가 CONFLICT 로 거부하는 게 설계대로다
(*"종착지를 안 떠난다"*). **유실이 아니다.**

**수리: 고아 = `status = 'UNKNOWN'`** — 웹훅이 옮겨줬어야 하는데 안 옮겨진 것만.

### 수리 후 재실행

```
[실측] 혼합 부하 100건(타임아웃 30 / 승인 70), 앱을 죽이지 않음
       키 100 / PAID 100 / FAILED 0 / 고아 0 / 기타 0 / 결제 행 없음 0
```

**0이 나와야 할 자리에서 0이 나왔다.** 이제 D4 의 kill 실행에서 나오는 숫자는
**kill 때문이라고 말할 수 있다.**

> **이 대조군을 안 돌렸으면** 정상 44건이 섞인 수치를 "고아"로 보고했을 것이다.
> W3 회고 §4 *"값은 어긋난 칸에서 나온다"* 가 오늘도 반복됐고, 이번에 어긋난 건
> **감시 대상이 아니라 측정 도구 쪽**이었다(W3D5 §13 *"깨진 건 명제가 아니라 명제를 재는 자"*).

## 11. Claude 오류

**① 단건 검증을 부하로 확대하면서 그 사이의 회로를 계산에 안 넣었다**(§10 ①).
§9 를 한 건으로 확인해놓고 같은 금액을 초당 10건 쏘면 무슨 일이 생기는지 안 따졌다.
어제 직접 만든 장치인데도 그랬다.

**② 고아 정의를 `!= PAID` 로 잡았다**(§10 ②). 상태 셋(`PAID`/`FAILED`/`UNKNOWN`)의 뜻이
서로 다른데 "성공 아니면 실패"로 이분했다. 이 프로젝트가 W1D1 §3 부터 *"실패와 정보의 부재는
다르다"* 를 축으로 삼아왔는데 그 구분을 검증 쿼리에서 놓쳤다.

**③ `seed.sql` 의 존재 검사를 가격만으로 했다.** 다른 셀러가 우연히 같은 가격의 상품을 가진
순간 `INSERT` 가 조용히 건너뛰고 부하가 **남의 상품**을 쓴다 — 실제로 겪었다(전날 손으로 넣은
10,222 상품 때문에). 셀러로 한정해 고쳤다.

> 셋 다 **실행해보기 전에는 안 걸리는** 종류였다. 스크립트를 쓰고 커밋만 했으면 D4 에서
> 잘못된 수치가 나왔을 것이다 — W4D2 §11 ④(대시보드를 안 보고 커밋)와 같은 계열이다.

## 12. 정직한 한계 / 이월

### 이 수치가 뜻하지 않는 것

- **고아 수는 kill 순간의 in-flight 수에 비례한다.** rate 를 올리면 커진다. 그러므로
  *"이 시스템의 고유한 값"* 이 아니라 **"이만큼의 동시성에서 이만큼 샌다"** 이다.
- **시나리오 ①은 완전 동시가 아니다.** `PaymentFlowTest` 는 `CyclicBarrier` 로 20개를 진짜
  동시에 발사하지만 k6 에는 배리어가 없다. **둘은 다른 성질의 검증**이다 — 테스트는 좁은 창의
  경합을, k6 는 규모를 본다.
- 부하는 **로컬 단일 머신**이다. 클라이언트·서버·DB·Redis 가 CPU 를 나눠 쓰므로 처리량은
  서버 용량이 아니라 **이 노트북의 값**이다.

### 이월 표

| 숙제 | 출처 | 비고 |

| **본 실행 + 결과 분석** | 계획서 W4D4 | 오늘은 스크립트까지 |

### 남겨둔 상태

- 앱은 `bootRun` 으로 떠 있고 회로는 **닫혀 있다**(승인 주문 4건으로 HALF_OPEN → CLOSED 확인).

- 컨테이너 6개 기동 중.

## 13. 체크리스트용 메모

**#1 설계** — 선택지 없이 먼저 나온 답: *"자원이 먼저 터진다"*(§2) / *"③도 실패해서 키가 남고
재전송은 SETNX 에 막혀 200 만 받는다"*(§3) / *"부하 중에 앱을 죽이면 되지 않나"*(§5) /
*"eventId 에 merchantPaymentId 를 넣으면"*(§8). 선택지를 받아 고른 것: 시나리오 분리,
헤드라인(`journal`), 회로 대응((가) 혼합).

**#3 AI 없이 푼 것** — §3 의 추적이 특히 그렇다. 코드를 따라가 **조용한 유실의 전체 사슬**을
스스로 냈다.

**#4** — *"Redis 커넥션 풀"* 예측이 **틀렸고**(§4), 틀린 덕에 *"풀이 없다"* 를 실측했고,
그게 *"볼륨만으로는 구멍에 도달 못 한다"* → 결함 주입으로 이어졌다. **어긋난 칸에서 나온
값이 오늘 시나리오의 방향을 정했다.**
