## 2. ★ 축 — "왜 Prometheus 인가"가 먼저였다

계기를 고르기 전에 걸린 게 있었다. **불일치 건수는 이미 DB 에 있다.** `reconciliation_run` 이
W3D5 부터 `(settlement_date, observed_at, discrepancy_count)` 를 append-only 로 쌓고 있고,
Grafana 는 Postgres 를 데이터소스로 직접 붙일 수 있다 — **SQL 한 줄로 그려진다.**

### 처음 세운 축은 틀렸다

> "메트릭은 실시간 알림용이고 DB 는 사후 조회용 아닌가" — 본인 최초 답

절반은 맞는데 이 프로젝트에 대면 어긋나는 칸이 셋 나왔다:

| | 어긋나는 이유 |
|---|---|
| "알림용"은 도구의 구분이 아니다 | Grafana 는 **Postgres 에도 알림을 건다**. `SELECT ... > 임계값` 이면 그게 알림이다 |
| 이 배치에 실시간이랄 게 없다 | cron 이 하루 1회다. 불일치 건수는 **하루 한 번 바뀌는 값**이고, 15초마다 긁으면 같은 숫자를 5,760번 다시 읽는다 |
| 부재 감지도 DB 로 된다 | `SELECT max(observed_at)` 이 24시간보다 오래됐으면 알림. **"배치가 안 돌았다"도 SQL 한 줄이다** |

### 남은 질문 하나에서 축이 나왔다

> **그 SQL 알림이 눈을 감는 순간은 언제인가?**
> — "DB 가 죽으면 알림도 같이 죽는다"(본인 답)

**W3D5 ③ 논증의 한 층 위 반복이다.** 거기선 *대사가 감시 대상에게서 볼 목록을 물려받으면
안 된다*였고, 여기선 *관측이 감시 대상과 같은 저장소에 있으면 안 된다*이다.

| | 독립시킨 것 | 상관 실패의 모양 |
|---|---|---|
| W3D4 | 금액을 **어떻게** 계산하나 | 같은 SQL 재실행 = 동어반복 |
| W3D5 ③ | **무엇을** 볼 것인가 | 트리거가 죽으면 정산도 대사도 눈을 감는다 |
| **W4D2** | **어디에** 남기나 | **Postgres 가 죽으면 알림도 같이 죽는다** |

Prometheus 가 하는 일은 "실시간"이 아니라 **저장 경로를 감시 대상에서 떼는 것**이다.
그리고 pull 이라 **앱이 응답을 못 하면 그 자체가 신호**다(`up=0`). DB 경로엔 이 신호가 없다 —
조회가 실패하면 그냥 조회가 실패한 것이다.

### 두 번째 축 — DB 는 끝난 일만 안다

DB 행은 **커밋돼야** 생긴다. 3시간째 돌고 있는 배치는 DB 에 아무것도 안 남겼고,
그건 *안 돈 배치*와 구분이 안 된다. 소요시간과 회로 상태는 **DB 에 아예 없다**.

### ⚠️ 이 독립은 완전하지 않다 — 정직하게

Prometheus 를 같은 `compose.yaml` 에 두면 `docker compose down` 한 번에 같이 죽는다.
실제로 얻는 건 **"DB 와 다른 저장 경로"까지**지 "독립된 관측"이 아니다.
없는 독립을 있다고 쓰면 W3D3 §8 의 함정(초록불이 옳다는 뜻이 아니라 경로를 안 밟았다는 뜻)이다.

## 3. 계기 — Counter 를 못 쓰는 이유

> "Counter 는 계속 쌓이니까 재대사하면 6이 되고 실제 불일치는 3건인데" — 본인

**재대사는 새 불일치가 아니라 같은 불일치를 다시 본 것이다.** `ReconciliationRunner` 의
날짜 출처 ②는 **해소될 때까지 같은 날짜를 계속 다시 본다** — 그게 설계된 동작이다.
Counter 는 **관측을 세고**, 알고 싶은 건 **대상의 수위**다.

> **가르는 기준: 해소되면 내려가야 하는 값인가.** 내려가야 하면 Gauge, 누적이 뜻을 가지면 Counter.

W3D5 가 `reconciliation_run` 을 append-only 로 만든 이유가 여기서 되돌아온다.
**DB 는 관측을 쌓는 게 맞고**("3일 연속 같은 불일치"는 그래야 보인다), **메트릭은 대상을 센다**.
같은 시스템에서 두 층이 반대 규율을 갖는 게 이상하지 않다 — 답하는 질문이 다르다.

## 4. 값의 출처 — 밀어넣기(b-1) vs 재구성(b-2)

Gauge 를 골라도 **누가 언제 그 값을 세팅하느냐**가 남는다.

| | 방식 | 대가 |
|---|---|---|
| **b-1** | 배치가 끝날 때 `gauge.set(3)` | 앱 재시작 → **0**. 미해소가 3건 그대로인데 그래프는 초록불 |
| **b-2 ✅** | 스크레이프마다 `repo.sum...()` 로 DB 재계산 | 15초마다 쿼리. DB 의존이 돌아옴 |
| b-3 | Postgres exporter 로 앱을 안 거침 | 쿼리가 앱 밖 YAML 에 문자열로 삶 |

**b-1 은 오늘 세운 축과 정면으로 부딪힌다.** (B) "배치가 안 돌았다"를 잡으려고 메트릭을 놓는데,
정작 그 메트릭이 **배치가 돌아야만** 갱신된다.

> b-1 도 값이 "유지"되긴 한다(마지막 `set` 이 계속 노출된다). 진짜 차이는 **값의 출처**다 —
> b-1 은 **메모리가 원본**이라 프로세스 수명에 묶이고, b-2 는 **진실에서 다시 계산**한다.
> "유지"가 아니라 **재구성**이 b-2 의 성질이다.

### 딸려온 일 — 그 값은 테이블에 바로 없다

`discrepancy_count` 는 **run 한 번의 스냅샷**이다. 그냥 다 더하면 같은 불일치를 며칠째 세는 만큼
중복으로 센다 — 관측을 쌓는 설계의 당연한 귀결이다. "지금 수위"는 **날짜마다 최신 run 만 골라**
합쳐야 나온다(`sumUnresolvedDiscrepancies`). **Counter 를 못 쓰는 이유와 같은 뿌리다.**

## 5. ★ 오늘의 발견 — 자동설정이 Boot 4 에서 조용히 미끄러진다

**증상**: `/actuator/prometheus` 는 **200** 이고 메트릭이 수십 개 나오는데
`resilience4j_circuitbreaker_state` **만** 없다. **에러 0건.**

### 증거 사슬

| | 확인 | 결과 |
|---|---|---|
| 1 | `resilience4j-micrometer:2.2.0` 이 클래스패스에 있나 | **있다** (의존성 트리) |
| 2 | `CircuitBreakerMetricsAutoConfiguration` 의 조건 (`javap`) | `@ConditionalOnBean(MeterRegistry.class)` + `@AutoConfigureAfter(name={"org.springframework.boot.actuate.autoconfigure.metrics.MetricsAutoConfiguration", ...})` |
| 3 | Boot 4.1.0 에 그 클래스가 있나 | **없다.** `spring-boot-micrometer-metrics-4.1.0.jar` 의 `org.springframework.boot.micrometer.metrics.autoconfigure` 로 이사 |

`@AutoConfigureAfter` 는 클래스를 **문자열 이름**으로 참조한다. 없는 이름은 에러가 아니라
**그냥 무시**되고 → 순서 제약이 증발 → `MeterRegistry` 빈 정의가 등록되기 **전에** 평가될 수
있고 → `@ConditionalOnBean` 이 false → 퍼블리셔가 안 만들어진다. **전 구간에 에러가 없다.**

> `@ConditionalOnBean` 은 *"완성된 컨텍스트에 그 빈이 있는가"* 를 묻지 않는다.
> **"지금까지 등록된 빈 정의 중에 그 타입이 있는가"** 를 묻는다. 그래서 이 조건은 평가 순서에
> 통째로 의존하고, 그것 때문에 애초에 `@AutoConfigureAfter` 가 붙어 있었다.
> **그 이름이 죽자 조건의 전제가 같이 죽었다.**

**W4D1 §2 가 예고한 실패 모양이 한 층 위에서 실현됐다.** 거기선 *"자동설정이 미끄러지면 에러가
아니라 무음"* 이라 스모크를 박았는데 그때는 안 미끄러졌고, **오늘 메트릭 층에서 미끄러졌다.**
`management.*` 를 yaml 에 적은 것만으로는 절대 안 걸린다 — 엔드포인트는 200 이고 다른 메트릭
수십 개가 멀쩡히 나오기 때문이다.

### 수리 — 퍼블리셔가 아니라 바인더

`TaggedCircuitBreakerMetrics` 는 `MeterBinder` 이고, Boot 는 **모든 `MeterBinder` 빈을 레지스트리가
만들어진 뒤에** 붙인다. **평가 순서에 기대는 부분이 없다** — 깨진 게 바로 그 순서라,
순서를 다시 전제하지 않는 배선을 골랐다.

> ⚠️ **"퍼블리셔 경로는 실패한다"는 검증하지 않았다**(§11 ①). 사용자 `@Configuration` 은
> 자동설정보다 먼저 처리되므로 그 경로도 성립할 수 있다.

### 워크어라운드에 만료 조건을 달았다

```java
assertThat(ctx.getBeanNamesForType(TaggedCircuitBreakerMetricsPublisher.class))
        .as("resilience4j 자동설정이 붙었다면 이 워크어라운드를 제거할 것")
        .isEmpty();
```
자동설정이 고쳐지면 이 단언이 깨지고 우리 빈이 중복이라고 알려준다.
**"왜 이 코드가 있는가"를 주석이 아니라 실행되는 것으로 남긴다.**

## 6. 지표 5종 — 축이 구현 모양에 그대로 드러난다

| 지표 | 타입 | 출처 | 재시작하면 |
|---|---|---|---|
| 미해소 불일치 건수 | Gauge(함수) | **DB 재계산** | 복원된다 |
| 대사 마지막 성공 시각 | Gauge(함수) | **DB 재계산** | 복원된다 |
| 배치 1회 소요 (A) | Gauge | 인메모리 | **사라진다** |
| 날짜 1건 소요 (B) | Timer | 인메모리 | **사라진다** |
| 이번 배치 날짜 수 (N) | Gauge | 인메모리 | **사라진다** |
| 회로 상태 ×2 | Gauge | 인메모리 | (resilience4j) |

**5종 중 2종은 배치 코드를 한 줄도 안 건드린다.** 뒷 무리는 그 선택지가 없다 —
**DB 에 아무 기록이 없어 재구성할 원본이 없다.** 재시작하면 사라지는 건 실수가 아니라
**알고 받는 대가**다. 소요시간을 남기려면 테이블을 하나 더 파야 하는데, 그건
"관측을 위해 진실 저장소를 늘린다"라 W2D1 §5 의 규율과 부딪힌다.

### A 는 Gauge, B 는 Timer

A 는 표본이 **하루 1개**라 분포가 없다 — 마지막 값만 뜻이 있다.
B 는 배치 한 번에 **N 개**가 나오므로 분포가 실재한다. Gauge 로 두면 마지막 날짜 하나만
남고 앞의 N−1 개가 버려진다.

**N 을 같이 내는 이유**: A 가 올라갔을 때 *느려졌다*인지 *밀린 날짜가 많았다*인지 N 없이는
못 가른다. **A ÷ N ≈ B** 가 닫혀야 해석이 완결된다.

### ⚠️ Timer 의 `_max` 는 대시보드에 안 올린다

`percentiles-histogram` 은 껐다(버킷 시계열 수십 개를 채울 표본량이 아니다). 그런데 Timer 가
함께 내보내는 **`_max` 는 감쇠 게이지**라 만료 창(기본 2분)이 지나면 **0 으로 떨어진다.**
하루 1회 배치에선 거의 항상 0 이라 **"빨랐다"로 오독된다** — 0 인 이유가 "빨랐다"가 아니라
"창이 만료됐다"라서, 오늘 축(부재를 부재로 읽는가)에 정면으로 걸린다.
쓰는 건 `_count`·`_sum` 이고, 하루 평균은 `increase(sum[1d]) / increase(count[1d])`.

### 계측을 `try/finally` 에 안 넣었다

**실패한 배치는 소요시간에 안 남는다.** 넣으면 3시간 돌다 죽은 배치의 시간이 성공한 배치와
같은 시계열에 섞여 *"느려졌다"* 와 *"실패했다"* 가 한 숫자가 된다. 실패는 **다른 지표가 잡는다**
(§7). 두 지표가 각자 한 가지씩 맡는 쪽을 골랐다.

## 7. 부재를 값으로 표현하기 — (가)안과 NaN

**미해소 게이지는 (B) 를 못 본다.** 배치가 3일째 멈춰도 `countUnresolved()` 는 계속 0 을
돌려준다 — 아무도 해소를 안 했으니 **값이 안 변하는 게 옳다**. DB 도 앱도 멀쩡히 응답하고,
게이지는 **0 = 초록불**이다.

| | 지표 | 알림 | 대가 |
|---|---|---|---|
| **(가) ✅** | 마지막 성공 **시각** Gauge | `time() - metric > 26h` | 인메모리면 재시작에 날아감 → **DB 재구성으로 해결**(b-2 와 같은 원칙) |
| (나) | 마지막 성공 이후 **경과** Gauge | `metric > 26h` | 시계열이 톱니, "언제 성공했나"를 역산 |
| (다) | 실행 **Counter** | `increase(...[26h]) == 0` | 앱이 죽으면 시계열 자체가 사라져 **평가할 게 없다** |

### NaN 을 쓴 판단

한 번도 안 돌았으면 **0 이 아니라 `NaN`** 을 낸다. 0 은 1970년이라 `time() - metric` 이 즉시
임계를 넘어 **갓 띄운 앱이 매번 거짓 경보**를 낸다. `NaN` 은 "값이 없다"를 그대로 말한다.

> ⚠️ **대가는 알고 남긴다**: `time() - metric > 26h` 는 `NaN` 에서 거짓이라 **한 번도 안 돈
> 상태는 이 규칙만으로 안 잡힌다.** 알림은 `absent()` 와 짝지어야 완결되고,
> 이건 (다)안이 가진 약점과 **같은 것**이다 — **부재를 값으로 표현하는 이상 어느 안을 골라도 남는다.**

## 8. 실측 ① — 테스트 6건 (전체 97 → 103건 0실패)

레지스트리를 직접 안 읽고 **HTTP 로 긁는다**. `MeterRegistry.get(...)` 으로 재면 *등록됐다*까지만
증명되는데, §5 에서 겪은 게 정확히 그 틈이다 — 레지스트리에 있을 법한데 **노출 경로에서 빠져
있었다**. 밖에서 보이는 것이 관측이므로 밖에서 잰다.

```
[실측] 재대사 → run=2건 관측=누적 / 게이지 1 → 1 (Counter 였다면 2)
[실측] 해소 → 게이지 1 → 0 (Counter 였다면 내려갈 수 없다)
[실측] 배치 → 날짜=2건 A=0.025s N=2 B_count=2 B_sum=0.020s (A÷N=0.013s, B평균=0.010s)
[실측] 빈 배치 → 정산=0건 A=0.0098s N=0 (NaN 아님 = 돌긴 했다)
[실측] 마지막 성공 시각 → NaN(한 번도 안 돎) → 1785810175 (차이=0s)
[실측] /actuator/prometheus — resilience4j_circuitbreaker_state, pg-approve open 0.0 → 1.0,
       같은 시점 pg-refund closed=1.0
```

**앞의 두 줄이 §3 판단의 직접 증거다.** 재대사에서 1→1, 해소에서 1→0 인데, Counter 였다면
각각 2 와 "내려갈 수 없음"이었다. 마지막 줄은 **격리가 관측에서도 보인다**는 증거다(W4D1 §7).

> Timer 는 단조 누적이고 레지스트리는 컨텍스트에 붙어 테스트 간에 살아남는다
> (W4D1 이 회로를 `@BeforeEach` 로 reset 한 것과 같은 자리). **Timer 에는 reset 이 없으므로
> 되돌리는 대신 기준선을 뜨고 델타로 잰다.**

## 실측 ② — 라이브 전 구간 (앱 → 스크레이프 → TSDB → 질의)

주문 5건을 `POST /orders` 로 넣고 Quartz job 을 actuator 로 트리거했다.
셀러·상품만 SQL 로 넣었고(마스터 데이터, API 가 없다) **주문·정산·대사는 전부 실제 코드가 했다.**

```
[실측] 정산 배치 — 밀린 날짜 1건 [2026-08-04]
[실측] 정산 배치 date=2026-08-04 [00:00+09:00 ~ 익일 00:00) 셀러=2건 표식정리=5줄
[실측] 대사 배치 — 대상 8건 (정산=1 미해소=0 최근7일)
```

| 지표 | 배치 전 | 배치 후 |
|---|---|---|
| `settlement_batch_duration_seconds` (A) | **NaN** | **0.1300** |
| `settlement_batch_dates` (N) | **NaN** | **1** |
| `settlement_date_duration_seconds_count` (B) | 0 | **1** |
| `..._sum` | 0 | **0.0745** |
| `reconciliation_last_success_timestamp_seconds` | **NaN** | **1785837144** |
| `time() - last_success` (패널 2) | NaN | **80초** 🟢 |

**컨테이너 → 호스트 경로도 증거로 갈렸다.** 앱이 뜨기 전 타겟 에러가
`no such host` 가 아니라 **`dial tcp 192.168.65.254:8080: connect: connection refused`** 였다 —
`host.docker.internal` 이 이미 제대로 풀렸고 포트에 아무도 안 듣고 있을 뿐이라는 뜻이다.

`prometheus` 잡을 스크레이프 대상에 함께 넣은 것도 판단이다. 이 줄이 없으면
**"긁는 쪽이 죽었다"와 "긁히는 쪽이 죽었다"가 같은 화면**이 된다.

### ★ 배치 전 화면이 오늘 설계의 요약이다

```
unresolved_discrepancies        0      ← 깨끗하다
last_success_timestamp_seconds  NaN    ← 한 번도 안 돌았다
settlement_batch_duration       NaN    ← 한 번도 안 돌았다
```

**미해소 게이지만 봤다면 `0 = 초록불`이다.** 옆의 NaN 이 (B)를 말해준다. 0 이었다면 화면은
`last_success = 0`(1970년) · `batch_duration = 0s` 로 읽혔을 것이고, 후자는
*"배치가 0초 만에 끝났다"* 는 거짓말이다.

## 10. ★ 결함 주입 — 1차 예측이 틀린 자리에서 값이 나왔다

`settlement_pending` 의 행을 지운다 = **트리거(`trg_journal_settlement_pending`)가 죽은 상황**.
W3D5 §9 가 출처 ③(최근 7일 창)을 만든 바로 그 시나리오다. **본인이 직접 실행**(규약).

| | 1차 — 오늘 날짜에 심음 | 2차 — 어제로 밀어서 심음 |
|---|---|---|
| 정산 | 밀린 날짜 없음 ✅ | 밀린 날짜 없음 ✅ |
| 대사 대상 | **7건** ❌ (예측 8) | 7건 ✅ |
| 불일치 | **0건** ❌ (예측 2) | **2건** ✅ |
| 유형 | — | `MISSING_IN_SETTLEMENT` ✅ |
| `settled`/`reconstructed` | — | `NULL` / 9,500·9,700 ✅ |
| 차액 | — | **−9,500 / −9,700** ✅ |
| 게이지 | 0 | **0 → 2** ✅ |

### 왜 1차가 0건이었나 — 오늘이 대상에서 빠진다

`recentDates()` 는 **어제부터** 거꾸로 7일이고, **오늘은 의도적으로 제외**된다:

> **오늘을 빼는 게 판단이다.** 오늘은 아직 안 끝난 날이라 정산이 돌 이유가 없고, 대사하면
> "장부엔 있는데 정산엔 없다"가 매번 뜬다 — 정상 상태의 거짓 경보다. — `ReconciliationRunner`

| | 출처 ① 정산이 돈 날짜 | 출처 ③ 최근 7일 | 합 |
|---|---|---|---|
| 1회차(정상) | **오늘** | 어제~7일 전 | **8** |
| 2회차(표식 제거 후) | **없음** | 어제~7일 전 | **7** |

결함을 **오늘**에 심었는데, 정산이 안 돌아 출처 ①에도 안 올라오고 ③은 오늘을 뺀다 →
**아무도 안 봤다.**

### 그래서 나온 것

> **출처 ③(최근 7일 창)은 "오늘"에 대해서는 상관 실패를 못 끊는다.**

W3D5 §9 의 논증은 *"트리거가 죽으면 정산 대상 0건 → 대사도 눈을 감는다 → ③이 그걸 끊는다"*
였다. 그 상황을 정확히 재현했더니 **오늘치에 대해서는 안 끊었다.** 날짜가 넘어가 "어제"가
되면 잡히므로 **버그가 아니라 감지 지연**이고, 크기는 **최대 하루 + 다음 배치까지**다.

**이건 W3D5 문서에도 테스트에도 없다.** `DiscrepancyFlagTest` 케이스 ④는
`pushTodaysJournalsTo(today.minusDays(2))` 로 **이틀 전**에 심어 이 자리를 안 밟았다.
**결함 주입이 아니었으면 안 나왔을 값이다** — W3 회고 §4 *"값은 어긋난 칸에서 나온다"* 의 반복.

2차에서 예측이 **전부** 맞은 건 그 원인 진단이 옳았다는 확인이다.

## 11. Claude 오류 2건

### ① 검증 안 한 것을 근거로 썼다 — 대화 중 자진 정정

`ObservabilityConfig` javadoc 에 *"퍼블리셔는 레지스트리가 만들어질 때 주입돼야 해서 **같은
순서 문제에 다시 걸린다**"* 라고 썼는데 **안 돌려봤다.** 사용자 `@Configuration` 은 자동설정보다
먼저 처리되므로 그 경로도 성립할 수 있다. 게다가 그걸 **정답이 있는 것처럼 질문으로 냈다.**
→ javadoc 을 *"이 방식이 순서를 전제하지 않는다"* 까지로 좁히고, 미검증임을 명시.

### ② 읽어놓고도 예측에 반영 안 했다

§10 의 예측표를 쓸 때 `recentDates()` 의 **"오늘 제외"를 같은 세션에서 직접 읽고도**
출처 ③이 오늘을 포함한다고 가정했다. 1차 결함 주입이 0건으로 끝난 원인이 이것이다.

> **다만 예측을 미리 적어둔 덕에 어긋난 게 즉시 드러났다.** 예측 없이 "불일치가 안 나오네"로
> 넘어갔으면 §10 의 발견은 안 나왔다.

### ③ 아닌 것 — 사용자 보고와 시스템 상태가 어긋난 건

중간에 *"정산=0 인데 대사 대상 8건, 불일치 2건"* 이라는 보고가 있었는데 DB 에 관측이 0행이었다.
대조해보니 **테스트 스위트 로그**를 본 것이었다(`DiscrepancyFlagTest` 가
`reconciliationRunner.run(List.of())` 로 부르므로 로그가 실제로 `정산=0` 으로 찍힌다).
자기보고를 그대로 승인하지 않고 DB·Prometheus 와 대조한 것이 걸러냈다.

> **여기서 걸린 것**: 테스트 로그와 라이브 로그가 **형식이 완전히 같아** 줄 안에 출처를 가릴
> 근거가 없다. 오늘 축("어디서 온 값인가")이 로그에도 걸리는 자리다 → §12 이월.

### ④ 절차 오류 — bash 문법을 PowerShell 사용자에게 줬다

결함 주입 명령을 `curl -s -X POST ... \` 로 줬는데 PowerShell 에서 `curl` 은
`Invoke-WebRequest` 별칭이라 바인딩 에러가 났다. 이 프로젝트의 셸은 PowerShell 이다.
