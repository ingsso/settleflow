## 1. 환불 — Order enum에서 Refund 엔티티로

### 문제
Week 2 주말 체크포인트가 "부분환불 **3번 반복**"을 요구한다. `Order`의 enum 하나로는 3번의 환불이 각각 얼마였는지 기록할 곳이 없다. `PARTIAL_REFUNDED`는 사실만 말하고 금액을 담지 못하는데, Week 2 Day 5의 역분개(reversing entry)는 **건별 금액**이 있어야 만들 수 있다.

### 결정
- `Refund` 엔티티 신설 (payment FK, amount, ...)
- Order의 환불 상태는 저장하지 않고 **파생**시킨다
  - `sum < payment.amount` → PARTIAL_REFUNDED
  - `sum == payment.amount` → REFUNDED
  - `sum > payment.amount` → 발생 불가여야 함 (과다환불)

### 과다환불 방어 — "DB 제약 걸면 되지 않나"의 함정

**CHECK 제약은 자기 행 하나만 볼 수 있다.** `sum(refund.amount) <= payment.amount`는 두 테이블에 걸친 집계라 CHECK로 표현 불가능. Postgres는 서브쿼리를 담은 CHECK를 거부한다 (`ERROR: cannot use subquery in check constraint`).

또한 CHECK만으로는 레이스가 안 막힌다. 결제 10,000원 / 기환불 5,000원 상태에서 3,000원 환불 2건이 동시에 오면:

```
T1: sum → 5,000        T2: sum → 5,000   (T1 미커밋)
T1: 8,000 <= 10,000 ✓  T2: 8,000 <= 10,000 ✓
→ 둘 다 INSERT → 11,000원 환불
```

READ COMMITTED에서 재현되는 고전적 lost update.

### 채택: A안 — 비정규화 + 원자적 조건부 UPDATE

```sql
UPDATE payment SET refunded_amount = refunded_amount + :amt
WHERE id = :id AND refunded_amount + :amt <= amount
```

- 영향 행 0이면 거부
- Postgres READ COMMITTED에서 T2는 T1 커밋을 기다린 뒤 **갱신된 행으로 WHERE를 재평가**하므로 튕김
- 여기에 `CHECK (refunded_amount <= amount)`를 얹어 수동 SQL·마이그레이션 사고까지 차단
- `UPDATE`(검사 겸 락) → `INSERT INTO refund`를 **같은 트랜잭션**에 묶으면 드리프트가 애초에 안 생김

**기각한 B안**: `SELECT payment FOR UPDATE` 후 sum 계산. 비정규화는 없지만 불변식이 애플리케이션 코드에만 존재하고 DB 스키마에 안 드러남. Week 2 Day 3의 산출물이 "불변식 **DB 제약**"이므로 서사에 안 맞음.

### 비정규화 드리프트는 어떻게 잡나
- **예방**: UPDATE + INSERT를 같은 트랜잭션 (드리프트 발생 자체를 막음)
- **탐지**: Week 3 대사 배치. 단 대사는 사후 탐지지 예방이 아님. 정상이면 항상 0건이어야 하고, 0이 아니면 코드 버그 신호

### 부수 효과 — 4중 교차검증
환불 금액에 대해 독립적인 기록이 넷 생긴다: `sum(refund.amount)` / `payment.refunded_amount` / 역분개 ledger entry 합 / PG 리포트.
Week 3 체크포인트("불일치 3건 심고 배치가 정확히 3건 잡기")에 심을 수 있는 불일치 종류가 풍부해짐.

## 2. Payment 행 생성 시점 — PG 호출 **전**

### 함정 1: 커밋 시점
```java
@Transactional
void pay() {
    paymentRepository.save(pending);  // 미커밋
    pgClient.approve(...);            // 여기서 터지면
}                                     // 롤백 → PENDING 행 소실
```
PG 호출 **전에 트랜잭션을 끊고 커밋**해야 한다.
트랜잭션1(INSERT PENDING, 커밋) → PG 호출 → 트랜잭션2(결과 반영).

### 함정 2: FAILED와 "모름"은 다른 상태
타임아웃은 **실패가 아니라 정보의 부재**다. PG가 승인을 끝냈는데 응답만 못 온 것일 수 있다.
FAILED로 찍으면 → 사용자 재결제 → 이중청구 → DB엔 FAILED 1 + PAID 1로 정상처럼 보임.

`FAILED` = PG가 명시적으로 거절한 **확정 정보**
`UNKNOWN` = 정보의 부재

Week 5 Dunning이 이 구분 위에 선다. 확정 실패(한도 초과)는 재시도할 값어치가 있고, 미확정은 재시도가 아니라 **PG 조회**를 걸어야 한다.

### 함정 3: 웹훅이 동기 응답보다 먼저 온다
동기 응답 처리 코드가 무심코 `setStatus()`를 하면 이미 확정된 상태를 뒤집는다. 상태 전이에 가드 필요.

### 함정 4: 웹훅을 무엇으로 매칭하나
PENDING 행 생성 시점에 `pgTransactionId`는 NULL. 웹훅은 그 ID를 들고 온다 → NULL 컬럼으로는 못 찾는다.
**우리가 만든 고유 키를 PG에 넘기고, 웹훅이 되돌려주게** 해야 한다 (토스페이먼츠의 `orderId` / `paymentKey` 구조).

즉 Payment에 식별자가 둘: PG가 주는 것(나중에 채움) + 우리가 만드는 것(처음부터 존재).
Postgres unique는 NULL을 서로 다른 값으로 취급하므로 여러 행이 NULL이어도 문제없음.

## 3. PaymentStatus — 4개

`PENDING` / `PAID` / `FAILED` / `UNKNOWN`

이름은 **돈의 어휘**로. `SUCCESS`/`ERROR`는 HTTP 클라이언트의 어휘(우리 코드가 겪은 일)이지, "고객 돈이 빠져나갔는가"에 대한 답이 아니다.

상태를 가르는 기준: **다음 수를 누가 두는가**

| 상태 | 다음 수 |
|---|---|
| `PENDING` | PG가 알려준다. 기다린다 |
| `UNKNOWN` | 아무도 안 알려준다. 우리가 조회한다 |
| `PAID` / `FAILED` | 없다 (종착지) |

### 3상태 vs 4상태
크래시(OOM·배포·인스턴스 종료) 시엔 `UNKNOWN`을 쓸 새도 없이 죽으므로 **"오래된 PENDING 쓸이 배치"는 어차피 필수**다. 그래도 4상태를 택함 — 타임아웃을 관측한 순간 명시적으로 남기면 Week 4 Grafana에 `UNKNOWN` 건수를 띄울 수 있다(관측성). 대신 PENDING·UNKNOWN 두 경로를 다 처리해야 함.

## 4. 전이표

들어오는 사건은 결국 셋. **출처(동기응답/웹훅/조회)가 아니라 내용만 중요하다.**

| 현재 \ 사건 | 승인 확정 | 거절 확정 | 타임아웃 |
|---|---|---|---|
| `PENDING` | → PAID | → FAILED | → UNKNOWN |
| `UNKNOWN` | → PAID | → FAILED | 무시 (유지) |
| `PAID` | 무시 | **무시 + 알람** | 무시 |
| `FAILED` | **무시 + 알람** | 무시 | 무시 |

**12칸 중 전이는 5개뿐.** 종착지 두 행은 통째로 안 움직인다.

### 규칙 두 개
> 1. **정보의 부재는 확정 정보를 뒤집지 못한다.**
> 2. **확정 정보끼리 모순되면, 상태를 바꾸지 말고 사람을 부른다.**

### 왜 종착지가 안 움직이나
`(order_id) WHERE status = 'PAID'` 부분 유니크 인덱스는 **status가 `PAID`인 동안에만** 그 행을 지킨다. `PENDING`이든 `FAILED`든 `UNKNOWN`이든 `MISMATCH`든, **`PAID`를 떠나는 것 자체**가 이중청구 구멍이다. 떠난 뒤 새 `PAID` 행이 정상 삽입되고, DB는 `FAILED` 1 + `PAID` 1로 아무 이상 없어 보인다.

→ **한 번 `PAID`면 영원히 `PAID`.**

### `PAID + 승인 확정`이 "무시"인 이유
전이시키면 `PENDING → PAID`에 딸린 부수효과(분개 생성)가 재실행되어 `sum(차변) == sum(대변)`이 깨진다. Week 1 Day 4의 웹훅 멱등성이 지키려는 게 정확히 이 칸.

### 굵은 두 칸 — 사람이 두는 수
`FAILED + 승인 확정`: PG가 "승인됐다"고 말한다. 우리는 실패로 적어놨다. **돈은 나갔고 상품은 안 나간다.** 무시하고 넘기면 대사 배치가 다음 날 새벽에 잡을 때까지 아무도 모른다.

`UNKNOWN`으로 보내는 것도 오답이다. `UNKNOWN`은 "모른다, 조회해야 한다"인데 지금은 **모르는 게 아니라 두 가지를 알고 그 둘이 모순**된다. 조회해도 같은 답이 오고 기계가 루프에 빠진다. 정보 부족이 아니라 모순.

→ 자동 전이도 무시도 아니고 **알람**. 상태는 그대로, 사건은 기록.

### 웹훅 응답과 상태 전이는 다른 층위
| 층위 | 무엇을 하는가 |
|---|---|
| 상태 전이 | 안 한다 |
| 웹훅 응답 | **200 OK** (non-2xx면 PG가 몇 시간 재전송) |
| 사실 기록 | 이상 테이블에 남긴다 |

"무시"는 **상태**를 무시하는 것이지 **사건**을 무시하는 게 아니다.

## 5. 이상 징후 저장 — 별도 테이블 (B안)

**기각한 C안(다섯 번째 상태 `MISMATCH`)**: `FAILED + 승인`엔 쓸 수 있지만 `PAID + 거절`엔 못 쓴다(`PAID`를 떠나면 유니크 인덱스가 풀림). 두 칸 중 한 칸에 못 쓰고, "모순은 상태를 바꾸지 않는다"는 규칙을 만들자마자 어긴다.

**기각한 A안(Payment에 플래그 컬럼)**: 조회는 쉽지만 같은 결제에 모순 사건이 두 번 오면 하나가 덮어써진다. 결제 이상은 append-only로 쌓여야 조사가 된다.

**채택 B안**: Week 3 Day 5의 불일치 플래그 테이블에 Week 1의 실시간 모순도 같이 꽂는다.

- 실시간 경로: 웹훅이 확정 상태와 모순 → 즉시 기록
- 배치 경로: 새벽 대사가 PG 리포트 대조 → 발견 시 기록

**탐지 경로는 둘, 저장소는 하나.** 운영자는 한 곳만 보고, Week 4 Grafana는 그 테이블 카운트만 센다.

### 이상 테이블은 자기 상태를 갖는다
그 테이블은 **사람의 작업 큐**다. `OPEN → INVESTIGATING → RESOLVED` 같은 자기 상태가 없으면 어제 처리한 건이 오늘 또 뜬다.

즉 상태 기계가 둘: **돈의 상태**(Payment) / **조사의 상태**(Anomaly).

조사가 끝나도 Payment는 여전히 `FAILED`다. 사람이 환불을 시켰든 주문을 살렸든, 그 결정은 **새 행**(새 Payment, 새 Refund)으로 표현되지 원래 행을 고치지 않는다.

> 회계 시스템은 과거를 수정하지 않고 정정 기록을 덧붙인다. **지우개가 아니라 빨간 펜.**
> Week 2의 역분개(reversing entry)가 정확히 같은 사고방식.

## 6. 금액 — 원 단위 Long (유지, 단 조건부)

KRW 단일 통화면 맞는 선택. BigDecimal은 과함.

**단 Week 2에서 물린다.** 결제 10,000원을 셀러 정산액 + PG 수수료로 쪼갤 때, 수수료율 3.3%면 9,999원 결제에서 **329.967원**이 나온다. 반올림하는 순간 `sum(차변) != sum(대변)` — Week 2 Day 3에서 DB 제약으로 막겠다는 바로 그 불변식이 깨지는 지점이고, 실무 정산 사고의 단골 자리.

→ **잔돈을 누가 흡수할지**를 Week 2 전에 정할 것. 통상 수수료를 버림/올림하고 차액을 셀러 정산액에 몰아 합을 강제로 맞춘다.

### 2. ERD + 엔티티 클래스 (Day 1 미완 산출물 이월)

### 3. 재고 차감 (원래 Day 2 주제)
`UPDATE product SET stock = stock - :qty WHERE id = :id AND stock >= :qty`의 영향 행 수를 보는 방식은 락 없이도 레이스가 없다.
**그럼 Redis 락은 왜 쓰는가?** — "StagePass 재사용"은 면접에서 안 통하는 답. 스스로 근거를 만들 것.
