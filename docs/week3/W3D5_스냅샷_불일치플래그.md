## 1. 오늘의 범위

**계획서 항목**: 불일치 건 자동 플래그 + 배치 중 신규 주문 유입 동시성 처리(스냅샷 기준 조회) → 동시성 테스트

### ★ 계획서의 문장과 실제 부채가 같지 않았다

계획서는 *"배치 중 신규 주문 유입"* 이라고 적었다. 그런데 배치는 **어제치**를 돌고, 배치 도중
들어오는 신규 주문은 전부 `[from, to)` **밖**이다 — 그 자체로는 문제가 안 생긴다.

W3D3 §4가 실제로 뚫은 건 더 좁다: **경계 직전에 `created_at`이 찍히고 배치 뒤에 커밋된 줄**.
26일자 배치엔 안 보이고 27일자 배치엔 범위 밖이라 **증발**한다. 원인은 유입 타이밍이 아니라
**타임스탬프 순서 ≠ 가시성 순서**다.

**후자를 겨눴다.** 계획서 문장이 아니라 W3D3이 실제로 남긴 부채를 갚는 쪽으로 읽었다.

**오늘이 기한인 이월 숙제**

| 숙제 | 출처 | 상태 |
|---|---|---|
| 커밋 가시성 구멍(스냅샷 기준 조회) | W3D3 §4·§9 | ✅ **해소 — §2~§5** |
| 불일치 자동 플래그 | 계획서 W3D5 | ✅ **§7~§9** |
| `ReconciliationService` 를 실제로 돌리기 | W3D4가 안 함(발견) | ✅ **§7** |
| `EXPLAIN` 으로 인덱스 실측 | W3D3 #5 → W3D4 | ⬜ **3회 이월** |
| `LedgerService.recordRefund` javadoc 정정 | W3D4 §7 | ⬜ 미이행 (§12) |
| 테스트 케이스 코드 안 보고 설명 | W3D3 #2 → W3D4 | ⬜ 미착수 |
| `UNKNOWN` 쓸이 배치 | W3D2 이월 | ⬜ 스코프 밖 — 계속 이월 |

## 2. 무엇을 보장할지부터 정했다

두 목표가 서로 다른 해법을 부른다:

- **(가)** *"한 줄은 정확히 한 정산에 정확히 한 번 들어간다"* — 증발도 중복도 없다
- (나) *"어느 날에 들어가는지는 흐려져도 되니 증발만 안 하면 된다"*

**(가)를 골랐다.** 그 순간 W3D3 §4의 표가 깨진다 —

| | (가) 시간으로 자른다 *(W3D3 채택)* | (나) 상태로 자른다 |
|---|---|---|
| 늦게 커밋된 줄 | **증발** | 다음 배치가 주움 |
| "26일자 매출"의 뜻 | 깨끗함 | **흐려짐** |

이 표대로면 "증발 없음"과 "뜻이 깨끗함"은 배타적이고, (가)는 **불가능**하다.
표가 틀렸거나 (가)가 불가능하거나 둘 중 하나였다.

## 3. 표가 틀렸다 — 두 다이얼을 하나로 묶어 그렸다

배치의 `WHERE` 한 줄이 **서로 다른 두 질문에 동시에 답하고 있었다**:

| 질문 | 답하던 것 | 시계 |
|---|---|---|
| 이 장부 줄은 **언제 귀속되는가** | `created_at` | persist 때 **멈춘다** |
| 이 줄을 **이미 셌는가** | `created_at` (같은 컬럼!) | 커밋 때 **움직인다** |

시계가 둘인데 컬럼이 하나였다. 그래서 없던 세 번째 칸이 나온다:

| | (가) 시간 | (나) 상태 | **(다) 둘을 나눈다 ✅** |
|---|---|---|---|
| 귀속 날짜 | `created_at` | 배치 실행일 | **`created_at`** |
| 셌는지 여부 | `created_at` | 표식 | **표식** |
| 늦게 커밋된 줄 | 증발 | 다음 배치가 주움 | **다음 배치가 주움 — 제 날짜로** |
| "26일자 매출"의 뜻 | 깨끗함 | 흐려짐 | **깨끗함** |

**(나)가 뜻을 흐린 건 상태로 잘라서가 아니라 주운 줄을 주운 날에 넣었기 때문이다.**
축을 나누면 그 대가가 사라진다. W3D3이 (나)를 기각한 사유는 (나)의 필연이 아니라 (나)를
그렇게 그린 탓이었다.

### 아웃박스는 왜 이 구멍을 안 겪었나

`OutboxRepository.findUnpublished` 는 시간을 **안 쓴다** — `publishedAt IS NULL` 뿐이다.
아웃박스엔 **축이 하나**고, 이벤트는 *어느 날에 속하지 않는다.* 그래서 구멍이 안 생긴다.

정산은 축이 둘이라 그 패턴을 그대로 못 쓰고, **"아웃박스 축 + 귀속 축"** 이 된다.

## 4. 표식의 역할 — 집계 대상이 아니라 "다시 볼 날짜"

표식이 할 수 있는 일이 둘이고 대가가 정반대다:

| 표식의 역할 | 쓰는 값 | 재실행 정책 |
|---|---|---|
| **집계 대상을 정의**(안 센 줄만 더한다) | 델타 | **누적**이어야 함 — 덮어쓰면 이미 센 걸 날린다 |
| **재실행할 날짜만 알려줌 ✅** | 그 날짜 전체 | **덮어쓰기 유지**(W3D3 §5 그대로) |

**후자를 골랐다.** 그 선택이 산 것:

- **표식이 정확성의 임계 경로 밖으로 나갔다.** 전체 재집계 + 덮어쓰기라 몇 번 돌려도 같은
  값이다 → **표식이 틀려도 금액은 안 틀린다.**
- 전자였으면 *집계한 줄과 표시한 줄이 정확히 같아야* 해서 둘의 원자성이 필수였다.
- W3D3 §5가 누적을 기각한 사유(*"재실행이 이중계상"*)를 다시 다툴 필요가 없다.
- **`V10`의 backfill 이 안전하다.** 마지막 `INSERT ... SELECT id FROM journal` 한 줄이,
  누적이었으면 **전체 이중계상**이었다.

### 미리 닫힌 반론 — "그냥 최근 3일씩 다시 돌리면?"

전체 재집계 + 덮어쓰기라 **실제로 된다.** 코드 한 줄이면 된다.
대가는 **3일 넘어 커밋된 줄은 여전히 증발**한다는 것 — 즉 lookback 은 (가)가 아니라
*"3일 안이면 보장"* 이다. **표식의 값어치는 그 N을 유한에서 무한으로 바꾸는 것** 하나로
정확히 좁혀진다. (가)를 골랐으니 값을 한다.

덤: 표식은 *"이 날짜에 안 센 줄이 없다"* 는 신호를 준다. lookback 은 안 준다. W3D3 §5의
전제(*"아직 아무에게도 통보 안 함"*)가 깨지는 날, **확정 시점을 물을 수 있는 건 표식 쪽뿐**이다.

## 5. 남은 구멍 하나와 `REPEATABLE READ`

배치가 하는 일이 이제 둘이다 — **집계해서 쓴다**, **표식을 찍는다**.

```
① SELECT ... 26일 범위 전체를 집계 → settlement 덮어씀
                    ← 이 사이에 26일자 줄 하나가 커밋되면?
② DELETE ... 26일 범위 전체의 표식
```

그 줄은 **①에 안 들어갔는데 ②에서 표식이 지워진다.** 다시는 아무도 안 본다 —
**증발이 부활한다.** 구멍의 크기만 하루에서 몇 밀리초로 줄고 성질이 같다.

**`READ COMMITTED`(Postgres 기본)는 문장마다 새 스냅샷을 뜬다.** 한 트랜잭션에 넣어도 그렇다.
**`REPEATABLE READ`** 는 트랜잭션의 **첫 문장**에서 뜬 스냅샷을 이후 모든 문장이 재사용하므로,
그 사이 커밋된 줄이 ②에도 **안 보인다** → 표식이 남고 다음 배치가 제 날짜로 줍는다.

### 두 오류 방향은 대칭이 아니다

| 잘못 | 결과 | |
|---|---|---|
| 안 셌는데 "셌다"(표식을 잘못 지움) | 그 날짜를 다시 안 봄 → **증발** | **치명** |
| 셌는데 "안 셌다"(표식이 남음) | 같은 값을 다시 씀 | 무해 |

그래서 표식 삭제가 정산 쓰기와 **같은 트랜잭션**이어야 한다. 그리고 이 비대칭이 보증 하나를
공짜로 준다 — **RR 직렬화 실패로 트랜잭션이 통째로 롤백돼도 (가)는 안 깨진다.** 표식도 안
지워져 *"안 셌다"* 로 떨어지고 다음 배치가 줍는다. **피해가 증발이 아니라 지연이다.**

### RR을 고른 대가

RR은 충돌을 **막지 않고 에러로 만든다**(`40001 could not serialize access`). 지금은 배치가
단일 인스턴스(`NON_CLUSTERED`)고 장부가 append-only 라 경쟁자가 없어 안 터지지만,
**"안 생기게 설계했다"가 아니라 "아직 조건이 안 됐다"** 다. 재시도는 아직 없다(§12).

### ★ "표식은 집계 뒤에"는 RR 하에서 일을 안 한다

같은 스냅샷을 쓰면 ①과 ②가 **정확히 같은 줄 집합**을 보므로 순서를 뒤집어도 결과가 같다.
순서가 실제 방어인 건 `READ COMMITTED`일 때다. 즉 방어가 **두 겹 들어갔고 겹친다.**

겹치는 게 나쁘진 않다 — 격리 수준은 설정 한 줄이라 조용히 되돌아갈 수 있고 그때 순서가
백스톱이 된다. **다만 "무엇이 실제로 막고 있는가"는 하나로 적어야 한다**: **`REPEATABLE READ` 하나다.**
(W3D2에서 `confirm()` fast-path와 조건부 UPDATE를 두 겹으로 정확히 갈라 적었던 것과 같은
자리 — 그때 한 겹만 찍어서 음성대조군 대상이 틀렸었다.) 음성대조군 C가 이 단정을 겨눈다.

## 6. 구현 — `V10` 과 진입점 교체

| 결정 | 고른 것 | 왜 |
|---|---|---|
| 표식 위치 | **별도 테이블** `settlement_pending` | `journal`/`ledger_entry` 에 UPDATE 되는 컬럼을 달면 append-only(W2D1 §5)와 정면충돌. **장부 바깥으로 내보내 규율을 한 글자도 안 건드린다** |
| 모양 | **pending 큐**(처리하면 DELETE) | 아웃박스와 같은 모양 → 새 개념 0. 테이블이 거의 항상 비어 있다 |
| 쓰는 주체 | **트리거** | 앱(`LedgerService` 두 곳)에 두면 journal 생성 경로가 새로 생겼을 때 **잊을 수 있고 그 누락이 조용하다**. 트리거는 잊는 게 불가능하다. 대가는 쓰기가 코드에서 안 보이는 것 — 전례 있음(`V5 trg_journal_balanced`) |
| 날짜 컬럼 | **안 둔다** | 담으면 트리거 SQL 에 `'Asia/Seoul'` 이 박혀 **`ZONE` 의 거처가 둘**이 된다(V8이 못박은 것). `journal_id` 만 들고 변환은 자바가 한다 |
| 진입점 | **`runPending()`** | 날짜를 *계산*하는 게 아니라 *물어본다*. `settleYesterday()` 삭제 |

### `SettlementRunner` 가 별도 빈인 이유 — 프록시 경계

`@Transactional(isolation = REPEATABLE_READ)` 는 **스프링 프록시를 통과할 때만** 적용된다.
반복문을 `SettlementService` 안에 두면 `this.settle(...)` 이 되어 프록시를 안 거치고,
**격리 수준이 조용히 무시된다** — 바깥 기본값(`READ COMMITTED`)으로 돌면서 오늘 닫은 구멍이
그대로 다시 열린다. **컴파일도 되고 테스트도 대부분 통과하는 종류의 실패다.**

`SettlementRunner` 에 `@Transactional` 이 **없는 것도 판단**이다. 붙이면 (1) 날짜 하나의 실패가
나머지를 다 막고 (2) 스냅샷이 하나로 합쳐져 날짜별 경계가 흐려진다. **날짜 하나가 트랜잭션 하나.**

### 실측 — `SettlementConcurrencyTest` 3케이스 (전체 83 → 86건 0실패)

```
[실측] 밀린 날짜=[2026-07-28] 처리=[2026-07-28] → 정산행=[2026-07-28:9500]
[실측] 늦게 온 줄 → 밀린 날짜=[2026-07-28] 1차=9500 2차=19000 정산행=1
[실측] 스냅샷 → 살아남은 표식=1 배치직후=9500 재실행후=19000
```

**둘이 서로 다른 걸 증명한다:**

| | 재현하는 것 | 증명하는 것 |
|---|---|---|
| **①② 상태** | 배치가 지나간 **뒤에** 그 날짜 장부가 커밋된 상태 | 늦게 온 줄이 **제 날짜로** 주워진다 = 오늘의 목표 그 자체 |
| **③ 타이밍** | 배치의 **집계와 표식 삭제 사이**에 다른 커넥션이 커밋 | 둘이 **같은 스냅샷**을 본다 = RR 선택의 검증 |

①②만 있으면 `READ COMMITTED` 로 되돌려도 **안 깨진다**(그 구멍은 밀리초짜리라 순차 실행에선
안 밟힌다). ③만 있으면 오늘의 목표를 직접 안 겨눈다. **그래서 둘 다 있다.**

> ③의 `살아남은 표식=1` 이 **성공**인 게 직관에 거스른다. 표식이 안 지워진 게 옳은 이유는
> 그 줄이 **집계에도 안 들어갔기 때문**이다(`배치직후=9500`, B의 9,500이 빠져 있다).
> **둘이 짝이 맞는 게 핵심** — 한쪽만 일어나면 그게 증발이다.

## 7. ① 불일치 자동 플래그 — 먼저 발견 둘

**발견 1 — 대사는 아무도 안 부르고 있었다.** `ReconciliationService` 를 호출하는 프로덕션
코드가 **한 줄도 없었다**(테스트만 불렀다). W3D4는 비교 로직만 만들고 멈춰 있었다.
즉 ①은 *"결과를 저장한다"* 이전에 **"대사를 실제로 돌린다"** 가 먼저였다.

**발견 2 — 오늘 ②가 기존 대사 테스트를 안 깨뜨렸는데, 그게 정보다.**
`ReconciliationTest.배치_뒤에_들어온_장부_줄을_잡아내고_재실행이_메운다()` 는 그대로 통과했다.
그 테스트가 `settlementService.settle(today)` 를 **손으로** 부르기 때문이다 — 새 진입점
`runPending()` 을 안 쓴다. 프로덕션에선 이제 그 불일치가 **안 생긴다.**

## 8. 저장 여부보다 수명이 먼저였다

W3D3 §1의 기준(*복제냐 별개의 사실이냐*)을 대사 결과에 대면 애매하다 — 다시 대사하면 같은
답이 나오니 파생 같다. **갈라주는 건 시간이다**: 원천이 바뀌면 답도 바뀐다(배치 재실행이
불일치를 메운다).

특히 **오늘 ② 이후 `MISSING_IN_SETTLEMENT` 는 대체로 일시적이다**(다음 배치가 줍는다).
그래서 값어치 있는 건 *"지금 어긋나 있다"* 가 아니라 **"며칠째 안 메워진다"** 이고,
그건 **관측을 쌓아야만** 나온다.

| | (A) 상태 있는 행 | **(B) 매일 관측을 쌓기 ✅** |
|---|---|---|
| 행 | 불일치 1건당 1행 | 대사 1회 × 불일치 1건당 1행 |
| 해소 | `resolved_at` **UPDATE** | **다음 관측에 안 나타남** |
| append-only(W2D1 §5) | **깨진다** | 지켜진다 |

> W2D1 §5의 원래 맥락은 **장부**(금액의 진실을 다투는 기록)다. 이 플래그는 금액의 진실이
> 아니라 **운영 상태**라, 그 규율이 여기까지 미치는지는 자동이 아니라 판단이었다. 미치게 했다.

### ★ (B)의 대가 — "안 나타남"이 두 가지를 뜻한다

*대사가 돌았는데 깨끗했다* vs *대사가 그 날짜를 아예 안 봤다.* 못 가르면 **"미해소 날짜"
목록을 만들 수 없고**, 그게 날짜 출처 중 하나라 시스템이 성립하지 않는다.

→ **`reconciliation_run`(실행 기록)이 부재에 뜻을 준다.** 불일치 0건이어도 행이 남는다.

> W3D4의 `ONLY_IN_INTERNAL` 이 *"아직 안 온 것"* 과 *"영영 안 올 것"* 을 못 가른 것과
> **정확히 같은 모호함**이다. 거기선 못 풀었고 여기선 기록으로 풀었다.

## 9. ★ 날짜 출처가 셋 — 셋 다 다른 걸 잡는다

처음 답은 *"정산이 돈 날짜를 넘겨받는다"* 하나였는데, **그것만으로는 "며칠째"가 1에서 멈춘다**:

```
D일 불일치 발생 (배치는 정상적으로 D를 돌았고 pending 도 비웠다)
다음날  runPending() → D는 밀린 게 없으니 목록에 없다 → 대사도 D를 안 본다
```

**불일치가 있다고 pending 이 남아 있는 게 아니다** — W3D3 §8의 부호 버그가 정확히 그
모양이었다(배치는 정상적으로 돌았고 표식도 제대로 지웠는데 값이 틀렸다).

| 출처 | 잡는 것 |
|---|---|
| **① 정산이 방금 돈 날짜** | 재정산된 **오래된 날짜**(최근 창 밖). 배치는 밀린 날짜를 아무리 과거라도 돈다 |
| **② 미해소 불일치가 있는 날짜** | 해소될 때까지 **스스로 살아남는다.** `settlement_pending` 과 같은 모양 |
| **③ 최근 7일** | **아무도 안 돈 날** |

### ③이 있는 이유 — 상관 실패를 끊는다

①만 두면 대사가 **감시 대상에게서 볼 목록을 물려받는** 꼴이 된다:

```
트리거가 죽는다 → pending 행 없음 → runPending() → [] → 정산 안 됨
                                                   ↓
                              대사도 볼 날짜가 없음 → 불일치 0건 → 초록불
```

**모든 장부가 조용히 증발하는데 대사는 "이상 없음"이라고 답한다.**

W3D4는 *금액을 어떻게 계산하는가* 를 독립으로 만들었는데(같은 SQL 재실행 = 동어반복),
***무엇을 볼 것인가*** 는 여전히 감시 대상이 정하고 있었다. **초록불이 "옳다"가 아니라
"그 경로를 안 밟았다"는 뜻이 되는 자리**다(W3D3 §8과 같은 모양).

> `RECENT_WINDOW_DAYS = 7` 이 정하는 건 **감당할 최대 배치 중단 기간**이다. 늘리면 매일
> 재구성하는 비용이 늘고, 줄이면 감지 지연을 못 견딘다. **측정된 값이 아니다**(§12).
> 최근 창에서 **오늘을 뺀 것도 판단** — 아직 안 끝난 날이라 대사하면 매번 거짓 경보가 뜬다.

### 실측 — `DiscrepancyFlagTest` 4케이스 (전체 86 → 90건 0실패)

```
[실측] 깨끗한 대사 → run=1건 관측=0건 미해소날짜=[]
[실측] 불일치 → 관측=1건 type=AMOUNT_MISMATCH 차액=-9500 미해소날짜=[2026-07-31]
[실측] 해소 → 대사대상=[07-24 … 07-31] run=2건 최신깨끗=true 누적관측=1건 미해소=[]
[실측] 최근 창 → 대사대상=7건 관측=1건 type=MISSING_IN_SETTLEMENT 재구성=9500
```

**해소 케이스의 대사 대상이 8건인 게 설계 확인이다.** 최근 창은 `07-24`~`07-30` 7일이고
오늘(`07-31`)은 일부러 뺐는데도 목록에 있다 — **출처 ②가 스스로 올린 것**이다.
그리고 `누적관측=1` 은 해소된 뒤에도 **옛 관측을 안 지운다**는 실측이다(append-only).

**최근 창 케이스는 정산을 한 번도 안 부른다.** 그게 트리거가 죽은 상황의 재현이고,
출처 ③이 그걸 끊는다는 증거다.

## 12. 정직한 한계 / 이월

**오늘 만든 것이 검증 안 한 것**
- **프로덕션 배치가 실제로 RR로 도는지 아무 테스트도 안 본다**(§11 B). 타이밍 케이스가
  `TransactionTemplate` 으로 직접 격리 수준을 걸기 때문이다
- **RR 직렬화 실패(`40001`) 재시도 없음.** 지금은 `NON_CLUSTERED` + append-only 라 경쟁자가
  없어서 안 터진다 — *안 생기게 설계한 게 아니라 아직 조건이 안 됐다.* W3D3 이월 ③과 같은 자리
- **상태 재현(①②)은 커밋 가시성을 진짜로 재현하지 않는다** — `created_at` 을 손으로 과거로
  찍는 시뮬레이션이다. 진짜 가시성은 케이스 ③이 본다
- **`RECENT_WINDOW_DAYS = 7` 은 측정된 값이 아니다.** "주말 낀 장애를 넘긴다"에서 나왔다
- **`reconciliation_run.discrepancy_count` 는 관측을 세면 나오는 파생이다.** "깨끗한 run"이
  압도적 다수라 매번 조인을 피하려고 뒀다 — W3D3 §1 기준으로는 복제 쪽에 가깝다
- **외부 축(`PgDiscrepancy`)은 아직 기록 안 한다.** 키 모양이 달라 테이블을 따로 두기로 했고
  오늘은 내부 축까지다
- **Quartz cron 발화는 여전히 미검증**(W3D3 이월 ①). 오늘 `SettlementBatchJob` 이 두 러너를
  부르도록 바뀌었는데 그 배선도 같이 미검증이다 — 테스트는 러너를 직접 부른다
