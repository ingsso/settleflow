## 2. 핵심 설계 판단 — "무엇을, 왜"

| 판단 | 근거 한 줄 | 출처 |
|---|---|---|
| **트랜잭셔널 아웃박스** | 이벤트를 장부와 같은 tx 에 써서 dual-write 소멸 — "진실은 하나"의 세 번째 적용(W1D3·W2D4에 이어) | W3D1 |
| `outbox.published_at` UPDATE 는 append-only 위반이 아니다 | **진실 vs 전송 큐** 를 가름. W3D5 `settlement_pending` 이 이 논거를 그대로 물려받는다 | W3D1 |
| **보상 트랜잭션을 구현하지 않고 소거** | 역분개를 PG 확인 뒤로 미루니 *취소할 장부 기록이 애초에 없다* | W3D2 |
| 그런데 **예약은 안 미뤘다** | 조건부 UPDATE 가 판정 그 자체라, 미루면 판정할 근거가 없어 동시 환불이 전부 통과 | W3D2 |
| 정산액은 **저장**한다 | W1D3·W2D4에서 두 번 기각한 저장을 채택 — 구분선은 *복제냐 별개의 사실이냐*. **파생이 안전하려면 언제 물어도 같은 답이어야 하는데 정산액엔 그 성질이 없다** | W3D3 §1 |
| 집계 원천 = **장부** | 환불의 날짜 귀속이 공짜로 따라온다(역분개가 찍힌 날 자동 차감) | W3D3 §2 |
| V8 에 CHECK 을 **하나도 안 건다** | `settlement == SUM(ledger)` 는 *어긋날 수 있는* 관계 → **제약은 절대 어긋나면 안 되는 것에, 대사는 어긋날 수 있는 것에** | W3D3 §6 |
| 대사는 **같은 SQL 을 재실행하지 않는다** | 배치 쿼리를 다시 돌리면 동어반복(가계부를 두 번 읽는 것) → 원천을 `payment`+`refund` 로 | W3D4 §4-2 |
| 조인 키 `pg_transaction_id` → **`merchant_payment_id`** | 전자는 웹훅 경로에만 채워져 동기 승인엔 null — **계획서·W3D1 상정이 성립 안 함** | W3D4 §5-3 |
| 라벨의 원천을 예약 → **확정**으로 | 한 컬럼이 *가드*(예약 포함해야 정확)와 *라벨*(빠져야 정확)을 겸할 수 없다 | W3D4 §2 |
| **귀속 축과 진행 축을 분리** | `WHERE` 한 줄이 *"언제 귀속되냐"*(멈춘 시계)와 *"이미 셌냐"*(움직이는 시계)에 동시에 답하고 있었다 | W3D5 §3 |
| 표식은 **집계 대상을 정의하지 않는다** | 전체 재집계+덮어쓰기 유지 → 표식이 틀려도 금액은 안 틀린다(정확성의 임계 경로 밖) | W3D5 §4 |
| 플래그는 **관측을 쌓는다**(상태 UPDATE 아님) | 값어치가 *"지금 어긋남"*이 아니라 **"며칠째 안 메워짐"** 에 있다 | W3D5 §8 |
| 대사의 **날짜 출처가 셋** | ①만 두면 대사가 감시 대상에게서 볼 목록을 물려받아, 트리거가 죽으면 **같이 눈을 감는다** | W3D5 §9 |

## 3. 검증한 것 vs 못한 것

**✅ 실측으로 검증**
- 아웃박스 Quartz 자동 발행(bootRun), 환불 Saga 3결과 → 3처리, 멱등 두 겹
- 정산 배치 6케이스(집계·환불차감·경계·멱등·복구·음수), 대사 내부 6 + 외부 5
- **주말 체크포인트 달성** — 불일치 3건 심고 **정확히 3건**, 종류도 하나씩
- **증발 구멍**: 뚫려 있을 때 대사가 잡고(`AMOUNT_MISMATCH[9,500 vs 19,000]`), 축 분리 후 제 날짜로 주워짐
- **`EXPLAIN` 3회 이월 숙제** — 날짜 단독 조회가 `Sort` 없이 인덱스를 타고, 셀러 인덱스를 지우면 12,000행 중 11,700행을 버린다
- **음성대조군 3회**(D3 부호 · D4 부호→대사가 잡나 · D5 A~D) — 전부 본인 실행·원복

**⬜ 못한 것 → W4 이월**

| 이월 | 승격/해소 트리거 |
|---|---|
| **프로덕션 `@Transactional(isolation=RR)` 미검증** | W3D5 §11 B 가 green 으로 확정. 테스트가 `TransactionTemplate` 으로 직접 걸어서 애노테이션을 안 지나간다 |
| **RR 직렬화 실패(`40001`) 재시도 없음** | 지금은 `NON_CLUSTERED`+append-only 라 경쟁자가 없다 — *안 생기게 설계한 게 아니라 조건이 안 됐다* |
| **Quartz cron 발화 미검증** | 새벽 2시라 bootRun 방식이 안 통한다. W3D1이 닫은 자리가 다시 열림 |
| `UNKNOWN` 쓸이 배치 없음 | W3D2부터 계속. 예약이 영영 잡힌 채 남는다 |
| Consumer DLT·재시도 정책 없음 | `[POISON]`·`[ORPHAN]` 로그 후 스킵뿐 |
| 외부 축(`PgDiscrepancy`) 기록 안 함 | 키 모양이 달라 테이블을 따로 두기로 함 |
| C축 대사(예약 ↔ 확정) 없음 | `UNKNOWN` 에 물린 예약을 아무도 안 본다 |
| 외부 축 **기준선 0건은 증명이 아니다** | Mock 리포트가 우리 DB 에서 나와 동어반복 — 진짜 PG 전까지 값은 *심은 불일치*에만 |

## 4. 반복된 패턴 (회고에서 뽑을 결)

- **★ "초록불은 코드가 옳다는 뜻이 아니라 경로를 안 밟았다는 뜻."** W3D3 §8이 처음 적었고(부호 제거에 4/6 통과), W3D5 에 **세 층위에서 반복**됐다 — **코드**(출처 ①만 두면 대사가 눈을 감고 초록불) · **음성대조군 절차**(D 를 겨누는 클래스를 필터에서 빼서 red 를 낼 능력 자체가 없었다) · **측정 하네스**(`seller_id=7` 이 실존 id 가 아니라 `rows=0`). 3주간 가장 값진 결.
- **"계획서의 전제를 근거를 갖고 폐기한다"가 3주 연속.** W1 재고 Redis 락 → W3D2 보상 트랜잭션 → W3D4 조인 키. 이번엔 **계획서가 상정한 컬럼이 그 경로에서 채워지지도 않는다**는 걸 코드에서 확인한 것.
- **한 컬럼이 둘을 겸하면 갈라진다.** `refunded_amount`(가드 vs 라벨, W3D4) → `created_at`(귀속 vs 진행, W3D5). **같은 모양이 한 주에 두 번.**
- **"제약 vs 대사"의 분업**이 W3의 축. 절대 어긋나면 안 되는 것엔 제약(W2D3 트리거), 어긋날 수 있는 것엔 대사. 후자를 제약으로 막으면 방어가 아니라 고장.
- **예측 선기록의 값은 맞은 칸이 아니라 어긋난 칸에서 나온다.** W3D2에서 붙었다 W3D3에 빠졌고 W3D5에 복원됐다 — 복원한 회차에서 A(예측 갈림)와 D(둘 다 빗나갔는데 원인이 코드가 아니라 절차)가 값을 냈다.
- **미이행 숙제의 수명이 길다.** `EXPLAIN` 3회 이월 후 닫힘, 재설명(#2)은 W3D3부터 **3세션 연속 미착수**, "AI 제안 거부/수정"은 **5세션 넘게 0건**.
