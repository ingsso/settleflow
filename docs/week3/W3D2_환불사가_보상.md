## 1. 가장 큰 판단 — 보상 트랜잭션을 *구현*하지 않고 *필요 없게* 만들었다

계획서가 요구한 건 "환불 실패 시 롤백"이었다. 그런데 롤백해야 할 대상을 먼저 봤다.

W2D5 까지 `requestRefund` 는 한 트랜잭션에서 **금액 누적 + refund 행 + 역분개 journal + 이벤트**를 전부 커밋했다. PG 환불 호출은 아예 없었다(`PgClient` 에 `approve()` 뿐). 즉 **돈이 실제로 돌아갔는지 확인하기도 전에 장부에 역분개를 써놓은 상태**였다. 오늘 consumer 가 PG 를 부르기 시작하면 이게 드러난다 — PG 가 거절하면 장부는 이미 돌려준 걸로 적혀 있다.

두 길이 있었다:

| | 선반영 + 보상 | **미룸(채택)** |
|---|---|---|
| 역분개 시점 | 요청 시 | PG 확인 뒤 |
| 실패 처리 | **보상 분개**로 상쇄 | 안 적는다 |
| 장부에 남는 것 | 역분개 + 보상분개(상쇄쌍) | 아무것도 없음 |
| 대사(W3D4) 부담 | 상쇄쌍을 이해해야 함 | 없음 |
| 대가 | 장부가 잠깐 거짓말 | 환불이 비동기가 됨 |

**미루기를 택했다.** 선반영은 *장부가 평시에 거짓말하고 나중에 정정하는 것*을 정상 경로로 만든다. W1D1 §5 의 append-only 는 "지우개가 아니라 빨간 펜"인데, 빨간 펜은 **사람의 실수**를 위한 도구지 기계의 평상시 동작이 아니다. 정정이 흔해지면 정정의 의미가 사라진다.

그래서 오늘 산출물에 "보상 분개"가 없다. **안 적었으니 지울 것도 없다** — 계획서의 "롤백"은 구현이 아니라 *소거*로 답했다.

## 2. 그런데 하나는 미루면 안 됐다 — 예약과 기록의 분리

`payment.refunded_amount` 누적까지 미루면 **W1D2 에서 실측한 레이스가 되살아난다.** 10,000 결제에 5,000 환불 요청이 동시에 셋 오면, PG 확인 전까지 `refunded_amount` 가 0 이라 셋 다 잔액 가드를 통과한다.

그 조건부 UPDATE 는 가드가 *아니라* **판정 그 자체**다 — `addRefundedAmount(...) == 0` 이 곧 거절 사유고, 읽고-판단하고-쓰는 틈이 없어 레이스가 성립할 자리가 없다. 미루면 "가드가 잠시 약해지는" 게 아니라 **판정할 근거가 아직 존재하지 않는** 상태가 된다.

그래서 갈랐다:

| | 시점 | 성격 |
|---|---|---|
| `refunded_amount` 누적 | 요청 | **예약** — 잔액을 잡아둔다 |
| 역분개 journal | PG 확인 뒤 | **기록** — 실제로 일어난 일 |

**이 패턴은 이미 프로젝트에 있었다.** `InventoryService` 가 주문 생성 시 재고를 원자적으로 깎아두고(`decrease`), 결제가 안 되면 되돌린다(`restore`). W1D3 §2 가 "Redis 가 풀던 건 동시성이 아니라 시한부 예약"이라며 DB 원자 UPDATE + 배치 복원으로 갈아탄 그것이다. 발명이 아니라 **이식**이다.

**대가**: `refunded_amount` 의 의미가 "환불된 금액"에서 **"환불된 + 진행중인 금액"**으로 바뀌었다. W2D4 의 `refundStatus()` 가 여기서 파생되므로, PG 응답 대기 중인 결제가 이미 `PARTIAL_REFUNDED` 로 보인다. 컬럼을 둘로 쪼개면(`reserved`/`refunded`) 정확해지지만 **값이 둘이 되고 둘 사이 불변식을 앱이 지켜야 한다** — W1D3(재고 진실 둘)·W2D4(환불 상태 저장)에서 두 번 기각한 모양이라 안 쪼갰다. 재고도 별도 `reserved_stock` 없이 `stock` 하나를 깎는다.

## 3. 세 결과, 세 처리 — UNKNOWN 이 핵심

`PgClient.refund` 는 승인 경로와 같은 3결과 계약이다(승인/거절은 `PgRefundResult` sealed, 타임아웃은 `PgTimeoutException`).

| PG | 장부 | 예약 | 상태 | 이벤트 |
|---|---|---|---|---|
| 승인 | 역분개 INSERT | 유지 | `COMPLETED` | `refund.completed` |
| 거절 | 건드리지 않음 | **해제** | `FAILED` | 없음 |
| 무응답 | 건드리지 않음 | **유지** | `UNKNOWN` | 없음 |

**무응답에 예약을 풀면 이중환불이 열린다.** PG 는 실제로 환불했는데 잔액만 되살아나 같은 돈을 또 내보낼 수 있다. 이건 W1D5 에서 이미 한 번 데인 구멍이다 — 쓸이 배치가 재고를 성급히 복원했더니 늦은 승인 웹훅이 도착해 **이중판매**가 열렸고, 결론이 이거였다:

> 복원은 **시간의 문제가 아니라 사실 확인의 문제**다.

그래서 `RefundPgStatus` 가 4상태다. `PaymentStatus` 가 4상태인 이유(W1D1 §3 — 타임아웃은 실패가 아니라 정보의 부재)가 환불에 그대로 온다. `UNKNOWN` 을 `FAILED` 와 같은 칸에 두는 순간 이 구분이 사라진다.

## 4. 소비자 멱등 — UNIQUE 가 아니라 조건부 UPDATE

처음엔 `refund.event_id UNIQUE` 를 생각했는데 **성립하지 않는다**. UNIQUE 는 INSERT 충돌을 막는 장치인데 **소비자는 INSERT 를 안 한다** — `refund` 행은 요청 시점에 이미 만들어져 있고 소비자는 그걸 *갱신*할 뿐이다. W1D4 의 SETNX 가 통했던 건 웹훅 핸들러가 키를 **직접 만들었기** 때문이고, 여기엔 그 대칭이 없다.

그래서 멱등을 영향 행 수에 건다:

```sql
UPDATE refund SET pg_status='COMPLETED', journal_id=?, pg_refund_id=?, confirmed_at=now()
 WHERE id = ? AND pg_status = 'REQUESTED'    -- 0행 = 이미 처리됨
```

`addRefundedAmount`·`decreaseStock` 이 쓴 것과 같은 패턴이고, **상태(§5)와 멱등이 한 컬럼을 공유한다** — 둘이 같은 문제였다.

넷을 **한 문장**에 넣은 것도 의도다. 쪼개면 그 사이에 V7 의 `chk_refund_journal_matches_status`(COMPLETED ⇔ journal 있음)를 위반하는 중간 상태가 생긴다.

방어는 두 겹이다: `confirm()` 진입부의 상태 확인이 **fast-path**(PG 를 두 번 부르지 않는다 — 돈이 두 번 나가는 걸 막는 게 여기), 조건부 UPDATE 가 **최종 보증**. W1D4 에서 SETNX 가 fast-path 이고 낙관적 락이 최종 보증이었던 것과 같은 구조.

## 5. `refund` 에 mutable 칸을 연 근거

`Refund` 는 append-only 였다(`updated_at` 도 일부러 없음). 그런데 `pg_status`·`journal_id`·`pg_refund_id`·`confirmed_at` 이 나중에 채워진다.

**W3D1 §3 에서 세운 잣대를 두 번째로 적용했다.** 거기서 `outbox.published_at` 을 UPDATE 하는 게 append-only 위반이 아니라고 판정한 근거는 *"아웃박스는 재무 진실이 아니라 전송 큐"* 였다. 같은 질문을 던지면 — **재무 진실은 `journal` 이 갖고, 이 칸들은 그 진실이 언제·어떻게 확정됐는지를 나르는 메커니즘**이다. 금액·결제·요청시각(무슨 환불이 요청됐나)은 여전히 한 번 쓰고 고치지 않는다.

**세터는 열지 않았다.** 전이는 전부 리포지토리의 조건부 UPDATE 로만 일어나고 엔티티 필드는 `updatable = false` 다 — W2D5 에서 journal 을 세터가 아니라 생성자로 받은 판단("규율이 아니라 벽")의 연장.

DB 쪽엔 CHECK 을 세웠다. `(pg_status='COMPLETED') = (journal_id IS NOT NULL)` — **양방향**이라 "확정했는데 장부에 안 적음"과 "안 일어난 일이 장부에 적힘"을 둘 다 막는다. 후자가 오늘 없애려던 바로 그것이다.

## 6. 이벤트 재배치 — fat 스냅샷이 `completed` 로 갔다

역분개를 미루자 **요청 시점엔 비출 거울이 없어졌다.** `RefundRequestedEvent.from()` 은 셀러별 안분을 *방금 만든 journal 의 줄에서 거울처럼* 읽고 있었는데, 그 journal 이 없다.

안분을 미리 계산해 담는 길도 있었지만 그러면 결과가 journal 과 별개로 존재하게 되어 **"재계산이 아니라 거울처럼 읽는다"는 W3D1 §4 의 핵심 방어가 무너진다** — 이벤트와 장부가 갈라질 문이 다시 열린다.

- `refund.requested` → **thin**(`paymentId`/`refundId`/`amount`). 담을 게 없는 게 아니라 **아직 사실이 아닌 것을 담지 않는** 것.
- `refund.completed` → **fat**(+ `sellers`/`refundStatus`/`pgRefundId`). journal 이 실제로 만들어지는 유일한 지점이라 거울 규칙을 지킬 수 있다.

부수 효과로 **이름과 내용이 일치하게 됐다.** W3D1 판 javadoc 이 *"requested 인데 이미 장부 반영이 끝났다?"* 고 스스로 변명하던 자리가 사라졌다.

## 7. 실측 (`RefundSagaTest` 8케이스, 실제 Kafka Testcontainers)

| 케이스 | 관측 |
|---|---|
| 요청만 | REFUND journal **0** · journal연결 **0** · 예약 **5,000** · `pg_status=REQUESTED` |
| PG 승인 | `COMPLETED` · REFUND journal **1** · 확정액 **5,000** · `pg_refund_id=pgr-7` |
| ↳ `refund.completed` | `{"amount":5000,"sellers":[{"amount":5000,"sellerId":5}],"pgRefundId":"pgr-7","refundStatus":"PARTIAL_REFUNDED"}` |
| **PG 거절** | `FAILED` · 예약 **5,111→0** · REFUND journal **0** · 줄 **0** · `refund.completed` **0** · refund행 **1** |
| 거절 후 재환불 | 19,111 거절 해제 뒤 20,000 재요청 → **Accepted** · 예약 20,000 |
| PG 무응답 | `UNKNOWN` · 예약 **5,222 유지** · REFUND journal **0** |
| 멱등(3회) | `COMPLETED/COMPLETED/COMPLETED` · REFUND journal **1** · 줄 **2** · 환불액 **5,000** · `refund.completed` **1** |
| 거절 멱등(2회) | `FAILED` · 남은 예약 **3,000**(다른 환불 몫만) |
| **리스너 자동 소비** | 아무것도 부르지 않고 대기 → `pg_status=COMPLETED` · REFUND journal **1** |

- **미룸의 증명**: 요청만으로 REFUND journal 이 **0**. W2D5 였다면 1 이었다.
- **보상이 없다는 증명**: 거절 후 journal **0**, ledger 줄 **0**. 상쇄쌍조차 안 남는다.
- **예약 해제가 진짜다**: 19,111 거절 뒤 20,000 재환불이 **통과**. 상태만 FAILED 로 바꾸고 금액을 안 풀었다면 잔액 889 라 거부됐을 것.
- **무응답은 아무것도 안 건드린다**: 예약 5,222 가 그대로. 여기가 이중환불 구멍이었다.
- **멱등**: 3회 처리에 journal **1**, 환불액 **5,000**(15,000 아님) — 조건부 UPDATE 가 2·3회차를 0행으로 끊었다.
- **예약이 동시성을 여전히 막는다**(`RefundConcurrencyTest`): 10스레드×5,000 → ACCEPTED **4** · refunded **20,000** · REFUND journal **4**. 예약까지 미뤘다면 10건 전부 통과했을 것.

### 음성대조군 — 멱등 두 겹을 다 제거 *(본인이 직접 실행, 6세션 만에 첫 이행)*

제거 대상은 §4 의 두 겹 전부: `RefundConfirmService.confirm()` 의 fast-path 조건문 + `RefundRepository` 세 쿼리의 `AND pg_status = 'REQUESTED'`.

**예측(제거 전 기록)**: 멱등 2건 red, `journal 3`.
**결과**: 8건 중 **2건 red**, `journal=3` — 예측대로.

```
3회 처리 → REFUND journal=3  줄=6  환불액=5,000  refund.completed=3
```

세 가지가 드러났다.

1. **진짜 피해는 journal 개수가 아니다.** `환불액=5,000` 이 <b>안 변했다</b> — `refunded_amount` 는 요청 시점에 한 번 예약되고 `applyCompleted` 는 그걸 안 건드리기 때문이다. 그래서 실제로 벌어진 일은 **장부는 15,000 환불됐다 하고(6줄 × 5,000) 예약은 5,000 이라 하는** 드리프트다. 가드가 막고 있던 건 "journal 이 3개가 되는 것"이 아니라 **§2 에서 갈라놓은 예약과 기록이 서로 어긋나는 것**이었다. W1D3 부터 계속 죽여온 "진실이 둘"이 정확히 여기서 되살아난다.

2. **거절 경로는 틀린 숫자가 아니라 예외로 터졌다.**
   ```
   IllegalStateException: 예약 해제 실패 refundId=1 paymentId=1 amount=5111
   ```
   `releaseRefundedAmount` 의 `AND refunded_amount - :amount >= 0` 하한이 잡았다 — 5,111 을 두 번 풀려니 남은 3,000 에서 뺄 수 없어 0행. 언더플로 백스톱이 실제로 발동한 것이고, **이중 해제가 조용히 음수가 되는 대신 시끄럽게 멈춘다**. W2D3 의 앱 가드 + DB 제약 이중방어와 같은 결이되, 아래층이 내놓는 건 "올바른 값"이 아니라 "정지"다.

3. **나머지 6건은 통과했다.** W2D5 음성대조군과 같은 모양(*2건 빨간불인데 나머지 5건은 통과*) — 가드가 자기 자리만 정확히 지킨다는 뜻이자, **이 2건이 없으면 이 회귀를 아무도 못 잡는다**는 뜻이다.

> 제거 대상 지정이 처음엔 부정확했다. "가드 하나"로 §4 ②만 찍었는데 ①이 남아 있어 그것만으로는 red 가 안 나온다 — 두 겹이라는 걸 지정 단계에서 놓쳤다. 예측이 ①·② 둘 다 없는 상태를 상정한 것이라 대상을 둘로 고쳐 잡았다.

### 곁가지로 잡힌 설정 버그

`src/test/resources/application.yaml` 이 `ddl-auto: validate` 한 줄만 갖고 있었는데, **같은 파일명이라 메인 yaml 을 병합이 아니라 통째로 가리고 있었다** — 테스트에서 `spring.kafka.*` 가 아예 안 읽혔다. W3D1 이 안 터진 건 그 값들(String 직렬화)이 우연히 Boot 기본값과 같아서였고, `auto-offset-reset: earliest` 처럼 기본값(`latest`)과 다른 설정이 생기자 리스너가 이벤트를 못 받으며 드러났다. 파일을 지우고 `IntegrationTestSupport` 의 `@DynamicPropertySource` 로 옮겨 가림막을 없앴다.

## 8. 정직한 한계 / 이월

- **`UNKNOWN` 을 푸는 쓸이 배치가 없다.** 현재 `UNKNOWN` 은 보류일 뿐 종착지가 아닌데, PG 재조회로 진실을 채우는 경로가 없어 **예약이 영영 잡힌 채 남는다**(고객이 그만큼 재환불 불가). W1D3 의 미결제 쓸이 배치와 같은 자리 — 그 배치도 아직 없다.
- **Consumer DLT·재시도 정책 없음.** 진짜 장애(DB 다운 등)면 무한 재배달이다. 역직렬화 실패(`[POISON]`)와 refund 행 부재(`[ORPHAN]`)만 로그 남기고 넘기도록 막아뒀는데, 이건 파티션이 막히는 걸 피한 것이지 정책이 아니다.
- **`refund.completed` 소비자 없음.** 발행만 한다. 소비는 W3D4 대사가 한다.
- **동시 확정 경쟁(`ConcurrentRefundConfirmException`) 경로는 미검증.** 단일 소비자 + 파티션 키가 같아 실제로는 순차 배달이라 재현할 자연스러운 방법이 없었다. 코드는 있고 실측은 없다.
- ~~red-light 미이행~~ **이행됨** — §7 음성대조군 참조. 6세션 만에 처음으로 제거→실행→관측→원복을 본인이 전부 수행했고, **예측을 먼저 적고 대조**했다(예측대로 2건 red / journal 3). 남은 결은 예측이 못 맞힌 부분이다 — 피해의 *형태*(개수가 아니라 장부·예약 드리프트)와 거절 경로가 예외로 터진다는 것 둘 다 결과를 보고서야 알았다.
