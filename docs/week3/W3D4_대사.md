## 2. ⑦ `refunded_amount` 의미 변화 — 여기까지 왔다

### 2-1. 확인된 사실 (전부 코드에서 직접 확인)

`refunded_amount` 는 **환불됨 + 진행중 + 보류중**의 합이다.

| 환불 건의 `pg_status` | `refunded_amount` | 장부 |
|---|---|---|
| `COMPLETED` | 남음 | 역분개 있음 |
| `REQUESTED` | **남음** | 없음 |
| `UNKNOWN` | **남음** | 없음 |
| `FAILED` | 빠짐(`releaseRefundedAmount`) | 없음 |

`Payment.refundStatus()` 는 이 값과 `amount` 만 보고 라벨을 만든다 → **진행중·보류중을 환불된 것으로 센다.**

**프로덕션 호출부는 정확히 둘**
- `RefundController:58` — 환불 요청 201 응답 본문. 이 시점 그 건은 **반드시 `REQUESTED`** 다. 20,000 결제에 20,000 환불을 요청하면 **PG 를 부르기도 전에** 응답이 `REFUNDED`.
- `RefundCompletedEvent:50` — `refund.completed` fat 스냅샷. **한 이벤트 안에 기준이 둘이다** — `sellers` 는 journal 을 거울로 읽고(W3D1 §4 규칙) `refundStatus` 는 예약을 읽는다.

**일시적 오차가 아니다.** `UNKNOWN` 은 쓸이 배치가 없어(W3D2 이월) 영영 안 풀린다 → 라벨이 **영구히** 틀린 채 남는다.

### 2-2. 문제의 구조 — 한 컬럼이 서로 다른 값을 원하는 둘을 겸한다

| 쓰는 쪽 | 원하는 값 | 예약이 |
|---|---|---|
| **가드** (`addRefundedAmount` 의 `+ :amount <= amount`) | 잔여 한도 | **들어가야 정확** — 빼면 W1D2 레이스 부활(8,000 → 11,000) |
| **라벨** (`refundStatus()`) | 실제 환불된 정도 | **빠져야 정확** |

둘 중 하나만 맞을 수 있다. W3D2 §2 가 "대가"로 적어둔 게 이 자리이고, 본인 #2 자기보고대로 **선택한 게 아니라 넘어간 것**이었다.

### 2-3. 오늘 내린 결정 ✅

**(1) 라벨의 의미 = "얼마나 환불됐나"** (본인 판단)
→ 가드는 예약을 포함해야만 정확하므로 **손대지 않는다. 라벨이 원천을 옮긴다.**

**(2) 원천은 A안 — 파생 유지** (본인 판단: *"파생 유지하는 게 맞을 것 같아"*)

확정 환불액 = `SUM(refund.amount WHERE pg_status = 'COMPLETED')`

기각한 대안:
- **B. `payment` 에 확정분 컬럼 추가(저장)** — W3D3 §1 의 *"복제냐 별개의 사실이냐"* 논리로 정당화는 되지만, 판정 기준을 세워놓고 매번 저장으로 기우는 것을 경계.
- **C. `refunded_amount` 를 확정분으로 되돌리고 예약을 새 컬럼으로** — 가장 정직하지만 **W1D2 에서 음성대조군으로 실측 검증된 유일한 SQL** 을 건드린다.

### 2-4. 제약 하나 — 장부에서 직접은 못 읽는다

`Journal` 에 payment 참조가 **없다**(`Journal.java` 필드는 `type`/`createdAt`/`entries` 뿐). 결제↔장부 연결은 `payment.journal_id` 와 `refund.journal_id` 쪽이 들고 있다.
→ *"이 결제의 확정 환불액을 장부에서 합산"* 은 결국 **`refund` 행을 경유**해야 한다. W3D3 처럼 "장부에서 바로 읽기"가 여기선 안 된다.

### 2-5. 이 판단이 오늘 대사에 준 것 — 축이 하나 더

```
refunded_amount − (확정 환불액) = PG 확인 대기중 + UNKNOWN 보류분
```

이 차이가 0 이 아닌 채로 오래 남으면 그게 **UNKNOWN 에 물린 예약**이다.
→ **대사가 W3D2 이월(`UNKNOWN` 쓸이 배치 없음)을 매일 드러내는 장치가 된다.** 고치진 못해도 보이게는 된다 — W3D3 §8 ③ 의 *"과지급은 아무도 신고하지 않는다"* 와 같은 종류의 침묵을 하나 더 깨는 자리.

### 2-6. A 로 옮기면 즉시 나오는 문제 ⚠️

`RefundController:58` 이 **반대 방향으로 틀린다.**

- 지금(예약 기준): 20,000 결제에 20,000 환불 요청 → `REFUNDED` — **과대**
- A 이후(확정 기준): 방금 만든 건은 `REQUESTED` 라 확정합에 안 들어감 → `NOT_REFUNDED` — **과소**

**어느 라벨을 줘도 틀린다 = 그게 이 자리의 진짜 정보가 아니라는 뜻.**
W3D2 가 환불을 Saga 로 쪼갠 순간 이 응답의 성격이 "결과"에서 **"접수증"**으로 바뀌었는데 본문만 옛 성격을 유지하고 있다.

> `RefundCompletedEvent:50` 은 반대로 A 가 깔끔히 맞는다. `RefundConfirmService.applyCompleted` 에서 `markCompleted` **다음에** `outboxWriter.append` 가 오므로 그 시점 자기 건은 이미 COMPLETED → 확정합에 포함된다. 그리고 `sellers`(journal 거울)와 `refundStatus`(확정합)가 **드디어 같은 기준**을 본다(§2-1 의 "기준이 둘" 해소).

## 3. ⑦ 구현 — 결정 셋과 그 결과

### 결정 1. 개명한다 ✅

`refunded_amount` → **`reserved_refund_amount`** (`V9__rename_refunded_amount_to_reserved.sql`).
V1 을 직접 못 고치는 이유는 Flyway 체크섬. CHECK 식은 Postgres 가 컬럼 개명 시 자동으로 따라 고치므로 **제약 이름만** 같이 바꿨다(`chk_payment_reserved_refund_amount`).

**로직은 한 줄도 안 바뀌었다.** 그리고 이름이 바뀌면서 그 제약이 실제로 지키는 게 드러났다 — *"환불액이 결제액을 넘지 않는다"* 가 아니라 **"예약 총액이 결제액을 넘지 않는다"**.

메서드 이름도 같이 갈았다(이름이 컬럼에서 메서드로 옮겨가 있었다):

| 지금 | 이전 |
|---|---|
| `PaymentRepository.reserveRefund` | `addRefundedAmount` |
| `PaymentRepository.releaseRefundReservation` | `releaseRefundedAmount` |

`RefundRaceTest` 는 자기 토이 테이블을 in-test 로 만들어 쓰므로 손대지 않았다 — W1D2 시점 스키마의 화석이고, 그게 검증하는 건 SQL 의 모양이지 우리 스키마가 아니다.

### 결정 2. `Payment.refundStatus(long completedAmount)` ✅

> **여기서 Claude 의 초안이 한 번 뒤집혔다.** 처음엔 *"`Payment.refundStatus()` 는 죽는다 → 순수 정적 함수로 내리고 가드는 호출부로"* 였는데, 그러면 **`PAID` 정의역 판정이 호출부 두 곳으로 복제된다**(`RefundStatus.of` 는 순수 함수라 `PaymentStatus` 를 모른다). 그 규칙은 `Payment.refundStatus()` javadoc 이 길게 정당화해둔 것이고 `RefundGuardTest` 가 지키고 있다 — 흩으면 그 테스트가 겨눌 대상이 없어진다.

**규칙은 `RefundStatus.of`, 정의역은 `Payment`** 로 갈랐다. 밖으로 나간 건 계산이 아니라 **데이터 출처**뿐이다.

- `RefundStatus.of(long amount, long completedAmount)` — 순수 함수
- `Payment.refundStatus(long completedAmount)` — `requirePaid` 후 위임
- `Payment.remainingRefundable()` — 예약 기준 잔여액(같은 정의역 가드)
- `RefundRepository.sumCompletedAmount(paymentId)` — 새 원천

### 결정 3. 다 — 두 축을 다 노출 ✅

`RefundResponse(refundId, amount, refundStatus, remainingRefundable)`.
서비스가 자기 tx 안에서 둘을 계산해 `RefundOutcome.Accepted` 에 실어 보낸다 — 컨트롤러가 리포지토리를 만지지 않게, 그리고 tx 밖 조회가 생기지 않게.

`RefundCompletedEvent.from(..., completedAmount)` 은 **`markCompleted` 뒤에** 센 값을 받는다. 앞에서 세면 방금 확정시킨 그 건이 빠져 라벨이 한 건만큼 뒤처진다.

## 3-1. 실측 — 전체 **70 → 72건 0실패**

`./gradlew test --rerun-tasks` (캐시 아닌 강제 — W3D3 §8 ④).

**HTTP 표면 — 결정 3-다가 실제로 하는 일**

```
[실측] 5,000 부분환불 요청 → HTTP201
       {"refundId":11,"amount":5000,"refundStatus":"NOT_REFUNDED","remainingRefundable":15000}
[실측] 전액 요청       → HTTP201
       {"refundId":10,"amount":20000,"refundStatus":"NOT_REFUNDED","remainingRefundable":0}
[실측] 그 뒤 1원       → HTTP409 EXCEEDS_REMAINING
```

두 번째 줄이 이 결정의 전부다. **라벨은 "환불 없음"인데 잔여는 0** — 모순처럼 보이지만 둘 다 참이고, 그 조합이 세 번째 줄의 409 를 **미리 설명한다.** 결정 3-가(라벨만)였다면 호출자는 "환불 없음"을 보고도 거부당하고, 응답 안에 이유가 없다.

**두 축이 갈라지는 구간이 실재한다**

| 케이스 | 라벨 | 예약 | 확정 | |
|---|---|---|---|---|
| 전액 환불 **요청만** | `NOT_REFUNDED` | 20,000 | **0** | 차 20,000 = PG 확인 대기중 |
| 요청 + `confirm` 3회 | `NOT_REFUNDED → PARTIAL → PARTIAL → REFUNDED` | 20,000 | 20,000 | 차 0 |
| 동시환불 10스레드(4건 통과) | `REFUNDED` | 20,000 | 20,000 | 차 0 |

**이벤트 — 기준이 둘이던 게 풀렸다**

```
[실측] refund.completed value={"amount": 5000, "sellers": [{"amount": 5000, "sellerId": 55}],
        "refundId": 30, "pgRefundId": "pgr-30", "refundStatus": "PARTIAL_REFUNDED"}
```

`sellers`(journal 거울)와 `refundStatus`(확정합)가 이제 **같은 기준**을 본다.

### ★ 테스트가 버그를 지키고 있었다

`RefundGuardTest.부분환불_3번이면_라벨이_..._REFUNDED로_간다` 는 **`confirm()` 을 한 번도 안 부르는데** 라벨이 `REFUNDED` 까지 가는 걸 단언했고, **그게 통과하고 있었다.**

W2D4 에 썼을 땐 옳은 테스트였다(요청 = 반영). W3D2 가 환불을 Saga 로 쪼갠 순간 이 단언의 의미가 뒤집혔는데, **테스트는 통과했으므로 아무도 안 봤다.** 초록불이 "코드가 옳다"가 아니라 "그 경로를 안 밟았다"는 뜻인 W3D3 §8 ①과 같은 계열인데, 형태가 더 나쁘다 — 여긴 경로를 밟았고 **틀린 값을 정답으로 적어두고 있었다.**

둘로 갈랐다:
- **`요청만_한_환불은_라벨을_움직이지_않는다`** (신설) — 라벨 `NOT_REFUNDED` / 예약 20,000 / 확정 0 을 한 자리에서 단언. **W3D4 이전엔 존재할 수 없던 테스트**다
- `PG확인까지_간_부분환불_3번이면_...` — `requestAndConfirm` 헬퍼로 Saga 두 번째 다리까지 태운다

`RefundApiTest` 에도 `전액환불_요청_직후_응답이_다음_요청의_409를_미리_설명한다` 를 추가했다(+1). 70 → 72 는 이 둘이다.

## 4. 대사 — 내부 축(장부 ↔ 정산)

### 4-1. ① 축이 몇 개인가 — 셋이고, 오늘은 둘

계획서는 한 축인데 실제로는 셋이 있다.

| | 축 | 어긋나면 무슨 뜻 | 생긴 곳 | 오늘 |
|---|---|---|---|---|
| **A** | 내부 장부 ↔ 외부 PG 리포트 | 우리와 PG 의 사실이 다르다 | 계획서 | ⬜ 미착수 |
| **B** | 장부 ↔ 정산 스냅샷 | 정산이 장부를 잘못 읽었거나 **증발했다** | W3D3 §1 | ✅ **오늘** |
| **C** | 예약 ↔ 확정 | PG 확인 대기중 또는 **UNKNOWN 에 물림** | 오늘 §2-5 | ⬜ 안 봄 |

**축을 안 가르면 엉뚱한 곳에 문의가 나간다.** W3D3 §4 의 증발분은 *"장부엔 있는데 정산엔 없다"* 인데, A 축만 보면서 정산 스냅샷을 끼워 쓰면 *"PG는 정산했는데 우리 장부엔 없다"* 처럼 보인다 — 원인은 우리 배치인데.

**C 를 뺀 이유**: A·B 는 *어긋나면 이상한* 관계인데 **C 는 어긋난 게 기본값**이다(요청부터 consumer 처리까지 항상 0 이 아니다). 대사로 다루려면 *"얼마나 오래 갈라져 있었나"* 라는 시간 축이 더 필요해 성격이 다르다.

### 4-2. 핵심 판단 — 같은 SQL 을 재실행하지 않는다

B 축에서 `settlement.net_amount` 를 무엇과 비교할 것인가. 가장 자연스러운 답은 배치가 쓴 집계 SQL 을 다시 돌리는 것인데, **그러면 동어반복이다** — 배치가 틀리게 계산했으면 대사도 똑같이 틀리게 계산해 항상 일치한다. *통장을 안 보고 가계부를 두 번 읽는 것.*

| | 대사가 값을 구하는 법 | 집계 버그를 |
|---|---|---|
| ㄱ | 배치와 같은 SQL 재실행 | ❌ |
| ㄴ | 같은 장부를 다르게 쓴 식으로 | ✅ (규칙이 코드 두 곳) |
| **ㄷ (채택)** | **다른 원천** — `payment`+`refund` 에서 재구성 | ✅ |

**W3D3 §2 가 *"payment+refund 를 읽을 수도 있었다"* 며 안 고른 길이, 대사에선 독립이라는 이유로 장점이 된다.**

### 4-3. 그 대가 — 무엇이 독립이고 무엇이 아닌가

| 항목 | 독립? | |
|---|---|---|
| 부호(환불 차감) | ✅ | 배치는 SQL `CASE`, 대사는 Java 뺄셈 |
| 수수료·셀러 배정 | ✅ | 대사가 `order_item` 을 다시 walk |
| 증발·미실행 배치 | ✅ | 나중에 돌아서 보므로 잡힌다 |
| **날짜 경계** | ❌ | `payment` 에 **승인 시각 컬럼이 없다** — 아래 |
| **환불 안분 규칙** | ❌ | 의도적 복사 — 아래 |

**날짜: `payment` 에 승인 시각이 없다.** `created_at` 은 PENDING 생성 시점이고, `updated_at` 은 `reserveRefund` 도 갱신하므로 **7/1 결제가 7/5 환불되면 시각이 7/5 로 밀린다.** 그래서 `payment.journal_id → journal.created_at` 으로 **"언제"만 장부에서 빌렸다.** 훼손은 딱 이 한 줄 — 금액 계산은 전부 독립이다. (대안이던 V10 `paid_at` 은 안 함. 어차피 "KST 하루"의 정의는 `SettlementService.ZONE` 한 곳에서 온다.)

**안분: 복사할 수밖에 없다.** 다르게 쓰면 반올림이 어긋나 **정상 상태에서도 매일 1 원씩 거짓 경보**가 뜬다. 허용 오차를 두면 진짜 1 원 오류가 묻힌다. 복사하고 *"안분 규칙 자체는 대사 범위 밖"* 이라고 못박았다.

> **★ 그래서 W2D5 의 승격 트리거는 이 대사로 안 울린다.** `LedgerService.recordRefund` javadoc 이 *"W3D4 대사에서 셀러별 불일치가 실제로 잡히면 품목 단위 환불로 올린다"* 고 적어뒀는데, 장부와 재구성이 같은 안분식을 쓰므로 둘은 **구조적으로 항상 일치한다.** 그 트리거가 겨냥한 건 *"A 물건만 반품됐는데 B 미지급금도 깎인다"* 이고, 그건 두 기록이 어긋나는 문제가 아니라 **둘 다 똑같이 현실과 다른** 문제다 — PG 리포트도 셀러를 모르니 A 축도 못 잡는다. **셀러 문의로만 발견된다.**

### 4-4. 실측 (`ReconciliationTest` 6케이스) — 전체 **72 → 78건 0실패**

```
[실측] 정상 경로       → 불일치=0건
[실측] 안분 낀 부분환불 → A net=8400 B net=5600 불일치=0건
[실측] 증발분          → AMOUNT_MISMATCH[정산=9500 재구성=19000 차액=-9500]
[실측] 재실행 후       → 불일치=0건
[실측] 배치 미실행     → MISSING_IN_SETTLEMENT[정산=null 재구성=9500 차액=-9500]
[실측] 스냅샷 조작     → AMOUNT_MISMATCH[정산=99999 재구성=9500 차액=+90499]
[실측] 유령 정산행     → MISSING_IN_RECONSTRUCTION[정산=7000 재구성=null 차액=+7000]
```

두 줄이 값이 크다:
- **안분 0건** — 복사가 `LedgerService` 와 1 원까지 같다는 증거. 어긋났으면 매일 거짓 경보였다
- **증발분 → 재실행 후 0건** — W3D3 §4 에서 **알고 뚫은 구멍을 오늘 잡았고**, W3D3 §5 의 *"덮어쓰기가 복구 수단"* 이 대사로 확인됐다. 뚫은 곳과 잡는 곳이 이어졌다

`Discrepancy.difference = settled − reconstructed`. **양수면 정산이 더 크다 = 과지급 방향** — W3D3 §8 ③ 의 "아무도 신고하지 않는 오류"가 이 부호로 나타난다.

### 4-5. 음성대조군 — W3D3 §8 이 남긴 기대를 닫았다 *(본인 실행·원복)*

**제거 대상**: `SettlementRepository:56` 의 `ELSE -le.amount` → `ELSE le.amount` (어제와 같은 자리, **다른 질문**: 대사가 잡느냐)

| 예측 | 실측 |
|---|---|
| `ReconciliationTest` 빨간불 **0건** | **1건** ❌ |
| (나머지 칸 미기입) | 아래 |

**W3D3 §8 이 기대로만 남긴 문장이 닫혔다.** *"이 클래스의 오류는 대사 말고는 발견 경로가 없다"* → **대사가 실제로 잡는다. 2건.**

- ② **오차는 환불액의 2배**: A `+6,000` + B `+4,000` = 10,000 = 2 × 5,000 ✅ 셀러별로 쪼개져도 총합으로 성립
- ③ **항상 셀러에게 유리한 방향**: 두 차액 모두 양수(정산 > 재구성 = 과지급) ✅
- `SettlementBatchTest` 2 red — 어제와 동일

#### ★ 그런데 그 증거가 단언에 없었다

빨간불은 `ReconciliationTest:94` 에서 났는데, 그건 **대사 단언이 아니라 정산 단언**(`assertThat(netOf(...))`)이다. AssertJ 는 첫 실패에서 멈추므로 `assertThat(found).isEmpty()` 는 **실행조차 안 됐다.**

대사가 2건을 잡았다는 사실은 **`[실측]` printf 에만 남았다** — 단언보다 먼저 실행돼서.

```
[실측] 안분 낀 부분환불 → A net=14400 B net=9600 불일치=2건
```

**W1 부터 써온 printf 관습이 처음으로 "단언이 못 본 것"을 봤다.** 그리고 이건 테스트 결함이다 — `ReconciliationTest` 인데 대사 단언이 맨 아래 있었다. 둘 다 고쳤다:
- 대사 단언을 **맨 위로** (클래스가 겨누는 축의 단언이 먼저 — 클래스 javadoc 에 규약으로 명시)
- printf 가 `found.size()` 뿐이라 차액을 **유도**해야 했다 → `found` 자체를 찍게 수정

원복 후 재실행(`--rerun-tasks`) **78건 0실패** 복귀. **오늘은 `git diff` 가 실제로 증거였다** — `SettlementRepository` 가 tracked 라, W3D3 §8 ④ 에서 무효였던 절차가 여기선 유효하다.

## 5. 남은 설계 질문 — A 축(외부)

**② 대사의 단위 — 건별인가 합계인가.** 일자·셀러 합계만 맞추면 `+5,000 / −5,000` 이 상쇄돼 통과한다. 건별이면 조인 키가 필요.

**③ 조인 키는 뭔가.** `pg_transaction_id`(웹훅으로 옴) / `merchant_payment_id`(우리가 보냄) / 환불은 `pgr-{refundId}`(`StubPgClient` 가 결정론적으로 발급 — 그 javadoc 에 *"대사가 '같은 환불엔 같은 번호'를 기대할 수 있어야 한다"* 고 이미 적혀 있음).

**④ Mock CSV 의 컬럼은 뭔가.** ← 오늘 남은 제일 큰 설계 판단.
현재 장부 계정은 `CASH` / `SELLER_PAYABLE` / `FEE_REVENUE` **셋뿐이고 PG 수수료 계정이 없다**(`LedgerAccount.java`). 실제 PG 리포트는 보통 `승인금액 − PG수수료 = 입금액` 으로 온다. 리포트에 PG 수수료 칸을 두면 *"우리 장부가 모르는 값"* 이 생기고, 안 두면 리포트가 현실과 멀어진다.

**⑤ 불일치의 종류를 어떻게 가르나.** (가) 리포트엔 있는데 장부에 없음 / (나) 장부엔 있는데 리포트에 없음 / (다) 금액 다름 / (라) 상태 다름. 원인이 전부 다르고, 특히 (나)는 *"아직 안 온 것"* 과 *"영영 안 올 것"* 이 섞여 있다.

**⑥ 대사 결과를 저장하나.** 또 저장 vs 파생. W1D3·W2D4 는 기각, W3D3 은 채택. 계획서 W3D5 가 "자동 플래그"라 **오늘은 비교까지만** 두는 선택지도 있다.
