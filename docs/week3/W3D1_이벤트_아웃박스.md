# Week 3 Day 1 — 이벤트 스키마 + 트랜잭셔널 아웃박스

*(계획서의 "Kafka 이벤트 설계 + Producer" 항목)*

**날짜**: 2026-07-25
**산출물**: `outbox` 테이블(`V6__`), `OutboxEvent`·`EventType`·`OutboxRepository`, 이벤트 페이로드 3종(`PaymentCompletedEvent`·`RefundRequestedEvent`·`RefundCompletedEvent`), `OutboxWriter`(같은 tx append), `OutboxRelay`(폴링 발행) + Quartz `OutboxRelayJob`·`OutboxRelayConfig`, 발행 지점 배선 2곳, `OutboxRelayTest`(3케이스). 전체 **53 → 56건 0실패**.

## 1. 가장 큰 판단 — dual-write, "진실은 하나"

결제가 PAID 로 커밋됐는데 Kafka 발행이 실패하면? 반대로 발행됐는데 tx 가 롤백되면? **장부와 이벤트가 갈라진다.** 그런데 이 프로젝트의 주제가 바로 그거다 — W1D3 에서 "재고의 진실이 Redis 와 DB 로 갈라진다"며 Redis 락을 폐기했고, W2D4 에서 "저장하면 진실이 둘로 갈라진다"며 환불 상태를 파생으로 뒀다. 그리고 W3D4 대사는 이 이벤트를 진실원본 중 하나로 쓴다.

**채택: 트랜잭셔널 아웃박스.** 이벤트를 `journal` INSERT 와 **같은 DB 트랜잭션**에서 `outbox` 에 INSERT 한다 → 둘이 갈라질 수 없다. 폴링 릴레이(Quartz)가 미발행 행을 긁어 Kafka 로 실어나른다.

기각: tx 안 직접 `send()`(발행이 tx 에 안 묶임), 커밋 후 인메모리 발행(앱 죽으면 미발행 행 유실 → 아웃박스가 무의미), CDC/Debezium(인프라·의존성 없음 → W3D1 이 인프라의 날이 됨).

## 2. 릴레이 — 폴링(Quartz), CDC 아님

Debezium 은 커넥터·Connect 인프라가 없어 기각. **Quartz 는 이미 스택에 선언돼 있다**(점검일 회고의 "확신 vs 불안"에서 *한 줄도 안 돌려봤다*던 그것 — 여기서 처음 쓴다). 2 초 주기 폴링. "느린 TTL"이 아니라 **필요한 만큼만 자주 조회하는 배치** — W1D3 미결제 쓸이 배치와 같은 결. 단일 인스턴스(`NON_CLUSTERED`)라 릴레이가 하나뿐이고, 그래서 같은 행을 둘이 집는 claim 경쟁이 아직 없다(클러스터링하면 `FOR UPDATE SKIP LOCKED`).

## 3. 아웃박스 스키마 + append-only 긴장

```
outbox(id BIGINT IDENTITY,   -- PK + 발행 순서
       aggregate_id BIGINT,  -- = paymentId. Kafka 메시지 키
       event_type, event_id UUID UNIQUE,  -- event_id = 소비자 멱등키
       payload JSONB,        -- fat 스냅샷
       occurred_at, published_at NULL)
+ 부분 인덱스 (id) WHERE published_at IS NULL   -- "발행 대기 큐" 크기로 수렴
```

**릴레이가 `published_at` 을 UPDATE 하는 건 append-only 위반이 아니다.** 이 프로젝트의 append-only 는 **장부**(재무 진실 — "정정은 역분개로")에 건 규율이다. 아웃박스는 진실이 아니라 **전송 큐** — 진실은 `journal`/`ledger_entry` 에 있고 여긴 그걸 나르는 파이프다. 그래서 `published_at` 한 칸만 mutable 로 열어도 규율과 안 부딪힌다. W2D4 에서 "환불 상태는 파생이라 저장 안 함 / 하지만 `refunded_amount` 는 원자적 UPDATE 로 쓴다"처럼, 무엇이 진실이고 무엇이 메커니즘인지를 가른 것과 같은 판단.

## 4. 스키마 — JSON, fat 스냅샷, 타입별 토픽

- **JSON**: payload 가 이미 `JSONB` 라 그대로 실어보낸다. Avro+레지스트리는 인프라 추가라 기각.
- **fat 스냅샷**: `payment.completed` 가 셀러별 미지급금·수수료 내역까지 담아, W3D4 대사가 외부 PG 리포트와 바로 대조하게 한다. **약점(발행 시점 스냅샷이 진실과 갈라진다)을 없앤 방법**: 내역을 **방금 만든 journal 의 줄에서 거울처럼 읽는다**(재계산 아님). 같은 tx 안에서 장부를 그대로 비추므로 이벤트가 장부와 갈라질 수 없다.
- **토픽 타입별**: `settlement.payment.completed` / `settlement.refund.requested` / `settlement.refund.completed`. 같은 결제의 payment→refund **교차 순서 보장은 불필요**(소비자가 DB 를 재조회, 이벤트 순서에 의존 안 함). 같은 타입 내 per-payment 순서(부분환불 3건)는 `aggregate_id` 키가 같은 파티션으로 보내 보장.

## 5. 발행 지점 — 스코프

| 이벤트 | 발행 자리 | 상태 |
|---|---|---|
| `payment.completed` | `PaymentTransitionService.applyApproved` TRANSITIONED 부수효과 (journal INSERT 옆) | ✅ producer |
| `refund.requested` | `RefundService.requestRefund` affected-rows==1 직후 (역분개 INSERT 옆) | ✅ producer |
| `refund.completed` | 아직 없음 — 현재 환불은 동기라 "완료"를 발행할 자리가 없다 | 스키마만 |

`refund.completed` 의 producer 는 실제 PG 환불이 확인되는 W3D2 consumer/보상 흐름에서 붙는다.

## 6. 실측 (`OutboxRelayTest`, 실제 Kafka Testcontainers)

| 케이스 | 관측 |
|---|---|
| 결제확정 → payment.completed | outbox 행 **1** · 미발행 **1** · `journal(PAYMENT)==outbox`(같은 tx 짝) · payload `amount:20000`·`payable:19000`·`fee:1000`(fat) |
| 릴레이 발행 | publishBatch **1** · 미발행 잔량 **0**(published_at 찍힘) · **재실행 0**(미발행만 긁음) · Kafka key=paymentId · value `amount:20000` |
| 환불 → refund.requested | publishBatch **1** · Kafka value `amount:5000`·`refundStatus:PARTIAL_REFUNDED`·`sellerId`(fat 안분) |

- **원자성**: `journal(PAYMENT)` 수와 `outbox(payment.completed)` 수가 같다 — 이벤트가 장부와 같은 tx 로 커밋됐다는 실측.
- **fat 스냅샷이 장부를 거울처럼**: payload 의 `payable:19000`/`fee:1000` 이 PAYMENT journal 줄과 정확히 일치.
- **미발행만 긁는다**: 2회 발행 시 두 번째가 0 — 부분 인덱스 + `published_at` 판정이 재발행을 막는다.

## 7. 정직한 한계 / 이월

- **Quartz 자동 발행은 미검증.** 테스트는 `spring.quartz.auto-startup=false` 로 끄고 `publishBatch()` 를 직접 부른다(결정적 검증). **릴레이가 2 초마다 스스로 도는 것**은 실제 앱(bootRun)에서만 일어나므로 아직 실측 안 됨 → bootRun 관통으로 닫을 자리.
- **배치 tx 의 중복 폭**: 배치 중 한 건 실패 시 tx 통째 롤백 → 앞서 발행된 건도 재발행(중복 폭 = 배치 크기). 단순함을 택했고 소비자 멱등이 흡수. 폭을 1 로 줄이려면 행별 tx(W3 이후).
- **소비자 멱등 미구현**: at-least-once 라 `event_id` 로 소비자가 중복 제거해야 한다. 소비자는 W3D2.
- **`refund.completed` producer 없음**(§5) — W3D2.
