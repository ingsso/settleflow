## 1. 구독 생성 경로 (2026-08-18)

**산출물**: `POST /subscriptions` + `V13` 부분 유니크 인덱스 + `SubscriptionCreationTest` 5건

### 왜 이게 먼저였나 — 미룬 대가가 다른 항목을 막았다

D1 이 엔티티를, D2 가 스케줄러를 만들어놓고 **아무도 구독을 만들 수 없었다.** D3→D4→D5 로
**네 번 이월**됐고, 그동안은 *"나중에 하면 되는 것"* 이었다. W5D5 에서 성격이 바뀌었다 —
k6 시나리오 ③이 구독 500개를 필요로 하는데 **만들 방법이 없어서** 실행이 막혔다.

**이월이 다른 이월을 막기 시작한 첫 사례**라, 남은 칸 중에서 이걸 먼저 골랐다.

`RefundController` 가 *"Week 2 산출물이 앱 밖에서 도달 불가능한 상태"* 를 푼 것과 같은
자리다. 다만 그때는 **기능이 닿지 않는 것**이 문제였고, 이번엔 **다른 작업이 못 시작되는 것**이
문제였다.

### ★ 결정 1 — 생성은 청구하지 않는다

`next_billing_date` 를 **오늘**로 두고 끝낸다. 청구는 P1 폴러가 집어서 한다.

선택지는 셋이었다:

| | 방식 | 왜 안 골랐나 / 골랐나 |
|---|---|---|
| A | 오늘로 두고 **폴러가 집는다** | ★ **골랐다** — 청구 경로가 하나로 유지된다 |
| B | 생성 즉시 **동기 청구**(주문처럼) | **청구 경로가 둘이 되고 두 번째엔 리스가 없다** |
| C | `오늘 + interval`(첫 주기 무료) | 계획서에 근거가 없다 |

B 가 편하다 — `POST /orders` 가 그렇게 하고 있고, 201 에 `PAID`/`FAILED` 를 실어줄 수 있다.
**그런데 그 순간 W5D2 가 세운 배타성이 한쪽에서만 성립한다.** 폴러는 리스로 집는데
동기 경로는 아무것도 안 집고 바로 청구한다.

> **W5D3 에서 터진 *"형제 진입점"* 의 거울상이다.** 그때는 진입점을 만들고 **배선을 안 해서**
> 터졌고(웹훅 → 구독 청구 NPE), 여기서 동기 청구를 넣으면 **규율이 다른 것을 배선하는** 것이다.
> 안 이어진 것보다 **다르게 이어진 것**이 찾기 어렵다.

**대가**: 201 이 청구 결과를 못 준다. 그래서 이 응답은 결과가 아니라 **접수증**이다
(`RefundController` 의 201 과 같은 성질 — 그쪽도 Saga 라 그 시점엔 아무것도 확정되지 않았다).

### 결정 2 — 셀러당 활성 구독은 하나 (V13)

주문에는 멱등 장치가 없다. 구독에는 뒀다. **손해의 모양이 다르기 때문이다**:

```
중복 주문   한 번의 손해
중복 구독   매달 반복되는 손해
```

`CHECK` 으로는 표현할 수 없다 — 조건이 *"다른 행과의 관계"* 다. W1D4 가 이중청구를 막은
`(order_id) WHERE status='PAID'` 와 같은 계열이고, **부분**이라 해지된 구독이 담기지 않아
**해지 후 재구독이 자연히 열린다**(조건 없는 UNIQUE 였다면 영영 못 한다 — §실측 ④).

### ★ 결정 3 — 같은 거절을 두 곳이 낸다

```
정상 경로   서비스의 사전 조회가 걸러  →  ActiveSubscriptionExistsException  →  409
경합        인덱스가 걸러             →  DataIntegrityViolationException     →  409
```

W1D2 는 *"조회 후 앱 판단"* 을 **기각**했다(읽고 판단하고 쓰는 사이의 틈에서 둘 다 통과한다).
여기서는 **둘 다 둔다** — 기각한 게 아니라 **역할을 갈랐다**:

> **사전 조회는 정합성 장치가 아니라 친절함이다.** 정상 경로가 예외 없이 거절되게 하고,
> 정합성은 인덱스 한 문장이 지킨다. 호출자에게는 둘을 구분할 이유가 없어 **같은 409 로 접는다.**

`saveAndFlush` 를 쓴 건 그 예외를 **커밋이 아니라 서비스 안에서** 받으려는 것이다 —
커밋에서 터지면 예외 종류가 트랜잭션 층에 따라 달라져 HTTP 매핑이 흔들린다.

### 실측

```
[실측] ① 전체 스위트 — cleanTest 부터 단일 실행, 1분 45초
        38클래스 / 171건 / 실패 0 (W5D5 166 → +5)

[실측] ② 생성은 청구하지 않는다
        HTTP 201 · 구독 1(ACTIVE) · 첫청구일 = 오늘
        ★ 폴링 전  주기 0 · 시도 0
          폴링 후  주기 1(PAID) · 시도 1 · 분개 2줄 · 다음청구일 +30일

[실측] ③ 동시 생성 10개 → 201=1 · 409=9 · 그 외 0 · 활성 구독 행 1
[실측] ④ 해지 후 재구독 → 201 · 구독 행 2(활성 1)
[실측] ⑤ 같은 셀러 2회 → 201, 409 · 구독 1
[실측] ⑥ 없는 셀러 → 404 · 구독 0
```

②가 이 작업의 알맹이다. **이 단언이 없으면 나중에 누가 *"생성할 때 첫 결제를 바로 하자"* 로
바꿔도 red 가 안 난다** — 그건 편의가 아니라 리스 없는 두 번째 청구 경로를 여는 일이다.

③의 단언은 **HTTP 상태가 아니라 행 수**가 낸다. *"그 외 0"* 을 같이 단언한 건 매핑이 새면
(500) 거기서 드러나게 하려는 것이다.

### 곁가지 — `SellerRepository` 가 다섯 주 만에 처음 생겼다

셀러는 늘 `Product`·`LedgerEntry` 를 통해 딸려왔고, **id 로 직접 찾을 이유가 구독 생성에서
처음 생겼다.** 도메인이 다섯 주 동안 *"셀러를 조회하는 화면"* 을 한 번도 안 요구했다는 기록이다.

### 안 한 것

| | 항목 | 왜 |
|---|---|---|
| **해지 API** | `cancel()` 의 호출부를 열면 **해지 사유 구분**(사람이 해지 vs 상한 초과로 끊김)을 함께 정해야 한다 — D1 이래 이월이고 오늘 범위 밖 |
| 구독 조회 API | k6 도 포트폴리오도 요구하지 않는다 |

| 첫 청구일 지정 | 요청에 날짜를 안 받는다. 받으면 *"미래 날짜 지정"* 이라는 정책 결정이 딸려온다 |

### 음성대조군 — 예측(미실행)

| | 제거 대상 | 겨누는 것 | **예측** | 결과 |
|---|---|---|---|---|
| A | `V13` 인덱스 | 중복 방어의 최종 보증 | **1건 red** — `열_개가_동시에_만들어도…`(활성 행이 2 이상). ★ `같은_셀러에_두_번…` 은 **green** — 순차 요청은 사전 조회가 걸러낸다 | 미실행 |
| B | 서비스의 `existsActiveBySeller` 분기 | 친절한 거절 | **0건 red 는 아니다** — 순차 2회가 인덱스에 걸려 **여전히 409** 이므로 `같은_셀러에_두_번…` 은 green. ★ 동시 생성의 *"그 외 0"* 도 green. **즉 red 0** | 미실행 |
| C | 인덱스의 `WHERE status='ACTIVE'`(전체 UNIQUE 로) | 부분을 고른 이유 | **1건 red** — `해지하면_같은_셀러가_다시_구독할_수_있다` 만 | 미실행 |

> **B 가 흥미롭다.** 예측이 맞다면 사전 조회는 **지워도 아무 red 가 안 나는 코드**다 —
> W5D5 의 백스톱과 같은 자리가 하나 더 생기는 셈이고, 그때와 달리 **처음부터 알고 넣은 것**
> (친절함은 테스트가 아니라 응답 본문으로만 드러난다)이라 기록해둔다.

## 2. k6 시나리오 ③ 실행 — 동시 재시도 레이스 (2026-08-18)

**산출물**: `k6/dunning-race.js`(시딩) + `k6/seed-subscription-race.sql` + `k6/verify-dunning.sh`
+ [`k6/dunning-race.md`](../../k6/dunning-race.md) §10(실행 결과)

### ★ 주말 체크포인트 달성

계획서 Week 5: *"동시에 여러 재시도 트리거가 발생해도 **중복 청구 0건**인지 수치로 증명"*

```
[실측] 인스턴스 3개 · 폴링 1초 · 구독 500개가 같은 날짜에 동시 도래
       ★ 중복 청구 0건 · 서로 다른 키 = 500 (구독·주기·시도와 정확히 일치)
       구독당 주기 2개 이상 = 0 · cycle_no 최대 1
       PAID 450 / PENDING 50 · journal 450 · 구독수익 13,500,000
       회로 3개 전부 CLOSED · PG 실호출 160 / 169 / 171 = 500
```

**세 인스턴스가 500건을 160/169/171 로 나눠 가진 것**이 경합의 직접 증거다. 셋 다 같은
`findBillingDue` 목록을 같은 순서로 훑었고, 어느 행이 누구 것이 되는지는 CAS 가 갈랐다.
설계 문서 §8 이 *"위반 0 은 레이스가 없다는 뜻이 아니다"* 로 경계한 자리를 이 분배가 메운다.

대조군(인스턴스 1개)에서 **0 이 나와야 할 자리에서 0 이 나왔다** — 위반 0 · 키 500 ·
PAID 350 / PENDING 150(설계한 타임아웃 30%와 일치). 그래서 3 인스턴스 수치를 다중화 탓으로
돌릴 수 있다.

### ★ 실행이 뒤집은 것 셋

| | 무엇 | 실행 전 | 실행 후 |
|---|---|---|---|
| ① | 타임아웃 30% 고정 | W4D3 이 *"난수 대신 인덱스로 고정"* 해 비율을 보장했다 | **인스턴스가 여럿이면 그 보장이 깨진다** — 각자 부분집합을 받고, 앞 10건 창에 타임아웃이 몰리면 열린다. `:8082` 가 전체로는 34.6%인데 열렸다 → **10%로 낮춰야** 셋 다 닫힌 채 끝났다 |
| ② | 회로가 열리면 **좌변 과다**(설계 문서 §3) | 열린 호출도 카운터에 잡힌다고 봤다 | **반대였다.** 개방 호출은 `failed`·`successful` 어디에도 안 잡혀 **좌변 과소**(393 < 500). 방향을 거꾸로 적었고 실행이 고쳤다 |
| ③ | *"인스턴스 3개를 띄웠다"* | 명령을 3번 냈으니 3개라고 봤다 | **`:8083` 이 포트 점유로 기동 실패**했는데 **판정 수치는 멀쩡했다**(위반 0 · 키 500 · 252+248). 그대로 적었으면 **거짓 기록**이 됐다 |

**③이 제일 나쁘다.** W4D4 는 *"분자는 부하 발생기의 자기 보고가 아니라 서버가 받은 수"* 를
세웠는데, 이번에 자기 보고를 한 건 스크립트가 아니라 **나 자신**이었다(*"3개 띄웠다"*).
드러난 계기도 판정 쿼리가 아니라 **`:8083` 의 프로메테우스 응답이 비어 있던 것**이었다.

> **규약 추가: 부하 전에 인스턴스 수를 `/actuator/health` 로 세어 기록한다.**
> 최종 실행은 `★ 3개 전부 up (5s)` 를 찍고 나서 시작했다.

### 회로가 열린 실행도 값이 있었다

첫 3 인스턴스 실행(타임아웃 30%)은 `:8082` 의 회로가 열려 헤드라인으로 못 쓴다. 그런데
**숫자가 정확히 설명된다**:

```
[실측] PG 실호출 393(179 / 52 / 162) + 미발송 107 = 시도 500
       주기 FAILED 107 = 미발송 107 과 정확히 일치
```

**그 107 은 유실이 아니라 W4D1 의 결정이 프로덕션에서 작동한 것이다** — 회로가 열려 PG 에
닿지 않았고, *"안 보냈으니 확실한 앎"* 이라 `FAILED` 로 확정됐다. **그 판단을 단위 테스트
밖에서 처음 관측했다.**

### 안 밟힌 경로

- **재전송** — `PENDING` 50건의 회수는 P1 이 **30일 뒤**에 한다(W5D4 이월 2). 그래서 항등식
  `PG 호출 − 키 = 재전송` 은 **`= 0` 으로만 확인됐고 0 이 아닌 값으로는 아직 못 봤다**
- **P2(재시도) 레이스** — 이 실행은 P1 만 겨눴다. `next_retry_at` 은 흩어져 있어 같은 시각
  도래분이 적고, 실패 주기를 만들려면 라운드를 하루 이상 굴려야 한다
- **CAS 패자 수** — 여전히 못 센다. 분배(160/169/171)가 대리 지표다

## 3. STAR — 정기결제 재시도 (2026-08-18)

**산출물**: `README.md` 의 다섯 번째 STAR 섹션

### 계획서가 요구한 4건은 이걸로 다 찼다 — 다만 README 엔 5건이다

계획서 최종 산출물은 *"STAR 4건 (웹훅 멱등성 / 이중장부 / 정산 대사 / 정기결제 재시도)"* 이다.
W4D5 에 **부하테스트 STAR** 를 하나 더 썼기 때문에 README 는 **5건**이 됐다 — 부족이 아니라
초과이고, 부하테스트는 계획서 목록엔 없지만 **k6 결과 2종**이 따로 산출물이라 버릴 이유가 없다.

```
계획서 4건   웹훅 멱등성(W1) · 이중장부(W2) · 정산 대사(W3) · ★ 정기결제 재시도(W5)  ← 오늘 닫힘
추가 1건     부하테스트(W4D5)
```

### 무엇을 헤드라인으로 골랐나

수치가 셋 있었고 **셋 다 싣되 역할을 갈랐다**:

| 수치 | 역할 |
|---|---|
| **인스턴스 3개 · 구독 500 · 중복 청구 0 · 키 500** | ★ 헤드라인. 계획서 주말 체크포인트 문장에 직접 답한다 |
| 리스 제거 시 **키 10 · PG 19 · 주기 10** | *"안 막으면 어떻게 되나"* — 방어의 크기를 준다 |
| **PG approve 3회 · 키 3개 → 키 2개** | 이중 청구가 **실재했다**는 것과 재전송이 닫았다는 것 |

**두 번째가 없으면 첫 번째가 공허하다.** *"0건"* 은 리스가 일했다는 뜻일 수도, 애초에 아무도
안 부딪혔다는 뜻일 수도 있는데, 대조군 수치가 그 갈림을 닫는다(W4 회고 §4-2 계열).

### 이 STAR 만 가진 것 — 계기의 이동을 본문에 넣었다

앞의 네 STAR 는 *"무엇을 만들었나"* 가 본체인데, 이건 **계기를 두 번 갈아탄 경위**를 A(행동)
5번으로 넣었다:

```
payment 행 수  →  PG 호출 수  →  서로 다른 키 개수
(자기 성질)       (재전송을      (지금의 헤드라인)
                  못 가름)
```

**면접에서 되물어질 자리가 여기라고 봤다** — *"중복 청구 0건을 어떻게 셌나"* 에 대한 답이
*"payment 행을 셌다"* 면 그 수치는 아무것도 증명하지 않는다. 그 함정에 한 번 빠졌다가
나온 기록이 이 프로젝트에서 가장 재사용 가능한 부분이다.

### 정직한 한계를 여섯 줄 넣었다

STAR 는 자랑하는 형식이라 한계가 빠지기 쉬운데, 이 주제는 **한계가 곧 설계의 일부**다:
*"PG 가 같은 키에 한 번만 과금한다"* 는 **검증 불가**(외부 계약)이고, 그래서 테스트 파일을
절로 갈라 우리가 보증하는 것과 PG 에 기대는 것을 **파일 구조로** 분리했다는 것까지 적었다.

### 남은 칸

STAR 는 닫혔고, 남은 것은 **아키텍처 다이어그램 이미지 · 포트폴리오 3번째 프로젝트 섹션 ·
회고 §5 다섯 주치 · 브랜치 머지**다.
