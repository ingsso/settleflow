## 2. ★ 헤드라인 셋

```

   "재시작해도 예약 유지" = next_retry_at 이 행에 있는 사실
```

## 3. 폴링이냐 예약이냐 — 시계가 둘이 되는 게 더 나쁘다

기술결정서(`:47-54`)는 *"@Scheduled 대신 Quartz"* 를 두 근거로 정해뒀다.

| | 원래 근거 | 오늘 |
|---|---|---|
| a | 이벤트마다 다른 시점 → **동적 트리거** | 유효하다 |
| b | QRTZ 테이블 영속화 → **재시작해도 예약 유지** | ★ **D1 이 이미 충족했다** — `billing_cycle.next_retry_at` 이 *행에 있는 사실*이라 재시작과 무관 |

b 가 사라지고 나면 Quartz 를 얹는 대가가 남는다: *"다음 시도는 언제인가"* 의 원천이
**주기 행과 QRTZ 트리거 둘**이 된다. W1D3(재고 Redis)·W2D4(환불 상태)·W5D1(`attempt_count`)
에서 세 번 기각한 모양이 스케줄러 층에서 재발하는 것이다.

### 물증은 스키마에 있었다

```
[실측] V12:133  idx_subscription_due        ON subscription (next_billing_date)  부분
[실측] V12:218  idx_billing_cycle_retry_due ON billing_cycle (next_retry_at)     부분
       V12:216 주석 "재시도 스케줄러의 조회: 지금 다시 걸 실패 주기"
[실측] 코드베이스의 @Scheduled · Quartz Job 중 dunning 관련 — 0건 (어제까지)
```

D1 은 이미 **폴링 전제로 부분 인덱스 둘**을 깔아뒀다. Quartz 를 골랐으면 둘 다 죽은 인덱스가
된다. 어제의 설계가 오늘의 선택을 이미 기울여둔 셈이고, 이건 D1 §12 ③(*"스케줄러는 구독이
아니라 청구 건을 긁는다"* — 예측)의 검증이기도 하다. **맞았다.**

### 폴링의 대가를 정직하게

| | 잃는 것 | 크기 |
|---|---|---|
| ① | 정밀도 — 폴링 간격만큼 늦는다 | 간격이 1·3·7**일**이라 뜻이 없다 |
| ② | **트리거 발화 1회 보증**(Quartz 클러스터 모드) | ★ 이게 진짜 대가다. §5 에서 갚는다 |
| ③ | 빈 쿼리가 계속 돈다 | 부분 인덱스가 있어 작다 |

## 4. 폴러가 둘인 이유 — 시계가 둘이라서

```
P1  subscription.next_billing_date  (날짜, 구독 단위)  → 정기 청구 개시 + 열린 주기 회수
P2  billing_cycle.next_retry_at     (시각, 주기 단위)  → 실패 주기 재시도
```

축이 다르다(날짜/시각, 구독/주기). 그리고 **둘이 같은 주기를 노리지 않게 갈라뒀다** —
P2 는 `FAILED` 만, P1 의 회수는 `PENDING` 만 본다. 이 조건이 없으면 두 폴러가 한 행에서
경합하고, 그건 §5 의 방어가 아니라 설계의 실수다.

## 5. ★ 낙관적 락이 이 레이스를 못 막는다 — 순서가 뒤집혔기 때문

이 자리가 오늘 제일 중요한 판독이다. **이미 있는 방어 둘이 둘 다 안 듣는다.**

```
t0   인스턴스 A: 주기 41 을 집었다 (version=7)
t0   인스턴스 B: 주기 41 을 집었다 (version=7)
t1   A: PG 청구 → 돈이 나갔다
t1   B: PG 청구 → 돈이 또 나갔다
t2   A: onPaymentSucceeded() → commit. version 7→8   ✔
t3   B: commit → 버전 불일치 → 예외 → 롤백
```

t3 에서 낙관적 락은 **제 일을 정확히 했다.** 그런데 **롤백은 우리 DB 만 되돌리지 PG 로 나간
돈은 못 되돌린다.**

| | 순서 | 락이 방어가 되나 |
|---|---|---|
| W1D4 `dispatch()` | 판정 → 부수효과 | **된다** — 커밋 검사가 부수효과보다 뒤에 오지 않는다 |
| 오늘 폴링 | **부수효과 → 판정** | **안 된다** — 돈이 검사보다 먼저 나간다 |

**락이 약해진 게 아니라 순서가 바뀌었다.**

PG 멱등키도 못 막는다:

```
[실측·코드읽기] Payment.java:98 — "merchantPaymentId 가 시도마다 새로 발급되는 게
                                   멱등의 단위를 시도로 만든다"
```

두 인스턴스가 만든 두 시도는 **서로 다른 키**다. PG 입장에선 정당한 별개 청구고,
계획서 D3 의 Idempotency-Key 는 *"같은 시도의 재전송"* 을 막지 *"같은 주기의 두 시도"* 를
못 막는다.

### 그래서 리스 — 집었다는 사실을 먼저 커밋한다

돈이 나가기 전에 **커밋된 사실**을 하나 만든다. 진 인스턴스는 0 행을 잡고 물러난다.

```sql
-- P2
UPDATE billing_cycle SET next_retry_at = :leaseUntil, version = version + 1, updated_at = now()
 WHERE id = :id AND status = 'FAILED' AND next_retry_at <= :now

-- P1
UPDATE subscription SET next_billing_date = :next, version = version + 1, updated_at = now()
 WHERE id = :id AND status = 'ACTIVE' AND next_billing_date = :expected
```

**판정과 실행이 한 문장**이고 반환된 영향 행 수가 곧 *"내가 집었는가"* 의 답이다 —
`PaymentRepository.reserveRefund`(W1D2)가 세운 패턴 그대로다. 읽고 판단하고 쓰면 그 틈에서
둘 다 통과한다.

> **P1 의 리스는 이미 정해져 있었다.** *"`next_billing_date` 를 주기 생성 시 전진"* 이
> 그 자체로 리스다. 구독 시계와 주기 시계에 **같은 모양이 두 번 선다.**

### 리스가 `next_retry_at` 한 칸에 얹히는데 두 뜻을 겸하는 게 아닌가

아니다. 그 칸을 읽는 쪽(폴링 쿼리)이 던지는 질문은 하나다 — **"이 시각까지는 아무도 손대지
마라"**. 정책이 정한 3일 뒤도, 리스로 밀어둔 5분 뒤도 그 문장의 두 사례일 뿐이라 읽는 쪽이
**서로 다른 행동을 할 필요가 없다.** 다른 행동이 필요했다면 그건 D1 이 하루 종일 걷어낸
"한 칸이 둘을 겸함"이고 갈랐어야 한다.

`chk_billing_cycle_retry_shape` 도 리스 중에 그대로 성립한다(`FAILED` + 값 있음).

### 트랜잭션 3단 — PG 호출이 밖이어야 하는 이유가 오늘은 둘이다

```
tx1: 시계를 밀어 커밋(리스) + PENDING payment 행 INSERT
--- 경계 ---   PG 동기 호출
--- 경계 ---
tx2: 결과 반영
```

W1D1 의 이유(터지면 롤백돼 PENDING 행이 사라지고 웹훅이 매칭할 대상을 잃는다)에 하나가
붙는다: **리스는 커밋돼야 리스다.** 같은 트랜잭션에 두면 PG 호출 중에는 아무도 그 리스를
볼 수 없어 다른 인스턴스가 같은 주기를 집는다.

## 6. 상한을 값으로 안 적었다

계획서 *"1일→3일→7일 후 3회"* 는 한 칸 틀리기 쉬운 자리다:

```
원 청구 실패 → +1일 → 재시도1 실패 → +3일 → 재시도2 실패 → +7일 → 재시도3 실패 → 포기

  간격 목록 길이 = 3   (재시도 횟수)
  payment 행 개수 = 4   (시도 횟수 — 원 청구를 포함)
```

`maxAttempts` 를 두면 3 과 4 중 하나를 골라 적어야 하고, 그 순간 목록과 어긋날 수 있는
복제가 생긴다. 그래서 **정책에 묻는 건 *"몇 번까지냐"* 가 아니라 *"시도가 N 번 결말났다.
다음은?"*** 이고, **포기는 목록에 다음 칸이 없다는 사실**이다.

D1 이 `attempt_count` 를 기각하며 쓴 문장(*"원본과 항상 같아야 하는 값의 복제"*)이 정책
객체 안에서 한 번 더 성립한다.

### 계획서 문장이 두 갈래로 읽혔다 — 백오프를 골랐다

```
A 직전 시도 기준(백오프)  → 첫 실패로부터 누적 1, 4, 11일   ← 고른 쪽
B 첫 실패 기준(고정)      → 첫 실패로부터 누적 1, 3, 7일
```

*"간격이 늘어난다"* 가 백오프의 뜻이고, B 는 세 번째 재시도가 두 번째의 4일 뒤가 아니라
그냥 첫 실패의 7일 뒤가 되는 고정 스케줄이다. **테스트가 누적 궤적을 단언해 못 박는다** —
`간격은_직전_시도_기준이라_누적이_1일_4일_11일이다` 가 red 로 바뀌면 해석이 바뀐 것이다.

## 7. ★ UNKNOWN — (c)가 닫은 고장과 안 닫은 고장

시도를 셀 때 `FAILED` **와 `UNKNOWN` 을 함께** 센다. `FAILED` 만 세면 타임아웃 시도가
공짜가 되어 PG 가 느린 동안 시도가 줄지 않는다 — W4D5 가 *"무한 재시도"* 로 데인 모양이다.

대가는 있고, **갈 자리가 이미 있다**: `UNKNOWN` 이 나중에 `PAID` 로 풀리면 셈이 틀렸던 게
되는데, 상한 초과로 `ABANDONED` 된 주기에 성공이 도착하면 D1 전이표가
`ABANDONED + 성공 = CONFLICT` 로 받는다. 돈은 `payment` 행에 남고 어긋남만 기록된다.

### 그런데 고장이 둘이었다

```
고장 ①  무한 재시도 — 시도가 안 줄어든다        → UNKNOWN 을 세서 닫았다 ✔
고장 ②  첫 시도 UNKNOWN — 주기가 유실된다       → 세는 것과 무관하다   ✘
```

②는 `PENDING` 주기가 `next_retry_at` 을 가질 수 없어서(스키마 CHECK) P2 의 부분 인덱스에
**담기지도 않는** 문제다. 회수는 P1(구독 시계)이 한다 — 다음 청구일에 열린 주기를 발견하면
새로 만들지 않고 시도를 하나 더 붙인다.

```
[실측] 타임아웃 → 주기 PENDING · 시도 UNKNOWN · 예약행 0
                 1년 뒤 재시도 폴러가 집은 수 = 0
```

**정직하게 적으면 ②를 닫은 게 아니라 늦춘 것이다** — 유실에서 지연으로 바꿨고,
**지연 상한은 한 주기(`interval_days`)다.** 그리고 회수는 `UNKNOWN` 시도가 살아있는 채로
다시 긁는 것이라 **이중 청구를 감수하는 선택**이다. 프로젝트가 환불에서 고른 태도
(`PAYMENT_UNKNOWN` → 503 + Retry-After, *"정보의 부재라 되돌릴 근거가 없다"*)의 **반대편**을
여기서 골랐고, 그 비대칭은 의도된 것이다.

### 겹침 — 둘은 다른 기간의 돈이다

열린 주기 N 이 남았는데 N+1 의 청구일이 오면 **N+1 을 만들고 N 에도 시도를 붙인다.**
N 만 회수하면 한 달치를 영영 못 받고 **그 사실이 어디에도 안 남는다.**

```
[실측] round=0..4  주기수 1/2/3/4/5 · 1번 주기 시도 1/2/3/4/4
```

## 8. ★ 설계 대화에서 나왔어야 할 결정이 구현 중에 나왔다

`UNKNOWN` 은 주기에 통보되지 않는다 — `applyTimedOut` 은 `payment` 만 건드린다.
그러면 **실패 통보 직후의 상한 판정에 도달을 못 한다.** 리스가 만료될 때마다 폴링이 그 주기를
집고, 또 타임아웃 나고, 또 집는다. **(c)로 막은 무한 재시도가 `UNKNOWN` 문으로 돌아온다.**

그래서 상한을 **집기 직전에도** 본다. 자리는 둘이지만 규칙은 하나다 — 같은 간격 목록이
답한다(`nextRetryAt` 은 시각을 쓰고, `hasRetryLeft` 는 있고 없음만 쓴다).

```
[실측] UNKNOWN 만 나는 구독으로 P1 을 5회 — 1번 주기 시도가 1/2/3/4/4
       round 4 에서 ABANDONED. 백스톱이 멈춘 지점이 사다리의 상한과 같다
```

**나쁜 건 이게 발견된 시점이다.** 근거는 설계 대화 때 이미 손에 있었다 — *"UNKNOWN 은 통보가
오지 않는다"* 를 그 자리에서 적어놓고도, 그것이 **상한 판정 경로에도 영향을 준다**는 연결을
못 했다. §10 ② 참고.

### 곁가지 하나 — 정의역이 둘로 갈렸다

`hasRetryLeft` 는 0 을 받고 `nextRetryAt` 은 안 받는다. 시도를 걸어놓고 결말 전에 죽으면
`PENDING` 행만 남아 결말 수가 0 일 수 있는데, 그때 *"더 걸어도 되나"* 는 성립하는 질문(답:
된다)이지만 *"직전 실패로부터 얼마 뒤인가"* 는 직전 실패가 없어 성립하지 않는다.
**같은 목록을 보는 두 질문의 정의역이 다르다.**

### ★ 거짓 red 가 한 번 났다 — 이번엔 회로였다

성공 경로가 `expected "PAID" but was "FAILED"` 로 깨졌는데 **원인이 그 테스트가 아니었다.**

```
[실측] 같은 클래스의 타임아웃 테스트들이 PgTimeoutException 을 15건 넘게 냄
       → pg-approve 회로 개방 (minimum-number-of-calls 10, threshold 50%, wait 30s)
       → 뒤에 온 성공 경로가 CallNotPermittedException → FAILED 로 확정
       → cleanDatabase 는 DB 만 비운다. 회로는 스프링 컨텍스트에 살고
         컨텍스트는 클래스를 넘어 캐시된다
```

W4 회고 §4-2(*"재는 자와 재이는 것이 같은 경로를 공유하면 그 수치는 스스로를 검증 못
한다"*)의 일곱 번째 사례고, **이번에 스위트가 물려준 건 데이터가 아니라 회로**다.

고친 자리는 `PgCircuitBreakerTest` 가 자기 클래스에서 하던 초기화를 `IntegrationTestSupport`
로 올린 것 — 회로를 흔드는 테스트가 그 클래스 하나가 아니게 됐기 때문이다.
**내 클래스만 고쳤으면 이번엔 통과하고 다음 클래스에 회로를 열어둔 채 넘겼을 것이다.**

> D1 의 거짓 초록 둘과 방향이 반대다(저건 실패가 성공으로 보였고 이건 성공이 실패로
> 보였다). 다만 **성공 경로를 실패 경로 뒤에 단언했기 때문에** 드러났다 — 테스트를 성공만
> 모아 짰으면 안 났고, 대신 회로 오염은 그대로 남았을 것이다.

## 10. Claude 오류

| | 단정 | 어떻게 드러났나 | 실제 |
|---|---|---|---|
| ① | **고장 ①②를 한 덩어리로 묶어 선택지를 냈다** — *"UNKNOWN 을 세면 무한 재시도가 막힌다"* 를 UNKNOWN 문제 전반인 것처럼 제시 | 본인이 (c)를 고른 **뒤에** 내가 갈랐다 | (c)는 고장 ①만 닫는다. 고장 ②(첫 시도 UNKNOWN 유실)는 **세는 술어와 무관**하다. 선택 시점에 대가가 불완전하게 제시됐다 |
| ② | *"이게 오늘의 마지막 설계 결정이다"*(레이스 방어) | 구현 중에 상한 백스톱이 필요해짐(§8) | 결정이 하나 더 있었고, **근거는 이미 설계 대화 안에 있었다** — *"UNKNOWN 은 통보가 안 온다"* 를 적어놓고 상한 경로와 연결을 못 했다 |
| ③ | *"quartz 의존성이 미사용이 된다"* | 커밋 전에 확인 | **거짓.** W3D1 아웃박스 릴레이가 쓰고 있다(`OutboxRelayConfig`·`OutboxRelayJob`). 거짓이 된 건 라이브러리가 아니라 **기술결정서에 적힌 근거**다 |

**②가 제일 나쁘다.** 틀린 사실이 아니라 **틀린 완결 선언**이라, 그대로 뒀으면 설계가 다
섰다고 믿고 코드로 넘어갔을 것이다. 실제로 그 결정은 코드를 짜다가 나왔고,
**설계 대화에서 나왔어야 했다.**

**③은 성질이 D1 §10 ②와 같다** — 개수·존재는 맞게 봤는데(의존성이 거기 있다) 그 쓰임을
안 열어봤다. *세는 것과 읽는 것은 다른 일*이라고 어제 적어놓고 하루 만에 같은 종류를 냈다.

## 11. 음성대조군

21건이 전부 첫 시도 green 이라, 이 테스트들이 **red 를 낼 능력이 있는지**를 따로 봤다.
예측을 먼저 적고 본인이 실행했다.

| | 제거 대상 | 겨누는 것 | **예측(먼저 적음)** | 결과 |
|---|---|---|---|---|
| A | `claimForRetry` 의 `AND next_retry_at <= :now` | 리스 CAS | 동시폴링 **1건만** red(payment 11행) | 미실행 |
| **B** | `stageAttempt` 의 `hasRetryLeft` 분기 | **집기 직전 백스톱** | `UNKNOWN_만_쌓여도…` **1건만** red. 사다리·동시폴링·성공경로 포함 **20건 green 유지** | ★ **적중** |
| C | `countConcludedAttempts` 의 `'UNKNOWN'` | 결정 (c) | B 와 같은 1건 red — **원인이 다른데 증상이 같다** | 미실행 |
| **D** | `claimBillingDate` 의 `AND next_billing_date = :expected` | **P1 리스** | ★ **21건 전부 green 유지** — red 를 하나도 못 낸다 | ★ **적중** |

### B — 이게 오늘의 §8 을 증명한다

정상 경로 테스트(사다리·동시 폴링·성공·타임아웃)가 **전부 green 인 채로** 백스톱만 무너진다.
**즉 백스톱 없이도 계획서가 요구한 것은 전부 통과한다.** D1 대조군 B(*"전이표 12칸이 다
green 인데 곁가지는 안 잰다"*)와 같은 성질이고, 오늘 버전은 *"정상 경로가 다 green 인데
`UNKNOWN` 문은 안 잰다"* 다.

### D — red 를 못 내는 게 결론인 대조군

**P1 리스의 CAS 조건을 통째로 없애도 21건이 다 green 이다.**
동시성 테스트가 P2 에만 있고 P1 에는 없다는 뜻이다 — §5 에서 *"같은 모양이 두 번 선다"* 고
적었는데, **재고 있는 건 한 번뿐이다.** 이건 §12 이월로 간다.

A·C 는 미실행이고 예측만 서 있다.
