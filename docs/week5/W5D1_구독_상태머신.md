## 3. 되돌아오는 상태머신 — 무엇이 부서지나

`Payment` 는 DAG 라 `status == PAID` **하나가** *"승인 사건이 이미 반영됐다"* 를 뜻했다.
그래서 `IGNORED` 판정이 상태만 보고 가능했다(W1D4 멱등 backbone). 구독은 다르다 —
`ACTIVE` 는 *"한 번도 청구 안 함"* 일 수도, *"3주기 성공"* 일 수도, *"5주기 재시도 성공"* 일
수도 있다. **같은 라벨, 다른 사실.**

구체적으로 부서지는 궤적:

```
3주기 청구 성공        → ACTIVE
4주기 청구 실패        → PAST_DUE
3주기의 지연된 웹훅 도착("성공")
   → 상태만 보는 코드: PAST_DUE 는 종착지가 아니다 → TRANSITIONED → ACTIVE
   → 실재하는 4주기 연체가 낡은 메시지에 지워졌다
```

**더 나쁜 게 하나 더 있다.** `PaymentTransitionService.dispatch()` 의 낙관적 락 루프는
*"재조회하면 이미 종착지라 `on*()` 이 IGNORED 를 돌려준다"* 를 전제로 **부수효과 1회**를
보증한다. 순환이 생기면 재조회 후 다시 `TRANSITIONED` 가 날 수 있고, 그 부수효과는
이번엔 **돈을 긁는 일**이다.

### 끊은 방법 — 주기를 행으로

```
subscription  id=1
billing_cycle id=31 sub=1 cycle=3 status=PAID     ← 낡은 웹훅은 여기로 간다
              id=41 sub=1 cycle=4 status=FAILED   ← 손도 안 탄다
```

사건은 구독이 아니라 **자기 주기 행**으로 가고, 그 행은 되돌아오지 않는다. 3주기 행은
이미 `PAID` 라 `IGNORED` 다 — `Payment.onApproved` 의 판정 규칙이 **그대로 다시 산다.**

> "낡음"을 따로 표시할 필요가 없어진 게 요점이다. `SubscriptionTransitionResult` 에
> `STALE` 값이 없는 건 누락이 아니라 이 설계의 귀결이다.

## 4. 축이 둘 섞여 있었다 — 갈라지기 **전에** 가른 첫 사례

| 값 | 무엇의 값인가 | 원천 |
|---|---|---|
| `CANCELED` | **계약 사실** — 사람이 해지했다 | 사용자 행위 |
| `PAST_DUE` | **청구 건강도** — 미해결 실패 주기가 있다 | `billing_cycle` 행들 |
| `ACTIVE` | 위 둘 다 아님 | **둘 다** ← 한 칸이 둘을 겸한다 |

W3D4(`refunded_amount`: 가드↔라벨) → W3D5(`created_at`: 귀속↔진행) → W4D5(`Sort` 단언:
인덱스 설계↔물리 배치) 로 **세 번 갈라진** 그 모양이다. 넷째인데, **앞의 셋은 전부 갈라진
뒤에 고쳤고 이번만 갈라지기 전이다.**

선례는 `payment` 안에 있었다 — `Payment.status`(사실, 저장) 와 `Payment.refundStatus()`
(라벨, 파생)가 다른 축이라고 명시돼 있고, 그 분리는 W3D4 에서 값을 치르고 얻은 것이다.

**결과**: `SubscriptionStatus` = `ACTIVE / CANCELED` **저장**(단방향 DAG),
`SubscriptionHealth` = `CURRENT / PAST_DUE` **파생**(순수 함수, 정의역은 엔티티).

부수 효과 하나: `PAST_DUE` 가 컬럼이 아니니 W5D2 스케줄러가 *"연체 구독"* 을 못 긁는다.
대신 `billing_cycle` 에서 `status='FAILED' AND next_retry_at <= now()` 를 긁는다 —
스케줄러가 실제로 원하는 것도 *구독*이 아니라 *재시도할 청구 건*이라 오히려 맞는 방향이다.
**다만 이건 예측이고 D2 에서 검증할 일이다**(§11).

## 5. 같은 ABA 가 주기 **안쪽**에서 재발한다 — 시도 층이 필요한 이유

```
4주기: 시도1 실패 → FAILED
       시도2 성공 → PAID
       시도1의 지연된 결과가 이제 도착한다
```

`FAILED → PAID` 자체는 순환이 아니다(A→B→C 꼴, DAG). 문제는 **한 주기 행이 시도 3번을
다 뒤집어쓴다**는 것 — 저 늦은 결과가 어느 시도의 것인지 행을 봐도 모른다.

그래서 시도마다 종착지 있는 행이 필요하고, 그 행은 **`payment`** 다. 종착지 전이표 ·
낙관적 락 · 멱등 backbone · 장부 연결을 이미 갖고 있어서, 새 테이블(`dunning_attempt`)을
만들면 그걸 **복제**하게 된다.

### 이게 `attempt_count` 컬럼을 안 둔 이유이기도 하다

시도 층이 행이면 횟수는 그 행들을 세면 나온다. 컬럼으로 두면 *"원본과 항상 같아야 하는
값의 복제"* 가 되고, W1D3(재고 Redis)·W2D4(환불 상태)에서 두 번 기각한 그 모양이다.

대가: 엔티티가 상한을 스스로 판정 못 한다 → **인자로 받는다.**
`Payment.refundStatus(long completedAmount)` 가 이미 같은 모양이다 —
**원천은 밖으로, 규칙은 엔티티에**(W3D4).

### `onPaymentFailed` 에 `IGNORED` 가 없다 — 이 설계에서 제일 조심할 자리

시도 2회 연속 실패는 상태가 둘 다 `FAILED` 지만 **서로 다른 사건**이다(`next_retry_at` 이
밀려야 한다). 그래서 이 메서드는 상태만으로 중복을 못 거른다. **전제: 시도 1회당 정확히
한 번 불린다.** 그 보증은 엔티티가 아니라 `payment` 행의 전이표가 준다.

> 시도를 카운터 한 칸으로 뒀다면 이 전제를 세울 곳이 아예 없었다.
> **"시도마다 행"은 선택이 아니라 이 메서드의 성립 조건이다.**

## 6. ★ 진짜 질문은 "구독료는 누구 돈인가" 였다

`payment.order_id` 는 `NOT NULL REFERENCES orders(id)`(V1) 다. 처음엔 이걸 *컬럼 하나*로
봤는데, 재보니 **경로 둘이 딛고 선 칸**이었다.

```
[실측] ① LedgerService.sharesOf() 가 payment.getOrder().getItems() 를 걷어 셀러 안분을 만든다
       → order_item 없는 주문은 shares 가 비고, 분개가 CASH 차변 1줄뿐
       → Journal.forPayment 의 Σ차변==Σ대변 자체검증에서 터진다. "아이템 없는 주문"은 불가

[실측] ② OrderService.place() 가 tx1 에서 stock 을 깎는다 — javadoc: "주문의 유일한 진입점"
       → 주기마다 주문을 만들면 구독료를 받을 때마다 재고가 깎인다

[실측] ③ chk_ledger_seller_presence(V4): CASH 아닌 모든 분개 줄에 seller_id 가 필수
       LedgerAccount 에 "셀러 없는 플랫폼 수익" 계정이 없다
```

③이 질문을 옮겼다. **구독료도 반드시 셀러에 귀속되므로, 정해야 할 건 FK 가 아니라
돈의 방향이었다.**

| | A. 셀러의 정기배송 상품 | **B. 셀러가 플랫폼에 내는 이용료** ← 선택 |
|---|---|---|
| 방향 | 고객 → 셀러 | 셀러 → 플랫폼 |
| `order` | 필요(셀러를 찾는 유일한 경로) | 불필요 |
| 재고 | 매달 차감 — **기능이지 버그가 아니다** | 차감할 물건 없음 |
| 정산 | `SELLER_PAYABLE` 생김 → **정산액에 들어간다** | V8 이 `SELLER_PAYABLE` 만 합치므로 **안 들어간다** |

**B 를 고른 결정적 이유(본인)**: *"정산 안 더러워지는 게 크다."*
A 면 3주치 정산·대사 실측 수치가 전부 재해석 대상이 된다. 부차적으로, A 는
`OrderService` 를 우회하는 두 번째 재고 경로를 요구하고 그 순간 위 ②의 javadoc 이
거짓이 된다 — **W4 가 두 번 데인 "검증 없이 적힌 단정"을 우리 손으로 만드는 셈.**

## 7. B 의 대가를 셌다 — 그리고 한 칸을 틀렸다

`payment.order_id` 를 널 허용으로 바꾸면 깨질 자리를 grep 으로 세었다. **4건.**

| 자리 | 경로 | 조치 |
|---|---|---|
| `PaymentTransitionService:76` `order.onPaymentConfirmed()` | 승인 부수효과 | 형제 진입점으로 분리 |
| `LedgerService:158` `sharesOf` | 승인 부수효과(분개) | `recordSubscriptionCharge` 신설 |
| `PaymentCompletedEvent:46` `getOrder().getId()` | 승인 부수효과(아웃박스) | 발행 안 함(§9 미결) |
| `ReconciliationService:281` `sharesOf` | ~~환불 안분~~ **결제 재구성** | `isSubscriptionCharge()` 로 건너뜀 |

앞의 셋이 **`applyApproved` 의 `onTransitioned` 람다 한 블록**에 몰려 있었다. 그리고
`dispatch()` 가 부수효과를 이미 `Consumer<Payment>` 로 파라미터화해 둬서, **분기문이 아니라
형제 진입점**으로 갈렸다 — 갈아끼울 자리가 설계에 이미 있었다(W4D1 §6 과 같은 성질).

### ★ 넷째 칸을 틀렸다

*"환불 안분 경로라 구독 환불이 생기기 전까지 안 닿는다"* 고 적었고, **V12 주석에도 그렇게
썼다.** 실제로는 `ReconciliationService:218` 의 `reconstructNetBySeller` 가
`findPaidInRange` 로 **그날 PAID 결제를 전부** 훑고 `sharesOf` 를 부른다. 구독 청구가
`PAID` 가 되는 순간 NPE 이고, **대사 배치가 그날 통째로 죽는다.**

**grep 개수는 맞았고 각 건을 열어보지 않은 게 틀렸다.** 세는 것과 읽는 것은 다른 일이다.

수정은 건너뛰기 한 줄인데, **회피가 아니라 정의상 0** 이다 — 구독 분개엔 `SELLER_PAYABLE`
줄이 없고 배치 쪽 V8 집계도 `SELLER_PAYABLE` 만 합치므로 **양쪽이 똑같이 0 을 낸다.**
대사의 두 축이 여전히 같은 답을 내야 한다는 성질이 유지된다.

## 8. 장부 — 계정은 늘리고 저널 타입은 안 늘렸다

```
구독 청구 분개 (2줄, 안분 없음)
    CASH                 차변 amount
    SUBSCRIPTION_REVENUE 대변 amount   (seller_id = 내는 셀러)
```

**`journal.type` 은 안 늘렸다.** `PAYMENT`/`REFUND` 는 *"돈이 들어오는 사건이냐 나가는
사건이냐"* 의 축이고, 구독 청구는 들어오는 사건이라 `PAYMENT` 가 맞다.
`SUBSCRIPTION_CHARGE` 를 만들면 그 축에 *"무슨 돈이냐"* 를 섞게 된다 — **§4 에서 걷어낸
모양을 장부에서 되풀이하는 것.**

**계정은 늘렸다.** 구독료를 `FEE_REVENUE` 에 넣으면 *"판매에서 뗀 수수료"* 와 *"셀러가 낸
이용료"* 가 한 계정에서 섞이고 가를 방법이 사라진다. 정산액(`SELLER_PAYABLE`)은 안
더러워지지만 **수익 계정이 더러워져서, B 를 고른 근거가 절반만 성립하게 된다.**

`seller_id` 의 뜻은 안 바꿔도 됐다 — V4 가 그것을 *"거래상대방이 아니라 분석 차원"* 으로
정의해둔 덕이다. `SUBSCRIPTION_REVENUE` 줄에서 `seller_id` 는 `FEE_REVENUE` 와 **같은
문장**을 뜻한다: *"그 수익이 누구에게서 났나."*

③을 따로 돌린 이유는 §12 ⑥ 참고 — **①+② 를 더한 131 은 실행 결과가 아니라 산수였다.**

`BillingCycleTransitionTest` 19건의 내역:

- **12칸** — 4상태 × 3사건 **전수**(`@ParameterizedTest` + `@MethodSource`, 표가 소스에 그대로)
- **1건** — `표에_빈칸이_없다`: 행 수 == 상태 수 × 사건 수. 상태나 사건이 늘면 여기서 먼저 깨진다
- **6건** — 라벨로 안 드러나는 것: 재시도 시각 박힘 / **자기 루프가 시각만 밈** /
  종착지 둘에서 예약 비움 / `CONFLICT` 가 곁가지도 안 건드림 / `null` 거부

### ★ 테스트를 쓰다가 표와 코드가 갈라진 걸 잡았다

`ABANDONED + 상한초과` 칸이 **javadoc 엔 `CONFLICT`, 코드엔 `IGNORED`** 였다. 코드가 맞다
(이미 포기한 주기를 또 포기하는 건 종착지 재도달 = 멱등). javadoc 을 고쳤다.

이건 §10 이 아니다 — **전이표를 테스트로 옮기는 행위 자체가 낸 값**이다. W4D5 가
*"회귀 테스트는 빈 존재가 아니라 배달 횟수를 잰다"* 로 정리한 것과 같은 자리: 표를
문장으로 두면 코드와 갈라지고, 실행 가능한 형태로 두면 못 갈라진다.

## 11. 음성대조군

27건이 **전부 첫 시도 green** 이다. W4D5 가 *"green/red 를 가른 게 코드가 아니었다"* 로
하루를 쓴 뒤라, 이 테스트들이 **red 를 낼 능력이 있는지**는 따로 봐야 한다.

| | 제거 대상 | 겨누는 것 | **예측(먼저 적음)** | 결과 |
|---|---|---|---|---|
| A | `onPaymentSucceeded` 의 `if (status == ABANDONED) return CONFLICT;` 한 줄 | 종착지 가드 | `ABANDONED+성공` 칸 **1개만** red | 미실행 |
| **B** | `onPaymentSucceeded`·`onRetriesExhausted` 의 `this.nextRetryAt = null;` **두 줄** | 예약 비우기 불변식 | **12칸은 전부 green 유지**, 불변식 **2건만** red | ★ **적중** |
| C | `BillingCycleStatus` 에 값 추가(예: `REFUNDED`) | 표의 완전성 | `표에_빈칸이_없다` red(12≠15), 나머지 26건 green | 미실행 |

### B — 실측 (본인 실행·원복)

```
[실측] 27 tests completed, 2 failed
       BillingCycleTransitionTest:132  성공하면_재시도_예약이_지워진다   FAILED
       BillingCycleTransitionTest:141  포기하면_재시도_예약이_지워진다   FAILED
       전이표 12칸 — 전부 green
       예측 1/1 적중
```

**이게 B 를 고른 이유다.** 상태 전이는 12칸 전부 정상인데, 스케줄러는 이미 끝난 주기를
영원히 집는다. **전이표 테스트만 있었으면 못 잡는 버그**다 — 전이표는 `status` 만 재고
곁가지는 안 잰다.

### ★ 덤 — 같은 필드를 보는 테스트가 못 잡았다

`CONFLICT_는_아무것도_안_바꾼다` 도 `getNextRetryAt()` 이 null 인지를 단언하는데
**green 으로 남았다.** 그 테스트의 `PAID` 주기는 `cycleIn(PAID)` 가 `PENDING → 성공` 으로
만들어서 `nextRetryAt` 이 **애초에 null** 이었기 때문이다 — 지워졌는지를 잰 게 아니라
처음부터 없었던 걸 다시 확인했을 뿐이다.

> **픽스처가 지나온 경로가, 그 테스트가 무엇을 잴 수 있는지를 정한다.**
> W4D5 의 *"테스트가 자기 데이터가 아니라 스위트가 남긴 배치를 재고 있었다"* 와 같은 축이고,
> 클래스 javadoc 에 *"상태를 직접 주입하지 않고 전이로 만든다"* 라고 적어둔 원칙이
> **이 칸에서는 반대로 작용했다** — 전이로 만들었기 때문에 곁가지가 안 심겼다.

A·C 는 미실행이다. 예측은 위 표에 서 있다.
