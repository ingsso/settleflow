## 1. 오늘의 범위 — 계획서 D5 를 반으로 갈랐다

계획서 D5 는 둘이다: **k6 부하 실행** + **최종 문서 정리**. 둘 다 안 했다.

이유는 **W5D4 §11 이 남긴 목록**이다. *"red 를 낼 수 없는 자리가 셋 — W5D5 에서 볼 목록"*
이라고 적어놓고 그 위에 부하테스트를 얹으면, **아무도 안 재는 코드를 부하로 재는** 모양이 된다.
그리고 오늘 확인한 바로는 k6 부하 실행에 **선결 조건이 하나 더 있다**(§7 — 구독 생성 경로).

```
갚은 것    P1 리스   → red 가 생겼다
           STALE 관측 → red 가 생겼다
바뀐 것    백스톱     → red 를 못 내는 게 아니라 ★ 잴 것이 없다는 게 확정됐다
```

## 3. 셋을 한 파일에 모은 기준 — 주제가 아니라 계기의 부재

`DunningBlindSpotTest` 는 P1 리스·백스톱·STALE 관측을 한 클래스에 담는다. **주제는 셋 다
다르다.** 묶은 건 다른 성질이다:

> **없어도 그날의 스위트가 전부 green 이었다.**

W5D2 대조군 D(P1 리스 지워도 21건 green) · W5D4 §8(백스톱 지워도 red 없음) · W5D4 대조군
D(STALE 호출 지워도 red 0). **셋 다 "있는데 아무도 안 보는 것"** 이고, 그건 코드의 위치가
아니라 **테스트의 부재**가 만든 범주라 파일 하나로 묶는 게 맞다고 봤다.

### 계기 둘을 나란히 둔 이유

| | 계기 | 무엇을 뜻하나 |
|---|---|---|
| 헤드라인 | 서로 다른 `merchant_payment_id` 개수 | PG 가 **별개 청구로 볼 것**의 수 (W5D4 축) |
| 교차검증 | `stubPgClient` delegate 호출 수 (Mockito) | **실제로 PG 에 간 횟수** (W5D3 축) |

하나만으로는 안 된다. **키만 보면 우리 DB 안에서 자족하고**(W5D3 이 정정한 자리),
**호출 수만 보면 재전송과 중복 청구를 못 가른다**(재전송은 호출을 늘리면서 키를 안 늘린다).

## 4. ① P1 리스 — 거울이 하나 없었다

W5D2 는 *"열 개가 동시에 폴링해도 청구는 한 번만"* 을 만들었는데 그건 **P2**
(`runRetryDue` → `claimForRetry`)다. **P1**(`runBillingDue` → `claimBillingDate`)을 때리는
짝이 없었고, 그게 W5D2 대조군 D 가 *"P1 리스는 아무도 안 재고 있다"* 로 끝난 이유다.

### 왜 예외가 아니라 키 개수로 단언하나

CAS 를 걷어내면 진 스레드도 새 주기를 만들려 든다. **그때 나는 예외를 단언에 쓰면 DB 제약이
잡아준 것을 재게 된다.** 주장하려는 건 *"돈이 한 번만 나갔다"* 이므로 계기는 **PG 로 나간 키의
수**여야 한다 — 스레드 예외는 삼키고 단언은 키와 호출 수가 낸다.

### ★ 그리고 대조군이 그 판단을 정당화했다 — 제약은 아무도 안 걸렀다

대조군 A 를 다시 걸어 **크기**를 쟀다(§11).

```
[실측] P1 동시 폴링 10개 · CAS 조건 제거 →
       서로 다른 키=10 · PG approve 호출=19 · 주기=10 · 시도=10
```

**`uq_billing_cycle_subscription_no` 가 한 건도 못 걸렀다.** 10 스레드가 전부 자기 주기를
만들었고 `cycle_no` 는 1~10 으로 깔끔하게 나왔다. 예외로 단언했으면 **red 가 아예 안 났을
것**이다.

#### 왜 제약이 안 걸리나 — 행 락이 직렬화하기 때문이다

`claimBillingDate` 는 **같은 구독 행 하나**를 UPDATE 한다. 그래서 10개 트랜잭션이 그 행의
락에서 **줄을 선다** — 동시에 뒤엉키는 게 아니라 **차례로 통과한다**. 각자 자기 차례에
`nextCycleNo()` 를 계산하므로 `max+1` 이 매번 새로 맞고, 번호가 안 겹치니 제약이 걸릴 일이 없다.

```
락이 하는 일    순서를 준다        →  10개가 차례로 지나간다
CAS 가 하는 일  판정을 준다        →  차례가 와도 "이미 남이 집었다" 면 0행
```

Postgres 는 READ COMMITTED 에서 앞 트랜잭션이 커밋되면 **뒤 트랜잭션의 `WHERE` 를 새 행
버전으로 다시 평가한다.** `next_billing_date = :expected` 가 거기 있으면 재평가에서 떨어져
0행이 되고, 없으면 그냥 통과한다. **직렬화는 공짜로 얻고 있었고, CAS 는 그 줄에서 승자를
가리는 일만 한다.**

> W5D2 는 이 리스를 *"동시에 집는 걸 막는다"* 로 설명했는데, 정확히는 **동시에 집히지도
> 않는다** — 락이 이미 갈라놨다. 리스가 없으면 **차례로, 아주 질서정연하게, 열 번 청구가
> 나간다.** 무질서가 아니라 **질서 있는 열 번**이라는 게 이 대조군의 그림이다.

#### PG 호출 19 — 재전송이 뒤처리를 하고 있었다

키 10 인데 호출이 19 다. 차이 **9** 는 `k6/dunning-race.md` §3 이 세운 항등식 그대로다:

```
PG 호출 증가분 − 서로 다른 키 개수 = 재전송 횟수      19 − 10 = 9
```

뒤 스레드들이 `findOpenPendingCycleIds` 로 **앞 스레드가 막 만든 `PENDING` 주기를 회수
대상으로 집었고**, 그 주기엔 미결 시도가 있으니 **새 청구가 아니라 재전송**으로 나갔다.
**W5D4 의 재전송이 피해를 키 10 에서 멈춰 세운 것**이다 — 그게 없었으면 19 개의 서로 다른
키가 나갔다.

*(9 라는 수는 [실측] 셋에서 따져 나온 값이다 — 시도 행이 10 인데 호출이 19 이고, 기존 행을
다시 보내는 경로는 재전송뿐이다. 재전송 로그를 이 테스트가 직접 세지는 않는다.)*

> **이 수는 시스템의 고유값이 아니다.** *"10 동시 폴링에서 이만큼 샌다"* 이고 스레드 수를
> 올리면 커진다(W4D4 가 고아 수를 두고 세운 태도와 같다).

## 5. ★ ② 백스톱 — 도달 가능한지를 오늘의 실험으로 만들었다

선택지가 셋이었다: (A) 도달 가능한지를 실험한다 / (B) 상태를 DB 로 심고 백스톱만 잰다 /
(C) 지운다. **A 를 골랐다.** B 는 red 를 만들되 아무것도 증명하지 않는다 — 프로덕션이 못 만드는
상태를 테스트가 만들어놓고 *"막았다"* 고 하는 건 W4 회고 §4-2 가 경계한 모양이다.

### 계기를 프로덕션 코드 밖에서 얻었다

`SubscriptionChargeService.abandon` 의 *"시도를 걸기 전 상한 판정"* 로그는 **집기 직전
백스톱에서만** 찍힌다. 통보 경로의 포기(`applySubscriptionFailure`)는 이 줄을 안 남긴다.
그래서 **이 문자열의 등장 횟수 = 백스톱 발화 횟수**다. 프로덕션 코드를 안 바꾸고 얻은 계기라
W4D1 이 회로를 데코레이터로 뺀 것과 같은 계열이다.

### 세 경로를 태웠고 셋 다 0회다

```
경로1  사다리 소진        4번째 실패 통보 → applySubscriptionFailure 가 ABANDONED
                          → 집히는 집합을 먼저 떠난다.            백스톱 0회
경로2  4번째가 타임아웃    UNKNOWN = 미결 → findUnresolvedAttemptId 가 먼저 잡아
                          재전송으로 빠진다.                      백스톱 0회
경로3  웹훅이 미결을 닫음  countConcludedAttemptsExcluding + 1 = 4 → ABANDONED
                          → 미결이 사라지는 순간 주기도 떠난다.    백스톱 0회
```

**경로2 가 오늘의 알맹이다.** 결말난 시도가 **4개**(상한 초과)인 주기가 **다시 집히는데도**
백스톱에 안 닿는다 — 재전송 분기가 그 앞에 있기 때문이다.

### 논증 — 나머지 경로도 못 닿는다 (실행 아님)

백스톱이 발화하려면 *"미결 없음 + 결말난 시도 ≥ 4 + 아직 집히는 주기"* 가 동시에 서야 한다.

```
결말이 FAILED 로 나면  → 통보가 사다리를 보고 4번째에 ABANDONED. 집히는 집합을 떠난다
결말이 UNKNOWN 이면    → 그 자신이 미결이라 "미결 없음"이 안 선다 → 재전송
```

즉 **4번째 결말은 반드시 `FAILED` 여야 하는데, 그 순간 주기가 종착지로 간다.** 그래서 세 조건이
동시에 서는 상태가 없다. **이건 코드를 읽어 세운 논증이고 실행이 아니다** — 실행한 건 위 세
경로다.

### 그래서 W5D4 의 판단이 부정됐다

W5D4 §8 은 *"없애면 안 된다 — 실패가 확정된 시도가 쌓이는 경로에서는 여전히 마지막 벽"* 이라고
적었다. **그 경로를 지목하지 않았고, 오늘 찾아보니 없다.** 어제 판단이 틀렸다기보다
**어제 스스로 만든 재전송이 그 전제를 없앴는데 그걸 같은 날 못 알아본 것**이다 —
W5D3·W5D4 에 이어 *"전제가 만료됐다"* 가 **사흘 연속**이다.

> ~~**지울지는 오늘 안 정했다.**~~ → **대조군 D 가 닫았다(§11).** [실측] 재전송 분기를 걷어내자
> **백스톱이 그 자리에서 1회 발화**했다. 죽은 코드가 아니라 **조건부로 잠든 코드**다.
> **남긴다** — 다만 지키는 대상이 *시나리오*가 아니라 **재전송 전제의 회귀**이므로, 그 의존을
> 코드 주석으로 못 박았다(`stageAttempt` javadoc).

## 6. ③ STALE — 쿼리를 재면 안 되는 자리였다

W5D4 대조군 D 는 `reportStaleUnresolved` **호출**을 지웠는데 red 가 0 이었다. 여기서
`countStaleUnresolvedAttempts` 쿼리만 테스트하면 **그 대조군은 여전히 green 이다** — 호출이
사라져도 쿼리는 멀쩡하기 때문이다. **호출의 결과**를 재야 하고, 지금 그 결과는 로그뿐이라
Logback `ListAppender` 로 잡았다.

양쪽을 다 본다: 갓 만들어진 미결은 **조용해야** 하고, 6시간을 넘긴 미결은 **소리를 내야** 한다.
앞쪽이 없으면 *"항상 경고한다"* 는 구현도 통과한다.

> **한계**: 재는 대상이 **로그 문자열**이다. 메시지를 바꾸면 깨지는데 그건 동작 변화가 아니다.
> 메트릭 승격(W5D4 이월 3)을 오늘 **안 골랐다** — 오늘은 red 를 채우는 날이지 관측을 늘리는
> 날이 아니라고 봤다. 이월은 그대로 남는다.

## 7. k6 시나리오 ③ — 설계까지 (`k6/dunning-race.md`)

### ★ k6 가 부하 발생기가 아니다

①②는 k6 가 HTTP 를 쏘면 그게 곧 부하였다. ③은 **부하원이 스케줄러 자신**이다 — Dunning 은
폴링으로 스스로 깨어나고, 밖에서 트리거하는 경로를 만들면 **프로덕션에 없는 모양**을 재게 된다.
그래서 동시성의 출처를 **앱 인스턴스 다중화**로 잡았다(리스가 겨누는 게 정확히 그것이다).
**k6 는 시딩 규모·표집·판정 쪽으로 물러난다.**

### 정정 — P1 의 충돌 창은 좁지 않다

선택지를 내밀 때 다중 인스턴스 방식을 *"창이 좁아 우연에 맡긴다"* 고 적었는데 **P1 에는
틀렸다**. `next_retry_at`(P2)은 주기마다 흩어져 있어 한 시각의 도래분이 적지만,
`next_billing_date`(P1)는 **날짜**라 그날 도래분이 통째로 한 배치다. `ORDER BY` 가 같아
인스턴스들이 **같은 목록을 같은 순서로 훑으므로 배치 전체가 경합 대상**이다.
→ 헤드라인 시나리오는 **P1**.

### 계기와 항등식

```
PG 호출 증가분  −  서로 다른 키 개수  =  재전송 횟수
```

부하 환경에서는 Mockito 가 없으므로 교차검증 계기를 `/actuator/prometheus` 의
`resilience4j_circuitbreaker_calls_seconds_count{name="pg-approve"}` 로 잡는다 —
`ResilientPgClient.approve` 가 이 회로로 감싸여 있어 **승인 호출이 전부 이 카운터를 지난다**.
성립 조건 둘을 **실행 조건으로** 못 박았다: 회로가 닫힌 채 끝날 것, 그 실행에 주문 결제가
섞이지 않을 것(카운터가 전역이다).

### 설계 중에 드러난 것 — k6 가 진짜 쓰이는 레이스는 따로 있다

*"동시에 여러 재시도 트리거"* 에서 **트리거의 종류가 둘**이다: 폴러와 **웹훅**. 폴러가 리스를
잡고 PG 를 부르는 사이 직전 시도의 웹훅이 도착하면 같은 주기의 사다리가 다시 계산된다.
**이쪽은 HTTP 라 k6 가 실제로 부하를 줄 수 있다.** W5D4 가 고친 off-by-one
(`countConcludedAttemptsExcluding`)이 정확히 이 경로이고 **단건으로만 검증됐다.**
③-b 로 세울지 ③에 합칠지는 실행일 판단으로 남겼다.

## 9. 프로덕션 **실행** 코드는 안 건드렸다

**`feat:` 이 없다** — 다섯 주 만에 처음이다. 의도한 결과다: 오늘 겨눈 셋은 전부 **이미 있는
코드**이고, 없던 것은 **그것을 보는 눈**이었다.

> **정확히**: 대조군 D 결과가 나온 뒤 `SubscriptionChargeService.stageAttempt` 에 **주석을
> 추가했다**(`docs:` 커밋). 실행 코드는 한 줄도 안 바뀌었지만 *"프로덕션 파일을 안 열었다"* 는
> 아니므로 적어둔다 — §12 ②를 지키려면 이 구분이 필요하다.

## 10. Claude 오류

| | 단정 | 어떻게 드러났나 | 실제 |
|---|---|---|---|
| ① | Q1 선택지 셋을 **"k6 가 부하를 준다"** 는 공통 전제 위에 짰다 | 사용자가 B 를 고른 뒤 설계에 들어가자마자 | **그 전제가 B 에서 무너진다**(§7). 선택지를 내밀 때 **셋이 공유하는 전제**를 안 적었고, 그래서 사용자는 *"부하를 어디서 만드나"* 가 아니라 *"k6 를 어디에 쏘나"* 만 고르게 됐다. 선택지의 폭이 아니라 **바닥**이 좁았다 |
| ② | 다중 인스턴스 방식을 *"창이 좁고 우연에 맡긴다"* 로 적었다 | 같은 설계 중에 | **P1 에는 틀렸다**(§7 정정). 그대로 갔으면 사용자가 고른 선택지가 *"약한 대신 진짜"* 로 문서에 남을 뻔했다. 실제로는 P1 배치 전체가 경합 대상이라 약하지 않다 |
| ③ | ② 선택지를 내밀며 *"코드를 따라가면 그 상태가 안 만들어진다"* 까지만 적었다 | 대조군 D 를 설계하면서 | **무엇이 막고 있는지를 못 짚었다.** 원인은 어제 넣은 재전송 분기이고, 그걸 짚어야 *"죽은 코드"* 와 *"조건부로 잠든 코드"* 가 갈린다. 진단을 *"안 닿는다"* 에서 멈추면 §5 의 마지막 판단(지울까)이 근거 없이 내려진다 |

| ④ | 대조군 A 의 크기를 **2~4** 로 예측했다 | 실측 **10** | **모델이 틀렸다.** *"`uq_billing_cycle_subscription_no` 가 같은 번호를 낸 무리를 거른다"* 고 봤는데, **행 락이 이미 직렬화**해서 겹치는 번호가 안 생긴다(§4). 제약은 한 건도 안 걸렸다 |

**①이 제일 나쁘다.** 틀린 사실이 아니라 **선택의 바닥을 안 보여준 것**이라, 사용자가 고른 뒤에야
전제가 드러났다.

**④는 성질이 다르다 — 이건 값을 냈다.** 예측을 먼저 적고 *"10 이 나오면 내 모델이 틀린 것"*
까지 같이 적어둔 덕에, 나온 수가 **모델을 반증하는 수**로 읽혔다. 그리고 그 반증이
*"직렬화는 공짜로 얻고 있었고 CAS 는 승자를 가릴 뿐"* 이라는 §4 의 설명을 끌어냈다 —
W3 회고 §4 이래 반복된 **"값은 어긋난 칸에서 나온다"** 가 또 한 번이다. W5D4 오류 ①(*"선택지가 둘"* 이라 단정해 세 번째를 닫음)과 **같은 계열이
이틀 만에 반복**됐다 — 그때는 선택지를 덜 냈고 이번엔 전제를 안 냈다.

## 11. 음성대조군 — 예측만, 실행은 사용자

예측을 먼저 적고 **넷 다 본인이 실행했다(4/4 적중).** 각각 따로, 전체 스위트로 돌렸다.

| | 제거 대상 | 겨누는 것 | **예측(먼저 적음)** | 결과 |
|---|---|---|---|---|
| **A** | `claimBillingDate` 의 `AND next_billing_date = :expected` | P1 리스 | **정확히 1건 red** — 오늘 만든 동시 폴링 1건만, 나머지 165건 green. ★ 지는 모양이 **예외가 아니라 키 개수**(1 기대 → 2 이상) | ★ **적중**(1건 red · `assertThat(keys)`) — 다만 **크기 예측은 빗나갔다**: 2~4 로 봤는데 **10** 이다(§4·§10 ④) |
| **B** | `stageAttempt` 의 백스톱 3줄 | 집기 직전 백스톱 | ★ **red 0건 — 166건 전부 green.** 오늘 만든 3건도 안 진다(세 경로 전부 발화 0회이므로) | ★ **적중 — red 0** |
| **C** | `runRetryDue` 의 `reportStaleUnresolved(now)` 호출 | STALE 관측 | **1건 red** — `aged` 가 1 이 아니라 0 | ★ **적중** — `expected: 1L but was: 0L` (`:328`) |

### A·C — 오늘 갚았다고 쓴 두 자리가 확인됐다

```
[실측] A  P1 리스 제거 → 166건 중 1건 red · DunningBlindSpotTest:167 = assertThat(keys)
          ★ 진 자리가 헤드라인 단언이다 — DB 제약이 던진 예외가 아니라 키 개수로 졌다
[실측] C  STALE 호출 제거 → 166건 중 1건 red · expected: 1L but was: 0L
          미결 1건 → 갓 만들어졌을 때 경고 0회 · 7시간 지난 뒤 누적 0회 (원래는 0 → 1)
```

**A 의 지는 모양이 예측대로였던 게 값이다.** CAS 를 걷어내면 `uq_billing_cycle_subscription_no`
가 일부 스레드를 예외로 떨어뜨리는데, 그 예외로 졌으면 **DB 제약이 잡아준 것을 잰 것**이라
리스에 대해 아무 말도 못 한다. 실제로는 `keys` 단언에서 졌다 — *"서로 다른 키가 둘 이상 나갔다"*
= **PG 에 별개 청구가 둘 이상 갔다**는 뜻이고, 그게 이 리스가 막으려던 바로 그것이다.

**C 는 W5D4 대조군 D 가 red 0 이던 자리다.** 같은 제거가 이제 red 1 을 낸다.

### ★ A 를 다시 걸어 크기를 쟀다 — 그리고 예측이 틀렸다

첫 A 실행에선 **키가 몇 개 나갔는지를 못 봤다**(이어서 C 를 돌리며 `cleanTest` 가 결과 XML 을
지웠고 콘솔엔 `[실측]` 줄이 없었다). *"막았다"* 는 증명됐는데 *"안 막으면 얼마나 새나"* 가
비어 있어 다시 걸었다 — W4D4 의 *"고아 수는 혼자 두면 값이 아니다"* 와 같은 자리이고,
**대조군의 red 도 크기를 같이 봐야 값이 된다.**

```
예측(먼저 적음)  키 2~4 · PG 호출도 같은 값 · 실행마다 흔들린다
                 근거: uq_billing_cycle_subscription_no 가 같은 번호를 낸 무리를 거른다
                 ★ "10 이 나오면 내 모델이 틀린 것" 이라고 같이 적었다

[실측]           서로 다른 키=10 · PG approve 호출=19 · 주기=10 · 시도=10
                 단언은 expected 1L but was 10L
```

**10 이 나왔다.** 제약은 한 건도 못 걸렀고, `cycle_no` 는 1~10 으로 깔끔했다. 원인은 §4 에
적었다 — **행 락이 이미 직렬화하고 있어서** 각자 자기 차례에 `max+1` 을 새로 계산한다.
겹치는 번호가 아예 안 생기니 제약이 걸릴 자리가 없다.

**그리고 이게 §4 의 단언 설계를 사후에 정당화했다.** 예외로 단언했으면 **red 가 아예 안 났다** —
*"제약이 잡아주니까 안전하다"* 는 초록불을 받았을 것이고, 그건 W5D1 이래 여러 번 나온
*"경로를 안 밟은 초록불"* 의 가장 나쁜 형태였을 것이다.
| **D** | `stageAttempt` 의 재전송 분기 전체 | **B 의 원인** | **6건 red** — W5D4 재전송 4건 + `DunningSchedulerTest` UNKNOWN 1건 + 오늘 경로2 1건. ★ 그리고 경로2 의 red 안에서 **백스톱 발화가 0 → 1**, 주기가 `FAILED` → `ABANDONED` | ★ **적중** |

### D 가 오늘의 핵심이었고, 적중했다

```
[실측] 재전송 분기 제거 → red 6건 · ★ 백스톱 발화 0회 → 1회
```

B 만 보면 *"백스톱은 죽은 코드"* 로 끝난다. **D 는 무엇이 죽였는지를 보였다** — 백스톱은 원래
살아 있었고 어제의 재전송 분기가 그 앞을 막은 것이다. **한 줄이 사라지자 그 자리에서 즉시
발화했다.**

그래서 §5 의 미결 판단이 닫힌다:

| | 실측 | 뜻 |
|---|---|---|
| **B (백스톱 제거)** | **166건 전부 green** | **아무도 이 줄을 안 지킨다** |
| **D (재전송 제거)** | **백스톱 1회** | **재전송이 사라지면 즉시 살아난다** |

> **B 를 정확히 읽을 것**: green 은 *"도달 불가"* 의 증명이 아니라 **"이 스위트에 그걸 지키는
> 테스트가 없다"** 이다. 도달 불가는 §5 의 세 경로 실측 + 논증이 세운다. 둘은 다른 주장이고,
> B 하나로 앞엣것까지 말하면 W5D1 이래 여러 번 잡은 *"초록불은 경로를 안 밟았다는 뜻"* 을
> 그대로 되밟는다.

**둘은 모순이 아니다.** 백스톱이 지키는 것은 *오늘의 어떤 시나리오*가 아니라
**"미결을 재전송으로 흡수한다"는 전제 자체가 사라지는 것**이다. 그건 시나리오가 아니라
**회귀**라, 테스트가 아니라 이 자리에 남는 코드가 막는다.

> **결정: 남긴다.** 다만 *"마지막 벽"* 이라는 W5D4 의 표현은 여전히 틀렸다 — 벽이 아니라
> **재전송 분기에 딸린 안전장치**다. 그 의존을 코드에 적어둔다(§5).

### 곁가지 — 거짓 red 하나 (B 1회차)

B 의 첫 실행은 **166건 중 1건 red** 였는데, `CircuitBreakerSmokeTest` 의 **컨텍스트 기동
실패**였다:

```
ApplicationContextException → TomcatWebServer → Connector
  → java.net.SocketException: Bad address: listen
```

**단언 실패가 아니라 소켓 바인딩 실패**다. 같은 코드로 같은 날 세 번 green 이었고, 2회차에서
재현되지 않아 **환경 일시 실패**로 판정했다.

기록해두는 이유는 **읽는 법이 다르기 때문**이다 — W5D2 의 거짓 red 는 *회로가 스위트를 넘어
남은 것*이라 **우리 격리 설계의 결함**이었지만, 이건 우리 코드 밖이다. 다만 둘 다
**"red 를 봤을 때 먼저 물을 것은 무엇이 red 인가"** 라는 같은 교훈을 낸다. 대조군의 판정을
그 자리에서 내렸으면 *"백스톱을 지우니 뭔가 깨졌다"* 로 잘못 적었을 것이다.

## 13. 체크리스트용 메모

> W5D5 — 계획서 D5(k6 실행 + 최종 문서)를 **반으로 갈라** k6 는 설계까지만 하고, W5D4 가 남긴
> **"red 를 낼 수 없는 자리 셋"** 을 갚았다. [실측] **P1 동시 폴링 10개 → 서로 다른 키 1개 ·
> PG approve 호출 1회** — W5D2 가 만든 P1 리스를 닷새 만에 처음 잰다(그때 만든 짝은 P2 였다).
> ★ **백스톱은 죽었고 죽인 것은 어제의 재전송이다**: 세 경로 전부 발화 0회이고, **상한을 넘긴
> 주기가 다시 집혀도**(결말난 시도 4 · 집은수 1) 재전송 분기가 앞을 막아 시도도 키도 4에서
> 안 움직인다. W5D4 가 *"마지막 벽이라 남겨뒀다"* 고 쓴 근거가 실행으로 부정됐다 —
> *"전제가 만료됐다"* **사흘 연속**. 계기는 프로덕션 코드를 안 바꾸고 얻었다(백스톱에서만
> 찍히는 로그). STALE 은 **쿼리가 아니라 호출의 결과**를 재야 대조군이 red 가 된다.
> ★ **k6 는 이 시나리오에서 부하 발생기가 아니다** — Dunning 은 폴링으로 스스로 깨어나므로
> 부하원은 인스턴스 다중화이고 k6 는 계기 쪽으로 물러난다. 어제 *"창이 좁다"* 고 한 것도
> **P1 에는 틀려서 정정**했다. 전체 **166건 green**, **프로덕션 코드 무변경(`feat:` 없는 첫 날)**.
> ★ 음성대조군 **A·B·C·D 예측 4/4 적중**(본인이 넷 다, 각각 전체 스위트로). **A** P1 리스 제거
> → 1건 red, ★ **키 개수 단언에서 졌다**(DB 제약 예외가 아니라 — 그래야 리스를 잰 것이다).
> **C** STALE 호출 제거 → 1건 red(`expected 1 but was 0`), W5D4 에서 red 0 이던 자리다.
> **B·D 는 짝으로 읽는다** — B: 백스톱을 지워도 **166건 전부 green**(아무도 그 줄을 안 지킨다) /
> D: 재전송 분기를 걷어내자 **red 6건 + 백스톱이 그 자리에서 1회 발화**. 그래서 백스톱은
> **죽은 코드가 아니라 그 분기에 딸린 안전장치**이고 **남긴다**(지키는 대상이 시나리오가 아니라
> *전제의 회귀*라 테스트가 아니라 주석으로 못 박았다). B 1회차에 **거짓 red 하나**
> (`CircuitBreakerSmokeTest` 소켓 바인딩 — 우리 코드 밖, 재현 안 됨).
> ★ **A 를 다시 걸어 크기까지 쟀다: 키 10 · PG 호출 19 · 주기 10**(예측 2~4 는 **빗나갔다**).
> `uq_billing_cycle_subscription_no` 가 **한 건도 못 걸렀다** — **행 락이 이미 직렬화**해서
> 각자 자기 차례에 `max+1` 을 새로 계산하기 때문이다. 즉 **직렬화는 공짜로 얻고 있었고 CAS 는
