## 1. 오늘의 범위 — 계획서 항목의 **전제**를 반증했다

계획서 D3 는 이렇게 적혀 있다:

> *"Week 1 의 Idempotency-Key 구조를 재시도에도 적용, 중복 청구 방지"*

이 문장은 **키를 적용하면 중복 청구가 막힌다**를 전제한다. W5D2 §5 에서 그 전제를 의심할
근거가 나왔고(*"PG 멱등키는 같은 시도의 재전송을 막지 같은 주기의 두 시도를 못 막는다"*),
오늘은 그걸 **실측으로 세웠다.**

**계획서·결정서 전제를 근거를 갖고 폐기 — 7주 연속**
(재고 Redis W1 → 보상 트랜잭션 W3D2 → 조인 키 W3D4 → DLT W4D5 → 전이표 W5D1 →
Quartz W5D2 → **오늘**).

다만 오늘은 앞의 여섯과 성질이 다르다. **앞의 것들은 "다른 방법으로 하겠다"였고, 오늘은
"그 방법으로는 이 문제가 안 풀린다"** 다 — 대안을 제시한 게 아니라 **문제와 도구가 서로 안
겨눈다**는 걸 보였다. 해결책은 §11 이월로 남는다.

## 3. 구멍 — 웹훅은 형제 진입점을 몰랐다

W1D3 설계에서 크래시·무응답을 회수하는 경로는 **웹훅**이다. 구독 청구도 같은 `payment`
행을 쓰므로 같은 웹훅이 온다. 그런데:

```
[실측·코드읽기] WebhookController:84 (어제까지)
    case APPROVED -> transitionService.applyApproved(...)
    → 분기가 없다. 언제나 주문 결제용 문으로 들어간다
```

터뜨려봤다:

```
[실측] 구독 청구에 APPROVED 웹훅 → HTTP 500
       java.lang.NullPointerException: Cannot invoke "Order.getItems()"
         because the return value of "Payment.getOrder()" is null
           at LedgerService.sharesOf(LedgerService.java:186)
           at LedgerService.recordPayment(LedgerService.java:44)

       멱등키 = null  ← 지워졌다
       payment UNKNOWN 유지 · 주기 PENDING 유지 · journal 0 · 분개 0줄
```

### 멱등키가 지워진 게 더 나쁘다

`WebhookController:72-76` 이 `RuntimeException` 에 키를 지우고 500 을 던진다. 그 설계 의도는
*"일시적 실패니까 재전송이 다시 처리하게"* 인데, **이건 일시적이 아니라 영구 결함**이다 —
PG 가 재전송하고 매번 다시 500 이고 그때마다 키가 또 지워진다. **회수 실패가 아니라 무한
재전송 루프**다. W4D5 가 *"무한 재시도라고 적혀 있던 자리"* 에서 데인 것과 같은 종류다.

> 이 구멍은 D1 이 만들었다. `order` 를 전제하는 자리를 4건 세고 형제 진입점으로 갈랐는데,
> **그 형제를 누가 부르는지는 안 봤다.** 동기 경로만 새 문을 쓰고 웹훅은 옛 문에 남았다.

## 4. 누가 분기하나 — 형제 진입점이 안 통하는 첫 경로

D1 의 원칙은 *"분기문이 아니라 형제 진입점"* 이었다. 그건 **자기가 무엇을 하는지 아는
호출자**를 위한 설계다. 동기 경로는 안다. **웹훅은 정의상 모른다** — PG 가 우리 도메인을
알 리 없으니 바디에 종류가 실려 오지 않고, 아는 건 `merchantPaymentId` 뿐이다.

| | 자리 | 대가 |
|---|---|---|
| A | `WebhookController` 가 먼저 조회하고 형제를 고른다 | 원칙 유지. 대신 조회 1회 추가 + 예외 처리가 두 곳 |
| **B** | **전이 서비스가 읽은 자리에서 고른다** ← 선택 | 읽기 1회, 틈 없음. 대신 분기문이 생긴다 |

A 의 *"조회와 전이 사이 틈"* 은 무해하다 — `payment.billing_cycle_id` 는 `updatable=false`
이고 배타적 아크가 CHECK 로 고정이라 **결제의 종류는 생성 후 안 바뀐다.** 그러니 A 도
성립하지만, **모르는 호출자에게 알라고 요구하면 그 지식이 컨트롤러로 샌다.**

### seam 이 이미 있었다

D1 이 부수효과를 `Consumer<Payment>` 로 파라미터화해 둔 덕에, seam 을 **값에서 선택자로**
올리는 것만으로 라우팅이 들어왔다:

```java
dispatch        (…, Consumer<Payment> onTransitioned)              // 아는 호출자
dispatchSelecting(…, Function<Payment, Consumer<Payment>> effectFor) // 모르는 호출자
```

전자가 후자에 위임한다. W4D1 §6 · D1 §7 과 같은 성질 — **갈아끼울 자리가 설계에 이미 있었다.**

> 오버로드로 두려다 컴파일이 막혔다: 람다는 `Consumer` 와 `Function` 양쪽에 맞아 모호하다.
> 이름을 갈랐고(`dispatchSelecting`), 결과적으로 **호출부에서 어느 쪽인지가 이름에 드러난다.**

## 5. 결말 규칙을 한 곳으로 — 호출부가 둘이 되자 드러난 복제

거절 웹훅은 승인과 **대칭이 아니다.** 주문 결제의 거절은 부수효과가 없지만, 구독 청구의
실패는 *"언제 다시 걸 것인가"* 를 정해야 한다. 그런데 D1 의 API 는:

```
applySubscriptionDeclined(mpid, pgTx, nextRetryAt)   ← 시각을 인자로 요구
applySubscriptionExhausted(mpid, pgTx)               ← 상한 판정이 끝나 있어야 함
```

**둘 중 무엇을 부를지를 호출부가 정했다.** 호출부가 폴러 하나일 땐 문제가 없었는데, 웹훅이
두 번째 호출부가 되는 순간 그 규칙을 양쪽에 복제해야 한다. 웹훅은 간격 규칙도 시도 수도
모르는데도.

**그래서 결말을 전이 서비스로 내렸다** — `applySubscriptionFailure(mpid, pgTx, failedAt)` 하나.
이제 폴러와 웹훅이 **같은 문**을 쓴다.

```
SubscriptionChargeService  ─┐
                            ├─→ applySubscriptionFailure ─→ 세고 → 정책에 묻고 → 엔티티 호출
WebhookController          ─┘
```

순환 의존이 안 생긴다: 정책(`DunningPolicy`)은 순수 함수고 시도 세기는 이미
`PaymentRepository` 에 있다. `SubscriptionChargeService` 를 부를 필요가 없다.

> **D1 이 이름으로 가른 건 그대로다.** `onPaymentFailed` / `onRetriesExhausted` 라는 엔티티
> 메서드 둘은 유지되고, 갈린 자리가 *서비스 진입점*에서 *엔티티 호출*로 한 칸 내려갔을 뿐이다.

## 6. ★ 호출부가 늘자 전제가 깨졌다 — off-by-one

실패 결말은 *"이번을 포함해 몇 번째냐"* 를 물어서 세어진 값에 `+1` 한다. 그 계산이 맞는
근거는 **이번 시도가 아직 `PENDING` 이라 안 세어진다**는 것이었다.

```
폴러  방금 만든 행이라 PENDING          → +1 맞다
웹훅  먼저 타임아웃돼 UNKNOWN 일 수 있다  → 이미 세어지는 쪽에 있다 → +1 하면 한 번을 두 번 센다
```

두 번 세면 `concluded=2` 가 되어 사다리가 **1일이 아니라 3일**로 건너뛴다. 그래서 결말
처리는 언제나 `countConcludedAttemptsExcluding(cycleId, paymentId)` 를 쓴다 — 이번 시도를
빼고 세면 현재 상태와 무관하게 항상 맞다.

`countConcludedAttempts`(빼지 않는 쪽)는 **이번 시도가 없는** 자리에서만 쓴다 —
집기 직전 백스톱(W5D2 §8).

```
[실측] 구독 거절 웹훅 → payment FAILED · 주기 FAILED · 다음 재시도 24시간 뒤
       (겹쳐 셌다면 72시간이 나온다 — 그 값을 단언으로 잠갔다)
```

**이 버그는 웹훅이 생기기 전까지 존재하지도 않았다.** 전제가 틀린 게 아니라, 전제를
성립시키던 조건(호출부가 하나)이 사라졌다.

## 7. ★ 반증 — 두 문장을 나란히 세운다

```
문장1  키는 정상이다      같은 시도를 몇 번 통보해도 부수효과는 1회
문장2  그런데 돈은 두 번   같은 주기에 시도가 둘이면 PG 호출도 둘
```

둘 다 참이므로 결론은 ~~**"멱등키는 중복 청구를 막는 물건이 아니다"**~~ 다.
키가 지키는 건 *같은 시도의 재전송*이고, 이중 청구는 *같은 주기의 두 시도*에서 난다.

> **정정(W5D4)**: 이 결론이 한 칸 넓다. 정확히는 ***"우리가 재전송해야 할 자리에서 새 시도를
> 만들었다"***. 아래 [실측] 둘은 그대로 참이고, 넓은 건 그것들로부터 끌어낸 문장이다.
> 경위는 §7 끝의 정정 상자.

### 문장1

```
[실측] 같은 merchantPaymentId 에 eventId 를 매번 바꿔 승인 웹훅 20회
       → journal 1 · 분개 2줄 · 현금 30,000
```

`eventId` 를 매번 다르게 보내 **Redis SETNX 를 일부러 우회시켰다**(W1D4 음성대조군 A 와 같은
수법). 막은 건 fast-path 가 아니라 `payment` 전이표다 — SETNX 는 효율이고 정합성은
종착지 판정이 지킨다.

### 문장2 — 리스가 정당하게 지는 경로

```
tx1  리스 커밋 + PENDING 시도 A          ← 여기까지는 남는다
---- PG 청구 나감 (돈이 움직였다) ----
     크래시                              ← tx2 가 영영 안 온다
---- 리스 만료 ----
tx1' 리스 재획득 + PENDING 시도 B
---- PG 청구 또 나감 ----                ← 같은 주기, 두 번째 돈
```

```
[실측] 크래시 직후: 주기 FAILED · 시도 2개(그 중 PENDING 1 = 고아)
       리스 만료 후 재집기 → 시도 3개
       ★ PG approve 호출 = 3회        (원 청구 1 + 크래시난 청구 1 + 재청구 1)
       ★ 서로 다른 merchantPaymentId = 3개
```

A 와 B 는 **서로 다른 키**를 갖는다. PG 는 둘을 정당한 별개 청구로 처리한다 — **멱등키가
개입할 자리가 없다.** 키가 고장난 게 아니라 이 문제를 겨누는 물건이 아니다.

### 왜 키를 주기 단위로 주면 안 되나

*"같은 주기의 두 시도에 같은 키를 주면 되지 않나"* — 그러면 **시도 층이 무너진다.**
W5D1 이 시도마다 행을 만든 이유가 *"시도 1회당 정확히 한 번"* 이라는 전제를 세우기
위해서였고(`BillingCycle.onPaymentFailed` 는 상태만으로 중복을 못 거른다), 두 시도가 한 키를
공유하면 그 전제가 사라진다. ~~**한쪽을 고치면 다른 쪽이 깨지는 자리다.**~~

> ### ★ 정정 (W5D4) — 선택지가 둘이 아니라 셋이었다
>
> 위 문단까지는 맞다. **마지막 문장이 틀렸다** — 세 번째 선택지를 못 봤다.
>
> ```
> 새 시도 B 를 만든다     새 청구. PG 에겐 별개 건        행이 는다
> 키를 주기 단위로        두 시도가 한 키를 공유          시도 층이 무너진다
> 시도 A 를 재전송        같은 시도의 재전송              ★ 안 무너진다
> ```
>
> 결말이 안 난 시도는 *"새 청구가 필요하다"* 가 아니라 *"답을 아직 못 들었다"* 이고,
> 같은 키로 다시 보내는 건 **재전송**이다. 행이 안 늘고, 상한 계산도 안 흔들리며
> (`PENDING` 은 애초에 안 세고 `UNKNOWN` 은 이미 세어졌다), 결과 통보는 그 행의 전이표가
> 흡수한다. **이 문서가 바로 위에서 *"키가 지키는 건 같은 시도의 재전송"* 이라고 정확히
> 적어놓고, 그 도구를 안 쓴 채 결론을 냈다.**
>
> 따라서 §7 첫머리의 결론 *"멱등키는 중복 청구를 막는 물건이 아니다"* 도 한 칸 넓다.
> 정확히는 ***"우리가 재전송해야 할 자리에서 새 시도를 만들었다"*** 다.
> 문장1·문장2 의 [실측]은 그대로 참이고, **그것들로부터 끌어낸 결론이 넓었다.**
> → [W5D4](W5D4_재전송으로_이중청구_창_닫기.md) §3

## 8. 계기를 바꿨다 — 어제 수치가 잰 것

```
[실측·어제] 동시 폴링 10개 → 이 주기의 payment 행 = 2개
```

**이중 청구의 정의는 "PG 에 승인 요청이 두 번 갔다"** 이지 "우리 행이 두 개다"가 아니다.
어제는 대리 지표로 쟀고, 그 대리가 성립하는 근거는 *"한 시도 = 한 PG 호출"* 인데 그건
**검증 대상 코드 자신의 성질**이다 — W4 회고 §4-2 의 그 모양.

오늘은 `@MockitoBean(name = "stubPgClient")` 로 delegate 를 갈아끼우고 **Mockito 로 PG 호출
횟수를 직접 센다**(W4D1 `PgCircuitBreakerTest` 가 세운 패턴). 회로를 가진
`ResilientPgClient` 는 그대로 남으므로 프로덕션 경로를 통과한다.

> 어제 수치가 틀린 게 아니라 **증명 범위가 좁았다**: *"우리가 시도 행을 하나만 만들었다"*
> 까지고 *"PG 에 한 번만 갔다"* 는 아니었다. 어제 체크리스트에 **"청구 1회"** 라고 쓴 건
> 그 범위를 넘은 요약이다(§9 ②).

| | 단정 | 어떻게 드러났나 | 실제 |
|---|---|---|---|
| ① | W5D1 에서 형제 진입점을 만들며 **웹훅 배선을 안 했다** | 오늘 크래시 회복 경로를 따라가다 발견, HTTP 500 재현 | `order` 를 전제하는 자리는 4건 다 셌는데 **그 형제를 누가 부르는지**를 안 봤다. D1 §10 ②(*"세는 데 성공하고 여는 데 실패했다"*)와 같은 모양이 하루 만에 재발 |
| ② | 어제 체크리스트에 *"동시 폴링 10개 → **청구 1회**"* | 오늘 계기를 PG 호출 수로 바꾸면서 | 잰 건 **payment 행 수**다. 문서 본문(§9 ④)엔 정확히 적었는데 요약에서 *"청구"* 로 승격시켰다 — **한 칸 넓은 주장** |
| ③ | 라우팅을 바꾸면서 기존 테스트 영향을 안 봤다 | 전체 스위트에서 `PaymentFlowTest` 3건 red | 스파이가 `applyApproved` 를 걸고 있었다. 바꾸기 전에 *"웹훅 진입점을 겨누는 테스트가 있나"* 를 확인했어야 했다 |
| ④ | Mockito 스텁을 `given(mock.method())` 로 재설정 | 테스트가 스텁 재설정 줄에서 터짐 | 그 형태는 메서드를 **실제로 호출**한다. 직전에 예외 스텁이 걸려 있으면 거기서 던진다. `will…given` 으로 통일 |

**①이 제일 나쁘다.** 어제 문서에 *"세는 것과 읽는 것은 다른 일"* 이라고 적어놓고, 같은
종류를 **바로 다음 날 발견**했다. 다만 이번엔 성질이 조금 다르다 — 어제는 *호출부를 안
열어본* 것이고, 오늘 건 *새로 만든 문을 아무도 안 쓰게 둔* 것이다. **만든 것과 이은 것이 다르다.**

**③은 결과적으로 신호였다.** 깨진 3건은 *"웹훅이 무엇을 부르나"* 를 재는 테스트가 실재한다는
뜻이고, 그게 없었으면 라우팅 변경이 조용히 통과했을 것이다.

## 10. 음성대조군

예측을 먼저 적고 본인이 실행했다.

| | 제거 대상 | 겨누는 것 | **예측(먼저 적음)** | 결과 |
|---|---|---|---|---|
| **A** | `applyApprovedFromWebhook` 의 종류 분기 | 라우팅 | 승인 웹훅 1건 + 문장1 1건 = **2건 red**(둘 다 500). 거절 웹훅 · 주문 웹훅 · 문장2 는 green | ★ **적중** |
| **B** | `countConcludedAttemptsExcluding` → 일반 count | off-by-one | 거절 웹훅 **1건만** red(24시간 → 72시간). ★ 사다리 · 문장1 · 문장2 · 승인 웹훅 **전부 green** | ★ **적중 — 72 나옴** |
| C | `applyDeclinedFromWebhook` 의 구독 분기 | 거절 라우팅 | 거절 웹훅 1건 red — 주기가 `PENDING` 인 채 예약이 안 박힌다 | 미실행 |
| D | `claimForRetry` 의 `next_retry_at <= :now` | 리스 CAS(W5D2 이월) | 동시 폴링 1건 red(payment 11행). ★ 오늘 만든 3건은 **전부 green** — 거기 동시성 시나리오가 없다 | 미실행 |

### A — 고친 게 진짜 고쳐졌는지의 증명

분기를 빼자 §3 의 HTTP 500 이 그대로 돌아왔다. **상설 테스트가 그 구멍을 실제로 잡는다** —
어제까지는 아무도 안 잡고 있었다는 뜻이기도 하다.

주목할 건 red 가 **2건**이라는 것이다. 승인 웹훅 테스트뿐 아니라 **문장1**도 깨진다 —
멱등을 재는 테스트가 라우팅에 의존한다. 구독 청구로 멱등을 재려면 먼저 웹훅이 도착할 수
있어야 하기 때문이고, **어제였다면 문장1 자체를 쓸 수 없었다.**

### B — 새로 생긴 경로에서만 드러나는 버그

```
[실측] 24시간 자리에 72 가 찍혔다 (concluded=2 → 사다리 두 번째 칸 3일)
       사다리 · 문장1 · 문장2 · 승인 웹훅 — 전부 green 유지
```

W5D2 대조군 B 와 같은 성질이 한 번 더다: **정상 경로는 다 green 인데 새 경로만 red.**
다만 오늘 건은 한 겹 더 있다 — 이 off-by-one 은 **웹훅이라는 두 번째 호출부가 생기기
전까지는 존재하지도 않았다.** 코드가 틀렸던 게 아니라, 코드를 맞게 만들던 조건(호출부가
하나)이 사라진 것이다. *"버그를 넣었다"* 가 아니라 *"전제가 만료됐다"* 에 가깝다.

## 11. 정직한 한계 / 이월

### 이 문서에서 **추론이지 실행이 아닌 것**

| | 주장 | 상태 |
|---|---|---|
| ① | §3 의 *"PG 가 재전송하며 무한 500 루프"* | **재현 안 함.** 500 한 번과 멱등키가 지워진 것까지가 실측이고, PG 의 재전송 동작은 스텁이 흉내내지 않는다 |
| ② | §7 의 *"크래시 시점에 PG 에서 돈이 실제로 빠져나갔다"* | 스텁 기준이다. Mockito 가 센 건 **호출**이고, 진짜 PG 의 과금 여부는 우리 계기 밖이다 |
