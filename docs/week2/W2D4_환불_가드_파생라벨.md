## 0. 계획서 항목의 변형 — 왜 "상태머신"이 아닌가

계획서 Day 4 는 *"환불 상태머신 구현(`PAID → PARTIAL_REFUNDED → REFUNDED`)"* 이었다. 그런데 상태를 **저장하지 않고 파생**하기로 하자(§1) 저 화살표는 전이가 아니게 된다 — 상태가 스스로 옮겨가는 게 아니라 `refunded_amount` 가 바뀌면 라벨이 따라 붙을 뿐이다.

**상태머신의 정의**: *(현재 상태, 사건) → 다음 상태 **또는 거부***. 값어치는 바꿔주는 게 아니라 **거부하는** 데 있다. `Payment.onApproved()` 에서 실제로 일하는 건 `FAILED → CONFLICT` 가지이고, `onTimedOut()` 의 `if (status != PENDING) return IGNORED` 는 종착지를 못 움직이게 하는 가드다(W1D3 에서 세 번 반복한 실수를 구조로 막는 자리).

파생 라벨은 사건을 받지 않고 자기가 어디서 왔는지도 모른다 → **아무것도 못 막는다.**

| | `PaymentStatus`(기존, 진짜 상태머신) | `RefundStatus`(오늘) |
|---|---|---|
| 입력 | (현재 상태, **사건**) | 금액 두 개 |
| 출력 | 다음 상태 **또는 거부** | 라벨 |
| 과거를 아나 | 안다(→ CONFLICT 판정 가능) | 모른다 |
| 막을 수 있나 | **그게 존재 이유** | **못 막는다** |

막는 일이 사라지진 않는다 — **옮겨간다**(§2). 그래서 오늘 만든 것의 정직한 이름은 *"환불 상태머신"* 이 아니라 **"요청을 받아줄지 판정하는 가드 + `refunded_amount` 에서 파생되는 라벨"** 이다. W1D3 에서 계획서의 Redis 락 항목을 근거를 갖고 폐기한 것과 같은 종류의 변형.

## 1. 상태를 저장하지 않는다

`RefundStatus` 는 `refunded_amount` 와 `amount` 의 함수다:

```
refunded_amount == 0        → NOT_REFUNDED
0 < refunded_amount < amount → PARTIAL_REFUNDED
refunded_amount == amount    → REFUNDED
```

**저장하면 진실이 둘로 갈라진다.** 금액과 라벨이 각각 갱신되면 어긋날 수 있다 — W1D3 에서 *"재고의 진실이 Redis 와 DB 로 갈라진다"* 며 Redis 락을 폐기한 것과 같은 모양. 파생이면 `refunded_amount` 가 환불의 **유일한 진실원본**이고, 그래서 그 컬럼의 원자적 갱신(§3)이 금액뿐 아니라 **라벨의 정확성까지** 책임진다.

### 딸려온 소득 둘

- **두 축이 안 섞인다.** 파생이라 `PaymentStatus` 에 `PARTIAL_REFUNDED` 를 끼워넣을 이유가 없다 → 결제 진행 축(`PENDING/PAID/FAILED/UNKNOWN`)과 환불 진행 축이 한 컬럼에서 안 만난다.
- **"REFUNDED 에서 추가 환불 금지" 가드가 불필요해진다.** `refunded_amount == amount` 면 `+x <= amount` 가 어떤 양수 x 에도 거짓이라 §3 의 SQL 이 자동으로 막는다(실측: §4-6).

### 어디서 계산하나 — A1 채택, A2 승격 조건 명시

| | 방식 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| **A1**(채택) | `Payment` 의 메서드 | 단순. 규칙이 도메인 객체에 | **SQL 로 못 묻는다** |
| A2 | Postgres `GENERATED ALWAYS AS ... STORED` | SQL 조회·인덱스 가능하면서 **진실은 여전히 하나**(DB 가 계산을 강제) | 표현식이 스키마에 박힘. enum 캐스팅의 immutable 조건 통과 여부 **미검증** |
| A3 | 뷰 | 조회 가능·유연 | 인덱스 불가, 매핑 애매 |

지금은 SQL 로 물을 일이 없어 A1. **승격 트리거를 미리 적어둔다** — *W3D3 정산 배치나 W3D4 대사가 이 라벨로 SQL 필터를 걸어야 해지면 A2 로 올린다.* (안 적어두면 W3 에서 같은 논쟁을 처음부터 다시 한다.)

### 정의역 — 조회는 던지고, 명령은 반환한다

파생식은 금액만 보므로 `PENDING` 결제에 물으면 `refunded_amount == 0` 이라 태연히 **"환불 없음"** 이라 답한다 — 거짓말이다. 애초에 받은 돈이 없어 환불이라는 축이 성립하지 않는다.

→ **정의역은 `PAID` 인 결제뿐**, 밖에서의 호출은 `IllegalStateException`.

그런데 환불 **요청**이 `PENDING` 결제로 들어오는 건 다르다 — 버그가 아니라 **정상적으로 예상되는 외부 입력**이다. 예상되는 입력을 예외로 처리하지 않는다(W1D4 에서 중복 웹훅에 예외 대신 `TransitionResult` 를 돌려주기로 한 그 선). 그래서:

- **조회**(`refundStatus()`) → 정의역 밖은 **예외**(프로그래밍 오류)
- **명령**(`requestRefund()`) → 거부는 **반환값**(`RefundResult`)

`TransitionResult` 를 재사용하지 않은 이유도 여기 붙는다. **`IGNORED` 가 없다** — 결제 승인은 같은 사건이 또 오면 중복이지만, 5,000원 환불 요청 두 번은 중복이 아니라 **진짜 환불 2건**일 수 있다(실측: §4-7). 거기다 거부 사유가 갈라져야 한다 — `NOT_REFUNDABLE`(영영 안 됨)과 `PAYMENT_UNKNOWN`(조회하면 될 수도)은 재시도 가능성이 정반대다(W1D1 §3: `UNKNOWN` 은 실패가 아니라 정보의 부재).

## 2. 가드 분업 — 겹치는 게 아니라 나뉜다

| # | 막을 것 | 앱 | SQL | DB CHECK |
|---|---|:--:|:--:|:--:|
| 1 | `PENDING` 환불 | ● | | |
| 2 | `FAILED` 환불 | ● | | |
| 3 | `UNKNOWN` 환불 | ● | | |
| 4 | 0원·음수 | ● | | ● `chk_refund_amount` |
| 5 | 잔액 초과 | | ● | ● `chk_payment_refunded_amount` |
| 6 | 전액환불 후 추가환불 | | ● | ● |

**W2D3 과 모양이 다르다.** 어제(앱 `assertBalanced` + DB 트리거)는 같은 것을 두 층에서 지키는 **이중방어**였다. 오늘은 **분업**이다 — 앱은 결제의 *자격*을, SQL 은 *금액*을 본다. 1~3 은 앱만, 5~6 은 SQL 만 막는다. 4 만 양쪽에 있고 DB CHECK 는 앱을 우회한 경로용 백스톱.

6 이 5 에 흡수되는 게 §1 의 파생 선택이 준 배당이다.

## 3. 판정을 어디서 — (가) 아니라 (나)

```
(가)  잔액 조회 → 앱에서 "충분한가?" 판단 → 충분하면 UPDATE
(나)  조건부 UPDATE 실행 → affected rows 가 판정 그 자체        ← 채택
```

(가)는 읽기와 쓰기 사이에 틈이 있고, 동시 환불들이 그 틈에서 **같은 잔액을 읽어 전부 통과**한다(lost update). W1D2 `RefundRaceTest` 에서 한도 조건을 WHERE 에서 뺐더니 8,000 이어야 할 값이 **11,000** 이 된 그 자리.

```sql
UPDATE payment
   SET refunded_amount = refunded_amount + :amount, updated_at = now()
 WHERE id = :paymentId
   AND refunded_amount + :amount <= amount      -- 판정과 실행이 한 문장
```

- **네이티브인 이유**: `refunded_amount` 가 엔티티에서 `updatable = false` — JPA 로는 못 쓰고 이 경로로만 쓴다(W1D2 설계). `@PreUpdate` 도 안 타므로 `updated_at` 을 직접 갱신.
- **`AND status = 'PAID'` 를 넣지 않았다**: `PAID` 는 전이표의 종착지라 밖으로 나가는 화살표가 없어(`onApproved`/`onDeclined` 모두 PAID 를 안 움직임) 앱 가드와 이 UPDATE 사이에 레이스가 없다. **PAID 를 떠나는 전이가 생기면 반드시 추가해야 한다**(주석에 명시).
- **앱은 금액을 안 본다.** 사전 안내가 필요하면 그건 UX 계층의 일이지 정합성 가드가 아니다.

금액 누적(UPDATE)과 `refund` 행 INSERT 는 **한 트랜잭션** — 갈라지면 잔액과 이력이 드리프트한다(`Refund` 클래스 주석).

## 4. 실측 (전부 실행 결과)

`RefundGuardTest` — 9 케이스:

| 케이스 | 관측 |
|---|---|
| 1. `PENDING` 환불요청 | `NOT_REFUNDABLE` / refunded=0 / refund행=0 |
| 2. `FAILED` 환불요청 | `NOT_REFUNDABLE` / refunded=0 / refund행=0 |
| 3. `UNKNOWN` 환불요청 | **`PAYMENT_UNKNOWN`** — `NOT_REFUNDABLE` 과 다른 값 / refund행=0 |
| 4. 0원·음수 | `INVALID_AMOUNT` ×2 / refunded=0 / refund행=0 |
| 5. 15,000 후 잔액 5,000 에 6,000 | `ACCEPTED` → `EXCEEDS_REMAINING` / refunded=15,000 / refund행=1 |
| 6. 전액환불 후 1원 | `ACCEPTED` → `EXCEEDS_REMAINING` / 라벨=`REFUNDED` (별도 가드 없이 막힘) |
| 7. 같은 5,000 두 번 | `ACCEPTED`, `ACCEPTED` / refunded=10,000 / **refund행=2** |
| 8. 부분환불 3번 | 라벨 `NOT_REFUNDED → PARTIAL → PARTIAL → REFUNDED` / refunded=20,000 / refund행=3 |
| 9. `PENDING` 에 `refundStatus()` | `IllegalStateException` (조용한 거짓말 대신) |

거부 케이스는 전부 **금액 불변 + refund행 0** — 부작용 0. 7·8 의 `refund행=2`/`3` 이 "환불엔 `IGNORED` 가 없다"(§1)를 실제로 보여준다.

`RefundConcurrencyTest` — **프로덕션 경로**로 (나)를 검증:

> 20,000 결제에 5,000원 환불을 **10 스레드 동시**(요청 50,000 vs 용량 20,000)
> → **ACCEPTED=4, EXCEEDS_REMAINING=6, refunded_amount=20,000, refund행=4, 라벨=REFUNDED**

W1D2 `RefundRaceTest` 와 다른 점: 그건 테스트가 손으로 만든 임시 테이블에 JDBC 로 직접 UPDATE 를 쐈다 — *"이 모양의 SQL 이면 된다"* 를 증명했지 *"우리 코드가 그렇게 돼 있다"* 는 증명하지 않았다. 여기선 `RefundService.requestRefund` 를 그대로 부른다(Spring 트랜잭션 경계·JPA 영속성 컨텍스트·실제 스키마가 다 낀 상태).

## 5. 음성대조군 — W1D2 와 다르게 나왔고, 그게 더 많은 걸 알려줬다

`WHERE` 의 `AND refunded_amount + :amount <= amount` 한 줄을 제거하고 재실행 → **3건 빨간불**(케이스 5·6 + 동시성). 그런데 **실패한 방식**이 W1D2 와 다르다:

```
ERROR: new row for relation "payment" violates check constraint "chk_payment_refunded_amount"
  Detail: Failing row contains (..., PAID, 20000, 20001, ...)   ← 케이스 6
  Detail: Failing row contains (..., PAID, 20000, 21000, ...)   ← 케이스 5
→ org.springframework.dao.DataIntegrityViolationException
```

| | W1D2 (임시 테이블) | W2D4 (실제 스키마) |
|---|---|---|
| 가드 제거 시 | **11,000 이 조용히 써짐** | **예외** — 값은 지켜짐 |
| 증명된 것 | WHERE 가 유일한 방어선 | 방어선이 **둘**이다 |

차이의 원인은 W1D2 테스트 테이블엔 CHECK 가 없었다는 것. 그래서 오늘 확인된 `WHERE` 한 줄의 진짜 역할은 **"과다환불을 막는 것"이 아니다** — 막는 건 `chk_payment_refunded_amount` 도 한다. `WHERE` 가 하는 일은:

> **거부를 예외가 아니라 `0행` 이라는 반환값으로 만드는 것.**

§1 에서 세운 *"예상되는 입력은 예외가 아니라 반환값"* 원칙이 정확히 저 SQL 한 줄에 얹혀 있었다. 설계 원칙과 구현이 같은 지점에서 만난 자리.

원복 후 전체 **40건 0실패** 재확인(diff 는 순수 추가 58줄, 삭제 0).

## 6. 정직한 한계 / 이월

- **동시성 테스트의 음성대조군 실패 모드는 미기록.** 케이스 5·6 의 예외는 확인했지만, `RefundConcurrencyTest` 가 어떤 모양으로 깨졌는지는 메시지를 뽑기 전에 전체 회귀가 결과 XML 을 덮어썼다. 추정하지 않고 미검증으로 남긴다.
- **파생의 대가 — `em.refresh()`.** 네이티브 UPDATE 는 영속성 컨텍스트를 모르므로 메모리의 `Payment` 가 낡는다. `refundStatus()` 가 최신을 보게 하려고 새로고침을 넣었다. **상태를 저장했으면 엔티티에 세팅하고 끝이었을 비용** — 파생을 택했기 때문에 생겼다. 정직하게 적어둔다.
- **A2 승격 판단은 W3 로 이월**(조건은 §1 에 명시).
- **`AND status = 'PAID'` 부재는 "PAID 가 종착지"라는 현재 전이표에 의존한다.** 전이표가 바뀌면 깨진다 — 코드 주석과 여기 양쪽에 남긴다.
- **역분개(reversing entry) 미착수** — Day 5. 오늘 만든 `Refund.journal` 은 아직 null 이고, **환불이 장부에 전혀 반영되지 않은 상태**다. 즉 지금은 결제 분개만 있고 환불은 금액·이력에만 있다.
- **반올림 `.5` 경로는 여전히 미검증**(W2D2 §5 → W2D3 §4 에서 두 번 이월). 부분환불 수수료 안분에서 Day 5 에 반드시 만난다.
- **주말 체크포인트("부분환불 3번 반복해도 장부 불변식이 안 깨짐")는 절반만 됐다** — 부분환불 3번은 §4-8 로 확인, 장부 불변식 쪽은 역분개가 생기는 Day 5 에.
