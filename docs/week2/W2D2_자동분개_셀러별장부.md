## 0. 왜 셀러별로 쪼개나

W2D1 은 `journal + ledger_entry` 를 만들며 20,000 결제를 **3줄**(현금 / 셀러미지급금 / 수수료수익)로 그렸다. 그 예시는 **셀러 1명을 암묵 가정**한 자리였다.

현실은 한 주문이 여러 셀러의 상품을 담는다 — `order_item → product → seller`. 그러면 `SELLER_PAYABLE` 을 **한 줄**로 적을 때 *"누구에게 얼마를 갚아야 하나"* 를 장부가 모른다. Week 3 의 "셀러별 일 매출 집계"가 바로 이 정보를 요구하는데, 한 줄짜리 미지급금은 그걸 **장부 밖**(주문 테이블 역산)에서 재구성하게 만든다 — 그 순간 **장부가 정산의 진실원본이 아니게 된다.** 이는 W2D1 이 C 방식을 고른 이유(무결성·대사)와 정면 충돌.

→ `SELLER_PAYABLE`·`FEE_REVENUE` 를 **셀러별로 쪼갠다.**

---

## 1. 세 번의 갈림길

### 1.1 갈림길 1 — 미지급금을 셀러별로 쪼갤까 → **쪼갠다**

안 쪼개면 Week 3 대사가 장부 밖을 역산 → 장부가 진실원본이 아니게 됨(§0). 비용은 `CASH` 줄처럼 셀러가 없는 줄이 생긴다는 것뿐이고, 역산 비용보다 싸다.

### 1.2 갈림길 2 — 수수료수익도 쪼갤까 → **쪼갠다**

합쳐서 1,000 한 줄로 적으면, 미지급금·현금을 다 알아도 *"셀러 A 의 수수료가 얼마였나"* 를 **복원할 수 없다**(A 의 원 매출을 모르니까). 합친 줄은 되돌릴 수 없는 정보 손실. 셀러별로 적으면 "누구에게서 얼마 벌었나"가 장부에 남는다.

셀러 A 12,000 / B 8,000 (요율 5%):

```
차변                     대변
현금  20,000             셀러미지급금(A)  11,400
                         셀러미지급금(B)   7,600
                         수수료수익(A)       600
                         수수료수익(B)       400
─────────               ─────────
Σ차변 20,000       ==    Σ대변 20,000   ✓
```

셀러 N명이면 `2N + 1` 줄. **계정 3개는 그대로** — 계정이 는 게 아니라 `SELLER_PAYABLE`/`FEE_REVENUE` 에 **차원(누구)** 이 하나 붙었을 뿐.

`seller_id` 의 뜻이 이 결정으로 바뀐다: `SELLER_PAYABLE` 에선 "갚을 상대", `FEE_REVENUE` 에선 "이 수익이 누구에게서 났나". 같은 컬럼, 다른 의미 — 즉 **거래상대방이 아니라 분석 차원**이다. 그래서 엔티티는 `@ManyToOne` 이 아니라 생 `Long` 으로 매핑하고(장부는 Seller 로 항해하지 않는다), 무결성은 DB FK 가 지킨다.

### 1.3 갈림길 3 — 누가 분개를 조립하나: B1(엔티티가 수수료 계산) vs B2(서비스가 쪼개서 넘김) → **B2**

W1 원칙 재사용: *엔티티가 전이표를 소유하고, 서비스가 부수효과를 소유한다*(`PaymentTransitionService`).

- **불변식 `Σ차변==Σ대변`** 은 journal 이 *무엇인가*의 본질 → 엔티티(`Journal`)가 소유.
- **수수료 쪼개기**(요율 × subtotal + 반올림)는 **가격 정책**이고 `Seller.fee_rate` 라는 **외부 데이터**를 읽어야 함 → 서비스(`LedgerService`)가 소유.

`Journal` 은 서비스가 조립을 틀렸으면 `assertBalanced()` 로 잡는 **가드**가 된다. B1 은 엔티티가 Seller 를 조회하게 만들어 이 경계를 흐린다.

### 확정 모델 (V4 반영)

```
journal        id · type(enum) · created_at                         ← 사건 헤더 (W2D1)
ledger_entry   id · journal_id(FK) · account(enum) · dr_cr(enum) · amount(BIGINT,>0)
               + seller_id(FK→seller, nullable)                     ← 분석 차원(W2D2)
seller         + fee_rate(bp INT, NOT NULL DEFAULT 500, CHECK 0..10000)
payment/refund + journal_id(FK, nullable, UNIQUE)                   ← 원인이 journal 가리킴 (W2D1)
```

- **`chk_ledger_seller_presence`**: `CASH` 면 `seller_id` 없고, 아니면 반드시 있다. 판정에 **자기 행의 두 컬럼**만 필요해 CHECK 로 표현된다 — W1D1 §1 *"CHECK 는 자기 행 하나만 본다"* 의 **뒤집힌 면**(그때는 한계였던 게 여기선 자격 요건). Day 3 의 `Σ차변==Σ대변` 이 CHECK 로 안 되는 것과 정반대(그건 여러 행 합).
- 엔티티 `Seller` 생성자가 `fee_rate` 기본값 500 을 넣는다 — JPA 가 INSERT 에 컬럼을 포함하므로 DB DEFAULT 는 생 INSERT 에만 먹기 때문.

## 2. 반올림 정책 — 균형을 계산이 아니라 구조로

**수수료만 반올림하고, 미지급금은 빼서 구한다.**

```
fee     = round(subtotal × bp / 10000)     // 정수 나눗셈은 버림 → (subtotal×bp + 5000)/10000
payable = subtotal − fee                    // 계산이 아니라 정의
```

`payable` 을 뺄셈으로 정의하면 `payable + fee == subtotal` 이 **정의상** 성립한다 — 반올림을 어떻게 하든(올림·내림·반올림 섞어도) 깨지지 않는다. 각각 반올림했다면 예: 셀러 몫 10원·5% 에서 `fee=1, payable=10` → 합 11 ≠ 10 으로 그 journal 이 Day 3 에서 불균형으로 잡혔을 것.

여기에 `현금 = payment.amount = Σsubtotal` 을 대입하면:

```
Σ대변 = Σ(payable + fee) = Σsubtotal = 현금 = Σ차변
```

**균형이 구조상 항상 성립**한다. 따라서 `assertBalanced()` 는 평소엔 늘 통과하고, 오직 서비스가 조립을 틀렸을 때만 빨간불 — 정확히 가드의 역할(안전벨트).

## 3. 타이밍·배선 — W1 을 그대로 재사용

- 자리: `PaymentTransitionService.applyApproved` 의 **TRANSITIONED 부수효과**(W2D1 §3). `ledgerService.recordPayment(payment)` → `payment.linkJournal(journal)`. tx2 안이라 **PAID 상태와 journal 이 원자적으로** 함께 커밋되거나 함께 롤백.
- LAZY walk(`order→items→product→seller`)도 tx2 안이라 안전(W1D5 트랜잭션 경계).
- **이중계상 방어**: 분개를 TRANSITIONED **1회에만** 만들면, W1D4 의 멱등 backbone(SETNX fast-path + 상태가드·@Version)이 그대로 막는다. 같은 승인이 20번 와도 전이 1회 → journal 1개. Week 1 위에 Week 2 가 조립되는 자리.
- **CONFLICT(취소된 주문 + 늦은 승인)** 도 분개는 **남긴다** — 돈은 실제로 들어왔으므로(승인은 사실). 이상은 주문/재고 쪽(이중판매)이지 현금이 아니다. `recordOrderAnomaly` 가 따로 기록.

## 4. 실측 (전부 실제 실행 결과)

| 시나리오 | 관측 |
|---|---|
| 단일 셀러 결제(20,000, 5%) | journal **1** · entries **3** · 현금 20,000 = 미지급금 19,000 + 수수료 1,000 · **균형** |
| 다중 셀러(12,000+8,000) | entries **5**(=2N+1) · 미지급금 2줄 · 수수료 2줄 · 차변=대변=20,000 |
| 같은 결제 승인 **20회** | journal **1** · entries 3 (이중계상 방어 물증) |
| `assertBalanced` 불균형 입력 | `IllegalStateException`("불균형") — 가드에 이빨 확인(영구 테스트) |
| `chk_ledger_seller_presence` | `CASH`+셀러 / `SELLER_PAYABLE`+셀러없음 **양방향 거부**, 올바른 조합 통과 |

- 음성대조군(멱등): TRANSITIONED 가드를 손으로 제거 → journal ~21 로 **빨간불 확인 후 원복**.
- 테스트 인프라 회귀 수정: 공유 컨테이너 클래스가 3개로 늘자 `@Container` 의 클래스별 stop 이 캐시된 Spring 컨텍스트를 고아로 만들어(`total=0` 커넥션 타임아웃) 터짐 → **싱글턴 컨테이너 패턴**(start 한 번, 안 끔) + 정리 로직을 베이스로 중앙화(FK 안전 순서).

## 5. 정직한 한계 / 이월

- **반올림의 실제 반올림 경로가 미검증.** 실측 fixture 가 요율 5% 에 20,000·12,000·8,000 을 써 전부 정확히 나눠떨어졌다 — `(subtotal×bp+5000)/10000` 의 **반올림이 실제로 일어나는 케이스**(소수점 .5 발생)를 아직 안 걸었다. 반올림 로직 자체의 정확성은 Day 3 또는 별도 케이스로 검증할 것. (개발 중 fixture 에 `5`(bp) 를 `500` 으로 착각해 `fee=10` 이 나온 오류가 실측에 걸려 잡힘 — 코드 반올림은 정상.)
- **`assertBalanced` 가드는 실제 흐름에선 안 터진다** — §2 대로 구조상 늘 균형이라, 프로덕션에서 이 가드가 발동하는 일은 설계상 없다(안전벨트). 이빨은 단위 테스트로만 확인.
- **`long` 오버플로 미가드**: `subtotal × bp` 는 이론상 오버플로 가능(비현실적 금액). 지금 범위 밖.
- **`Σ차변==Σ대변` DB 제약은 없다** — Day 3. 오늘은 앱 계층(`assertBalanced`)뿐. "여러 행 합 불변식을 DB 가 어떻게 강제하나"가 Day 3 의 핵심(W1D1 §1 과 만남).
- **부분환불 역분개** — Day 5. 오늘 분개는 결제(PAYMENT)만.
- **`PaymentAnomaly` 는 여전히 로그** — Week 3 대사 배치와 함께 테이블로.
