# Week 2 Day 1 — 이중장부(Ledger) 설계

**날짜**: 2026-07-19
**산출물**: 데이터 모델 결정(`journal` + `ledger_entry`, C 방식 FK). DDL·엔티티는 내일(`V3__`)로 이월.
**방식**: 개념(회계 규약)은 받고, 모델은 본인이 초안 → 선택지+트레이드오프 → 재선택

> **주의: 오늘은 전부 설계 결정이다. 코드·실측 없음** — W1D1 과 같은 성격의 설계 문서.
> 수치는 아직 하나도 실행되지 않았다(증거 원칙).

---

## 0. 왜 장부를 추가하나

현재 스키마는 `payment.status` + `refund` 합계로 *"얼마 받았나"*는 안다. 하지만 Week 3 의 **정산·대사**(셀러에게 얼마 주나, PG 리포트와 우리 장부가 맞나)는 **돈이 어느 계정에서 어느 계정으로 갔는지**의 불변 기록을 요구한다. 상태 필드로는 그걸 못 만든다 — 그래서 이중장부를 얹는다.

---

## 1. 이중장부 기본기 (찾아보는 규약)

1. 모든 돈의 사건은 **최소 2줄**로 기록된다. 한 줄은 **차변(debit)**, 다른 줄은 **대변(credit)**, 각각 **계정과목** 위에.
2. **불변식: 한 사건 안에서 `Σ차변 == Σ대변`.** 깨지면 돈이 허공에서 생기거나 사라진 것.
3. 장부는 **append-only** — 지우지 않고 **역분개를 새로 추가**해 고친다.

3번은 W1D1 §5 *"지우개가 아니라 빨간 펜"* 과 같은 원칙이다 — 본인이 이미 적어둔 것.

### 20,000 결제 한 건 (본인 도출 — "수수료 떼고" 한 마디 힌트로 3줄 분개를 세 계정으로 쪼갬)

```
차변                    대변
현금        20,000      셀러 미지급금   19,000
                        수수료수익       1,000
─────────              ─────────
Σ차변 20,000    ==    Σ대변 20,000     ✓ 균형
```

- **현금 차변** = 우리 자산 20,000 증가(돈이 들어옴)
- **셀러 미지급금 대변** = 셀러에게 갚을 **부채** 19,000 발생 — 이 돈은 우리 게 아니다
- **수수료수익 대변** = 그중 1,000 만 진짜 우리 수익

(수수료율 5%는 비즈니스 파라미터. **구조**가 핵심.)

## 2. 모델 — 두 번의 갈림길

### 2.1 엔티티 초안 (본인)

`id · payment_id · 계정과목 enum · 차대변 enum · 금액 · 생성일`

잘한 두 칸(W1D3 교훈 적용):
- **`updated_at` 없음** — 장부는 append-only 불변 테이블. W1D3 §5 *"`updated_at`은 이 행은 변한다는 선언"* 이 그대로 적용.
- **차대변 enum + 양수 금액** — 부호 있는 금액/두 컬럼보다 읽기 쉬움. enum 은 `@Enumerated(STRING)`(ORDINAL 이면 순서 바꿀 때 저장된 뜻이 통째로 바뀜, W1D3 §5).

### 2.2 갈림길 1 — 줄에 `payment_id`(평평) vs `journal` 묶음 → **B 채택**

**스트레스 테스트(부분환불)**: 결제 20,000 에서 5,000 부분환불 시 역분개가 생기는데, 환불 줄도 같은 `payment_id` 를 달면 **원 결제 3줄과 환불 3줄이 한 바구니에 섞인다.**
- *"환불 #1 하나의 분개만 꺼내와"* 가 안 된다.
- 불변식을 **사건 단위**로 검증 못 한다(결제+환불 전체 합만 보임).

→ **B: `journal` 헤더로 사건 단위 묶음.** `payment_id` 는 줄 하나하나의 속성이 아니라 **사건의 속성**이라 한 층 위로 올라간다.

### 2.3 갈림길 2 — `journal` 이 원인을 가리키는 법: polymorphic vs FK → **C 채택**

- **A. polymorphic (`type` + `source_id`)**: 컬럼 한 쌍으로 어떤 원인이든. 하지만 `source_id` 는 FK 를 못 건다(type 따라 다른 테이블) → **참조 무결성 없음.** 없는 결제를 가리키는 고아 journal 을 DB 가 못 막는다.
  - **이 프로젝트에서 치명적**: 장부는 대사의 진실원본이고, `journal→없는 payment` 는 Week 3 대사가 잡아야 할 불일치의 전형이다. 그걸 스키마에 처음부터 심는 꼴. 게다가 V1 은 전면 진짜 FK 라 그 일관성이 처음 깨지는 자리.
- **C. 원인이 `journal` 을 가리킴**: `payment.journal_id`·`refund.journal_id` 가 진짜 FK 로 journal 을 가리킨다. **무결성 최상.**
  - 트레이드오프: *"journal 만 보고 원인 찾기"* 는 `type` 보고 해당 테이블 역조회(감수).

**무결성 대 유연성의 저울에서, 이 프로젝트는 무결성(대사)에 주제가 걸려 있어 C.**

### 확정 모델

```
journal        id · type(enum: PAYMENT/REFUND/…) · created_at      ← 사건 1개 = 헤더
ledger_entry   id · journal_id(FK→journal) · 계정과목(enum) · 차대변(enum) · 금액(BIGINT, CHECK>0)
payment/refund + journal_id(FK→journal, nullable)                  ← 원인이 journal 을 가리킴
```

전부 진짜 FK · enum 은 STRING · journal/ledger_entry 에 `updated_at` 없음(append-only).

## 3. 타이밍 — `journal` 은 PAID 확정 시 생긴다

결제는 **PENDING 으로 먼저 태어난다**(PG 호출 전 선커밋, W1D5). 그런데 **PENDING 시점엔 돈이 회계적으로 안 움직였다** — 승인이 나야 "현금이 들어오고 미지급금이 생긴다".

- `payment.journal_id` 는 PENDING 동안 **null**.
- journal + 3줄 분개는 **승인 확정(PENDING→PAID = TRANSITIONED) 시점**에 생성 + `journal_id` 세팅.
- 자리: `PaymentTransitionService.applyApproved` 의 **TRANSITIONED 부수효과**(`onTransitioned.accept(payment)`) — 지금 `order.onPaymentConfirmed()` 를 부르는 그 자리. tx2 안이라 **PAID 상태와 journal 이 원자적으로** 같이 생기거나 같이 롤백된다.
- 타임아웃→UNKNOWN→나중 웹훅 PAID 경로도 결국 TRANSITIONED 를 타므로 같은 자리에서 처리된다(경로 무관, 일관).

---

## 4. Week 1 이 그대로 살아난다 — 이중계상 방어

분개를 **TRANSITIONED 에만** 만들면, W1D4 의 보증을 재사용하는 것이다:

> 같은 승인 웹훅이 20번 와도 실제 전이 1회, 부수효과 한 번만.

이게 없으면 중복 웹훅마다 journal 이 하나씩 생겨 **돈이 20번 기록된다** — 이중장부에서 제일 치명적인 이중계상. 즉 **W1D4 의 멱등 backbone(SETNX fast-path + 상태가드·@Version)이 Week 2 의 이중계상을 그대로 막는다.** 승인이 IGNORED(이미 PAID)면 새 journal 은 안 생긴다.

Week 1 위에 Week 2 가 **조립되는** 자리 — STAR 로 쓸 때 강력한 연결.

## 5. 오늘 미룬 것 / 내일 DDL 에서 결정할 열린 질문

**이월 작업:**
- **`V3__` DDL + 엔티티** — Day 1 잔여(내일). journal · ledger_entry · payment/refund 에 journal_id.
- **불변식 `Σ차변==Σ대변` DB 제약** — Day 3. **오늘 DDL 엔 넣지 않는다**(테이블 모양만).
- **자동 분개 로직(`LedgerService`)** — Day 2, TRANSITIONED 자리에 배선.
- **부분환불 역분개** — Day 5.

**DDL 쓸 때 정할 열린 질문:**
- `payment.journal_id` 를 UNIQUE 로 둘까(결제당 charge journal 1개 = 1:1 보장)?
- `ledger_entry` 에 `created_at` 을 둘까(journal 에 있으면 중복 — 사소).
- **계정과목 enum 최종 목록** — 현금 / 셀러미지급금 / 수수료수익 + 환불 때 필요한 것.
- `journal.type` 이 payment/refund 가 이미 가리키는데도 필요한가? → **역조회 없이 자기식별**하려면 유지가 낫다(잠정).
