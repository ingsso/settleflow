## A. 환불 엔드포인트 — Week 2 산출물을 앱 밖에서 도달 가능하게

### 문제 — 산출물이 앱 밖에서 닿지 않았다
`RefundService.requestRefund` 를 부르는 프로덕션 코드가 **하나도 없었다**(테스트 전용). 컨트롤러는 `OrderController`·`WebhookController` 뿐이라 Week 2 의 가드·역분개가 실제 앱에서 도달 불가능한 상태였다. W1D5 가 *"로컬 실행용 주문 엔드포인트가 없다"* 를 보고 `POST /orders` 를 만든 것과 같은 자리 → **`POST /payments/{id}/refunds`** 를 만든다.

### 반환형 — enum 하나에서 sealed 로
성공과 거부는 비대칭이다: 성공은 생성물(`Refund`)을 딸고 오고, 거부는 사유만 있으면 된다. `(RefundResult, Refund)` 한 record 로 담으면 `refund` 가 거부에서 null 이 되고 "ACCEPTED 일 때만 읽어라"가 **규율**로 남는다(NPE 함정).

```
RefundResult (enum, 5값)  →  RefundOutcome (sealed)
                              ├─ Accepted(Refund refund)
                              └─ Rejected(RefundResult reason)   // enum 은 거부 4갈래로 축소
```

`Rejected` 에는 refund 필드가 **존재하지 않아** 실수로 읽을 방법 자체가 없다 — 규율이 아니라 벽이다. ACCEPTED 를 enum 에서 빼서 `Rejected` 가 성공을 담는 것 자체가 불가능해졌다. W2D5 의 *"세터가 아니라 생성자"*, W1D5 의 *"규율을 지키는 게 아니라 어길 수 없게 만든다"* 와 같은 선.

### HTTP 매핑 — 5갈래를 상태로 (설계 판단)

| 결과 | 상태 | 근거 |
|---|---|---|
| `Accepted` | **201** | refund 가 payment 밑 하위 리소스로 생성. 바디에 요약 |
| `Rejected(INVALID_AMOUNT)` | **400** | 0·음수. 실제론 `@Positive` 가 서비스 도달 전에 끊음 — 서비스 분기는 백스톱 |
| `Rejected(NOT_REFUNDABLE)` | **409** | PENDING·FAILED — 결제의 현재 상태와 요청이 충돌(`OrderController` 재고부족=409 와 같은 결) |
| `Rejected(EXCEEDS_REMAINING)` | **409** | 잔액 초과 — `refunded_amount` 라는 현재 자원 상태에 걸린 거절 |
| `Rejected(PAYMENT_UNKNOWN)` | **503 + `Retry-After`** | "충돌"이 아니라 상류(PG) 진실 미확정(W1D1 §3). 재시도 성격이 정반대라 위 409 들과 **상태로** 구분 |
| (없는 결제 id) | **404** | 환불 판정 밖의 리소스 문제. `RefundService` 가 던지는 유일한 예외 |

핵심 판단 둘: **(1)** NOT_REFUNDABLE·EXCEEDS 는 409 로 묶되 바디 `{"error":...}` 로 세부를 살린다. **(2)** PAYMENT_UNKNOWN 만 503 으로 뗀다 — `RefundResult` javadoc 이 "재시도 성격이 정반대라 나눴다"고 못박은 걸 HTTP 까지 관철. 503 의 "서버 다운" 오해는 바디 + Retry-After 로 상쇄("나 살아있고 이 건만 미확정").

### 실측 2 — bootRun 관통 (실제 앱 + compose Postgres)
지금까지 장부·환불·역분개는 **테스트로만** 검증됐다(관통 기록은 주문→결제까지, W1D5 §9). 실제 running app(port 8080) 으로 그 뒤를 재현:

| 단계 | 요청 | 결과 |
|---|---|---|
| 주문 | `POST /orders {productId, qty:2}` | 201 · orderStatus **PAID** · 20,000 |
| 결제분개(자동) | — | PAYMENT journal 1 · **3줄**: CASH 차변 20,000 / SELLER_PAYABLE 대변 19,000 / FEE_REVENUE 대변 1,000 · 균형 |

## B. Kafka 로컬 브로커 — W3D1 선결

의존성(`spring-boot-starter-kafka`·`testcontainers-kafka`)은 이미 있고 **로컬 브로커만 없었다.** 미리 빼두지 않으면 W3D1 설계 도중 인프라를 만지게 된다. `compose.yaml` 에 `apache/kafka:3.9.1`(KRaft 단일 노드, Zookeeper 없음) 추가.

**포트 9092 고정** — Postgres/Redis 는 랜덤 포트로 두고 Spring 이 자동 주입하지만 Kafka 는 다르다. `advertised.listeners` 가 클라이언트에게 자기 주소를 되돌려주므로, 랜덤 호스트 포트면 브로커가 런타임에 못 정해진 포트를 광고해 접속이 깨진다(Testcontainers 가 별도 스크립트로 푸는 그 문제). 9092 고정이면 advertised 도 Spring Kafka 기본 bootstrap(localhost:9092)도 일치해 속성 설정 0.

**실측**: `docker compose up kafka` → healthy → 토픽 생성·조회 성공.
**함정(기록)**: 이미 떠 있는 스택엔 `spring-boot-docker-compose` 가 `up` 을 재실행하지 않는다 → 새 서비스 반영엔 `compose down` 후 재기동 필요(W3D1 주의).

## D·E — 이월 두 건 처리

- **E (닫음)**: `RefundConcurrencyTest` 에 REFUND journal 수 단언 추가. 동시 환불 10건 → ACCEPTED 4 · **REFUND journal 4** 실측. 그동안 refund행 4개는 봤지만 journal 이 4개인지는 안 봤다(W2D5 §7 이월). 하나라도 새면 장부와 이력이 드리프트.
- **D (음성대조군, 닫음)**: `addRefundedAmount` 의 `AND refunded_amount + :amount <= amount` 를 떼고 `RefundConcurrencyTest`(10스레드×5,000, 한도 20,000) 를 돌렸다.

### D 관측 — 실측 (2026-07-24)

**결과: assertion 이 아니라 예외로 빨간불.** 6개 스레드가 `chk_payment_refunded_amount` CHECK 위반:

```
WARN [pool-5-thread-1/4/5/6/8/9] ERROR: new row for relation "payment"
     violates check constraint "chk_payment_refunded_amount"
java.util.concurrent.ExecutionException  (RefundConcurrencyTest.java:69, f.get())
  Caused by: DataIntegrityViolationException → ConstraintViolationException → PSQLException
```

- 앱 WHERE 를 떼자 `addRefundedAmount` 는 `WHERE id` 만 남아 **항상 1행을 갱신하려 한다**. 하지만 `@Modifying(flushAutomatically=true)` 가 즉시 flush 하고, 한도를 넘는 6건은 **DB CHECK 가 거부** → 예외. 4건(20,000/5,000)만 성공.
- **과다환불은 persist 되지 않았다.** W1D2 의 "8,000→11,000 lost update" 와 다른 모양인데, 그 차이가 핵심이다: W1D2 는 CHECK 없는 맨 테이블이라 가드를 떼면 조용히 오염됐다. 여기선 `chk_payment_refunded_amount`(V1) 가 **두 번째 방어선**이라 데이터는 지켜진다.
- 그래서 **앱 WHERE 한 줄의 역할은 "막는 것"이 아니라 "거부를 예외가 아닌 `0행` 반환값으로 만드는 것"**(W2D4 §3 그대로). 떼면 정합성 구멍이 아니라 **실패 품질**이 깨진다: 깔끔한 `EXCEEDS_REMAINING`(→ 409) 대신 `ConstraintViolationException`(→ 500 급). 방어선은 둘이되 층이 다르다 — 앱은 *친절한 거부*, DB 는 *최후의 벽*.
- 원복(`AND` 줄 복구) 후 전체 회귀 초록불 재확인.
