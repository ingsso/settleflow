## 1. 먼저 걷어낸 오해 — "환불을 두 곳에 하는 게 아니다"

한 주문에 셀러가 둘일 수 있다(`Order → OrderItem → Product → Seller`, 마켓플레이스 모델). 그래서 *"환불을 A 에게도 하고 B 에게도 하나?"* 라는 질문이 자연스럽게 나오는데, **아니다.**

```
결제:  고객 ──20,000──> 우리     (실제 현금 이동 1회)
환불:  우리 ──5,000───> 고객     (실제 현금 이동 1회)
```

셀러에게는 **아직 한 푼도 안 나갔다.** 결제 시점에 한 일은 장부에 빚을 적은 것뿐이고, 실제 송금은 W3 정산 배치가 한다. 그러니 환불 5,000 은 *아직 안 준 돈(미지급금)* 에서 나온다.

> 역분개가 하는 일은 셀러에게서 **돈을 뺏는 게 아니라, 갚을 빚을 줄이는 것.**

`SELLER_PAYABLE` 은 부채 계정이라 차변이 감소다. 여러 줄로 갈리는 건 송금이 아니라 **"누구 몫에서 깎느냐"** 이고, 이건 장부 내부의 일이다.

**피할 수 없는 이유**: `chk_ledger_seller_presence`(V4)가 CASH 아닌 줄에 `seller_id` 를 NOT NULL 로 강제한다. *"그냥 5,000 깎기"* 는 스키마가 거부한다. 안 정하면 W3 에서 **A 에게 얼마 송금할지 계산이 안 나온다** — 그게 이 프로젝트의 결승선이다.

## 2. 배분 단위 — A 채택, 추정임을 명시하고 승격 조건을 박아둠

현재 API 는 `requestRefund(paymentId, amount)` — **금액 단위**다. 그래서 어느 셀러 물건이 돌아왔는지가 **요청에 없다.**

| | **A**(채택) 비례 안분 | B 품목 단위 환불 |
|---|---|---|
| 셀러 귀속 | **추정** | **사실** |
| 반품 케이스 | A 물건만 반품돼도 B 미지급금이 비례만큼 깎임 | 정확 |
| 반올림 문제 | **발생**(§3) | 소멸(각 품목이 자기 셀러에 통째 귀속) |
| 비용 | 없음 | `refund.order_item_id` + W2D4 잔액 가드를 **품목별로 재설계** |
| 금액 보상(쿠폰·지연보상) | 표현 가능 | 불가 |

문제의 정체는 배분식이 아니라 **정보의 부재**다(W1D1 §3 `UNKNOWN` 과 같은 모양). 비례는 정보가 없을 때의 최선 추정일 뿐.

B 는 W2D4 의 "결제 1건 = 잔액 1개" 조건부 UPDATE 가드를 품목별 잔액으로 갈아엎어야 해서 그것만으로 하루다. 그래서 A 를 택하되 **추정이라는 사실을 코드 주석과 여기 양쪽에 남기고, 승격 트리거를 미리 적어둔다**(W2D4 의 A1→A2 승격 조건 명시와 같은 처리):

> **승격 트리거**: W3D4 대사에서 셀러별 불일치가 실제로 잡히면 품목 단위(B)로 올린다.

전액환불에서는 A 와 B 의 결과가 **일치**한다 — 비례가 틀릴 수 있는 건 부분환불뿐.

## 3. 잔여 처리 — 뺄셈이 균형을 *구조*로 만든다

### 비례만으로는 장부가 안 맞는다

```
A 10,000 / B 10,000, 환불 5,001 → 각 2,500.5
  둘 다 반올림: 2,501 + 2,501 = 5,002   → 차변 5,002 vs 대변 5,001
  둘 다 버림  : 2,500 + 2,500 = 5,000   → 차변 5,000 vs 대변 5,001
```

둘 다 불균형이다. 배분식만으로는 균형이 성립하지 않는다.

### 채택 — 마지막 셀러는 계산하지 않고 뺄셈으로

```java
portion = last ? amount - allocated                                  // 뺄셈
               : (amount * share.subtotal() + total / 2) / total;    // 비례 + 반올림
```

Σ배분액이 **정의상** `amount` 라 반올림을 어떻게 하든(올림·내림·섞어도) 균형이 깨질 수 없다. W2D2 의 *"수수료만 반올림하고 미지급금은 빼서 구한다"* 와 같은 트릭의 환불판이다.

**이게 `assertBalanced` 통과보다 강한 보장인 이유**: `assertBalanced`(와 V5 트리거)는 **검사**다 — 조립이 끝난 뒤 결과를 보고, *그 입력을 실제로 밟았을 때만* 틀렸다고 알려준다. 테스트가 `.5` 케이스를 안 밟으면 못 잡는다(그래서 3일 이월됐다). 뺄셈은 **불균형한 목록을 애초에 만들 수 없게** 한다 — 입력과 무관하다. 증명 대상이 *"모든 입력"* 에서 *"코드 한 줄의 형태"* 로 줄어든다.

→ 그래서 `Journal.forRefund` 의 `assertBalanced` 는 **균형을 지키는 장치가 아니라 조립 오류를 잡는 장치**다. `forPayment` 와 같은 지위(*"여기서 걸리면 프로그래밍 오류"*).

### 대가 둘 — 정직하게

**(1) 마지막 자리가 오차를 흡수한다.** 앞 셀러들이 올림된 만큼 마지막이 덜 받는다(실측: A 2,501 / B **2,500**). 부분환불이 반복되면 편향이 한 셀러에 쌓인다 — 환불 N 건에 최대 N 원 미만. 감수하되 **규칙을 결정적으로** 못박았다: `sellerId` **오름차순의 마지막**.

기각한 대안: *최대잔여법*(가장 공평하지만 "지금까지 누가 얼마 흡수했나"를 알려면 과거 환불 journal 을 다 읽어야 한다 — 한 건의 환불이 이력에 의존하게 됨, append-only 장부에 상태를 얹는 꼴), *플랫폼이 흡수*(`FEE_REVENUE` 차변 1 — 셀러는 정확해지지만 W2D1 의 "역분개는 `FEE_REVENUE` 를 안 건드린다"에 예외가 생김).

**(2) 정렬이 계약의 일부가 됐다.** 기존 `recordPayment` 는 `HashMap` 을 순회했다 — 순서가 명세되지 않는다. 잔여 흡수 셀러를 "마지막"으로 정의한 이상 순서가 바뀌면 **같은 입력에 1원이 다른 셀러에게 간다.** 그러면 *"왜 B 가 1원 덜 받았나"* 에 답할 문장이 없어진다(장부는 W3 대사의 진실원본이다). → `sharesOf()` 로 뽑으면서 `sellerId` 정렬을 넣고, 정렬이 계약임을 주석에 남겼다.

### 0원·음수 몫

안분 결과가 0 인 셀러는 **줄을 만들지 않는다** — `chk_ledger_amount` 가 `amount > 0` 을 요구하고, 그 셀러 몫에선 실제로 아무 일도 안 일어났으므로 빈 줄이 맞다. Σ는 그대로라 균형 무관.
뺄셈은 균형은 지켜주지만 **부호까지 지켜주진 않는다**(앞 셀러들의 올림 합이 마지막 몫을 넘어서면 음수 가능). 이론적 경로라 실측은 못 걸었고, 걸리면 프로그래밍 오류로 보고 `IllegalStateException` 을 던진다(§6).

## 4. 실측 (전부 실행 결과)

`RefundLedgerTest` — 7 케이스:

| 케이스 | 관측 |
|---|---|
| 1. 단일셀러 5,000 부분환불 | REFUND journal **1** · 줄 **2** · 현금대변 5,000 · 미지급금차변 5,000 · **수수료줄 0** |
| 2. `refund → journal` 연결 | 연결 **1** / journal 없는 refund **0** (D4 까지는 전부 null) |
| 3. 다중셀러 12,000+8,000 에 5,000 | 안분 **[3000, 2000]** · 합 = 현금대변 |
| 4. **`.5` 경로** 10,000+10,000 에 **5,001** | 안분 **[2501, 2500]** · 차변합 **5,001** = 현금대변 |
| 5. 3셀러 7,000+6,000+4,000 에 **3,333** | 안분 **[1372, 1176, 785]** 합 **3,333** |
| 6. **부분환불 3회**(8,000→7,000→5,000) | journal **4**(PAYMENT 1 + REFUND 3) · 차변 40,000 = 대변 40,000 · 사건 단위도 전부 균형 · **미지급금순액 −1,000** · 수수료순액 **1,000** |
| 7. 잔액초과 환불 | `EXCEEDS_REMAINING` · **REFUND journal 0 · refund행 0** |

- **4·5 가 3일 묵은 이월을 닫았다.** 어느 셀러도 나눠떨어지지 않는데 합이 환불액과 정확히 일치한다.
- **6 이 주말 체크포인트**(*"부분환불 3번 반복해도 장부 불변식이 안 깨진다"*)의 나머지 절반. 전체 합(Σ차변==Σ대변)과 **사건 단위**(journal 별 균형)를 따로 확인했다 — W2D1 §2.2 에서 `journal` 묶음(B)을 택한 이유가 *"불변식을 사건 단위로 검증하기 위해"* 였으므로 전체 합만 보면 그 선택을 검증하지 않은 것이 된다.
- **7 이 §5 의 분업을 재확인한다** — 판정이 UPDATE 한 문장이라(W2D4 §3) 거부는 역분개 앞에서 끊긴다. 부작용 0.

### 미지급금이 음수인 게 정상이다

케이스 6 에서 **미지급금 순액 −1,000**. 20,000 결제의 미지급금은 19,000 인데 전액환불로 20,000 을 깎았으니 음수다. 수수료를 환급하지 않는(W2D1) 정책의 **직접적 귀결** — 셀러가 우리에게 1,000 을 빚진 상태이고, W3 정산에서 다음 회차와 상계된다.

막을 자리도 없다: `SELLER_PAYABLE` 잔액은 컬럼이 아니라 `ledger_entry` 합계에서 나오는 **파생값**이다. 제약을 걸 대상 자체가 없다.

## 5. 호출 자리 — 결제와 대칭이 아니다

결제 분개는 `PaymentTransitionService` 의 TRANSITIONED 부수효과에 얹혀 있다. 이유는 **웹훅이 중복 도착하기 때문** — 같은 eventId 가 20번 와도 journal 은 1개여야 하는데, 그 서비스가 이미 *"전이가 실제로 일어난 1회"* 를 보증하고 있었다(W1D4). 멱등을 새로 만든 게 아니라 **있는 backbone 에 올라탄 것**이다.

환불엔 그 전제가 없다. W2D4 §1 에서 정한 대로 **같은 금액 환불 요청 두 번은 중복이 아니라 진짜 환불 2건**이고(`RefundResult` 에 `IGNORED` 가 없다), journal 도 2개가 **정답**이다.

| | 결제 분개 | 환불 역분개 |
|---|---|---|
| 같은 요청 2번 | 분개 1개 (중복) | **분개 2개** (진짜 2건) |
| 필요한 보증 | 멱등 | **1:1 대응** |
| 얹을 자리 | 이미 있는 멱등 backbone | **조건부 UPDATE 의 affected rows 직후** |

`affected rows == 1` 이 곧 *"이 환불이 실제로 일어났다"* 는 판정이므로(W2D4 §3) 그 직후가 journal 이 붙을 자리다. 그리고 **금액 누적 + `refund` INSERT + journal INSERT 가 한 트랜잭션** — 갈라지면 돈·이력·장부가 드리프트한다(`Refund` 클래스 주석의 논리를 장부까지 확장).

### `Refund.journal` 은 세터가 아니라 생성자로

`Refund` 는 append-only 다(*"지우개가 아니라 빨간 펜"*, `updated_at` 없음). 세터를 열면 **고칠 수 있는 문**이 생겨 그 주석과 스키마가 거짓말이 된다.

생성자로 받으면 **순서가 강제된다**: `journal 조립·저장 → new Refund(payment, amount, journal) → save`. 세터였다면 자유로웠을 순서를 생성자가 고정한다 — 오늘 반복해서 나온 패턴(*규율을 지키는 게 아니라 어길 수 없게 만드는 것*)의 세 번째 사례.

## 6. 음성대조군 — 예측과 정확히 일치

뺄셈을 끄고(`if (false && last)`) 마지막 셀러도 계산으로 구하게 → **2건 빨간불**:

```
케이스 4 (.5 경로)  IllegalStateException: 분개 불균형: 차변=5002 대변=5001   ← 둘 다 올림, 1원 초과
케이스 5 (3셀러)    IllegalStateException: 분개 불균형: 차변=3332 대변=3333   ← 전부 버림, 1원 부족
```

**나머지 5건은 그대로 통과했다.** 이게 더 중요한 관측이다 — 단일 셀러와 나눠떨어지는 12,000/8,000 은 뺄셈이 있든 없든 똑같이 맞는다. *(단일 셀러는 `(amount×total + total/2)/total == amount` 라 구조적으로 면역이다.)*

> **3일간 이 버그가 숨어 있을 수 있었던 이유가 이걸로 설명된다.** W2D2 fixture 가 요율 5% 에 20,000·12,000·8,000 을 써 전부 나눠떨어졌고, 그런 케이스만 있으면 뺄셈의 부재가 **아무 증상도 안 낸다.**

W2D4 와 또 다른 점: 거기선 앱 가드를 제거하자 **DB CHECK 가 대신 잡아** 방어선이 둘임이 드러났다. 오늘은 **앱(`assertBalanced`)이 먼저 터져 V5 트리거까지 가지도 못했다** — flush 전에 잡히기 때문. 이중방어이긴 하되 이 경로에서는 앱이 바깥층이다.

원복 후 전체 **47건 0실패** 재확인. `git diff --stat` = 4파일 154추가/23삭제.

**메시지를 회귀 전에 먼저 뽑았다** — W2D4 §6 에서 *"결과 XML 이 덮어써져 실패 모드를 못 남겼다"* 는 실수를 반복하지 않으려고 순서를 바꿨다.

## 7. 정직한 한계 / 이월

- **비례 안분은 추정이다**(§2). 반품 케이스에서 틀린 셀러의 미지급금을 건드린다. 승격 트리거는 §2 에 명시 — W3D4 대사에서 셀러별 불일치가 잡히면 품목 단위로.
- **잔여 흡수 편향은 감수했다**(§3). 규칙(`sellerId` 최대)은 결정적이지만 공평하지는 않다. 장부 내부에선 균형이 맞으므로 **W3 대사에 안 걸린다** — 셀러가 항의할 때만 드러난다.
- **마지막 몫이 음수가 되는 경로는 미검증.** 이론상 가능(앞 셀러들의 올림 합 > 마지막 몫)하지만 실제로 만드는 입력을 못 찾았다. 방어(`IllegalStateException`)는 넣었으나 **발동을 실측하지 못했다** — 추정하지 않고 미검증으로 남긴다.
- **W2D4 의 동시성 음성대조군 실패 모드는 여전히 미기록.** 오늘도 안 했다.
- **환불의 동시성 × 역분개는 미검증.** `RefundConcurrencyTest`(10스레드)는 금액·refund행만 보고 **journal 수는 안 본다.** ACCEPTED 4건이면 REFUND journal 도 4개여야 하는데 확인 안 했다 → W3 로 이월.
- **`refund.journal_id` UNIQUE 의 실제 위반 경로는 미검증**(V3 에 있지만 오늘 그걸 깨는 테스트는 없다).
- **A2 승격(`GENERATED STORED`) 판단은 W3 로 이월**(W2D4 §1 조건 그대로).
